no longer true** — confirmed by reading the actual files:

**Conclusion: T9 is real and working — the docstring in `pipeline.py` describing it as

### 1a. `Channel Output Structures.xlsx` — confirmed NOT used, precisely

AA-439-07 already dumped this file's full contents (7 channels: LinkedIn, Facebook, Instagram,
TikTok, Email/Newsletter, Landing Page/Sales Page, Ads — each with real `structure`/`style`/
`avoid` columns). Comparing that content directly against `adapt.py`'s real prompts:

- **Only 2 of the file's 7 channels are covered at all** — `adapt.py:60`
  (`ChannelName = Literal["facebook", "tiktok"]`) and `adapt.py:125-128`
  (`_CHANNEL_INSTRUCTIONS`) — no LinkedIn, Instagram, Email/Newsletter, Landing Page, or Ads
  adaptation exists anywhere in `services/acp_produce/`.
- **The 2 channels that ARE covered use independently-written instructions, not the xlsx's
  content.** The file's Facebook row: *"1. Warm but specific opening / 2. Destination feeling
  with concrete detail / 3. Practical travel idea / 4. Why this trip fits Adventure Asia's
  audience / 5. Friendly CTA"* — `adapt.py`'s real `_FACEBOOK_INSTRUCTIONS` (`:89-104`) instead
  specifies a completely different structure: one 50-120 word paragraph built around exactly ONE
  atom (`hook_story_cta` framework), ending on the literal branded CTA phrase "Design This
  Journey," followed by a `HASHTAGS:` line. No step in the code matches the file's 5-point
  structure.
- **The file's `avoid` lists are not carried over at all.** Facebook's xlsx `avoid` column:
  *"corporate tone, generic 'discover paradise' language, too many facts without feeling, cheap
  promotional wording, vague scenic language."* None of these specific phrases or concepts appear
  anywhere in `_FACEBOOK_INSTRUCTIONS`. Same for TikTok's xlsx avoid list ("cheap viral hooks,
  exaggerated danger, fake urgency, luxury flexing") versus the real `_TIKTOK_INSTRUCTIONS`
  (`:106-123`), which has its own separate HOOK/SCRIPT/VISUAL format with no reference to those
  specific avoid-items.

**Confirmed: the real pipeline writes its own channel guidance independently — the same general
intent (channel-appropriate voice/structure) but not a port of this specific spreadsheet's
content, and covering fewer channels than the file describes.**

`services/acp_produce/gates.py` — grepped every `gate_*` function: `gate_grounding` (F1),
`gate_atom_density` (F5 — renumbered per `pipeline.py`'s own docstring, AA-404's addition slotted

`run_gates(piece, [_f1, _f5, _f2, _f3, _f4, _f6, _f7, _f8, _f9], ...)`). `gates.py`'s own header
confirms lineage: *"F1 ported from the aa-marketing-v2 research build's `aamc/gates.py`"* —
directly matching the source folder audited in AA-439-04/07.

**Is this the same gate stack T3 (tenant QA gate) uses? No — confirmed by imports.**
`services/acp_produce/tenant_pipeline.py` (T3) imports from `api.routers.v1_atoms` and
`services.acp_shared.grounding` — **it never imports anything from `services.acp_produce.gates`

`services.acp_produce.models`, and — the one overlap — **also from
`services.acp_shared.grounding`** (`find_novel_numeric_claims`). **T3 and T10 are two separate,
independently-implemented QA systems that share exactly one small grounding-detection utility
function — not the whole F1-F9 stack.** The ADR's "T10 = N7, tái dùng F1-F9 gate stack" claim is
accurate **for T10 itself** (F1-F9 is real, is the aa-marketing-v2 port, does run for every N7
piece) — it is not the same machinery as T3's own grounding/structural check, which is a
separate, tenant-rewrite-specific implementation (confirmed AA-439-01).

**Confirmed actively firing on real data** — live query, `held_reason` breakdown across the 125
real held pieces:

## 3. T11 (Publish) — confirmed cleanly absent, by the code's own words

Grepped `services/acp_produce/` and `services/acp_deliver/` for any real social-platform API
integration (`facebook.*api`, `linkedin.*api`, `meta.*api`, `tiktok.*api`, `post_to_`,
`publish_to_channel`, `distribute`) — **zero hits anywhere.**

The closest real function, `services/acp_produce/packets.py::deliver_packet()`
(`:209-247`) — its own docstring states plainly: *"AA-367: the `ready` → `delivered` transition.
**Today this is ONLY a `packets.status`/`delivered_at` marker — there is no real send-to-tenant**
[action]."* The function's real body (`:226-247`) confirms this exactly: it counts `status
='passed'` pieces, writes a usage-log entry, then `UPDATE packets SET status = 'delivered',
delivered_at = now()` — **a database column flip, nothing more.**

**This is correctly, precisely distinct from two things this audit already covered and could
easily be confused with:**
- **A2→A3's `published_tours`** (AA-438-03) — a completely different tier (aa_internal admin
  content), completely different table, unrelated to N7/N8 social content at all.
- **`trust_ramp.py`'s `publish_mode`** (AA-439-06) — governs *whether AA lets this packet
  advance toward eventual publishing* (the trust-ramp/veto-window gate), not the act of actually
  posting content anywhere. A packet at `publish_mode='veto_window_auto'` still wouldn't cause
  anything to appear on a real Facebook/LinkedIn/TikTok account — no code path exists that would
  do that regardless of `publish_mode`.

**Confirmed: T11 does not exist, matching the ADR exactly** — not merely "no UI for it," but no
backend integration of any kind with any real social platform.
