### Decisions
- **`channel` added to `Piece`** (models.py): `Literal["blog","facebook","tiktok"] = "blog"`. No

    since the FAQ-removal itself was explicitly pre-authorized in this issue's own title/context).

## STEP 0 (06/08/2026, before any code) — design confirmed, still accurate

## Decisions

- **1 Piece = 1 channel — already decided, not a new choice.** `acp_deliver.pieces` (migration 094,
  AA-364) has `channel TEXT NOT NULL` as a plain scalar column, not a list/JSONB — the schema was
  already built for "one row per channel artifact" before AA-371 existed. E3 therefore produces TWO
  new `Piece` rows (channel="facebook", channel="tiktok") alongside the existing blog Piece
  (channel="blog"), all sharing the same `slot_id` (confirmed `slot_id` is a plain nullable TEXT
  column with no uniqueness constraint, so 3 rows/slot is already legal) but each with its own
  `piece_id`. Proposed convention for IMPLEMENT: `f"{blog_piece_id}#facebook"` /
  `f"{blog_piece_id}#tiktok"` — not binding, just a suggestion for whoever writes the slot-runner.
- **`channel` field: Pydantic-model-only, NO migration.** The DB column has existed since migration
  094; only `services/acp_produce/models.py::Piece` is missing the field (confirmed — `pipeline.py`'s
  own docstring already flags this gap: `"channel"/"slot_id"/"tenant_id" are NOT fields on Piece ...
  they are supplied by the caller, not invented on the model ahead of a real consumer"`). E3 IS that
  real consumer now. Add:
  ```python
  channel: Literal["blog", "facebook", "tiktok"] = "blog"
  ```
  Default `"blog"` preserves every existing hand-constructed `Piece(...)` in the 4 pre-AA-371 test
  files (none pass `channel`) — no test breakage from adding this field.
  - Migration 094's own comment explicitly deferred a DB `CHECK` constraint on `channel` ("ahead of
    the code that doesn't validate it yet"). Recommend continuing to skip it even now: the Pydantic
    `Literal` enforces the same 3 values before any DB write ever happens (same "don't validate what
    the framework already guarantees" principle), so a DB-level CHECK would be pure redundancy, not a
    new capability. Next migration slot if ever needed later: **096**.
- **E3 runs in the same E1-E5 generation pass, BEFORE gates — not after a first gate-pass.** This
  matches the original AA-298 order (`brief compile → apply_output_rules() → E1-E5 generation →
  F1-F9 gates`, per `pipeline.py`'s own module docstring) — E3/E4 are part of "E1-E5", not a
  post-gate step. **No temporary workaround is needed for AA-372 (F7 FAQ dedup) not being built
  yet**: F1/F8/F9 already run independently per-Piece today (AA-364), and F7 will simply start
  running against E4's FAQ output once AA-372 lands, the same way F1 already runs against E2's blog
  output today. Nothing about E3/E4 is gated on F2-F7 existing.
- **E3 does not need to wait for E4.** E3's input explicitly excludes the blog's "FAQ" `## `
  section (see Should-know below for why that section is being reworked) — a Facebook caption or
  TikTok script has no reason to carry FAQ content, so stripping that one section before adapting is
  safe regardless of whether E4 has processed it yet.
- **E3 needs an LLM call — Sonnet acc1 satellite, same `invoke_claude(..., model="sonnet")` as E2.**
  One call per channel (not batched — the whole condensed blog is already short input, unlike E2's
  per-section batching). Draft prompt shape (system prompt = same `AA_BRAND_IDENTITY_PROMPT` base as
  E2, plus):
  ```
  You are adapting an already-written blog piece into a shorter channel format. You may ONLY use
  [R:atom_id] ids that already appear in the input — never invent a new id, never state a fact whose
  id is not already cited in the input. Do not add claims that go beyond what's already in the blog
  text.

  FACEBOOK: one short paragraph (50-120 words) in the brand voice, then a final line
  "HASHTAGS: #tag1 #tag2 #tag3" (3-5 tags).

  TIKTOK: three labeled blocks —
  "HOOK:" (one line, ≤15 words)
  "SCRIPT:" (100-150 words, spoken-style)
  "VISUAL:" (1-2 lines of shot/visual direction, no citation tags needed here)
  ```
  Input given to the model: the blog `body_tagged` with the FAQ section stripped, plus
  `{atom_id: atom_text}` restricted to only the ids already cited in that stripped text (a subset of
  `atom_text_by_id`, extracted via the same tag regex gates.py already uses — see Changed below).
- **E4 needs an LLM call only for the ANSWER text, not the question.** `Brief.faq_candidates` (AA-369,
  confirmed present on `Brief` — `question` + `source_id`, source_id already resolved against a real
  atom by `research.py::_match_faq_source()`) already supplies the questions. E4's job is: for each
  `FAQCandidate`, write a 1-3 sentence answer from `atom_text_by_id[source_id]` only, tagged
  `[R:source_id]` (the id is already known — not model-invented, same spirit as H2 headings being
  code-inserted in E2). Batch 2-3 candidates/call, same batching convention as E2.
  ```
  For each numbered question below, write a 1-3 sentence answer using ONLY the fact given for that
  question's id. Cite it with [R:<id>]. Do not introduce any fact not in the text given. If the given
  fact cannot actually answer the question, write the closest honest partial answer and still cite
  the id — never fabricate a fuller answer than the fact supports.
  ```
- **JSON-LD is 100% deterministic (no LLM)** — a pure function `question + answer -> schema.org
  FAQPage dict`, built purely from E4's own already-produced Q/A pairs. **Not stored as a new Piece
  field / DB column.** Recommend rendering the FAQ section into `body_tagged` in a fixed, parseable
  format (code-inserted, same principle as E2's H2-insertion): e.g.
  ```
  **Q: <question>**
  A: <answer text with [R:id] tags> [R:id]
  ```
  and have the JSON-LD builder re-derive `{question, answer}` pairs from that markdown at
  export/publish time by parsing the same fixed format — this mirrors the AA-241 precedent already
  in this codebase ("failures array re-derived on CURRENT content ... no logic copy, no new
  migration") instead of duplicating the same data into a second storage location that can drift.

## Should know (findings, not yet code)

- **Real gap found in already-shipped AA-370 `generate_draft()` (not a bug — E4 didn't exist yet
  when it was written):** `build_outline()` already emits a literal `"FAQ"` `OutlineSection` whenever
  `compile_brief()` sets it (`research.py` line ~282, `fw_cfg.get("faq")`), and today's
  `generate_draft()` drafts it exactly like any other section — generic prose, using whatever atoms
  landed in `atoms_by_section["FAQ"]`, **never touching `Brief.faq_candidates` at all**. Once E4
  exists, E2 drafting a throwaway FAQ paragraph that E4 immediately replaces is wasted work and a
  correctness trap (two different, possibly conflicting FAQ texts in the same piece transiently).
  **Recommended IMPLEMENT-time change:** have `generate_draft()`'s batching skip any
  `OutlineSection` whose `title == "FAQ"` and let E4 render that section instead, spliced into
  `body_tagged` at the same position E2 would have put it. Small, localized change to AA-370's
  code — flagging now so it's not a surprise mid-AA-371-implementation.
- **F8/F9 rubric mismatch risk for facebook/tiktok Pieces — not solved here, flagging for whoever
  wires the real slot-runner (or AA-372).** `pipeline.py::run_piece_through_produce_gates()` runs
  F1+F8+F9 unconditionally for every `Piece` regardless of channel. `FRAMEWORK_RUBRICS` (gates.py) and
  `BRAND_SEO_FAILURE_CODES` (SEO_TITLE_WEAK, META_INCOMPLETE_SENTENCE, ...) are blog/SEO-shaped and
  don't obviously fit a 1-paragraph FB caption or a TikTok hook/script/visual triple. F1 grounding
  IS channel-agnostic and needs no change (confirmed — `gate_grounding()` only cares about tags vs.
  `valid_ids`/`text_by_id`, never about structure). F8/F9 as currently coded may need
  channel-conditional rubrics or a lighter gate set for non-blog channels — a real open question for
  AA-372/the slot-runner, out of AA-371's own scope (E3/E4 are generation, not gating).
- **`Slot.channel` (acp_planning, existing) and `Piece.channel` (new, this issue) are different
  concepts, not to be confused.** A `Slot` is planned for one destination channel (usually "blog");
  `Piece.channel` is per-artifact — one blog `Slot` fans out into 3 `Piece` rows sharing one
  `slot_id`. This is exactly what the schema (`slot_id` nullable TEXT + `channel` NOT NULL TEXT, no
  compound uniqueness) was already shaped for.
- **`atom_usage.py`'s `channel_by_piece_id` external-dict workaround becomes redundant once
  `Piece.channel` lands**, per its own docstring ("optional since Piece has no channel field yet").
  Not fixed here — AA-361 already shipped and this is a non-blocking cleanup, not something AA-371
  needs to touch.
- `gates.py::TAG_RE` / `atom_usage.py::ATOM_CITE_RE` are two independent regexes for the same
  `[R:id]`/`[F:id]` pattern. E3's "extract already-cited ids from the blog text" step should reuse
  `gates.py.TAG_RE` (import it) rather than writing a third copy — `generation.py` importing from
  `gates.py` introduces no cycle (`gates.py` never imports `generation.py`).
