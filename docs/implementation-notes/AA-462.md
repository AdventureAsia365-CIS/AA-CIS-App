# AA-462 — Publish channel #2: Facebook (T11 was blog-only)

## Decisions
- **Channel choice — real DB query, not guessed** (per this chain's own build prompt): of the 6
  non-blog channels the issue names (facebook/tiktok/instagram/linkedin/email/ads), `facebook`
  has by far the most real `content_piece` data today — 3 approved pieces vs 0 for every other
  channel (`SELECT channel, COUNT(*) FROM acp_shared.content_piece GROUP BY channel`). Confirmed
  it's a real generation-ready channel (`CHANNEL_BARS["facebook"]["on_demand"] == False`,
  `services/acp_shared/slate.py`), not a stub. The other 5 remain unbuilt.
- **Scope note vs. the issue's own text**: AA-462's own "Không thuộc scope" section originally
  framed this issue as investigation-only ("chưa phải build ticket"). The chain's 04/09 build
  prompt explicitly asked for 1-2 real channel adapters here, superseding that framing — flagged
  for review, same as AA-489's business-decision flag, not silently treated as uncontested.
- **New package `services/acp_publish/`**, not `services/acp_s4_blog/cms/` (wrong shape — a
  social post has no title/slug/seo_title) and not `services/acp_s4_social/` (that name is tied
  to dead ACPv1, per CLAUDE.md's own tech debt notes — reusing it would blur the "ACPv1 is dead"
  boundary ADR-2026-038 §0.5 already established for every T-series build).
- **No new migration** — `shared.tenant_integrations` (migration 117) already generalized to
  `(tenant_id, integration_type)` with the comment "meant to hold more than just WordPress
  later." `integration_type='facebook'`, `secret_key` at a distinct `acp/social/{tenant_id}`
  prefix (not `acp/cms/{tenant_id}` — a Page Access Token isn't a CMS credential, and a tenant
  connecting both needs two independent secrets).
- `v1_publish.py::publish()` generalized to dispatch by `channel` (`_call_adapter()`), keeping
  the exact pre-existing 422/502/publish_log-write control flow and status codes unchanged for
  the blog path (verified against the pre-existing test suite, all 17 original tests still pass
  unmodified except one deliberately renamed — see Changed).

## Changed
- New: `services/acp_publish/base.py` (`SocialPost`/`SocialPostResult`/`SocialAdapter`),
  `services/acp_publish/facebook.py` (`FacebookAdapter`, Graph API `POST /{page_id}/feed`).
- `api/routers/v1_integrations.py` — `SaveFacebookRequest`, `GET/POST /v1/integrations/
  facebook`, `POST /v1/integrations/facebook/test` (mirrors the WordPress save/status/test shape
  exactly, including the AA-460 don't-trust-bare-200 lesson applied to Graph API's own
  `{"error": {...}}` envelope).
- `api/routers/v1_publish.py` — `_SUPPORTED_CHANNELS = ("blog", "facebook")` replaces the old
  single-channel `_BLOG_CHANNEL` constant; `list_pending()` filters `channel = ANY(...)`
  instead of `= 'blog'`; `publish()`'s integration lookup is keyed by `channel` instead of the
  hardcoded `'wordpress'`; a new `_call_adapter()` helper holds the per-channel adapter-call
  branch (blog vs facebook), called from inside the same try/except that already existed.
- `tests/unit/test_aa458_publish.py` — updated 2 pre-existing tests whose assertions were
  blog-only-specific (`test_publish_404_when_channel_not_blog` renamed to
  `..._when_channel_unsupported`, now asserts on `tiktok` instead of `facebook`, since facebook
  is supported now; `list_pending`'s SQL-param assertion updated for the new `ANY($2::text[])`
  shape). All 17 original tests pass unmodified otherwise.
- New: `tests/unit/test_aa462_facebook_adapter.py` (6 tests),
  `tests/unit/test_aa462_publish_facebook.py` (4 tests),
  `tests/unit/test_aa462_integrations_facebook.py` (8 tests).

## Tradeoffs
- **No frontend UI built** — the chain build prompt's own wording for this issue ("build
  publish adapter") is backend-focused; the issue's own STEP0 didn't ask for FE either. Real,
  disclosed rough edge because of this: `PublishPendingList.tsx`'s `wordpressConnected` prop
  gates the Publish button's disabled state for EVERY piece in the list regardless of channel —
  now that `list_pending()` returns facebook pieces too, a tenant with WordPress connected (but
  not Facebook) sees an enabled-looking Publish button on a facebook piece. Clicking it does NOT
  fabricate success — the real `422 "Connect Facebook to publish"` still surfaces correctly via
  the existing `body.detail` fallback in `handlePublish()` — so this is a UX polish gap, not a
  correctness bug. Flagged for a follow-up FE task (per-channel connection-state prop), not
  fixed here.
- **No real live-verify possible** — same class of gap AA-458/460 already disclosed for
  WordPress's own test site. Checked `aws secretsmanager list-secrets` for any
  facebook/meta-named secret: none exist. A real Facebook Page Access Token requires a live,
  human-driven Meta Business/Developer Console flow (create app, verify business, generate a
  long-lived Page token) — nothing this session can provision, unlike AA-256/AA-257's IAM gaps
  (Terraform can at least stage those for review; there's no code artifact that provisions a
  real Facebook credential). Positive-path proof is unit-test-only, mirroring
  `test_create_post_success_real_wp_response`'s own precedent for WordPress.
- `_connect_action_verb()` hardcodes `{"blog": "WordPress", "facebook": "Facebook"}` rather than
  reading a display name from `tenant_integrations` or elsewhere — matches the existing literal
  "Connect WordPress to publish" copy exactly (a pre-existing, tested string), simplest thing
  that keeps both channels' 422 messages correct.

## Should know
- The Graph API's post-id shape is `"{page_id}_{post_id}"` (e.g. `"1234567890_998877"`) — used
  directly as both `publish_log.external_id` and to build `external_url`
  (`https://www.facebook.com/{that_id}`), which resolves correctly on Facebook's own domain.
- `FacebookAdapter.create_post()` checks for a Graph API `{"error": {...}}` envelope BEFORE the
  status-code/shape check — Graph API can return a 200 with an error body in some cases (e.g.
  rate limiting), so status alone still isn't proof of success even beyond the anti-bot-page
  class of failure WordPress hit.
