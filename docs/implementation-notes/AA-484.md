# AA-484 — Cannibalization gate T10 (cross-tenant)

Branched off `feat/aa-499-decision5-pgvector-reuse` (not `origin/main`) — this issue's real
`blockedBy` is AA-499 (`find_similar_pieces(cross_tenant=True)`), which was not yet merged to
main when this build started (carries a migration, needs manual merge). Flagged as a deliberate
deviation from the usual "fresh worktree from origin/main" convention, not an oversight.

STEP0 was already answered by AA-520's audit (per this issue's own Linear description): T10 is
now 7 (non-blog) / 11 (blog) gates, `GateResultLite` has a real `blocking` field, and the
`tenant_brand_rules` fallback `{}` gap is confirmed still real. No re-investigation needed.

## Decisions

- **Cross-tenant scope: relied on the already-confirmed Q6=B decision (25/07/2026, AA-332
  origin, cited in this issue's own Linear comment) rather than re-asking.** The confirmed design
  is explicit: compare a piece-about-to-publish's embedding against every OTHER tenant's
  published pieces (not scoped to the same tour_id specifically) — `find_similar_pieces
  (cross_tenant=True)` (AA-499) already matches this literally, no changes needed there beyond
  adding `exclude_tenant_id` (new, this build) to keep the writing tenant's own pieces out of its
  own cross-tenant comparison.
- **A real BLOCKING gate, not a soft flag** — matching Q6=B's own words ("chặn + yêu cầu đổi
  góc"). Architecturally different from AA-499's `within_tenant_reuse` flag (post-hoc, after the
  gate loop): the embedding + cross-tenant lookup now happens INSIDE the attempt loop, BEFORE
  `run_quality_gates()`, so a real match becomes a real `first_failure` that drives the SAME
  repair-then-hold flow every other blocking gate uses (attempt 2's `rewrite_with_feedback()`
  gets the cannibalization violation as `revision_feedback`, same as any other repairable gate).
  `quality_gates.py` itself stays synchronous/pool-free — `gate_cannibalization()` is a pure
  function taking an ALREADY-COMPUTED `match: dict | None`, matching `gate_seo_surface()`'s own
  precedent (precomputed inputs, no I/O inside the gate function itself).
- **Gate name/position**: `F10_cannibalization_cross_tenant`, next available F-number (F1-F9
  fully used by blog's own 11-gate stack), runs for EVERY channel (not blog-only — cannibalization
  risk isn't channel-specific), placed right after `F2_banned_patterns` in the ledger.
- **Threshold: reused 0.92 verbatim** from AA-499 (which itself reused Q6=B's own number) — one
  shared threshold, not two.
- **"Ưu tiên tenant thiếu tenant_brand_rules" (issue's own priority item 2): satisfied via the
  gate's own diagnostic hint, not a separate mandatory-setup gate.** The issue's own text offers
  this as an "HOẶC" (OR) between two approaches — validate/force brand-rules setup before atomize,
  OR block/warn on detected similarity. Built the second (this whole gate IS that). Additionally:
  when a cannibalization match fires, one extra query (`_tenant_missing_brand_rules()`) checks if
  the WRITING tenant (not the colliding one — that's not actionable from this write) has no
  active `shared.tenant_brand_rules` row, and appends a plain-language hint to the violation text
  when true. **Did NOT build the first option** (mandatory brand-rules setup gating T5 atomize)
  — that's a bigger, tenant-onboarding-flow-wide product decision the issue's own text frames as
  "cân nhắc" (a consideration), not a requirement; flagging it here rather than silently deciding
  it either way.

## Changed

- `services/acp_content_writing/quality_gates.py` — new `gate_cannibalization(match)`, wired into
  `run_quality_gates()` (new optional `cannibalization_match` param, defaults `None` so every
  existing caller/test is unaffected in behavior when it doesn't pass one).
- `services/acp_shared/piece_similarity.py` — `find_similar_pieces()` gains `exclude_tenant_id`
  (cross-tenant path only).
- `services/acp_content_writing/service.py`:
  - The embedding computation (previously only after the gate loop, approved-only — AA-499's
    original shape) now runs INSIDE the loop, every attempt, whenever `tenant_id` is present —
    needed so the cannibalization gate can be re-checked on a retry. The within-tenant reuse
    check (AA-499, still approved-only, still after the loop) now REUSES that same embedding
    instead of recomputing — one embedding call per attempt total, not two.
  - `content_embedding` is still only PERSISTED for the real `approved` outcome (a held piece
    still never ships, nothing to index it for) — computed-every-attempt vs.
    persisted-only-if-approved are now two separate facts, both real and both intentional.
  - New `_tenant_missing_brand_rules()` helper (queries `shared.tenant_brand_rules`).
  - `_REUSE_SIMILARITY_THRESHOLD` (renamed from AA-499's `_WITHIN_TENANT_REUSE_THRESHOLD`, same
    0.92 value) now documented as shared by both AA-499's flag and this gate.

## Tradeoffs

- Did not scope the cross-tenant comparison to "same underlying tour_id" specifically, even
  though that's the concrete business scenario in this issue's own "Bối cảnh" section (2 tenants
  licensing the same tour) — followed the ALREADY-CONFIRMED Q6=B design literally instead (any
  2 tenants' published content, no tour_id filter). If Nghiệp wants it tour_id-scoped after all,
  that's a real design change to `find_similar_pieces`'s own cross-tenant query, flagged here as
  a real gap between the origin scenario and the confirmed mechanism, not silently reconciled.
- Did not add a cross-account satellite/fallback for the extra embedding calls this gate adds
  (same as AA-499's own tradeoff — Cohere Embed v4 is native on acc2, no known failure pattern
  yet to build a fallback for).
- The `writer_missing_brand_rules` hint only fires when a cannibalization match ALREADY exists
  (one extra query on the rare path, not every attempt) — a tenant with no brand rules but no
  actual collision gets no proactive nudge from this gate. Acceptable: that's the "validate/nudge
  before atomize" alternative this issue explicitly left as a separate, undecided option.
