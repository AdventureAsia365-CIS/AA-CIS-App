## Phần E — systemic sticky-header audit (2026-09-09)

### Decisions
- Grepped the whole frontend for `overflowY: "auto"|"scroll"` (31 files), then narrowed to files
  where `flex: 1` and `overflowY` co-occur without `minHeight: 0` nearby (a Python heuristic
  script, not manual page-by-page guessing) — 24 genuine hits, 3 false positives (bounded
  `maxHeight` lists, not flex-driven growth; left untouched).
- **Real correction mid-audit**: my first pass only added `minHeight: 0` to the inner flex:1
  overflow pane, mirroring what I assumed the AA-564 atom-curation fix did. Live-tested against
  `/admin/dashboard` and found it did NOT work — `document.scrollingElement.scrollTop` moved
  2000px on a real wheel scroll, meaning the whole page scrolled, not `<main>` internally.
  Diagnosed via `main.scrollHeight === main.clientHeight` (11190 === 11190) — `<main>` was never
  actually height-constrained. Re-read atom-curation's own proven fix and found the real missing
  ingredient: the flex-column ancestor ALSO needs a hard `height: "100vh"` (not just
  `minHeight: "100vh"`, which is a floor, not a ceiling) — `minHeight: 0` on the inner pane does
  nothing without an ancestor that actually caps the available height. Went back and added
  `height: "100vh"` to the correct ancestor in every one of the 24 files (either an existing
  `<div flex:1 display:flex flexDirection:column minWidth:0>` wrapper, or the outermost
  `<div display:flex minHeight:"100vh">` row itself when there's no intermediate wrapper).

### Changed — 24 files, `minHeight: 0` on the flex:1 overflow pane + `height: "100vh"` on its
flex-column ancestor (see git diff for the exact line per file):
`(internal)/{brand,catalog,review,upload}/page.tsx`, `(tenant)/portal/layout.tsx` (affects every
tenant portal page, including My Catalog), `admin/_components/{CompareModal,TourDetailPanelV2}.tsx`
(already viewport-pinned via `inset:0`/`top:0 bottom:0`, only needed `minHeight:0`, not the
ancestor change), `admin/{a4-oversight,brand,dashboard,llm-usage,master-content,review,
run-health,s1-rewrite,settings,tenant-activity,tenants,upload}/page.tsx`,
`admin/pipeline/{s1,s2,s3,s4-blog,s4-social}/page.tsx`.

### Tradeoffs
- Did not touch 3 flagged-but-false-positive sites (`admin/pipeline/s1/page.tsx:507`,
  `(internal)/review/page.tsx:54` — both bounded by an explicit `maxHeight`, not flex-driven,
  so they were never actually vulnerable to this bug) — applying the fix there would be a no-op
  at best, so left alone to keep the diff scoped to real fixes.
- `master-content/page.tsx` and `admin/tenant-activity/page.tsx` already had the correct
  `height: "100vh"` at the right ancestor level (the former from its own multi-panel-compare
  build, the latter from AA-551's sticky-header fix) — only needed the inner `minHeight: 0`
  additions, already covered by the earlier pass.

### Live-verify
`tests/e2e/aa566-partE-sticky-audit.spec.ts` — structural check (content pane's `clientHeight`
stays capped at the viewport while `scrollHeight` can exceed it, instead of both being equal —
the bug's signature) across 8 admin pages + the tenant portal shell, plus a real mouse-wheel
scroll check on 2 representative pages confirming `document.scrollingElement.scrollTop` stays 0
(the page itself never scrolls, only the internal pane does). 11/11 passing locally.

### Should know
- This is the 4th time this exact bug class has been fixed (after AA-554/557/564, all on
  `/admin/atom-curation` alone) — this pass is the first to audit the WHOLE codebase instead of
  the one page Nghiệp happened to notice, per his explicit ask.
- The 2-ingredient fix (`height: "100vh"` on the flex-column ancestor + `minHeight: 0` on the
  flex:1 overflow pane) is the complete, minimal, already-proven-correct pattern — confirmed by
  re-reading `atom-curation/page.tsx`'s own working implementation, not re-derived from scratch.

## Phần B — My Catalog UX upgrades (2026-09-09)

### Decisions
- Row click-to-open: made the whole `<tr>` clickable (Notion/Linear/Airtable pattern, per the
  issue's own reference), except the checkbox `<td>` (kept its `stopPropagation()`) and the
  Actions `<td>`'s own button (also stops propagation, so it stays a redundant-but-harmless
  second way to open the same row).
- DOCX export: new tenant-scoped `GET /v1/tours/versions/{id}/export-docx` in `v1_tours.py`,
  deliberately NOT sharing code with Admin's `export_tour_version_docx()` — different source
  table (`gold_aa_internal.tenant_tour_versions` vs `silver_aa_internal.generated_content`) and
  the tenant version renders no SEO/score section at all (see Phần B.5 below), so a shared
  helper would need more branching than just writing two small functions.
- Sortable headers: mirrored `admin/_components/auditPanels.tsx`'s own `toggleSort()`/arrow
  convention (AA-557's precedent) rather than inventing a new one — `sortKey`/`sortDir` state,
  `▲`/`▼`/`▲▼` indicator.
- Confirmed `raw_tours.inclusions`/`exclusions` (TEXT) exist in the schema
  (`api/migrations/003_schema_v3.sql`) before adding them to `get_version()`'s SELECT — per the
  issue's own "confirm data availability first" instruction.

### Changed
- `api/routers/v1_tours.py`: `get_version()` SELECT gained `rt.inclusions, rt.exclusions`; new
  `export_version_docx()` endpoint.
- `CatalogTab.tsx`: `#` row-numbering column; sortable Tour Name/Country headers; Country filter
  dropdown; whole-row click opens the drawer; Subtitle shown under the tour name (table row);
  drawer gained a "Trip Details" section (Duration/Inclusions/Exclusions, only rendered when at
  least one is present); SEO Title/SEO Meta `CompareRow`s removed; `SeoHealthBar` section removed
  entirely (import dropped); `SeeOriginalToggle`'s `seoTitle`/`seoMeta` props passed `null` (the
  shared component itself untouched — still used elsewhere with those fields, just not from this
  call site); "Export DOCX" button added next to "Request Rewrite".

### Tradeoffs
- SEO Title/SEO Meta removed from the tenant-facing UI only — `editSeoTitle`/`editSeoMeta` state
  and the PATCH body in `saveEdit()` are UNTOUCHED, so Save still round-trips those fields
  (preserves whatever value was already there) even though the tenant can no longer see or edit
  them. Confirmed with Nghiệp's own AA-565 precedent: hide from tenant UI, never delete data —
  Admin's oversight views still read the same columns.
- `SeeOriginalToggle` (a shared component) kept its `seoTitle`/`seoMeta` props in its own
  signature rather than removing them, since this is its only call site today but removing the
  props would be a breaking API change for a component that might get reused — passing `null`
  achieves the same visible result with a smaller diff.

### Should know
- Live-verified locally (`tests/e2e/aa566-partBCD-catalog-pool-upgrades.spec.ts`, real WanderLux
  session against the real ECS backend + RDS): row numbering, sortable headers actually reorder
  rows, Country dropdown present, whole-row click opens the drawer, SEO Title/SEO Meta/SEO Health
  Bar all absent (0 count) from the drawer, Trip Details section renders (confirmed "Duration:
  HALF DAY" on a real tour). **The Export DOCX button IS present and fires the correct request**,
  but the actual download could not complete pre-deploy: `.env.local` points the local dev

## Phần D — Rewrite Config tab removed (2026-09-09)

### Decisions
- Removed the "Rewrite Config" tab (`RewritePanel` + `ConfigBlock`) entirely — Nghiệp's own
  decision (b), already made in the issue text: the external bulk "Rewrite N" bar already covers
  triggering a rewrite.
- **Real functional gap found and fixed, not just a deletion**: the bulk bar only rendered on
  `checked.size > 0` (checkbox multi-select). A tenant who just clicks a row to view details
  (`selected` set, nothing checked) would have had NO way left to trigger a rewrite for that one
  tour once Rewrite Config's own button was gone — a real regression, not a hypothetical. Fixed
  by changing the bar's visibility condition (and its target/count) from `checked.size` to
  `rewriteTargets.length` (`checked.size > 0 ? Array.from(checked) : selected ? [selected.id] :
  []` — already existed, just wasn't wired to the bar's visibility before). "Clear" now resets
  both `checked` and `selected`.
- Language/SEO Mode/Brand Rules disposition — **explicitly flagged per the issue's own "cần điều
  tra, không tự quyết định thay" instruction, not silently decided**: these 3 knobs had no other
  home anywhere in the tenant portal to move into. Hardcoded them as top-of-file constants
  (`REWRITE_LANGUAGE = "en-US"`, `REWRITE_SEO_MODE = "standard"`, `REWRITE_USE_BRAND_RULES =
  true`) at `RewritePanel`'s own prior defaults — functionally unchanged for the common case,
  since almost every real rewrite already used these defaults (confirmed no other call site in
  the codebase ever changed them away from default before this change). **Open question for
  Nghiệp/Claude Chat**: if a tenant ever needs a different language or SEO mode, where should
  that control live now — a Settings page, a per-tenant brand-rules field, or somewhere else?
  Not decided here.

### Changed
- `PoolTab.tsx`: `RewritePanel`/`ConfigBlock` functions deleted; `panelTab` state + tab-bar UI
  deleted (single panel now, always `DetailPanel`); `rwLang`/`rwSeo`/`rwBrand` state deleted,
  replaced by the 3 module-level constants above; batch bar condition changed from `checked.size
  > 0` to `rewriteTargets.length > 0`, label/button text now branches on `rewriteTargets.length`
  (mirrors the exact "Rewrite this tour"/"Rewrite N tours" branching the old panel's own button
  had, so the wording tenants see is unchanged).

### Tradeoffs
- Did not add a `data-testid` anywhere in `CatalogTab.tsx` (real semantic `<table>`/`<tr>`/`<td>`
  elements are already stable Playwright selectors) but DID add one (`data-testid=
  "pool-tour-row"`) to `PoolTab.tsx`'s `TourRow` root — that file has no semantic table structure
  to select against, and guessing at inline-style string matching in a test is fragile (confirmed
  in this build's own first test draft, which failed for exactly that reason before being fixed).

### Should know
- Live-verified locally: no "Rewrite Config"/"📄 Tour Details" tab bar visible anywhere, single
  tour selection alone (no checkbox) surfaces a "Rewrite this tour" button via the batch bar
  (screenshot: `tests/e2e/results/aa566-bcd/6-single-tour-rewrite-bar.png`) — confirming the real
  gap above is actually closed, not just theoretically closed.
- Did NOT click the "Rewrite this tour"/"Rewrite N tours" button in either local or (planned)
  production live-verify runs — doing so consumes a real rewrite credit and a real Bedrock call,
  and this exact trigger path (`doRewrite()` → `POST /pool/{id}/rewrite`) was already proven live
  multiple times this session (AA-565, AA-567's full end-to-end run) — re-spending quota here
  would test nothing new.
