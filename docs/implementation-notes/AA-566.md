# AA-566 — My Catalog count bug + systemic sticky-header audit + UX upgrades

Working incrementally, per repo convention. Order: Phần A → Phần E → Phần B/C/D.

## Phần A — sidebar/heading count mismatch (2026-09-09)

### Decisions
- Extracted a shared `countUniqueTours()` helper into `_components/ui.tsx` rather than
  duplicating the dedup logic in `layout.tsx` — both the sidebar badge and `CatalogTab.tsx`'s
  heading must count the same thing, so one function is the single source of truth.

### Changed
- `layout.tsx`: sidebar's `catalogCount` used to read `GET /v1/tours/my-versions?page_size=1`'s
  flat `pagination.total` (every `tenant_tour_versions` row, including old hidden versions).
  Changed to fetch `page_size=50` (matches `CatalogTab.tsx`'s own fetch) and compute
  `countUniqueTours(d.data)` — same client-side dedup-by-`published_tour_id` `CatalogTab.tsx`
  already does. `refreshCatalogCount()` gets the identical fix.

### Should know
- Root cause: AA-565 made `CatalogTab.tsx`'s own heading count unique tours (1 row per tour,
  latest version only) but nobody updated `layout.tsx`'s sidebar badge, which kept reading the
  old flat per-version total from the same endpoint.
- Live-verified locally: sidebar and heading both read `11` for WanderLux Travel after the fix
  (screenshot: `tests/e2e/results/aa566-a/1-count-match.png`).

## Phần E — systemic sticky-header audit (2026-09-09)

### Decisions
- Grepped the whole frontend for `overflowY: "auto"|"scroll"` (31 files), then narrowed to files
  where `flex: 1` and `overflowY` co-occur without `minHeight: 0` nearby (a Python heuristic
  script, not manual page-by-page guessing) — 24 genuine hits, 3 false positives (bounded
  `maxHeight` lists, not flex-driven growth; left untouched).
- **Real correction mid-audit**: my first pass only added `minHeight: 0` to the inner flex:1
  overflow pane, mirroring what I assumed the AA-564 atom-curation fix did. Live-tested against
  `/admin/dashboard` and found it did NOT work — `document.scrollingElement.scrollTop` moved
  2000px on a real wheel scroll, meaning the whole page scrolled, not `<main>` internally.
  Diagnosed via `main.scrollHeight === main.clientHeight` (11190 === 11190) — `<main>` was never
  actually height-constrained. Re-read atom-curation's own proven fix and found the real missing
  ingredient: the flex-column ancestor ALSO needs a hard `height: "100vh"` (not just
  `minHeight: "100vh"`, which is a floor, not a ceiling) — `minHeight: 0` on the inner pane does
  nothing without an ancestor that actually caps the available height. Went back and added
  `height: "100vh"` to the correct ancestor in every one of the 24 files (either an existing
  `<div flex:1 display:flex flexDirection:column minWidth:0>` wrapper, or the outermost
  `<div display:flex minHeight:"100vh">` row itself when there's no intermediate wrapper).

### Changed — 24 files, `minHeight: 0` on the flex:1 overflow pane + `height: "100vh"` on its
flex-column ancestor (see git diff for the exact line per file):
`(internal)/{brand,catalog,review,upload}/page.tsx`, `(tenant)/portal/layout.tsx` (affects every
tenant portal page, including My Catalog), `admin/_components/{CompareModal,TourDetailPanelV2}.tsx`
(already viewport-pinned via `inset:0`/`top:0 bottom:0`, only needed `minHeight:0`, not the
ancestor change), `admin/{a4-oversight,brand,dashboard,llm-usage,master-content,review,
run-health,s1-rewrite,settings,tenant-activity,tenants,upload}/page.tsx`,
`admin/pipeline/{s1,s2,s3,s4-blog,s4-social}/page.tsx`.

### Tradeoffs
- Did not touch 3 flagged-but-false-positive sites (`admin/pipeline/s1/page.tsx:507`,
  `(internal)/review/page.tsx:54` — both bounded by an explicit `maxHeight`, not flex-driven,
  so they were never actually vulnerable to this bug) — applying the fix there would be a no-op
  at best, so left alone to keep the diff scoped to real fixes.
- `master-content/page.tsx` and `admin/tenant-activity/page.tsx` already had the correct
  `height: "100vh"` at the right ancestor level (the former from its own multi-panel-compare
  build, the latter from AA-551's sticky-header fix) — only needed the inner `minHeight: 0`
  additions, already covered by the earlier pass.

### Live-verify
`tests/e2e/aa566-partE-sticky-audit.spec.ts` — structural check (content pane's `clientHeight`
stays capped at the viewport while `scrollHeight` can exceed it, instead of both being equal —
the bug's signature) across 8 admin pages + the tenant portal shell, plus a real mouse-wheel
scroll check on 2 representative pages confirming `document.scrollingElement.scrollTop` stays 0
(the page itself never scrolls, only the internal pane does). 11/11 passing locally.

### Should know
- This is the 4th time this exact bug class has been fixed (after AA-554/557/564, all on
  `/admin/atom-curation` alone) — this pass is the first to audit the WHOLE codebase instead of
  the one page Nghiệp happened to notice, per his explicit ask.
- The 2-ingredient fix (`height: "100vh"` on the flex-column ancestor + `minHeight: 0` on the
  flex:1 overflow pane) is the complete, minimal, already-proven-correct pattern — confirmed by
  re-reading `atom-curation/page.tsx`'s own working implementation, not re-derived from scratch.
