# AA-377 + AA-378 — N7 weekly run + Slot persistence (migration 096, 1 PR)

STEP 0 (offline session, prior to this one) already surveyed both issues — see conversation
history / Linear AA-377 & AA-378 comments for the full raw findings. This doc covers the
implementation session only: the decisions STEP 0 handed off, and what actually got built.

## Decisions (carried in from STEP 0, confirmed by Nghiep before this session started)

1. **New table `acp_shared.acp_v2_runs`, NOT reuse of `acp_shared.acp_runs`.** The existing
   `acp_shared.acp_runs` (M0 migration, AA-41, applied outside `api/migrations/` via
   `DBeaver/acp_m0_migration.sql`) is the acpcore v0.4.0 S1-S4 pipeline's run table — live,
   read/written by `api/routers/v1_s1.py`, `v1_s3.py`, `v1_s4_blog.py`, `v1_s4_social.py`,
   `services/acp/s2/router.py`, `services/acp_s3/handler.py`, `services/acp_canary/lambda_handler.py`,
   and `api/routers/admin_pipeline.py`'s stuck-run sweep. Its `status` vocabulary
   (`s1_pending`/`s4_blog_status`/...) and admin/canary logic are all S1-S4-specific. Reusing it
   for N7 weekly runs risks a weekly run row being swept/misread by that S1-S4 logic. A separate
   table has zero blast radius on that live path.
2. **Slot persists as its own table (`acp_shared.acp_v2_slots`), 1 table not 2**, FK'd to
   `acp_v2_runs(run_id)` — matches the shape `services/acp_produce/slot_runner.py` (AA-375) already
   committed to (`run_id: str` and `slot: Slot` as two separate caller-supplied params, implying a
   run is created first, then N slots are allocated under it). `status` (`due`/`produced`/`skipped`)
   lives directly on this table rather than a second table, since due/produced/skipped is
   per-slot-per-run state, not an independent entity.
3. **Deterministic `slot_id`**: `sha256(tenant_id|year|week|tour_id|channel)` instead of
   `uuid.uuid4().hex[:10]` — fixes the AA-377 bug directly (slot_id changing every
   `allocate_month()` call). Re-running allocation for the same (tenant, week, tour, channel) now
   yields the same row; `ON CONFLICT (slot_id) DO NOTHING` on insert makes re-allocation a no-op
   for slots that already exist, satisfying "resume/retry the same slot, not duplicate content"
   from the AA-377 issue text.
4. **1 migration (096) + 1 PR** for both issues — `acp_v2_slots.run_id` FKs straight into
   `acp_v2_runs`, so the two tables can't be split across migrations without a broken intermediate
   state.

## Changed

- `api/migrations/096_acp_v2_runs_slots.sql` — new tables `acp_shared.acp_v2_runs` /
  `acp_shared.acp_v2_slots`, re-points `acp_deliver.pieces.run_id`'s FK (migration 094) from
  `acp_shared.acp_runs(run_id)` to `acp_shared.acp_v2_runs(run_id)`. Live-confirmed 0 rows in
  `acp_deliver.pieces` immediately before writing this file (re-checked, not reused from STEP 0's
  earlier count) — no backfill needed, straight `DROP CONSTRAINT` / `ADD CONSTRAINT`.
- `services/acp_planning/allocator.py` —
  - `make_slot()`: `slot_id` now `_deterministic_slot_id(tenant_id, week, trip_id, channel)`
    instead of `uuid.uuid4().hex[:10]`. `reactive_hold` slots (no `trip_id`) keep a random id —
    there's nothing meaningful to derive from for a slot with no destination/channel-bound content,
    and de-duplicating them isn't the bug AA-377 names (see Tradeoffs).
  - `create_weekly_produce_run(db, tenant_id, year, week) -> run_id`: inserts one
    `acp_v2_runs` row, `ON CONFLICT (tenant_id, year, week) DO NOTHING` + re-select, so calling it
    twice for the same week returns the same `run_id`.
  - `persist_slot_grid(db, run_id, tenant_id, week, slot_grid) -> list[Slot]`: writes every
    non-`reactive_hold` slot in a `SlotGrid` into `acp_v2_slots` (`status='due'`),
    `ON CONFLICT (slot_id) DO NOTHING` — re-running allocation is a no-op for slots that already
    exist.
  - `fetch_due_slots(db, run_id) -> list[Slot]`: reads back `status='due'` rows for a run,
    reconstructed as `Slot` objects for `slot_runner.py` to consume.
  - `mark_slot_status(db, slot_id, status, reason=None)`: flips a slot's status
    (`due`→`produced`/`skipped`) — `slot_runner.py` itself is NOT modified to call this in this
    issue (out of scope, see "Not done" below); the verify script calls it directly to prove the
    read-path excludes non-`due` slots.
  - `allocate_and_persist_week(...)`: the combined flow STEP 5/6 asked for — creates (or reuses) the
    run, calls the existing `allocate_month()`, persists the resulting grid, returns
    `(run_id, list[Slot])`.
- `tests/unit/test_aa377_aa378_run_slot_persist.py` — new, mocked-DB unit tests.
- `tests/verify_scripts/aa377_aa378_run_persist_verify.py` — new, ADR-2026-037 real-DB verify
  script (test-only, never imported by `services/`, never run by CI).

## Not done (explicitly out of scope, per the issue's own STEP boundary)

- No router / HTTP endpoint.
- No cron/EventBridge trigger — same reason AA-375 deferred it: wiring a trigger before this
  session's persistence layer existed would have handed every re-run a fresh `slot_id`.
- `slot_runner.py` (`run_slot_production()`) itself is untouched — it already takes `run_id`/`slot`
  as caller params; this session is the caller that now has real values to hand it instead of the
  interim `INSERT INTO acp_shared.acp_runs (...) VALUES ('running')` the AA-375 verify script used
  as a stand-in. It does not call `mark_slot_status()` after producing a piece — that wiring is a
  reasonable next step but wasn't asked for here, and doing it silently would change
  `run_slot_production()`'s existing tested behavior without a issue asking for it.

## Tradeoffs

- **`reactive_hold` slots keep a random `slot_id`.** They have no `trip_id`/no real content
  target (`Slot.topic_hint` is a static "HELD EMPTY" string) — hashing on `(tenant_id, week, None,
  channel)` would collapse every reactive-hold slot in the same week+channel into ONE row via
  `ON CONFLICT DO NOTHING`, silently dropping slots the allocator intentionally created as
  separate empty placeholders. Keeping them random matches the pre-existing intent (each is its own
  placeholder) at the cost of leaving AA-377's literal bug description ("slot_id ngẫu nhiên") true
  for this one slot kind. Flagged here rather than silently deciding it doesn't matter.
- **`persist_slot_grid` re-derives `week` from `SlotGrid`'s 4-slot-per-week convention
  (`allocator.py`'s `weeks = [1, 2, 3, 4]`, i.e. week-of-month, not ISO week)** — same convention
  `compute_slot_grid()` already uses internally; not changed or reconciled with `acp_deliver.packets`'
  ISO `year`+`week` columns (migration 094) in this issue. `acp_v2_runs`/`acp_v2_slots.week` store
  this same week-of-month integer (1-4), a deliberate scope boundary, not an oversight — reconciling
  the two week numbering schemes is a separate decision nobody has made yet.
