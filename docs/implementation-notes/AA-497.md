# AA-497 — [AA-494 Decision 3] status mới sau `approved` + API chọn lại angle

STEP0-refresh confirmed PR #253's `choose_angle()` unset-fix is live in current code (the other 2
options are explicitly set `chosen=false` in the same transaction) — this is the prerequisite
Decision 3 itself named as mandatory before any re-selection design could ship safely.

**Real finding before writing any code**: migration 124 (a prior session, same day) already added
`'reusable'` to `angle_gate_request.status`'s CHECK constraint — confirmed live via direct schema
read, not assumed. So this build did **not** need a new status-name migration; it needed the
service/API/frontend wiring that actually uses the value, plus one more schema fix migration 124's
own header explicitly flagged and deferred (see Decisions below).

## Decisions

- **Status value name: `reusable` (already live, migration 124 — not re-chosen here).** The
  design doc's original mechanism for reaching it ("auto-flip on first successful piece,
  permanent thereafter") was NOT what this issue's own task description asked for. AA-497's task
  description instead specifies a tenant-triggered, transient **reopen** action:
  `approved` → (tenant clicks "Change angle") → `reusable` → (tenant re-picks) → `approved` again.
  Treated AA-497's own text as the authoritative, later refinement of Decision 3's mechanism
  (the design doc itself left the exact trigger condition explicitly undecided — "needs to be
  decided during migration write-up"). Reused the existing `reusable` string rather than adding a
  second value or renaming it — zero live rows were ever in that status (confirmed), so renaming
  would have been free but pointless churn; the word still reads correctly for "this request's
  angle choice is reusable/re-selectable," just describing a transient state rather than a
  permanent post-first-write flag.
- **`start_write()`'s status guard needs ZERO changes — verified, not assumed.** The task
  description asked me to confirm this rather than take it on faith. Confirmed true: because
  `choose_angle()`'s final UPDATE sets `status = 'approved'` unconditionally regardless of whether
  it was called from `pending_choice` or `reusable`, `start_write()` never actually observes
  `status = 'reusable'` in practice — by the time a write can happen, status is always back to
  `approved`. No code change made to that guard.
- **Necessary companion fix, found via STEP0-refresh, not optional: `content_piece`'s
  `UNIQUE (angle_gate_request_id, attempt_number)` constraint.** Migration 124's own header had
  already flagged this as "a genuine, separate schema question... flagged for the next session."
  Traced why: `_insert_placeholder_piece()` hardcodes `attempt_number=1` on every `start_write()`
  call (that column is T9's own internal 1-2 write/rewrite retry counter within ONE session,
  finalized in place by `_finalize_piece()` — never a per-request sequence number). A second real
  write on a reopened request would try to INSERT a second `attempt_number=1` row for the same
  request, colliding with this constraint in the common case (first write passed on its first
  internal try). This is not a theoretical risk — it is the direct, immediate, and near-certain
  consequence of shipping the reopen action without also fixing it, so it's treated as in-scope
  for this build, not a follow-up. Fix: migration 125 drops the constraint (confirmed via grep
  that no code anywhere relies on it for a "latest piece per request" query).
- **`content_piece.angle_gate_option_id` (migration 124's Decision 2 column, previously
  unpopulated) is now populated at write time.** Necessary companion fix: once re-selection is
  real, `angle_gate_option.chosen` is mutable — `api/routers/v1_publish.py`'s `list_pending()`/
  `publish()` used to join a piece's displayed angle name via `ago.chosen = true`, which would
  retroactively show the WRONG angle for an OLD piece after a later re-choice on the same
  request. Fixed both queries to join via the new FK first, falling back to the old `chosen=true`
  join only for pre-AA-497 rows (`angle_gate_option_id IS NULL`).
- **"Reopen" only re-selects a different ANGLE for the same atom+channel — does not let a tenant
  swap the ATOM.** AA-469 Việc 2 originally described the target UX as "chọn lại atom cho slot đã
  viết" (colloquially: "pick something different for this already-written slot"); the concrete,
  approved mechanism (this issue's own task text) is angle re-selection on the EXISTING request,
  not a new atom/request. Picking a genuinely different atom for an already-written slot is a
  separate, bigger product question (effectively a new request) — out of scope here, flagged
  rather than silently expanded into.

## Changed

- **No new status migration** — `'reusable'` already live (migration 124).
- **New migration 125** — drops `content_piece_angle_gate_request_id_attempt_number_key`.
- `services/acp_angle_gate/service.py`:
  - New `reopen_request(tenant_id, request_id, pool)` — `approved` → `reusable` only, else
    `WrongStatusError`.
  - `choose_angle()`'s guard widened: `status in ("pending_choice", "reusable")` (was
    `"pending_choice"` only). Everything else unchanged — the final `status='approved'` UPDATE
    already worked for both source statuses.
  - `fetch_request()`'s angle SELECT now includes `option_id` (needed by `start_write()` below).
- `services/acp_content_writing/service.py`:
  - `_insert_placeholder_piece()` now takes `angle_gate_option_id` and writes it on INSERT;
    `start_write()` passes `chosen.get("option_id")` through.
- `api/routers/v1_angle_gate.py` — new `POST /requests/{request_id}/reopen`.
- `api/routers/v1_publish.py` — `list_pending()`/`publish()` join `angle_gate_option` via
  `cp.angle_gate_option_id` first, `chosen=true` as a legacy fallback.
- `services/acp_planning/tenant_pool.py` — `UsedAtom` gains `request_id` (the LATEST approved
  piece's `angle_gate_request_id` for that atom this month — not the earliest, unlike
  `used_at`/`channel`), surfaced automatically through `GET /v1/planning/slot-suggestions`'s
  existing `used_atoms` dict (`_asdict()` — no endpoint code change needed there).
- Frontend:
  - `SlotPickerPanel.tsx` — an already-written slot's expanded view now shows a compact
    "Already written" summary + **Change angle** button (replacing the atom-picker for that
    branch only) instead of the atom-picker; calls `.../reopen` then navigates to
    `/portal/t8-angle-gate?resume_request_id=...`.
  - `AngleGateTab.tsx` — new `resume_request_id` query param loads an existing request via
    `GET /requests/{id}` and renders straight into the angle-choice card (status `reusable`
    treated like `pending_choice` for that card, with copy distinguishing "choose" vs. "choose a
    different one"); the existing auto-write-on-approve behavior (`choose()` already calls
    `writeContent()` the instant `status === "approved"`) needed **zero changes** to also cover
    the re-selection path — it was already generic.

## Tradeoffs

- Did not build a "swap atom for this slot" flow (see Decisions) — flagged as a separate,
  bigger product question rather than guessed at.
- Did not backfill `angle_gate_option_id` for pre-migration-124 `content_piece` rows — confirmed
  live there are currently 0 rows with `status IN ('approved','reusable')`, so there is nothing to
  backfill; `v1_publish.py`'s fallback join covers the (currently empty) legacy case anyway.
- Left `idx_content_piece_request (angle_gate_request_id, attempt_number DESC)` in place after
  dropping the UNIQUE constraint it partially backed — harmless, still valid for a future
  request-scoped piece-listing query, not worth a second migration to remove.
