## Should know — the answer itself

**Segment's real input** (re-confirmed, matches AA-540): `services/acp_contract/
segment_matching.py:395-412`, `run_segment_matching(tenant_id, pool)` reads
`acp_contract.tour_atoms` filtered to `owner_scope='platform'` atoms whose `tour_id` is one the
calling tenant has picked (`gold_aa_internal.tenant_tour_versions`) — confirmed: two tenants
picking the identical tour read the exact same underlying atom rows.

**Why Segment is still per-tenant despite that, traced to two separate moments, neither of which
is "the algorithm requires it":**

1. **AA-509 (01/09/2026, `5f6a740`), 4 days before Atom became platform-wide.** The build task's
   own literal first sentence (`docs/claude_tasks/AA-509-segment-build.md:12-13`) defines Segment
   as grouping atoms "qua nhiều tour của **cùng tenant**." At that point Atom was STILL a
   per-tenant resource (the old tenant-triggered T5 endpoint, removed later by AA-526) — a
   shared-Segment alternative wasn't a live question because its premise (shared atoms) didn't
   exist yet. `atom_segment.tenant_id UUID NOT NULL` (migration 129) is a direct, unexamined
   consequence of that framing, not a debated choice.
2. **AA-526 (05/09/2026, `5f2b438`), when Atom did become platform-wide.** A platform-wide
   Segment was actually attempted (`docs/implementation-notes/AA-526.md`'s own "STEP0 correction
   #3") and reverted for two concrete blockers hit in the moment: `atom_segment.tenant_id`'s
   `NOT NULL` FK crashes on the literal string `'platform'` (not a UUID); and even past that,
   `atom_ranking.py` (AA-515, already shipped by then) reads Segments scoped to one specific
   tenant, so a platform-scope Segment row would be invisible to every real tenant's ranking read
   regardless. The fix chosen — keep Segment per-tenant, scope its atom READ to the shared pool
   instead — avoided a coordinated redesign of Ranking/Route/Slate that was out of AA-526's own
   scope. Nghiệp's quoted confirmation at that moment ("atoms are shared platform-wide, but
   Segments/Route/Ranking stay a PER-TENANT product") ratified this scope-avoidance fix; it is
   not evidence of a fresh technical analysis concluding the algorithm needs tenant awareness.

**No algorithmic/technical reason was found for Segment needing to know which tenant an atom
belongs to** — confirmed by reading `segment_matching.py` itself: `derive_segments()`/`_mint()`
are pure functions (Jaccard on place, verb-match on action), no I/O, no LLM call, no reference to
brand/voice/tenant content anywhere in the matching logic itself. The ONLY place `tenant_id`
enters is the identity/isolation layer (the hash + the FK), not the grouping decision.

**Rough cost estimate, since none was in the original decision record**: segment-matching is
pure CPU (no LLM/DataForSEO call), so N tenants picking the same tour each recomputing an
identical Segment set costs N× redundant CPU time (Jaccard over a typical tour's dozen-ish atoms
— milliseconds, not the multi-second/dollar cost Search Demand's real API calls carry) plus N×
duplicated storage in `atom_segment`/`atom_segment_member`/downstream `atom_ranking`/`route`/
`subject` rows. Real, but non-trivial only at meaningfully larger tenant-count-per-shared-tour
than exists today — plausibly why, unlike Search Demand (a real, reasoned, dollar-motivated
sharing decision at AA-515), nobody has revisited this with the same urgency even after AA-526
exposed the underlying atoms as shared. Whether to redesign Segment/Ranking/Route/Slate to be
platform-wide remains Nghiệp's own open decision — not made here, per this issue's explicit
"KHÔNG sửa code" scope.
