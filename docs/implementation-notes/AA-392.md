## Decisions

- **Reused the existing `_call_claude_satellite()` seam instead of rewriting `_call_palmyra()`.**
  The file already had a real, tested, wired-but-not-default Claude path (added when AA-306
  first built the `model_tier` seam) that calls the exact same `invoke_claude()` function N7's
  `generation.py` uses — same cross-region inference-profile ARN resolution
  (`INFERENCE_PROFILE_SONNET` in `bedrock_satellite.py`, not a hardcoded base-model ARN), same
  account (acc1 satellite). Flipping `DEFAULT_MODEL_TIER` from `"palmyra"` to `"claude"` and
  deleting `_call_palmyra()` achieves AA-392's goal with less code than modifying
  `_call_palmyra()` into a second, duplicate Sonnet-calling function would have.
- **`model_tier="palmyra"` now raises loudly instead of being deleted as a case.** Added an
  explicit branch in `generate_draft()` that raises `ValueError` naming AA-392/AA-337 if anyone
  (a stale caller, a future regression) passes `model_tier="palmyra"` again — this directly
  guards against the exact failure class that triggered this issue (a live run silently using a
  model everyone thought was already retired elsewhere).
- **No lightweight/Haiku sub-step exists to route separately.** Re-read the full S1-from-atom
  flow (`fetch_curated_atoms` → `build_user_prompt` → one `generate_draft()` writer call →
  deterministic `check_grounding()` → retry-with-feedback loop): the only LLM call in the module
  is the single assembly call itself — there is no separate filter/validate LLM sub-step to
  offload to Haiku. Sonnet is the only real writer role here, same conclusion N7 reached for its
  own single E2 draft call.
- **Verified in-place against the real ECS container, not just unit tests.** Unit tests mock the
  Bedrock call entirely, so they can't catch a real quality regression. Uploaded the patched
  `s1_from_atom.py` into the running `aa-cis-dev-api` task's filesystem (a temporary,
  session-only overwrite — restored from `/tmp/s1_from_atom.py.orig_backup` immediately after
  verification; the real fix ships via this PR + normal deploy, not a live container edit) and
  ran `tests/verify_scripts/aa392_sonnet_writer_verify.py` against 5 real Laos/South Korea tours
  that AA-391's own (killed mid-run) chain had already decomposed + curated.

**5/5 passed** (vs Palmyra's 1/2 on the two tours that got far enough to compare — one clean
pass, one hard failure). Every pass cleared all three real gates (closed-world, density,
entailment) with zero unknown citations across the sample. One real, reportable false-positive
signal along the way: `IMPRESSIONS OF LAOS` attempt 0 was rejected for `novel_numbers=['1','2']`
on the sentence *"Site 1 holds over 300 jars; Site 2 has 93 jugs..."* — the entailment checker
flagged the `1`/`2` site-label digits as fabricated numbers; retry 2 rephrased around it and
passed. This looks like a pre-existing sensitivity in `find_novel_numeric_claims()` to small
ordinal/label digits (not something AA-392 introduced or something specific to Sonnet — the same
checker runs regardless of writer model) — worth a note for whoever next touches
`services/acp_shared/grounding.py`, not fixed here (out of this issue's scope).

No DB writes beyond `generate_s1_from_atom()`'s own normal read-only behavior — this function
doesn't persist anything itself (the router's `_log_run()` does that, not called by this verify
script). Full unit suite: 1110/1110 pass, flake8 clean.
