# AA-489 — Real per-tenant monthly rewrite quota (first-ever enforcement)

## Decisions
Business questions were not separately re-confirmed live with Nghiệp (mid-chain, build-prompt
instruction was to pick the conservative default and flag it, not stop to ask). Decisions taken,
per the chain build prompt's own explicit direction:
- **Limit**: `PLAN_LIMITS[plan_tier].tours_per_month` exactly as already defined in `admin.py`
  (starter=100, growth=500, business=2000, internal=999999) — no new number invented.
- **Reset**: calendar month (`year_month = 'YYYY-MM'`), not rolling 30 days.
- **Enforcement**: hard-block (429), not soft-warning — the issue's own stated purpose is LLM
  cost control, which a warn-only gate doesn't actually deliver.
- **plan_tier read live from `shared.tenants`**, not trusted from the JWT's own `plan_tier`
  claim — mirrors AA-432's rationale for `rate_limit_rpm`/`is_active` (a plan change shouldn't
  take up to 24h, the JWT's TTL, to take effect).
- **Increment-then-check**, not check-then-increment: a single atomic `INSERT ... ON CONFLICT
  DO UPDATE ... RETURNING rewrite_count` avoids a race window between two concurrent requests
  from the same tenant reading the same pre-increment count. Matches
  `rate_limit_middleware`'s own `redis.incr()`-then-compare order — a request that pushes the
  count past the limit still counts, "quota consumed by requesting."
- New table `shared.tenant_rewrite_usage` (migration 142) — explicitly NOT `acp_quota_ledger`
  (that's ACPv1 S2/S3/S4 quota, an architecture dead since 13/07/2026, per the issue's own
  instruction).

## Changed

  year_month, rewrite_count, updated_at)`, PK `(tenant_id, year_month)`. **Applied live**
  (`shared.schema_versions` confirms version 142).

    UI already expected.

- `tests/unit/test_aa489_rewrite_quota.py` — 7 new tests.
- `tests/unit/test_aa469_viec1_t4_t5_split.py` — updated its `conn.fetchval.side_effect`

## Tradeoffs
- No frontend UI rebuilt. Issue's own scope says "nếu muốn" (if wanted) — `GET /v1/quota` is
  built and ready, `CatalogTab.tsx`'s dialog can be restored to call it whenever that's wanted,
  but that's a separate, smaller follow-up, not bundled here.
- `QuotaBar.tsx` (api-playground, the issue's other named `rewrites_remaining` bug) no longer
  exists in the repo at all — grepped, 0 hits for that filename or field anywhere in
  `frontend/`. Nothing to fix; the issue's reference to it is stale.
- Blocked requests keep incrementing the stored count on every retry (same as
  `rate_limit_middleware`'s own counter does past its RPM limit) — the displayed "used" number
  can exceed the limit after repeated blocked attempts within the same month. Not a
  correctness bug (blocking still works every time), just a cosmetic detail if a UI ever
  surfaces the raw count instead of `rewrites_remaining` (which is clamped to 0, never negative).

## Should know
- `trigger_rewrite()`'s quota check runs inside the SAME `pool.acquire()` block already used
  for the published-tour lookup — one connection, sequential, no new connection-pool pressure.
- The 429 response body includes the actual used/limit numbers and reset date
  (`"Monthly rewrite quota exceeded (101/100 used this month, resets 2026-10-01)"`) — enough
  for a future frontend error toast without a second `GET /v1/quota` round-trip.
- `internal` plan_tier's limit (999999/month) is effectively unlimited by design, matching
  `PLAN_LIMITS`'s own existing shape — not something this task changed.
