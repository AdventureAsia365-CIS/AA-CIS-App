# AA-513 — [T9] Route-aware write

## Decisions

- **AA-511's own Gap A fix (PR #274, merged) already built most of this ticket's ask** — a Route/
  Blog pick's write seed was already the joined text of every Segment's live representative atom,
  in the Route's own day order (`_fetch_route_text()`, now `_fetch_route_segments()`). The one
  genuinely missing piece, confirmed by reading (not guessed): the citation-tag mechanism still
  only ever knew ONE atom_id (the first Segment's) — every fact from every OTHER Segment in the
  joined seed was still told to cite that same single id. That's the real gap this ticket closes.
  Full evidence: `docs/claude_audit/AA-513-step0-investigation.md`.
- **F1/F2/F5 gates already worked correctly for the joined multi-segment text with zero code
  change** — `gate_grounding()`/`gate_banned_patterns()` already check against the FULL joined
  `atom_text` (not one atom), and `gate_atom_density()`'s `TAG_RE` already generically matches
  ANY id, not one hardcoded literal. Confirmed by reading, not assumed — only a stale docstring
  comment ("T9 has exactly one atom per piece") needed correcting.
- **Deliberately did NOT label the gate-facing `atom_text`** with per-segment ids — only the
  PROMPT's own content-seed rendering gets labeled moments (`[Moment id=<id>]`). Embedding an id
  like `atom_00af646e46` into the text `find_novel_numeric_claims()` scans would let its embedded
  digits register as a false "supporting number", silently weakening F1. `atom_text` (gates) and
  the labeled seed (prompt) are now two separate strings built from the same `route_segments`
  list, not one shared variable.
- Route-awareness (2+ segments) is gated on `channel == 'blog'` in `prompts.py` itself, not just
  assumed from the caller — matches the real domain invariant (`grain: "route"` is blog-only,
  `services/acp_shared/slate.py::CHANNEL_BARS`) defensively, in case that ever changes upstream.
- A single-element `route_segments` (or none) behaves byte-identically to the pre-AA-513 path —
  one moment needs no "which one" disambiguation.

## Changed

- `service.py::_fetch_route_text()` → `_fetch_route_segments()`: now returns `list[(atom_id,
  text)]` instead of one joined string.
- `service.py::start_write()`: builds `context["route_segments"]` (None for every non-Route
  request) alongside the unchanged `atom_text` (still the plain joined text, for the gates).
- `service.py::run_write_background()`: reads `route_segments` from context (`.get()`, backward
  compatible with any context dict built without the key) and passes it through to
  `write_content()`/`rewrite_with_feedback()`.
- `generate.py`: both functions gain `route_segments` kwarg, defaults `None`, passed straight
  through.
- `prompts.py::build_user_prompt()`: gains `route_segments` kwarg. When blog + >1 segment, the
  CONTENT SEED section renders as labeled moments and a new `_BLOG_FORMAT_INSTRUCTIONS_ROUTE`
  variant tells the model to tag a fact with its OWN moment's id.
- `quality_gates.py`: comment-only fix on `TAG_RE`'s stale "exactly one atom per piece" docstring.

## Tradeoffs

- Did not port ADR 0009's "claim support" gate (verifying a cited sentence shares a distinctive
  word with the SPECIFIC id it cites, not just tag presence) — not asked by AA-513 or AA-514,
  and a real, separate scope AA-450/452 already deliberately left unported. Flagged, not built.

## Should know

- Full pipeline (Segment/Route/Ranking/Subject) is genuinely empty tenant-wide right now
  (pre-existing atoms predate migration 129's place/action split) — real live-verify used 2 real
  atoms + minimal manually-inserted Segment/Route/Subject rows to exercise this build's own
  changed code, same disclosed pattern AA-512 used.

## Live Verify (real Bedrock + real RDS, via ECS exec, 2026-09-02)

- Real Route with 2 real Segments (Wat Sisaket / atom_00af646e46, That Chomphet Stupa /
  atom_092b91dfda) → `pick_subject()` → `route_segment_ids` correctly carries both, in order.
- `start_write()`'s `context["route_segments"]` correctly resolved BOTH segments' real
  (atom_id, text) pairs; `context["atom_text"]` (fed to the gates) stayed the plain joined text.
- Real T9 write (Bedrock satellite acc3, GPT-4.1 judge): raw output (captured pre-strip via a
  spy on `strip_citation_tags`) contained 8 citation tags using BOTH real distinct ids —
  `atom_00af646e46` and `atom_092b91dfda` — confirming the model correctly attributed facts to
  their OWN Segment, not one blanket id. Final persisted `content_text` had ZERO raw tags
  (piece landed `held` on a real, legitimate F1_grounding catch — gates evaluating for real, not
  rubber-stamping; the strip step ran regardless of status, per its own "runs unconditionally"
  design).
- Regression: a non-Route, single-atom Facebook request (`context["route_segments"]` correctly
  `None`) ran end-to-end unaffected — approved on attempt 2, zero tags in the final content,
  confirming the other 7 channels' behavior is byte-for-byte unchanged.
- Test data (2 Segments, 1 Route, 1 Subject, 2 requests, 2 pieces) fully cleaned up — 0 leftover.
