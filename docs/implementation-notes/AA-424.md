# AA-424 — Fix /admin/brand-identity hardcoded tenant_id + static-secret-only auth

## Decisions

- **Dual-auth resolver instead of a hard swap to tenant-JWT-only.** While implementing, found a
  SECOND real caller of `GET/POST /admin/brand-identity` that AA-424's description didn't know
  about: `frontend/app/(internal)/{brand,upload}/page.tsx`, via the confusingly-named
  `/api/tenant/pipeline/brand-identity` proxy (that file's own header comment already flags the
  naming as misleading — it's actually an admin route). These are genuine staff pages (admin/
  content role) that manage the AA-internal pseudo-tenant's own brand rules, carry no tenant JWT,
  and must keep working unchanged. A straight rewrite to "tenant JWT required" would 401 them.
  `_resolve_brand_tenant_id()` (`api/routers/admin_pipeline.py`) tries a tenant Bearer JWT first
  (the real fix — `verify_jwt()`, same helper `v1_tours.py`/`v1_atoms.py`/`v1_s3.py`/
  `v1_competitors.py`'s `get_tenant`/`_get_tenant` already use) and falls back to the pre-existing
  `X-Admin-Secret` + hardcoded AA-internal tenant_id path only when no Bearer token is presented —
  preserving the two staff pages exactly, while a real tenant caller now gets its own tenant_id.
- **`/brand-identity/upload` (3rd endpoint, same file) left untouched.** AA-424's issue text scopes
  this to "2 endpoint" (GET/POST). Upload still hardcodes the AA-internal tenant_id
  (`admin_pipeline.py:~4160`, unchanged) — it was already broken for real tenants before this fix
  (401 via the admin-only FE proxy) and stays broken after; not made worse. Tracked as a follow-up,
  not filed as a separate issue per this task's "small, independent, ~30 min" framing.

## Changed

- `api/routers/admin_pipeline.py`: `GET/POST /admin/brand-identity` — removed the hardcoded
  `tenant_id = "00000000-0000-0000-0000-000000000001"` line from both function bodies; both now
  take `tenant_id: str = Depends(_resolve_brand_tenant_id)`.
- `frontend/app/(tenant)/portal/_components/BrandTab.tsx` — GET/POST fetch calls changed from
  `/api/admin/brand-identity` (routes through `requireAdmin()`, 401s any real tenant session with
  no `cis_admin_token`) to `/api/tenant/admin/brand-identity` (routes through the existing tenant
  proxy — `frontend/app/api/tenant/[...path]/route.ts` — which already branches staff vs. tenant
  correctly and attaches `Authorization: Bearer <cis_tenant_token>` for a real tenant session).
  Without this FE change the backend fix would be unreachable by BrandTab.tsx — a tenant session
  would still 401 at the FE proxy layer before ever reaching the fixed backend code.

## Tradeoffs

- Dual-auth on one endpoint is slightly less clean than a single auth model, but the alternative
  (splitting into two endpoints, or migrating the two staff pages to a new admin-only endpoint) is
  a bigger, riskier change than this issue's stated scope — deferred.
