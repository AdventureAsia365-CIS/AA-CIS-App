# AA-362 [N8-2] — 5/6 CloudWatch alarms for N8, Python side (metric emission)

This note covers the AA-CIS-App half only (metric emission). The Terraform half
(alarms) lives in AA-CIS-Infra's own implementation-notes/AA-362.md.

## STEP 0 finding (05/08/2026)

- `services/acp_produce/gates.py`, `models.py`, `reliability.py` read in full: **zero** CloudWatch
  metric emission anywhere in `services/acp_produce/`. `run_gates()` (gates.py) is a pure decision
  loop, `run_produce_slot()` (reliability.py) only writes DB checkpoints (AA-107
  `stage_checkpoint.py`).
- The **only** existing custom-metric emission in this repo: `api/routers/acp_health.py`
  (`_emit_cloudwatch_metrics`, AA-141) — namespace `"acp"` (lowercase, no slash), best-effort
  `boto3.client("cloudwatch").put_metric_data`, try/except-log-and-skip, never raises. Grepped
  the whole repo + AA-CIS-Infra's `modules/monitoring` dashboard for `"ACP/Pipeline"`/`"ACP/Produce"`
  — 0 hits anywhere. Reused `"acp"` rather than inventing a second namespace.
- **`grounding_score` does not exist as a numeric value anywhere in the real code.** The issue text
  assumes a "HARD FLOOR = 1.0" numeric score; the real F1 gate (`gates.py::gate_grounding`) is
  binary pass/fail (`GateResult.passed: bool`, no score field) — same class of "issue/docstring
  promises a shape the code doesn't have" already caught repeatedly in AA-298 (P0-1, P0-2, B14).
  Resolved by mapping F1's `passed` boolean directly to `1.0`/`0.0`: a hard floor of `1.0` then
  means exactly "alarm the instant F1 fails even once," which matches the issue's actual intent for
  that gate without inventing a score that isn't real.
- `held_rate` is not something Python computes: emits two per-piece counts (`piece_passed`,
  `piece_held`); the CloudWatch alarm's own metric math computes the ratio over its evaluation
  window (standard practice, avoids this module needing any cross-piece state).

## Decisions

- New module `services/acp_produce/metrics.py` — `piece_metric_data()` (pure) + `emit_piece_metrics()`
  (boto3 I/O wrapper), same pure/wrapper split as every other `acp_produce`/`acp_planning` module.
- **Not** wired into `gates.py::run_gates()` itself. That function's existing test suite
  (`tests/unit/test_aa298_gates.py`) runs today with zero AWS mocking and treats it as a pure
  repair-budget state machine; adding a boto3 call inside it would force every existing gates test
  to mock boto3 for no benefit. Kept separate, same way `reliability.py`'s checkpoint wrapper is
  kept apart from the gate stack it wraps. Meant to be called once per `Piece`, immediately after
  `run_gates()` returns a terminal (`passed`/`held`) piece, by the not-yet-assembled full N7
  orchestrator (`docs/implementation-notes/AA-298.md`: "chưa lắp ráp thành 1 luồng end-to-end") —
  same "ready building block, no live call site yet" situation as AA-361's `write_usage_log()`.
- Emits exactly once per piece (not per gate, not per repair round, not per atom) — the issue's
  explicit constraint to minimize `PutMetricData` call volume.

## Changed (vs. issue text)

- `grounding_score` reinterpreted from an assumed numeric score to the real gate's binary
  passed/failed, as above — reported rather than fabricated.

## Tradeoffs

- `repair_count` alarm threshold and `held_rate` alarm threshold are unverified placeholders (see
  Terraform-side notes) — no real N7 traffic exists yet to tune them against, same acknowledged gap
  as AA-298's `SWEEPER_SLA_HOURS`.

## Should know

- Bedrock daily-cost alarm and the `week_run` Tuesday-deadline alarm are **not** in this module —
  see the chat report / AA-CIS-Infra implementation notes for why (AA-360 scope overlap risk for
  cost, AA-364 not-yet-built for week_run).
- Tests: `tests/unit/test_aa362_metrics.py` (10 tests) — pure `piece_metric_data()` shape checks +
  `emit_piece_metrics()` with `boto3.client` mocked (no real AWS calls). Full suite: 874 passed.
