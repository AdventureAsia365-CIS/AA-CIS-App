# AA-471 — test-n1-flow missing default brand_rules row

## Decisions
- The tenant informally referred to as "test-n1-flow" in prior session notes does not exist
  as a real slug in `shared.tenants`. Cross-referenced via `acp_shared.angle_gate_request` /
  `audit_log` timestamps (all from 2026-08-24 to 2026-08-26, matching the T7-T11 session
  history) to identify it as `wanderlux-travel` (`a1b2c3d4-0001-4000-8000-000000000001`).
  `exploreasia-co` (`a1b2c3d4-0002-4000-8000-000000000002`) has the identical gap.
- Both are migration-007 seed tenants ("S7 RLS verification"), not real onboarded B2B
  customers — no tenant has ever gone through `create_tenant()` successfully with a working
  brand_rules row until this fix, confirmed via `acp_shared.audit_log` having zero
  `action='agency.onboard'` rows for any of the 3 tenants that exist today.
- Root cause has two independent parts that produce the same symptom (generic
  `AA_BRAND_IDENTITY_PROMPT` fallback):
  1. `wanderlux-travel`/`exploreasia-co`'s `shared.tenant_brand_rules` rows (originally seeded
     by migration 007, real per-tenant content) are gone from the live DB — no migration
     deletes them; most likely a manual test-data cleanup during a prior live-verify session
     that didn't realize it was deleting the tenant's only brand-voice content.
  2. `create_tenant()` (`api/routers/admin.py`) seeded its placeholder brand_rules row with
     `brand_name = body.name` (the tenant's own company name) instead of the literal
     `'default'` sentinel every reader (`fetch_brand_rubric_text()` in
     `services/acp_produce/brand.py`, `_resolve_brand_rule()`'s default branch in
     `admin_pipeline.py`, AA-198's multi-brand convention since migration 044) actually
     queries for. This meant every tenant created through the normal admin flow would also
     fall through to the generic fallback, independent of issue (1).
- Fix scope: restore (1) via a direct data INSERT using migration 007's original seeded
  content (brand_name='default' added, since that column didn't exist when migration 007 was
  written — migration 044 later backfilled all NULL brand_name rows to 'default', so this
  matches the established convention, not new content). Fix (2) via a one-line code change
  in `create_tenant()`. Both fixed in the same PR since they're the same root symptom family
  (AA_BRAND_IDENTITY_PROMPT fallback) even though the causes are independent.

## Changed
- `api/routers/admin.py::create_tenant()` — placeholder `tenant_brand_rules` INSERT now uses
  `brand_name = "default"` instead of `body.name`.
- Data-only: restored `shared.tenant_brand_rules` rows for `wanderlux-travel` and
  `exploreasia-co` (via S3-mediated ECS exec, direct INSERT, not a numbered migration file —
  see Should know).

## Tradeoffs
- Considered changing `fetch_brand_rubric_text()`'s query to filter by `tenant_id` only
  (dropping the `brand_name = 'default'` filter), mirroring the unused
  `TenantConfigService.get_brand_rules()`. Rejected: that would diverge from
  `_resolve_brand_rule()`'s already-established multi-brand convention (AA-198/AA-129,
  migration 044's `UNIQUE(tenant_id, brand_name, version)`), and would behave
  non-deterministically (no `ORDER BY`) if a tenant ever has more than one active brand row.
  The write side (`create_tenant()`) was the actual bug; the read side was already correct.
- Did not delete the dead `TenantConfigService.get_brand_rules()` (`shared/services/
  tenant_config_service.py`) — out of scope for this PR, no live caller confirmed via grep,
  noted for a future cleanup issue if wanted.
