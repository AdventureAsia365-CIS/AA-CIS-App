# AA-485 — Buffer HELD retry (Q5=C origin, AA-331)

Independent of AA-484/AA-499 (no `blockedBy`) — branched fresh from `origin/main` (which
includes AA-498 but not the still-open AA-499/AA-484 PRs), the correct base per this issue's own
dependency graph.

STEP0 was already answered by AA-478's own investigation (cited in this issue's description):
`content_piece.status='held'` is the real T9/T10 equivalent of "N6 held", 0 existing retry
mechanism (confirmed by grep). `allocator.py`'s `reactive_held_empty` is unrelated (a different
concept, same name — confirmed not to touch it).

## Decisions

- **Read AA-331 (the actual Q5=C-confirmed origin decision, "chốt 25/07/2026") directly, not just
  AA-478's summary of it** — AA-331 has real, load-bearing "Done when" criteria this issue's own
  text only partially restates:
  1. *"Slot HELD chạy lại vẫn giữ nguyên lý do treo"* (a re-run keeps/knows the original hold
     reason) — mapped to piece-level as: the buffer retry uses `rewrite_with_feedback()`, seeded
     with the ORIGINAL hold's own final `violations`, not a blind fresh `write_content()` call.
     This is a real, deliberate design choice beyond what this issue's own text explicitly asked
     for (which only said "tự động re-queue để viết lại qua T9") — flagged here as the reasoning,
     not silently assumed.
  2. *"Không lặp vô hạn... số N cần quyết khi build"* — chose **N=1**: exactly one buffer retry
     per request. A repeat hold after the buffer retry itself just stays held — no second buffer
     retry, no counter needed (see mechanism below for why).
  3. `$0 LLM` was N6's OWN allocation-decision constraint (a pure-Python SLOT-assignment choice,
     unrelated to whether the RETRY ITSELF calls an LLM) — does NOT apply here; the buffer retry
     is, by definition, a real T9 write, which always calls the LLM. Not misapplied.
- **"Cơ chế RIÊNG, khác retry trong-luồng" (a genuinely separate mechanism, not just raising
  MAX_ATTEMPTS)** — resolved explicitly: the buffer retry is a SEPARATE, single-attempt session
  (its own new `content_piece` row, own `rewrite_with_feedback()` call, NO in-flow 2-attempt loop
  of its own) that fires as a TRAILING step of `run_write_background()` — same background task
  (AA-466's fire-and-forget architecture), not a new scheduler/cron/Lambda. No new infra needed;
  this stays entirely within the existing async-task model.
- **Eligibility gate 1 — repairable-cause only.** A NON-repairable hold (`F6_cta_present`'s
  missing-CTA case) has an external root cause a rewrite can't fix — the same condition recurs
  immediately, wasting a real LLM call. `repair_log[-1]["repairable"]` (already computed by
  `run_quality_gates()`) is reused directly, no new logic needed to detect this.
- **Eligibility gate 2 — exactly N=1, enforced structurally, not by a counter.** Checks whether
  ANY other `content_piece` row already exists for the same `angle_gate_request_id`. The buffer
  retry's own new row becomes that "other row" — so if IT also holds, a hypothetical second
  buffer-retry-of-a-buffer-retry would see a prior row and stop on its own. No recursion is
  actually built (the retry function doesn't call itself), but the guard would hold even if it
  did — a deliberately simple, hard-to-get-wrong cap.
- **`promises_an_option`-class flag-not-block gates need no special exclusion** (AA-520's own
  update note on this issue, confirmed not just assumed): they never produce `first_failure`,
  never appear in `repair_log` (built only from real blocking failures), so they can never be
  the reason a piece reaches `status='held'` in the first place — nothing to exclude.
- **No UI change** — same scope precedent as AA-484 (a "BUILD" issue about the backend
  mechanism, no UI ask in its own text). A buffer-retry piece that succeeds surfaces through the
  existing `list_pending()`/`GET /pieces/{id}` endpoints once `approved`, same as any other piece.

## Changed

- `services/acp_content_writing/service.py`:
  - `context` (built by `start_write()`) now also carries `route_hub_name`/`route_segment_count`
    — previously used inline at the placeholder INSERT and discarded; the buffer retry's own
    placeholder insert needs the same values again.
  - New `_maybe_buffer_retry_held_piece()` — the 2 eligibility checks, then triggers the retry.
  - New `_run_buffer_retry_attempt()` — the actual single-attempt write (`rewrite_with_feedback()`
    seeded with the original violations → `run_quality_gates()` → `_finalize_piece()`), a
    deliberately separate, smaller function from `run_write_background()`'s own loop (not
    extracted/shared — matches this codebase's own stated preference for per-function
    readability over premature DRY, e.g. `quality_gates.py`'s one-function-per-gate shape).
  - `run_write_background()` calls `_maybe_buffer_retry_held_piece()` as a trailing step, only
    when the just-finalized status is `'held'`.

## Tradeoffs

- Did not build any tenant/admin-facing UI for buffer-retry pieces — matches the issue's own
  backend-only scope; a tenant currently discovers a successful buffer retry the same way they'd
  discover any other approved piece for their request (existing endpoints), and a held-again
  buffer retry looks like any other held piece.
- Did not persist an explicit link from the buffer-retry piece back to the original held piece
  (no new column) — traceability is via structured logs (`t9_buffer_retry_triggered`/
  `_done`, naming both piece ids) and via `created_at` ordering within the same
  `angle_gate_request_id`, not a queryable FK. If a future issue needs to query "which pieces
  were buffer retries" at scale, that's a real, flagged gap, not silently solved here.
- Did not build the N8-side "held_rate > 10% alarm" AA-331 also mentions — N8 (weekly flywheel)
  predates T-series and isn't this issue's own scope (AA-331's own text already flagged this as
  a soft dependency, not a hard blocker).
