# AA-561 — A/B report-sai investigation + Segment lineage + Slate clarity + 06-08 lineage rebuild

## Decisions

- **Mục 1a/1b (sticky header + Star selected) — NOT re-fixed, because they are not currently
  broken.** Real evidence, gathered before touching any code (per the issue's own instruction to
  investigate before fixing):
  - Real Playwright run against `https://aa-cis.lumiguides.it.com/admin/atom-curation` (real
    `e2e-test-admin` login, real scroll — confirmed via `scrollTop` actually moving 0→2000 on the
    real scroll container, not just an unchanged bounding box) shows: title "Social Content" +
    description + stat bar all stay visible after scroll (mục A), and 3 checked checkboxes DO
    produce a visible "Star selected (3)" button (mục B). See
    `tests/e2e/results/aa561/A-before.png`, `A-after.png`, `B-selected.png`, `B-with-button.png`.
  - Vercel deployment history (`get_deployment`/`list_deployments`, project
    `prj_glZmOvskbPdMg20mbI9ywEI9S5tr`) shows the AA-557 fix (commit `d86c1f8`, PR #338) went
    `READY` on production at **15:59:45 UTC**, a full **33 minutes before** AA-561 itself was
    filed (16:33:20 UTC) — the fix was already live well before Nghiệp's screenshots were taken.
  - Conclusion: AA-557's own report was correct for A/B on the code that actually shipped.
    Nghiệp's screenshots most likely came from a browser tab that was already open (and had
    already loaded the pre-fix JS bundle into memory) before the 15:59:45 UTC deploy went live —
    a plain scroll/click in an already-open SPA tab does not re-fetch JS just because the server
    has a newer build. This is a stale-tab artifact, not a caching-header issue (the page's own
    `cache-control: public, max-age=0, must-revalidate` header rules out the browser serving a
    stale HTML shell on a fresh navigation). No code change was made for 1a/1b — a rewrite of
    already-correct code would be exactly the kind of fabricated "fix" this issue is about
    stopping. **This finding is disputable — if a hard-refreshed reproduction still shows the bug,
    treat this note as wrong and re-open.**

- **Mục 1d (Segment multi-tour) — investigated per STEP0, all 4 required steps done:**
  1. Read `docs/AI-gent-for automation works/aa-soscial-media-main/src/aa_social/segments.py`
     (Ms. Thư's origin) — `derive_segments(atoms: list[Atom])` takes whatever atom pool the
     caller passes it; nothing in the pure grouping function itself is tour- or tenant-scoped.
  2. Read the ported `services/acp_contract/segment_matching.py` — its own module docstring
     states AA-545 (06/09/2026) **removed** `tenant_id` from `_mint()`/`derive_segments()`,
     restoring the exact origin formula `sha256(place|verb)` alone, specifically so that "2
     tours/tenants describing the same real-world moment collide onto one id" (its own words).
  3. Queried the real DB (`atom_segment_member ⋈ tour_atoms`, `GROUP BY segment_id HAVING
     count(DISTINCT tour_id) > 1`): **0 of 23 real Segments currently span >1 tour** — but this
     is a fact about the current small (7-tour, non-overlapping) catalog, not a code limitation.
     Confirmed no `tenant_id` column exists at all on `atom_segment`/`atom_ranking`/`route`/`hub`
     (migration 146 fully applied).
  4. `api/routers/admin_dashboard.py`'s own `list_segments()` docstring already states "a Segment
     can span multiple tours" and its query already returns one row per (Segment, Tour, Market) —
     the backend was already built correctly for this; only the frontend's grouped-card rendering
     needed to change.
  - **Important correction to the issue's own premise**: AA-561 cites ADR-0001/0003 as if the
    "should Segment be per-tenant or platform-wide" question were still open. It is not —
    **CONTEXT.md's own top banner (added AA-551, 07/09/2026, one day before this issue was filed)
    already states AA-545 shipped the platform-wide redesign**; the "tech debt, not fixed" wording
    that ADR-0001/0003 and CONTEXT.md's own Language/Ownership-table sections still carry is
    explicitly flagged by that same banner as **stale**, not current design guidance. This
    investigation is about a different, narrower question the docs don't already answer — does a
    Segment span multiple *tours* in practice — which required the code+DB reads above.
  - **UI decision, per the issue's own stated criteria**: Segment/Route-Hub cells are
    row-span-merged (1 Segment = 1 merged block), but **Tour is its own per-row column, never
    merged** — because the design (confirmed above) allows a Segment to span multiple tours, even
    though no real row does yet. Merging Tour into the Segment cell today would look identical to
    not merging it (7 tours, 0 overlap) but would silently misrepresent the data model the moment
    a second tour joins an existing Segment.

## Changed

- `frontend/app/admin/atom-curation/page.tsx`
  - `SegmentSection`: replaced the "one `<div>`+mini-table per Segment, header repeated 23×"
    layout with a single `<table>`, one `<thead>`, Segment/Route-Hub cells `rowSpan`-merged, Tour
    a plain per-row column (see Decisions above for why).
  - `SlateSection`/`SlateExplainerNote`: replaced the one-line technical note with a plain-language
    intro card (what Slate is, all 4 states, both Kind values) always visible above the table, not
    hover-only. "Kind" column values changed from raw `Segment`/`Route` to `One place (Segment)`/
    `Whole journey (Route)` with an explanatory tooltip.
- `api/routers/admin_a4.py::get_content_log` — the lineage rebuild (PHẦN 3a):
  - Added `subject → atom_segment`/`route` LEFT JOINs so a Piece's source (Segment place+action,
    or Route hub+day-range) is now in the response; pieces with no `subject_id` (the pre-existing
    atom-picker path, AA-449, never retired — confirmed 2/12 real pieces today) get an explicit
    `{"kind": "direct_atom"}` instead of a blank/broken cell.
  - Replaced the old `angle`/single-object field (only ever the CHOSEN angle, via a
    `COALESCE(ago, ago_chosen)` that discarded the other 2) with `angles`: all 3
    `angle_gate_option` rows per request, each carrying its own `chosen`/`recommended` flags.
  - **Real bug fixed**: the old `tour_atoms` join condition was
    `ta.owner_scope = cp.tenant_id::text` — this stopped matching anything the moment AA-526 made
    atoms platform-wide (`owner_scope='platform'`), silently NULLing `atom_text`/etc for every
    piece written after that migration. Verified live against real DB: **before this fix, 0/12
    real pieces would have gotten atom detail; after, 12/12 do.**
  - Added `is_buffer_retry` (derived from sibling `content_piece` row count + `created_at` order,
    since migration 115 deliberately has no `previous_piece_id` column) and `sibling_piece_count`.
  - Live-verified against real RDS data via the S3-mediated ECS exec pattern before deploying:
    12 real rows, 2/12 correctly flagged `direct_atom`, 12/12 now resolve atom text, 12/12 now
    return the full 2-3-angle list instead of 1.
- `frontend/app/admin/_components/auditPanels.tsx`
  - `ContentLogRow` gained `goal`/`angles`/`source`/`is_buffer_retry`/`sibling_piece_count`;
    added `sourceLabel()` helper shared by Write/Gate and Review.
  - `WriteGateSection` rebuilt around a new `PieceLineageCard`: always-visible one-line lineage
    (`Tour → Source → Goal`), click-to-expand full detail (all angles with the chosen one marked,
    retry note, full gate ledger, publish status) — answers Nghiệp's own spec verbatim from data
    already fetched in one request, no second per-piece fetch.
  - `ReviewSection` gained `Source`/`Goal`/`Retry` columns so cross-tab lineage doesn't require
    flipping to Write/Gate to see where a Piece came from.
- `tests/unit/test_aa469_viec5_a4_feedback_loop.py` — updated `_full_row()` fixture for the new
  columns, replaced the old single-`angle` assertion with the new `angles` list, added 4 new tests
  (`direct_atom` source, `route` source, `is_buffer_retry`, and the `owner_scope` join fix).

## Tradeoffs

- Kept the existing 3-tab shell (`/admin/tenant-activity` → Write/Gate, Review, Publish) instead
  of collapsing into one page, per the issue's own "Claude Code đề xuất, Nghiệp duyệt qua ảnh"
  option — a full page merge is a bigger, riskier UI change than the actual ask (full lineage per
  Piece); the 3 tabs now read off the SAME enriched endpoint and cross-reference (Review shows
  Source/Goal/Retry, Write/Gate shows the full expand), which satisfies "dữ liệu liên kết chặt"
  without a page-structure rewrite. Open for Nghiệp to redirect after seeing the screenshots.
- `PublishSection` (mục 08) was left unchanged beyond its existing `CrossLinkNote` — it reads a
  genuinely different table (`publish_log`, not `content_piece`) and adding the same lineage join
  there would duplicate most of `content-log`'s own query for a page whose job is specifically
  "what got published, where, and did it error," which it already shows.
- Did not rehash/backfill the 2 pieces with no `subject_id`, and did not touch the atom-picker
  entry point itself (AA-449) — out of this issue's scope, which is UI/lineage display, not the
  underlying write path.
