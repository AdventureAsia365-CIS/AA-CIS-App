# AA-579 — GET /v1/tours (bare) + POST /v1/exports return empty for every real tenant

## Decisions

- Deleted both routes outright (Hướng A, confirmed by Nghiệp) rather than fixing the JOIN to go
  through `tenant_tour_versions` (Hướng B) — CloudWatch showed zero real tenant traffic, and the
  real functionality is already covered by `GET /v1/tours/pool` + `GET /v1/tours/my-versions`.
- Deleted `api/routers/v1_exports.py` as a whole file (not just the one function) — it contained
  exactly one route (`POST /v1/exports`), confirmed via full-file read before deleting.
- Left `GET /v1/tours/{tour_id}` (`get_tour()`, still has the identical `WHERE id=$1 AND
  tenant_id=$2` bug) untouched — out of AA-579's explicitly named scope (only the bare list route
  and the exports route were named), flagged for a future issue if it needs the same treatment.
- Did NOT touch the separate `(internal)/catalog` 401 bug found during this investigation
  (staff-proxy auth mismatch, unrelated root cause) — tracked in the same Linear thread, pending
  Nghiệp's decision on fix-vs-abandon after the audit_log/CloudWatch usage check.

## Changed

- `api/routers/v1_tours.py` — removed `list_tours()` (`@router.get("")`), replaced with a comment
  pointing to AA-579 for anyone tempted to re-add it.
- `api/routers/v1_exports.py` — deleted entirely.
- `api/main.py` — removed the `v1_exports` import + `include_router` call.

## Tradeoffs

- Considered keeping the routes but fixing the JOIN (Hướng B) — rejected: no evidence of product
  need for "browse tenant's own published_tours rows directly" or "bulk export all tours" as
  separate features from what `/pool`/`/my-versions` already provide; would have been speculative
  work for a feature nobody uses today.

## Should know

- **Root cause is architectural, not a typo**: both routes were written correctly for a
  now-abandoned architecture generation (S8/S9, 21/04/2026, real per-tenant RLS rows on
  `published_tours`) that a newer model (Pool/Rewrite, 05/05/2026, `tenant_tour_versions`)
  replaced just 2 weeks later in the same file — full commit-by-commit trail in the AA-579 Linear
  comments.
- CloudWatch evidence (`/ecs/aa-cis-dev`, 14-day retention, uvicorn access log lines): 12 total
  hits on the 2 bare paths over 14 days — 3 were this investigation's own live-verify calls
  (10/09/2026), the other 9 were all `401 Unauthorized` (no valid Bearer JWT ever reached this
  route) — i.e., real tenant traffic was 0/14 days, not just "low."
- Those 9 401s are NOT unrelated noise — they're the same signal that led to discovering the
  separate `(internal)/catalog` staff-proxy auth bug (see Linear AA-579 comments) — that page
  calls this same bare route and gets 401 before ever reaching the now-deleted logic. Deleting
  this route changes that page's failure from 401 to 404 — no behavior change for its real users
  either way (frontend doesn't check `res.ok`, silently shows an empty table regardless).
