## Việc 2 — built this session

1. **Quarter/month plan history (view)** — new tenant-facing routes in `api/routers/
   v1_planning.py`:
   - `GET /v1/planning/quarter-plan/history?year=&quarter=` — every saved version for that
     tenant/quarter (new `fetch_quarter_plan_version_history()` in `services/acp_planning/
     quarter.py`, newest-first). Returns an empty list, not 404, for a quarter with no saved
     versions — a real, valid history-view answer, distinct from `GET /quarter-plan`'s 404 for
     "no current plan".
   - `GET /v1/planning/quarter-plan/versions/{version_id}` — wires the pre-existing
     `fetch_quarter_plan_version()` (built for AA-323's admin Preview screen, confirmed by STEP0
     to have never been imported into this tenant router before) into a tenant-facing read, with
     an ownership check (cross-tenant `version_id` 404s identically to a nonexistent one — never
     leaks existence).
   - Frontend: `HistorySection` in `PlanningTab.tsx` — collapsed by default, lists versions
     (version_no/status/approved_by/date), click a version to see its snapshot (trip count,
     forced-specials count, destination shares) inline.

2. **"Edit after finalize" — Decision, flagged explicitly (not silently picked)**: this session
   generalizes the pre-existing `specials`/`excluded_trip_ids` override-replay mechanism
   (`QuarterPlanRequest` already accepted both; only `PlanningTab.tsx`'s own hardcoded `[]` was
   wiring them away) rather than inventing a new primitive — a tenant can now type force-include
   trip names and check per-trip "Exclude" boxes in the Trips table, then re-Preview/Finalize.
   Re-finalizing always creates a new `quarter_plan_version` (never overwrites, migration 092's
   own design) — the History section above is what makes that trail browsable.
   **Explicitly NOT built**: re-picking a different atom for an already-written slot (the
   slot/atom-level "edit"). Per the STEP0-refresh finding above, this is blocked on AA-494
   Decision 3's still-unbuilt status-transition wiring and its own flagged schema question
   (`content_piece`'s UNIQUE constraint) — building against that schema now would risk the exact
   kind of guess-and-rework AA-494's own design doc warns against. Left as a clearly-scoped
   follow-up, not silently dropped.

## Việc 4 — built this session

**DFS/PAA → angle generation (Item 2 of the suggested order)** — the confirmed, contained gap.
- New `SearchDemandSignal` dataclass + `fetch_search_demand_signal(tour_id, pool)` in
  `services/acp_shared/dfs_relevance.py` — a single-tour variant of the existing
  `fetch_dfs_relevance_by_tour()` (which only ever returns the 3-bucket relevance value, not the
  raw PAA/related-keyword text T8's prompt needs). Reads `people_also_ask`/`related_keywords`
  (migration 069/AA-218, plain JSONB string arrays) alongside the existing `keyword_ideas`
  relevance scoring from the same `silver_aa_internal.seo_context` row.
- `services/acp_angle_gate/service.py::set_goal_and_generate()` — fetches this signal (only when
  the request has a `trip_id`, same guard as the existing `trip_name`/`destination` resolution)
  and passes it through to `generate_angles()`.
- `services/acp_angle_gate/generate.py`/`prompts.py` — new optional 6th prompt block ("SEARCH
  DEMAND SIGNAL"), added to the existing 5-block structure (seed/trip/goal/channel/brand) per the
  brief's own suggested shape. Omitted entirely (not rendered empty) when there's no seo_context
  row, or when the row has neither PAA questions nor related keywords — a request with no real
  signal produces byte-identical prompts to before this change. `SYSTEM_PROMPT` gained one
  paragraph instructing the model to treat this block as search-behavior evidence, never as a
  new source of facts about the trip (mirrors the seed's existing no-fabrication instruction).

### Decisions
- Built as a genuinely new function (`fetch_search_demand_signal`), not a widened
  `fetch_dfs_relevance_by_tour()` — T8 always resolves exactly one tour per request, so a bulk
  by-list shape (T7's own convention) would be a wasted round trip for N=1; kept each function's
  contract matched to its one real caller.
- Kept in `services/acp_shared/dfs_relevance.py` rather than a new module — same file already
  owns "real search-demand data for a tour" as a concept, just previously only for T7's scoring
  need.

### Not built (open design questions) — Việc 4 items 3-4

Per the brief's own instruction not to plow into a half-designed build for these two:

**(d) Blog multi-atom input.** Confirmed still a single-`atom_id` mechanism end to end
(`angle_gate_request`/`content_piece`, `create_request()`, `_fetch_atom_text()`). Open questions
that need a decision before any schema/code is written:
- Does a multi-atom blog request need a NEW request shape (e.g. `atom_ids: list[str]` on
  `angle_gate_request`, with `atom_id` staying single-value for the other 7 channels), or does
  every channel move to a list-of-one/list-of-many shape for consistency?
- If multi-atom, how does T9's single `_fetch_atom_text(tenant_id, atom_id, pool)` become
  `_fetch_atom_texts(tenant_id, atom_ids, pool)` — and does the atom-availability rule (AA-494,
  currently keyed on one `atom_id` per `content_piece`) need to lock N atoms per piece instead of
  one?
- How does the tenant actually pick multiple atoms in T8's UI — `SlotPickerPanel.tsx`'s
  atom-picker (AA-494) is single-select by design; multi-select needs its own UX pass, not an
  assumed checkbox-list retrofit.

**(e) T8-T11 flow/UI unification.** Confirmed still a linear, one-way wizard (T8-T10) with T11
fully separate. Open questions:
- Does "back-navigation" mean literally stepping back within the existing state machine
  (`pending_goal → pending_choice → approved`) while preserving prior choices, or a different UI
  pattern (e.g. a persistent stepper the tenant can jump between, backed by re-fetching the
  request's current state rather than local-only state)?
- Folding T11 into the same flow/component as T8-T10 is a bigger scope change than adding a
  "Back" button — worth deciding whether T11 stays a separate page reachable via a clear
  hand-off link (smaller change) vs. becoming one continuous component (larger rewrite,
  echoing the T8+T9+T10 merge AA-450 already did).
- Both of the above should probably be designed together with Việc 2's still-open slot/atom-level
  "edit" question and AA-494 Decision 3's reuse-write UX (also still unbuilt) — the same
  `AngleGateTab.tsx` component is the likely site of all three changes, and designing them one at
  a time risks the kind of rework AA-494's own design doc explicitly built its ordering to avoid.
