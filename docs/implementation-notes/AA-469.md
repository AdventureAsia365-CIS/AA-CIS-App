# AA-469 — Việc 1: split T4/T5 into independent triggers

STEP0-refresh confirmed `docs/claude_audit/AA-469-viec1-step0-t4-t5-split-investigation.md` still
matches current code exactly (`api/routers/v1_tours.py:trigger_rewrite()` /
`_do_rewrite_and_save()`, `services/acp_produce/tenant_pipeline.py::run_t5_atomize()`) — nothing
else touched T2-T5 since that audit.

## Decisions

- **"Already atomized" is DERIVED, no migration.** Followed the `admin_atoms.py` precedent
  (`GET /admin/atoms/summary`'s own `MAX(created_at)`/`COUNT(*)` subquery, ~line 271 of that
  file) rather than adding a column to `tenant_tour_versions`. Reasoning: (1) the source of
  truth (`acp_contract.tour_atoms`) already has everything needed — a column would just be a
  cache of this same query, one more place to keep in sync; (2) this codebase already has an
  established pattern for exactly this derivation, at the platform (`owner_scope='platform'`)
  scope — `_ATOMIZED_SUBQUERY` (new, `v1_tours.py`) is the same subquery re-scoped to a specific
  tenant's `owner_scope`; (3) zero migration risk for a tenant-facing UI badge that isn't on any
  hot path. Tradeoff accepted: one more JOIN on `/my-versions` and `/versions/{id}` per request —
  negligible at current tenant/atom volumes, and the admin equivalent already runs this same
  shape of query.
- **Atomize allowlist, not blocklist**: `POST /versions/{id}/atomize` only accepts
  `ai_generated` / `needs_review` / `approved`. Explicit allowlist chosen over "block
  pending+rejected" so a future new status added to the state machine doesn't silently become
  atomizable by default.
- **`qa_auto_passed=true` is NOT blocked from atomizing.** STEP0 flagged this as the one real
  open product question. Left it as the tenant's own call (button still shows, no warning
  copy) rather than gating on it — Việc 1's ask was to separate the TRIGGER, not to add new
  judgment about WHEN atomizing a QA-auto-passed tour is a good idea; that's a product-copy
  decision for Nghiệp, not an engineering default to bake in silently.
- **Idempotency inherited, not reimplemented.** `run_t5_atomize()` already keys its skip check
  off `(tour_id, owner_scope)`'s latest `source_hash` (unchanged by this Việc). The new endpoint
  does nothing extra for a repeat call — a second call on unchanged content returns
  `{"status": "skipped", "atom_count": 0}` straight from that existing mechanism. A second call
  after the tenant requests a genuinely new version (different `rewritten_content` → different
  hash) legitimately re-atomizes, exactly as it always would have.
- **Defense-in-depth status guard**: beyond the `ttv.status` allowlist, the endpoint also checks
  the rewritten_content JSON's own inner `"status"` field equals `"done"`. Needed because
  `trigger_rewrite()`'s except-block can leave `ttv.status='needs_review'` while
  `rewritten_content` is still the INITIAL placeholder (inner `status="generating"`, written
  before T2 ever ran) — without this, that edge case would pass the outer allowlist and try to
  atomize empty/placeholder content.

## Changed

- `api/routers/v1_tours.py::trigger_rewrite()` — removed the unconditional `run_t5_atomize()`
  call at the end of `_do_rewrite_and_save()` (AA-436's bug: ran on a real QA pass AND a
  QA-auto-pass alike, no gate). T4's UPDATE is now the real stopping point of this background
  chain; `escalate_t3_failure()` (A4/review_queue path) is untouched, still fires on QA failure.
- New `POST /v1/tours/versions/{version_id}/atomize` (`v1_tours.py::atomize_version()`) — the
  standalone trigger. Reconstructs `rewritten`/`tour_id`/`country` from just `version_id` +
  tenant (the adapter STEP0 flagged as needed, since nothing previously re-read those values
  back out of `tenant_tour_versions`), then calls the unchanged `run_t5_atomize()`.
- `GET /v1/tours/my-versions` and `GET /v1/tours/versions/{id}` now also return
  `atomized_at`/`atom_count` per version, via the new `_ATOMIZED_SUBQUERY` LEFT JOIN.
- Frontend `CatalogTab.tsx` (My Catalog): the header's "View atoms →" link is no longer
  unconditional — it now only shows once `atomized_at` is set. Before that, an "Atomize" button
  shows instead (only for `ATOMIZABLE_STATUSES`), calling the new endpoint and refreshing the
  list on success. Added inline error display for a failed atomize call.

## Tradeoffs

- Left `run_t5_atomize()` itself completely untouched (per scope — "confirm it's still
  parameter-pure" was the ask, not refactor it) even though Việc 5's future job (persisting T5
  errors, currently CloudWatch-only) will need to touch this same function. Didn't pre-build
  that — per the cross-Việc note in `docs/claude_tasks/AA-469-redesign-t-series.md`, only made
  sure this pass's new call site (the endpoint) doesn't make that later change any harder: the
  endpoint already surfaces `result.get("error")` as the HTTP 502 detail on failure, so Việc 5
  adding a persisted-error column later is a change to `run_t5_atomize()`'s return path, not a
  second call site to update.
- No new admin/tenant "atomize history" view — `atomized_at`/`atom_count` are surfaced only
  where the button already lives (My Catalog). A fuller history (e.g. re-atomize log, per-attempt
  audit trail) was out of scope for this Việc.

## Decisions

- **Step structure: 1 Atom+Channel · 2 Goal · 3 Angle · 4 Write — a flat Stepper, not T7's 4-level
  drill-down.** T7's Year▸Quarter▸Month▸Week hierarchy exists because each level is a genuine
  container of the next (a quarter contains months). T8/T9's steps are sequential stages of ONE
  request, not nested containers — forcing T7's exact drill-down shape onto a linear flow would
  misrepresent the data model. Kept T7's visual language (chevron-separated breadcrumb, active
  crumb bold, done crumbs dim + checkmarked) since that's the actual "same interaction style" ask,
  without forcing its specific 4-level nesting.
- **Only the "3 Angle" crumb is ever clickable, and only from step 4 — flagged explicitly, not
  guessed.** `reopen_request()` (AA-497) is the ONLY backend endpoint that supports moving
  backward without discarding history (`approved → reusable`, no new LLM call). Steps 1→2
  (`create_request()`) and 2→3 (`set_goal_and_generate()`) are still one-way — there is no
  "un-submit a goal" or "un-create a request" endpoint, and building one was explicitly out of
  scope ("Don't touch backend logic beyond what's needed... existing endpoints"). Making those
  crumbs clickable would imply a capability that doesn't exist. "Start over" (full reset) remains
  the only way back past step 3.
- **Pick-then-confirm for angle selection (new).** Previously, clicking an angle card's "Choose
  this angle" button submitted immediately. Redesigned to match `SlotPickerPanel.tsx`'s atom-pick
  + separate "Start writing" button: clicking a card only highlights it (local `pendingAngleIdx`
  state, gold 2px border + checkmark); a separate "Confirm this angle" button (disabled until a
  card is picked) actually calls `choose()`. This was the one place the old UI genuinely violated
  the brief's "no silent auto-navigation on selection, a separate action button to advance" rule —
  angle choice is the real T8 gate (ADR-2026-038 §0.2), worth the same care as T7's atom pick.
- **"Change angle" (AA-497) is now first-class, not bolted-on, via TWO entry points that call the
  same `changeAngle()`**: the Stepper's clickable "3 Angle" crumb, and a "Change angle" button
  inline on step 4's own meta row (right next to the angle/goal/channel summary it affects).
  Both existed as candidate designs; shipped both rather than picking one, since they serve
  different habits (breadcrumb-driven vs. read-the-result-then-decide) and cost nothing extra —
  same function, same guard (`req.status === 'approved'`, hidden while `writing`).
- **The step-3 angle-choice CARD now renders ONLY while actively choosing (`pending_choice`/
  `reusable`), never once `approved`.** The old code re-rendered the full 3-angle detail block
  AND the write/result card simultaneously once approved — redundant, and inconsistent with T7's
  own pattern of collapsing a decided level rather than re-showing it in full (see
  `SlotPickerPanel.tsx`'s breadcrumb collapsing Year/Quarter/Month once a week is picked). Step 4
  now shows a compact one-line summary (`Angle: … · Goal: … · Channel: …`) instead.
- **"Start over" consolidated from 3 per-card buttons to 1, next to the Stepper — plus a
  confirm-before-wipe guard.** It's a full reset (atom/channel/goal/angle all discarded), strictly
  more destructive than "Change angle" (angle only), so it needed to look and behave more
  cautiously now that a lighter-weight option exists. Added `window.confirm(...)` before wiping,
  skipped when there's nothing to lose yet (`!req`). Not scoped down to a partial reset (e.g.
  "only reset from the current step backward") — a partial reset would need to selectively
  re-open state the backend can't currently unwind (steps 1-2 have no reopen equivalent, per the
  Stepper decision above), so a full reset stays the only well-defined "go back past step 3"
  action; flagged rather than guessed at a partial-reset design.
- **Loading/error states preserved verbatim, not regressed**: the 202+poll cycle (AA-466), the
  180s poll-ceiling "Check status" recovery, the 422 CTA-prompt fallback, and the `failed`-piece
  Retry button are all unchanged in behavior — only their visual container moved (now under the
  step 4 meta row instead of a bare card top).
- **Found, flagged, NOT fixed: resuming directly into an `approved` request with no `content_piece`
  yet is a dead end** (Write card renders with no CTA prompt, no spinner, no result — only "Start
  over"/"Change angle" do anything). Hit this by accident during live-verify test-script cleanup,
  not via any real product path: `SlotPickerPanel.tsx`'s only real `resume_request_id` handoff
  navigates AFTER a successful `.../reopen` call, which always lands on `reusable`, never bare
  `approved` — so this exact state is not reachable through any shipped navigation today, only via
  a hand-typed/bookmarked URL or a resume mid-way through an interrupted write. A fix exists (auto-
  fire `writeContent()` when `status==='approved' ∧ !piece ∧ !writing ∧ !needsCtaInput`) but was
  deliberately NOT added: it would mean a bare page load/reload can silently trigger a real LLM
  call and create a new `content_piece`, including a genuine risk of a duplicate piece if a
  tenant reloads a page that already has a real completed result they just haven't seen re-fetched
  (T8's `GET /requests/{id}` does not return prior `content_piece` rows, so a resumed load can't
  even tell the difference). That's a real product/cost decision, not a redesign-scope call to
  make silently.

# AA-469 Việc 4, PASS 2 (same session) — flow-order fix: Channel moves to AFTER Angle

**Corrects the section immediately above.** Mid-session, Nghiệp confirmed the pass-1 build's
premise was wrong: it assumed the existing `[atom+channel] -> goal -> angle -> write` order was
already correct and only needed a UI facelift. The real, confirmed order is:

**`[atom, DFS/PAA, brand]` (server-side) -> pick Goal -> generate 3 angles -> pick 1 angle (the
other 2 stay available via AA-497's reopen) -> pick Channel -> T9 write -> T10 -> T11.**

Channel moves from step 1 (alongside atom, and an INPUT to angle generation) to a brand new step
8, strictly after angle choice. This is a real behavior/schema/API change, not a visual reorg.

## (1) Confirmed OLD order, before touching anything

Verified directly against code (not assumed): `services/acp_angle_gate/service.py::
create_request(tenant_id, atom_id, channel, pool, year=None, month=None)` required `channel` as a
mandatory positional param; `set_goal_and_generate()` passed `channel=req["channel"]` straight
into `generate_angles()`, which used it (`get_channel_style(channel)`) to inject a full CHANNEL
block (structure/style/avoid) into the angle-generation LLM prompt itself
(`services/acp_angle_gate/prompts.py::build_user_prompt()`). `acp_shared.angle_gate_request.
channel` was `NOT NULL` (migration 113). This matches pass 1's own (correct, at the time)
STEP0 finding — it just didn't question whether that order itself was right.

## (2) What changed to reach the corrected order

**Confirmed first, not assumed**: `services/acp_content_writing/prompts.py::build_user_prompt()`
(T9's OWN write-time prompt, untouched by this fix) already includes the FULL `channel_style`
block independently, at write time, regardless of what angle generation does. So removing channel
from angle generation loses no real channel-fit in the final written piece — channel guidance was
always being re-applied in full at write time anyway; this only removes an early, now-redundant
channel-conditioning pass over the angle's own `best_final_style` field.

- **`services/acp_angle_gate/generate.py`/`prompts.py`** — `channel`/`channel_style` removed
  entirely from `generate_angles()`/`build_user_prompt()`. The CHANNEL block is gone from the
  angle-gen prompt; `best_final_style`'s field description reworded to describe the angle's own
  narrative style in general terms, not "how to write it for the given channel" (channel isn't
  known yet at this step anymore).
- **`services/acp_angle_gate/service.py::create_request(tenant_id, atom_id, pool)`** — `channel`/
  `year`/`month` params all removed. Inserts `channel=NULL, cta=NULL`. The AA-451 slot-CTA
  prefill (`_fetch_slot_cta()`/`_compute_and_persist_slot_cta()`) moved out of here entirely (see
  next bullet) — it's genuinely keyed by channel, which isn't known at creation anymore.
- **New `services/acp_angle_gate/service.py::set_channel(tenant_id, request_id, channel, pool,
  year=None, month=None)`** — the new step 8. Valid only from `status='approved'` (an angle must

### A real bug this reorder would have introduced, found and fixed in the same pass

Once `set_channel()` allows changing `angle_gate_request.channel` MORE THAN ONCE while a request
stays `'approved'` (pick a channel, change your mind before writing), `agr.channel` is no longer a
stable per-piece value the way it was when channel was fixed once at creation. Two real call sites
were still reading `agr.channel` as if it were immutable-per-piece, which would have silently
mis-attributed an OLD piece's channel to whatever the request's channel was LATER changed to for
its NEXT write:
- `services/acp_planning/tenant_pool.py::_USED_ATOMS_QUERY` (T7 slot-view's "already written"
  display) — switched to `cp.channel` (content_piece, populated per the bullet above), same
  denormalization reasoning AA-497 already established for `angle_gate_option_id` on this exact
  table.
- `api/routers/v1_publish.py::list_pending()`/`publish()` (T11) — both switched to
  `COALESCE(cp.channel, agr.channel)`, `cp.channel` first, `agr.channel` only as a fallback for
  pre-this-session rows. `publish()`'s blog-only gate (`piece["channel"] != _BLOG_CHANNEL`) would
  otherwise have been checking the WRONG (possibly-since-changed) channel value.
0 real `content_piece` rows existed at the time of this fix (confirmed live) — no backfill needed,
every row from here on is written under the new code path.

## (3) AA-497's reopen mechanism, reconciled with channel-after-angle

**Decided, not guessed**: reopening (`reopen_request()`, `approved -> reusable`) does **not**
reset or re-ask channel. Channel has no dependency on which specific angle was picked — the write
prompt applies the channel's style block independently of the angle's own `best_final_style` (see

reopen cycle, since channel carries over; false on a first-time choice, where the UI advances to
the new Channel step instead, and `submitChannel()` is what eventually fires the write).

**Explicitly NOT built**: a symmetric "Change channel" action. `set_channel()`'s own design
(callable repeatedly while `'approved'`) makes one technically trivial to add later — no backend
work needed — but it wasn't part of this task's ask, so it wasn't built; flagged here rather than
silently expanded into.
