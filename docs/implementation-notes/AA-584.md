# AA-584 — My Catalog Tours (t4-pool) panel too narrow vs Browse Tours (t1-rewrite)

## STEP0 finding

Two separate components, not one shared component with divergent wrappers:
- `/portal/t1-rewrite` → `PoolTab.tsx` — detail panel is an **inline grid column**
  (`gridTemplateColumns: "minmax(0,36%) minmax(0,64%)"`, `frontend/app/(tenant)/portal/_components/PoolTab.tsx:121`),
  sticky-positioned, scales with the page's content width (no hard cap).
- `/portal/t4-pool` → `CatalogTab.tsx` — detail panel is a **fixed-width right-side
  overlay drawer** (`position: "fixed", ... width: 700, maxWidth: "92vw"`,
  `frontend/app/(tenant)/portal/_components/CatalogTab.tsx:581-585`). Architecturally a
  different UI paradigm (dimmed backdrop, close button, inline edit/save — CatalogTab's
  panel supports editing the tenant's rewritten copy; PoolTab's is read-only), not a
  copy-paste drift of the same component.

At common desktop widths the fixed 700px drawer reads narrower than PoolTab's 64%
column once the browser window is wider than ~1090px (700 / 0.64 ≈ 1094px) — on a
1440px+ screen (the kind Nghiệp's screenshots were taken at) PoolTab's panel scales up
to ~750-900px while CatalogTab stays pinned at 700px, producing the visible gap.

## Changed

`CatalogTab.tsx`'s drawer `width` changed from a fixed `700` to
`clamp(700px, 62vw, 1100px)` (`maxWidth: "92vw"` kept unchanged for mobile/narrow
windows, where it already governed). Nothing else touched — no change to the drawer's
overlay/backdrop/edit mechanics, no change to PoolTab.

## Decisions

- **Kept the drawer paradigm, did not convert to an inline grid column.** CatalogTab's
  panel is a real overlay drawer with editing affordances (Save/Cancel, per-field Edit
  buttons) that PoolTab's read-only panel doesn't have — restructuring it into an inline
  2-column grid like PoolTab would be a much larger, riskier change for a "too narrow to
  read" complaint that a width-only fix fully resolves. Issue text explicitly allows this
  ("không cần pixel-identical nếu có lý do UX khác nhau").
- **`clamp()` over a bigger fixed px value.** A plain `width: 1000` would fix wide
  screens but not scale down proportionally on mid-size laptops, and would need a
  separate media query to avoid regressing narrow windows. `clamp(700px, 62vw, 1100px)`
  keeps the exact old floor (700px — unchanged behavior below ~1129px viewport width)
  and old `maxWidth: 92vw` mobile behavior intact, only growing on screens where the gap
  vs t1-rewrite was actually visible.
- **62vw, not 64vw (PoolTab's exact fraction).** PoolTab's 64% applies to the *content
  area* (viewport minus sidebar minus page padding), not the raw viewport — matching
  PoolTab's literal 64vw would overshoot on screens with a narrower effective content
  area. 62vw of the raw viewport lands close to PoolTab's real rendered width without
  copying its layout math exactly (see Live-verify below: 872px vs PoolTab's 750px at
  1440px viewport — slightly wider, not narrower, which resolves the complaint).

## Tradeoffs

- The fixed drawer now reads *slightly wider* than t1-rewrite's reference panel at
  1440px (872px vs ~750px) rather than pixel-matching it. Accepted per the issue's own
  "doesn't need to be pixel-identical" allowance — erring wide is safer than erring
  narrow for the stated problem (hard to read a long itinerary).
- 1100px cap means on very wide monitors (2560px+) the two panels' proportions diverge
  further (PoolTab keeps scaling, CatalogTab caps). Judged acceptable — an unbounded
  drawer width on an ultrawide monitor would produce an unreadably long line length,
  which is its own readability problem the cap is deliberately avoiding.
