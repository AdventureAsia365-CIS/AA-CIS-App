## STEP0 findings (full detail in the audit file)

1. **Slate never computes a score** — Ms. Thư's own `slate.py` reads `atom_scores` (the origin's
   equivalent of `atom_ranking`) verbatim, never recomputes. `subject.score` = a straight copy of
   `acp_contract.atom_ranking.total_rank` (Segment) — confirms the build prompt's own suspicion
   that a separate `segment_score` table/module would duplicate AA-515. Not built.
2. **Route Score has no origin answer at all** — the origin has NO Route-Subject concept
   (Subject is always Segment-grain there; Route only contributes `hub` grouping and an optional
   `walk` field). Blog-as-Route-Subject is AA-CIS's own extension, already built and live-verified
   in AA-510 (`acp_contract.route.score` = mean of member Segments' `total_rank`, rounded) — reused
   as-is, not reinvented.
3. **Bar thresholds are literal, not binary** — `reference/channels.toml`'s real numbers: Blog
   `needs_demand=1000, needs_questions=3`; LinkedIn/Facebook/Instagram/TikTok `needs_said=150`;
   Email/Landing Page/Ads (`on_demand=true`) have no threshold at all in the origin — and the
   origin never proposes a Subject list for them either (`derive_posting_rhythm()` explicitly
   skips `on_demand` Channels). Bar reads `acp_contract.atom_ranking.demand_volume`/`questions`/
   `said` directly (already-computed AA-515 output), NOT `silver_aa_internal.seo_context` — a
   correction to the build prompt's own Bar section (STEP0 point 3a).
4. **A second, unanticipated table collision found and resolved**: `acp_contract.subject`
   (AA-510, migration 131 — a one-time Route-pick snapshot) already existed and would have
   collided with this build's `acp_shared.subject` (a Slate proposal, entirely different grain/
   purpose). Reported before building (STEP0 point 3b); Nghiệp's decision (Option C): renamed
   AA-510's table to `acp_contract.route_pick` everywhere (migration 132) rather than extend it
   or let two same-named tables coexist. See "Renamed (AA-510, pre-existing)" below.

## Decisions

1. **`acp_shared.subject` schema built exactly as the prompt specified** (migration 133) — the
   XOR `segment_id`/`route_id` check, the 4-state machine, `cleared_bar_reason jsonb NOT NULL`
   (populated for both a cleared AND a failed check — "an exclusion is arguable rather than a
   silent absence", the origin's own philosophy for transit/unnamed-place, applied here to a
   failed Bar too). Two partial unique indexes added beyond the prompt's literal SQL —
   `(tenant_id, channel, segment_id)`/`(tenant_id, channel, route_id)`, each `WHERE ... IS NOT
   NULL` — needed for `propose_slate()`'s idempotent upsert (a re-run must refresh a still-
   `proposed` row rather than duplicate it, and must never touch a `picked`/`used`/`cut` one).
2. **`angle_gate_request.subject_id`** (new nullable column, migration 133) traces a T8 request
   back to the Slate pick that created it. The pre-existing atom-picker entry point (AA-449's
   `create_request()`, still used by `SlotPickerPanel.tsx`'s "Start writing" and any future
   direct-atom flow) is untouched — it creates a request with `subject_id = NULL`, exactly as
   before.
3. **`channel` is set on `angle_gate_request` immediately at pick time**, not through AA-469
   Việc 4's two-step atom-then-channel flow — the Slate already knows the channel (it's a column
   on `subject`). `AngleGateTab.tsx`'s own `currentStep()` (`if (req.status === "approved" &&
   !req.channel) return 4`) already treats a pre-set channel as "already known, skip the picker"
   — the exact same behavior the AA-497 "Change angle" reopen path relies on — so this needed
   zero frontend changes to accommodate.
4. **Representative-atom resolution for `pick_subject()`** (`_resolve_representative_atom()`):
   T8/T9's whole pipeline is atom-grain, not Segment/Route-grain. A Segment subject resolves to
   the lexicographically-first live member atom; a Route/Blog subject resolves to the first live
   atom of the Route's FIRST ordered Segment, in the Route's own `tour_id`. **Disclosed
   simplification, not silently absorbed**: T9's writer therefore sees only that one atom's text
   for a Blog piece, not the whole journey `route.ordered_segment_ids` describes — flagged in
   `pick_subject()`'s own docstring for whoever next extends T9 to read a Route's full walk (the
   same class of "wired but not yet fully consumed" gap AA-515's own `said_rank` note carries).
5. **Blog's Route-grain Bar aggregates across member Segments** (a choice this build discloses,
   since the origin never bars a Route at all): `demand` = MAX across member Segments (mirrors
   `_demand()`'s own "the strongest rather than the sum" philosophy, one level up); `questions` =
   SUM across member Segments (the FAQ pool a Blog piece draws from is genuinely the union of
   every moment's questions along the walk — matches how the origin's own `_asked()` already pools
   questions across every `atom_id` a Subject carries). Live-verified numerically correct
   (MAX(18100,50)=18100, SUM(28,1)=29).
6. **`choose()`'s "one place per Channel" de-dup and `most_per_hub` hub-cap were NOT ported.**
   The build prompt's own scope for this build is Bar + Score only ("đọc atom_segment/route theo
   tenant, join atom_ranking lấy Score, áp Bar theo Channel, ghi cleared_bar_reason") — de-dup
   requires a Hub join for every one of the 7 non-Blog (Segment-grain) Channels, which nothing in
   this build's scope asked for. `most_per_hub` is "effectively off" (99) for every Channel in
   the origin anyway, so this mainly costs the de-dup rule: a Channel's list can currently show
   the same place twice via two different Segments/actions. Disclosed, not silently dropped —
   worth a follow-up once a real Hub-per-Segment join has a consumer to justify building it.
7. **`GET /v1/slate`/`POST /v1/subjects/{id}/pick` live in `api/routers/v1_planning.py`** (per
   the build prompt's own instruction), but under a SEPARATE `APIRouter(prefix="/v1")`
   (`slate_router`) rather than the file's existing `/v1/planning` prefix — needed so the paths
   match the prompt's own literal spec exactly. Every existing endpoint in that file (quarter-
   plan, slot-grid, slot-suggestions, metrics, trip-reallocation) is completely untouched.
8. **Frontend**: `SlotPickerPanel.tsx` is NOT deleted — `PlanningTab.tsx` now renders the new
   `SlateTab.tsx` in its place (one import + one JSX line changed). `SlateTab.tsx` hands off to
   T8 via `?resume_request_id=` (the SAME mechanism AA-497's "Change angle" reopen already uses),
   not `?atom_id=` — because `pick_subject()` already creates the `angle_gate_request` server-side
   before the frontend ever navigates.

## Gap A + Gap B fix (2026-09-02, post-Done follow-up)

Nghiệp flagged 2 gaps he self-identified before agreeing to Done, plus a separate FE design audit

### Gap A — a Blog/Route pick was collapsing the whole Route to one representative atom

**Decision.** `pick_subject()` (`services/acp_shared/slate.py`) already resolved a Route pick down
to one representative atom for `angle_gate_request.atom_id`/`trip_id` — kept AS-IS (every other
T8 reader, e.g. the goal/angle steps, is atom-grain and untouched). ADDED a new nullable column,
`angle_gate_request.route_segment_ids` (migration 134), populated ONLY for a Route/Blog pick with
the Route's full `ordered_segment_ids` (read live from `acp_contract.route` at pick time, exactly
as asked). `_resolve_representative_atom()` now returns a 3-tuple — the third element is `None`
for a Segment pick, the full segment array for a Route pick — one query, no extra round trip.

T9's `start_write()` (`services/acp_content_writing/service.py`) is the consumer: when
`route_segment_ids` is present, a new `_fetch_route_text()` resolves EVERY Segment's live
representative atom (same per-Segment query `_resolve_representative_atom()` already used for its
own single-atom case, just run once per Segment instead of only the first) and joins their `text`
in the Route's own day order — that joined string becomes `content_seed` in place of the single
atom's text. Nothing else in T9's pipeline changes: `write_content()`/`rewrite_with_feedback()`/
`run_quality_gates()` all take `atom_text` as an opaque string already, so no prompt/gate code
needed to change.

**Tradeoff, disclosed.** `_fetch_route_text()` is best-effort per Segment (same precedent
`route_detection.py::create_route_pick()`'s own docstring already sets — "a partial/empty join
degrades the snapshot's detail but never fails") — a Segment rebuilt away since pick time is
silently skipped, not fatal; only a Route with EVERY Segment gone raises (nothing left to write
from). `atom_id`/`trip_id` still carry only the first Segment's atom, kept for backward
compatibility with every other atom-grain reader — this is additive, not a grain migration.

### Gap B — `choose()`'s place de-dup + `most_per_hub` hub-cap, ported

**Decision.** Read the origin's real `choose()` (`docs/AI-gent-for automation works/
aa-soscial-media-main/src/aa_social/stages/slate.py`) and `reference/channels.toml` again, per
Nghiệp's explicit instruction not to invent a threshold. Confirmed: `most_per_hub = 99` is the
origin's own literal number, identical across all 5 weekly-rhythm Channels (Blog/LinkedIn/
Facebook/Instagram/TikTok), "effectively off" per the origin's OWN docstring — kept as 99, not
re-tuned. The origin has NO number at all for the 3 on-demand Channels (Email/Landing Page/Ads —
`derive_posting_rhythm()` skips them, `choose()` never runs for them there) — `None` (uncapped) is
this build's own honest choice rather than inventing a number with no precedent. Iteration order
is strongest-first (ascending score/rank-sum), ties resolved first-come in that order — the origin
has no "prefer newest" rule anywhere in `choose()`, so none was added here either. Applied PER
CHANNEL (fresh `taken`/`seen_places` every call), never globally — matches `recommend()`'s own
per-slot invocation.

New `_choose(channel, candidates, hub_of)` in `slate.py` is the ported mechanism; `propose_slate()`
now calls it (instead of a raw per-candidate Bar loop) so only what BOTH clears the Bar AND
survives de-dup/hub-cap gets `INSERT`ed as `proposed` — exactly what `_store()` does in the origin
(only `choose()`'s returned list is stored, not everything that merely cleared the Bar).

**Grain differences, disclosed (the origin has no Route concept to answer these from — AA-CIS's
own extension, same STEP0 Q2 gap the original AA-511 pass already flagged elsewhere):**
- **Place de-dup applies to Segment candidates only** — a Route already spans several places, so
  there is no single `place` to de-dup on at Route grain (`Candidate.place` is `None` for a Route).
- **Hub-cap applies to both.** A Route candidate uses its own Route's hub (`hub_id`, falling back
  to its own `route_id` when standalone — "a family of one is not a family", the identical rule
  `route_detection.py` already applies one layer up). A Segment candidate needed a NEW join —
  `_fetch_segment_hub_map()` — since a Segment has no hub column of its own; it resolves to
  whichever containing Route's hub most of the Segment's Routes belong to (ties broken by hub
  name), one grain down from the origin's own "the hub most of its trips are in" rule. This is
  the exact join the original AA-511 pass's own module docstring said it was NOT building
  ("requires a Hub/Route join for every one of the 7 non-Blog channels... nothing in this build's
  scope asked for") — built now, on request.

**Tradeoff, disclosed.** `most_per_hub=99` is real but, per the origin's own words, "effectively
off" — a live scenario that naturally hits it needs ~100 Routes/Segments in one Hub, which no
real tenant's catalogue has yet. Live-verified anyway by temporarily setting the cap to 1 for the
verify run (see below) rather than only trusting the unit tests — the plumbing is proven at a
real, triggerable threshold, not just at the untriggerable real one.

## FE audit fix (2026-09-02) — all 6 findings closed except #4 (explicitly skipped)

Nghiệp's own review of the earlier FE audit report asked for 5 of the 6 findings fixed outright
(#4 — "3 on-demand tabs vs 5 weekly, no UI distinction beyond in-panel copy" — explicitly marked
"không cần sửa, bỏ qua", so left as-is, on purpose, not an oversight).

### Decisions

1. **#1 (skeleton) — per-tab shaped, not per-tab fetched.** `GET /v1/slate` still loads all 8
   Channels in one call (unchanged) — there is no per-Channel fetch to show a "this one tab's own
   loading" state for. What changed: the full-panel centered `LoadingScreen` spinner (which hid
   the tab strip's own counts and looked the same regardless of which tab was active) is replaced
   by `SkeletonPanel` — 3 `SubjectRow`-shaped shimmer placeholders rendered in the SAME slot the
   real content occupies, while the tab strip stays visible and clickable throughout (unchanged
   from before). Shimmer keyframes reuse the exact pattern already established in `admin/
   pipeline/s2-s4/page.tsx`'s own `Skeleton` component — not a new convention.
2. **#2 (the important one) — `pick()`'s success/error branches now do genuinely different
   things.** Before: `onPicked()` (refresh the whole Slate) ran unconditionally in BOTH branches
   — a real network failure (including a client-side timeout after the backend had already
   written the pick) refreshed the Slate anyway, which could show this exact row's stale
   `pickError` text sitting next to a `state: 'picked'` badge that had just appeared underneath
   it. Now: `onPicked()` and `setPickError(null)` run ONLY inside the `.then()` of a confirmed
   `r.ok` response. The `.catch()` branch (any 4xx/5xx, or a real browser-level network failure)
   sets `pickError` and stops — it never touches the Slate's own data, so the row keeps showing
   its last KNOWN state (still `proposed`, "Chọn viết" still there) next to the error, never a
   state the tenant never asked for. Added a small manual "Refresh" link inside the error box
   itself (calls the same `onPicked()`) so the tenant has an explicit, deliberate way to check
   whether the pick actually went through server-side — never automatic.
3. **#3 (empty vs. no-longer-eligible) — a real 3-way branch, not 2.** `channel.subjects.length
   === 0` (never had ANY Subject, any state) keeps the original "Nothing here yet" +
   atomize-a-tour guidance. NEW: `proposed.length === 0` (but `decided.length > 0`) now shows its
   own `EmptyState` — "Không còn Subject mới đủ điều kiện lúc này — xem lại các Subject đã quyết
   định bên dưới, hoặc rewrite/atomize thêm tour để có đề xuất mới" (Nghiệp's own wording, used
   verbatim) — immediately above the (now always-rendered-when-non-empty) "Already decided"
   list, factored into a small shared `DecidedList` component to avoid duplicating that block
   across the 2 render branches that now need it.
4. **#4 — explicitly skipped**, per Nghiệp's own instruction. No code change.
5. **#5 (on-demand vs. weekly, visually) — a thin divider + a group icon**, not just a text
   difference once a tab is opened. Each `CHANNEL_TABS` entry now carries a `group: "weekly" |
   "on_demand"` field; a 1px vertical divider (`aria-hidden`) renders between the last weekly tab
   (TikTok) and the first on-demand one (Email), and every tab button gets a small `Calendar`
   (weekly) or `Zap` (on-demand) icon (`lucide-react`, already a dependency) ahead of its label,
   plus a `title` tooltip ("Nhịp tuần" / "Theo yêu cầu (on-demand)").
6. **#6 (mobile) — `flexWrap: "wrap"` → `overflowX: "auto"` + `flexWrap: "nowrap"`**, scrollbar
   hidden cross-browser (`scrollbar-width: none` + `-ms-overflow-style: none` +
   `::-webkit-scrollbar{display:none}`, scoped to a `.aa511-slate-tabstrip` class via a plain
   `<style>` tag — the same inline-`<style>`-tag convention `CatalogTab.tsx` already uses in this
