## STEP0 findings (full detail in the audit file)

1. **Slate never computes a score** — Ms. Thư's own `slate.py` reads `atom_scores` (the origin's
   equivalent of `atom_ranking`) verbatim, never recomputes. `subject.score` = a straight copy of
   `acp_contract.atom_ranking.total_rank` (Segment) — confirms the build prompt's own suspicion
   that a separate `segment_score` table/module would duplicate AA-515. Not built.
2. **Route Score has no origin answer at all** — the origin has NO Route-Subject concept
   (Subject is always Segment-grain there; Route only contributes `hub` grouping and an optional
   `walk` field). Blog-as-Route-Subject is AA-CIS's own extension, already built and live-verified
   in AA-510 (`acp_contract.route.score` = mean of member Segments' `total_rank`, rounded) — reused
   as-is, not reinvented.
3. **Bar thresholds are literal, not binary** — `reference/channels.toml`'s real numbers: Blog
   `needs_demand=1000, needs_questions=3`; LinkedIn/Facebook/Instagram/TikTok `needs_said=150`;
   Email/Landing Page/Ads (`on_demand=true`) have no threshold at all in the origin — and the
   origin never proposes a Subject list for them either (`derive_posting_rhythm()` explicitly
   skips `on_demand` Channels). Bar reads `acp_contract.atom_ranking.demand_volume`/`questions`/
   `said` directly (already-computed AA-515 output), NOT `silver_aa_internal.seo_context` — a
   correction to the build prompt's own Bar section (STEP0 point 3a).
4. **A second, unanticipated table collision found and resolved**: `acp_contract.subject`
   (AA-510, migration 131 — a one-time Route-pick snapshot) already existed and would have
   collided with this build's `acp_shared.subject` (a Slate proposal, entirely different grain/
   purpose). Reported before building (STEP0 point 3b); Nghiệp's decision (Option C): renamed
   AA-510's table to `acp_contract.route_pick` everywhere (migration 132) rather than extend it
   or let two same-named tables coexist. See "Renamed (AA-510, pre-existing)" below.

## Decisions

1. **`acp_shared.subject` schema built exactly as the prompt specified** (migration 133) — the
   XOR `segment_id`/`route_id` check, the 4-state machine, `cleared_bar_reason jsonb NOT NULL`
   (populated for both a cleared AND a failed check — "an exclusion is arguable rather than a
   silent absence", the origin's own philosophy for transit/unnamed-place, applied here to a
   failed Bar too). Two partial unique indexes added beyond the prompt's literal SQL —
   `(tenant_id, channel, segment_id)`/`(tenant_id, channel, route_id)`, each `WHERE ... IS NOT
   NULL` — needed for `propose_slate()`'s idempotent upsert (a re-run must refresh a still-
   `proposed` row rather than duplicate it, and must never touch a `picked`/`used`/`cut` one).
2. **`angle_gate_request.subject_id`** (new nullable column, migration 133) traces a T8 request
   back to the Slate pick that created it. The pre-existing atom-picker entry point (AA-449's
   `create_request()`, still used by `SlotPickerPanel.tsx`'s "Start writing" and any future
   direct-atom flow) is untouched — it creates a request with `subject_id = NULL`, exactly as
   before.
3. **`channel` is set on `angle_gate_request` immediately at pick time**, not through AA-469
   Việc 4's two-step atom-then-channel flow — the Slate already knows the channel (it's a column
   on `subject`). `AngleGateTab.tsx`'s own `currentStep()` (`if (req.status === "approved" &&
   !req.channel) return 4`) already treats a pre-set channel as "already known, skip the picker"
   — the exact same behavior the AA-497 "Change angle" reopen path relies on — so this needed
   zero frontend changes to accommodate.
4. **Representative-atom resolution for `pick_subject()`** (`_resolve_representative_atom()`):
   T8/T9's whole pipeline is atom-grain, not Segment/Route-grain. A Segment subject resolves to
   the lexicographically-first live member atom; a Route/Blog subject resolves to the first live
   atom of the Route's FIRST ordered Segment, in the Route's own `tour_id`. **Disclosed
   simplification, not silently absorbed**: T9's writer therefore sees only that one atom's text
   for a Blog piece, not the whole journey `route.ordered_segment_ids` describes — flagged in
   `pick_subject()`'s own docstring for whoever next extends T9 to read a Route's full walk (the
   same class of "wired but not yet fully consumed" gap AA-515's own `said_rank` note carries).
5. **Blog's Route-grain Bar aggregates across member Segments** (a choice this build discloses,
   since the origin never bars a Route at all): `demand` = MAX across member Segments (mirrors
   `_demand()`'s own "the strongest rather than the sum" philosophy, one level up); `questions` =
   SUM across member Segments (the FAQ pool a Blog piece draws from is genuinely the union of
   every moment's questions along the walk — matches how the origin's own `_asked()` already pools
   questions across every `atom_id` a Subject carries). Live-verified numerically correct
   (MAX(18100,50)=18100, SUM(28,1)=29).
6. **`choose()`'s "one place per Channel" de-dup and `most_per_hub` hub-cap were NOT ported.**
   The build prompt's own scope for this build is Bar + Score only ("đọc atom_segment/route theo
   tenant, join atom_ranking lấy Score, áp Bar theo Channel, ghi cleared_bar_reason") — de-dup
   requires a Hub join for every one of the 7 non-Blog (Segment-grain) Channels, which nothing in
   this build's scope asked for. `most_per_hub` is "effectively off" (99) for every Channel in
   the origin anyway, so this mainly costs the de-dup rule: a Channel's list can currently show
   the same place twice via two different Segments/actions. Disclosed, not silently dropped —
   worth a follow-up once a real Hub-per-Segment join has a consumer to justify building it.
7. **`GET /v1/slate`/`POST /v1/subjects/{id}/pick` live in `api/routers/v1_planning.py`** (per
   the build prompt's own instruction), but under a SEPARATE `APIRouter(prefix="/v1")`
   (`slate_router`) rather than the file's existing `/v1/planning` prefix — needed so the paths
   match the prompt's own literal spec exactly. Every existing endpoint in that file (quarter-
   plan, slot-grid, slot-suggestions, metrics, trip-reallocation) is completely untouched.
8. **Frontend**: `SlotPickerPanel.tsx` is NOT deleted — `PlanningTab.tsx` now renders the new
   `SlateTab.tsx` in its place (one import + one JSX line changed). `SlateTab.tsx` hands off to
   T8 via `?resume_request_id=` (the SAME mechanism AA-497's "Change angle" reopen already uses),
   not `?atom_id=` — because `pick_subject()` already creates the `angle_gate_request` server-side
   before the frontend ever navigates.

## Tradeoffs

- Choose()'s hub-cap/one-place-per-Channel de-dup not ported (Decision 6) — disclosed gap.
- Blog/Route pick's representative-atom resolution loses the full-journey context for T9's
  writer (Decision 4) — disclosed, flagged for a future T9 extension.
- `SlateTab.tsx`'s `useEffect(() => { load(); }, [load])` triggers the same
  `react-hooks/set-state-in-effect` ESLint warning already present, unfixed, in
  `MarketplaceTab.tsx`/`PublishPendingList.tsx` (pre-existing repo pattern, not enforced by CI —
  no workflow runs `eslint`/`next lint`) — kept consistent with the existing pattern rather than
  deviating alone in one new file.
- On-demand Channels (Email/Landing Page/Ads) having a Slate list at all is an AA-CIS-specific
  extension beyond the origin (STEP0 Q3) — the origin never proposes Subjects for them, they are
  written ad hoc. Implemented as "run the same Bar at its default-zero threshold", per the build
  prompt's own explicit ask for 3 on-demand tabs.
