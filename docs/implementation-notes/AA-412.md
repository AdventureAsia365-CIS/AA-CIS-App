# AA-412 — Gate C per-piece review + N7 run history view

Task: `docs/claude_tasks/AA-412-01-gate-c-piece-detail-history-view.md`. Linear AA-412 (full
audit already done there — `frontend/app/admin/produce/page.tsx`, `api/routers/admin_produce.py`
confirmed to have no per-piece content route at all, not just a missing link). Read first, not
re-investigated here.

## Decisions

- **D1 — per-piece approval needs a new column; there is no existing per-piece approval state.**
  `acp_deliver.pieces.status` (migration 094) is the GATE outcome (`in_progress`/`passed`/`held`),
  not a human review decision — confirmed by reading `gates.py::run_gates()` (only `run_gates()`
  writes `status`) and `packets.py::assemble_packet()` (only assigns already-`'passed'` pieces to
  a packet). There was never a column recording "a human looked at this piece and said yes/no".
  Added migration 105: `review_status` (`pending`/`approved`/`rejected`, default `pending`),
  `reviewed_by`, `reviewed_at`, `review_note` on `acp_deliver.pieces`. Additive only, matches the
  style of migration 102 (repair_log/repair_budget columns added the same way).
- **D2 — ramp mechanism (`trust_ramp.confirm_ramp_transition()`) left untouched, per the task's
  explicit fallback instruction.** `confirm_ramp_transition()` still operates on `packet_id` only
  and is not modified. Instead, `POST /packets/{id}/gate-c/approve` now REFUSES to call it (409)
  for `mode != 'propose_only'` unless every piece currently assigned to that packet has
  `review_status='approved'`. This is exactly the task's stated safe fallback: "packet chỉ chuyển
  ramp khi 100% piece đã approve riêng lẻ, KHÔNG đổi ramp mechanism." No change to `RAMP`, to
  `packet_has_bofu_piece()`, or to the F6/BOFU guards in `trust_ramp.py`/`packets.py`.
- **D3 — rejected pieces are NOT auto-removed from the packet.** A `rejected` piece permanently
  blocks that packet's ramp transition past `propose_only` under D2's rule — there is no "drop
  this piece from the packet and proceed with the rest" flow in this task. Flagging this as a
  real trade-off for Nghiep: today a single rejected piece stalls the whole weekly packet. Fixing
  that (splitting a packet, or re-running just the rejected piece) is a bigger design question
  (does a new packet get created? does N7 re-run just that slot?) that's out of AA-412's scope —
  documented in the PR description for an explicit decision, not decided here.
- **D4 — `GET /run/{id}` extended in place, not a new endpoint**, per the task's own "hoặc mở
  rộng GET /run/{id} đã có" option — adds `gate_ledger`, `brand_seo_audit`, `review_status` to
  the existing pieces array. Cheaper than a new endpoint and the history drill-down UI already
  needs exactly the same run-detail shape the live-run view uses.
- **D5 — `GET /produce/runs` returns tenant_id only, not a resolved tenant name.** The frontend
  already loads the full tenant list via `/api/admin/tenants` for the trigger form; the History
  tab reuses that same in-memory map instead of adding a cross-schema join (`acp_v2_runs.tenant_id`
  is TEXT, `shared.tenants.tenant_id` is UUID — a join needs an explicit cast, and no existing
  route in this file does that join today either, see `get_produce_run()`).
- **D6 — gate_ledger aggregation for `/produce/runs` reads `gate_ledger` as one entry per gate,
  not deduped/last-wins.** Confirmed via `gates.py::run_gates()`: `piece.gate_ledger = []` is
  reset at the top of every repair-loop round, so the persisted ledger is always the FINAL round's
  full gate-stack result — one `GateResult` per gate name, never a same-gate history. The
  `docs/claude_audit/AA-404-n7-run6-results.md` report's "final-state fail counts" framing is
  simply what `gate_ledger` already contains as-is; no extra last-per-gate logic needed.

## Changed

- New migration `105_acp_deliver_pieces_review.sql`.
- `services/acp_produce/packets.py`: added `set_piece_review_status()` and
  `packet_pieces_review_complete()` (used by the approve endpoint's new gate).
- `api/routers/admin_produce.py`: `GET /packets/{packet_id}/pieces` (new),
  `POST /pieces/{piece_id}/review` (new), `GET /produce/runs` (new), `GET /run/{run_id}` extended,
  `POST /packets/{id}/gate-c/approve` gated on D2/D3 above.
- `frontend/app/admin/produce/`: new `PieceReviewModal.tsx` + `HistoryTab.tsx`, `page.tsx` wires
  both in (packet row gets a "Review Pieces" action instead of a bare Approve button; a tab bar
  switches between the live-run view and History).

## Tradeoffs

See D3 above (rejected piece blocks the whole packet, no split/re-run flow) — the one open
question flagged for Nghiep per the task's own instruction to stop and describe rather than
decide silently.

## Should know

- `acp_deliver.pieces.status` (gate outcome) and the new `review_status` (human decision) are
  two independent state machines on the same row — don't conflate them when reading the diff.
- The Gate C approve endpoint's new 409 case is additive: `mode='propose_only'` still always
  succeeds (matches a packet's own default state, nothing to gate).
