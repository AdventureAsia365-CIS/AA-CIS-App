# AA-355 — S1-from-atom now reads itinerary_day (was inert since AA-352)

Found while scoping the AA-353 before/after measurement (S132, 01/08/2026): diffing
`b1f0b90..HEAD` to isolate what to re-run showed `services/content_generation/s1_from_atom.py`
completely unchanged across AA-352+AA-353. Reading it confirmed `fetch_curated_atoms()` never
`SELECT`s `itinerary_day` and `_build_atom_pack()` never surfaces it to the model — AA-352 (Câu 1
AA-350, first half) populated the column at decompose time, but S1-from-atom (the consumer) never
read it. Second half of Câu 1 AA-350, done here.

## Decisions
- Grouping strategy: atoms with a non-null `itinerary_day` are grouped under ascending `DAY N:`
  headers in the atom pack; atoms with `itinerary_day IS NULL` (pre-migration-093 atoms never
  re-decomposed, or ones the extractor couldn't place) go in a separate `UNDATED` section appended
  after all DAY groups — never silently dropped, never assigned an invented day. A tour with zero
  dated atoms produces only the UNDATED section, which is byte-for-byte the old flat/narrative
  atom pack shape (verified by test — `test_build_atom_pack_all_undated_reproduces_flat_pre_aa355_shape`).
- Day-count instruction in `build_user_prompt()` is derived from the DAY groups actually present in
  *this tour's* atom pack (`len(day_numbers)`, `min`/`max`), not from any external "source day
  count" — the model has no way to independently verify a source-side number, so the only
  obligation given is internal consistency with what it was shown in the pack.
- `fetch_curated_atoms()`'s `ORDER BY` changed to `itinerary_day NULLS LAST, created_at` so the
  fetched atom order already matches pack-building order (dated atoms ascending, undated after) —
  `_build_atom_pack` doesn't depend on this ordering (it groups by day itself) but keeping row
  order consistent with pack order made this easier to reason about while writing it.

## Changed
- `services/content_generation/s1_from_atom.py`:
  - `_row_to_atom()` — carries `itinerary_day` through (defaults `None` via `.get()`, safe against
    pre-AA-355 row shapes with no such key at all).
  - `fetch_curated_atoms()` — `SELECT`s `itinerary_day`, `ORDER BY itinerary_day NULLS LAST, created_at`.
  - `_build_atom_pack()` — groups into `DAY N:` sections + trailing `UNDATED` section instead of one
    flat list.
  - `build_user_prompt()` — new `DAY STRUCTURE:` instruction block, derived from the atom pack's own
    day groups (see Decisions).
- `tests/unit/test_aa306_s1_from_atom.py` — 9 new tests: `fetch_curated_atoms` query shape,
  `_row_to_atom` itinerary_day passthrough (present + absent-key case), `_build_atom_pack` day
  grouping (ascending headers, multiple atoms sharing a day, undated atoms excluded from DAY
  blocks, all-undated fallback matches old flat shape), and `build_user_prompt`'s day-count
  instruction (dated case + undated fallback case).

## Tradeoffs
- Did not touch any gate/validation logic — confirmed via `grep -n "day" api/routers/v1_s1_from_atom.py`
  that no day-count gate exists anywhere in the router; AA-339's "0/30 tour survived" day-count
  axis was the *bake-off harness's own* post-hoc measurement, not an enforced code gate. Scope per
  AA-355 is strictly read-and-use `itinerary_day` in this one file — a future day-count gate (if
  wanted) is a separate issue, not folded in here.
- Did not backfill/force-redecompose any atoms as part of this PR — the 30-tour AA-353 measurement
  fixture's atoms were already fixed (soft-delete + re-decompose) in the paused before/after task;
  this PR only makes the code able to use `itinerary_day` when present.
