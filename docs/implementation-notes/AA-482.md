# AA-482 — Landing page engine (ADR-2026-030, D5: AA hosts the white-label tour page)

## Decisions
Real architecture decisions made in this build, per the issue's own explicit "quyết định
kiến trúc/UX thật sự chưa rõ" flag. `AskUserQuestion` was checked and is NOT available in this
background session (no interactive UI to answer it) — per this chain's own general operating
mode ("pick the conservative default and flag it, not stop to ask" — AA-489's own precedent
this session), picked considered defaults and flagged them clearly here + in the Linear
comment, rather than blocking the whole issue indefinitely on an unreachable confirmation.

- **Hosting: Next.js route in the EXISTING `AA-CIS-App` frontend** (`frontend/app/trip/
  [tourId]/page.tsx`), not new S3+CloudFront infra. Reuses the already-live Vercel deploy
  pipeline (atomic deploy + instant rollback, per this repo's own `CLAUDE.md`) — zero new
  infra/Terraform/domain/cert work for a v1.
- **Domain: existing `aa-cis.lumiguides.it.com`, path-based** (`/trip/{tour_id}`) — no new
  domain provisioning.
- **Content source: `gold_aa_internal.published_tours`' `aa_*` fields directly**
  (`aa_name`/`aa_subtitle`/`aa_summary`/`aa_itineraries`/`aa_highlights`/`seo_title`/
  `seo_meta`) — exactly the field set ADR-2026-030's own `v_trip_registry` view already
  selects for this purpose. NOT T9's `landing_page`-channel AIDA copy (`content_piece`) — that
  copy is generated per weekly slot/campaign, not 1:1 with a canonical tour, and reusing it
  would need new "pick the canonical piece" logic with no clear v1 benefit. The issue's own
  "Ghi chú thiết kế mở" explicitly named this as a new decision to make when building, not a
  pre-decided one — made here.
- **Scope: aa_internal's admin-canonical published tours only** (the shared catalog) — matches
  `v_trip_registry`'s own real, current JOIN shape exactly (it doesn't disambiguate multiple
  tenants' pages for the same `tour_id` today either — see STEP0 below). Real per-TENANT
  rewritten versions (`gold_aa_internal.tenant_tour_versions`) are NOT wired into this page —
  flagged as a real, separate follow-up.
- **Liveness check: direct DB re-check, not HTTP self-ping.** Since AA now hosts the page
  itself (D5), "is this page alive" reduces to "does the underlying tour still qualify" — a
  cheap, reliable DB query, not an HTTP round-trip against our own domain. Implemented two
  ways: (1) self-healing on every real page render (`GET /v1/trip/{tour_id}` stamps
  `url_alive`/`last_checked_at` on each hit), (2) an admin-triggered batch
  `POST /admin/trip-pages/recheck` sweep for the cases nobody happens to visit.

## STEP0 (real, this session — every item from the issue's own checklist)
- **`acp_deliver.tenant_tour_pages` DOES exist live** (migration 078, confirmed via
  `information_schema.tables`) — **87 rows**, NOT the "0 rows" the issue's own description
  (citing AA-478, 06/08) expected.
- **Real, critical finding the issue's own description could not have known**: sampled the 87
  rows — every single one has `url = "https://aa-cis.lumiguides.it.com/"` (the admin
  frontend's own root URL, not a real per-tour page) and the SAME `published_at` timestamp to
  the microsecond across every sampled row — a one-time bulk placeholder seed, not real pages.
  **0 real, working landing pages existed before this build**, despite the table looking
  "87/87 populated."
- **Code write-path: re-confirmed 0 real callers** (grepped `INSERT INTO
  acp_deliver.tenant_tour_pages` / `UPDATE ... tenant_tour_pages` across `api/` + `services/`
  — 0 hits) — AA-478's "0 writers" finding still holds today, only the "0 rows" half was
  stale.
- **Gate F6 reads this table for real, not mocked** — `services/acp_produce/gates.py` +
  `pipeline.py` genuinely `SELECT url_alive FROM acp_deliver.tenant_tour_pages WHERE
  tenant_id = $1 AND tour_id = $2::uuid`, fail-closed (no row = not alive) — confirmed by
  reading the real query, not assumed.
- **Real, pre-existing bug found in `v_trip_registry`'s own JOIN** (not introduced or fixed
  here, flagging only): `LEFT JOIN acp_deliver.tenant_tour_pages ttp ON ttp.tour_id =
  rt.tour_id` — no `tenant_id` in the join condition, even though `tenant_tour_pages`' own PK
  is `(tenant_id, tour_id)`. If 2 different tenants ever each published their own page for the
  same underlying `tour_id`, this view would return 2 rows or ambiguously match one — a real
  gap in the view's own multi-tenant correctness, separate from this issue's own scope.

## Changed
- `api/routers/v1_trip_page.py` (new) — `GET /v1/trip/{tour_id}` (public, no auth, the real
  page-data endpoint + self-healing liveness stamp), `POST /admin/trip-pages/{tour_id}/publish`
  (the real write path this table never had), `POST /admin/trip-pages/recheck` (batch
  liveness sweep).
- `api/main.py` — registers both new routers.
- `frontend/app/trip/[tourId]/page.tsx` (new) — public Next.js server component, fetches
  directly from the backend (no proxy route needed, no secret to protect for public data),
  renders name/subtitle/summary/highlights/itinerary + a `mailto:admin@adventureasia.com`
  "Design This Journey" CTA (the brand's mandated CTA phrase, `services/content_generation/
  brand_standards.py`). No price shown — ADR-2026-030 §8.4's own deterministic-missing-field
  policy ("không bao giờ đoán giá") — this v1 has no real price source wired in, so it's
  omitted, not fabricated.
- `frontend/middleware.ts` — untouched deliberately: `/trip/:path*` is correctly NOT in
  `config.matcher`, so the new route passes through with no auth gate, exactly right for a
  genuinely public page.
- `tests/unit/test_aa482_trip_page.py` — 5 new tests.

## Tradeoffs
- Did not backfill/replace all 87 existing placeholder rows in this pass — the publish
  endpoint makes that a trivial per-tour follow-up call, not a schema/code change; doing a
  full 87-row real backfill blind (without per-tour review) risked mass-writing 87 URLs
  nobody has looked at individually. Live-verified the mechanism against 1 real tour instead
  (see Linear comment) — proves the pattern works end-to-end.
- Did not fix `v_trip_registry`'s tenant-scoping JOIN gap — real, but out of this issue's own
  scope (a view used by N7/N4-N6 planning code, changing its row semantics needs its own
  review), flagged for a separate ticket.
- Did not build a full multi-tenant version of this page (tenant-specific rewritten content) —
  scoped to the admin-canonical catalog for v1, matching `v_trip_registry`'s own current real
  shape; a real, valuable, but separately-sized follow-up.
- No migration — reused the existing `acp_deliver.tenant_tour_pages` table (migration 078)
  as-is, no schema change needed.
