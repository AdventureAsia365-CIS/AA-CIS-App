# AA-343 — Phần 4: mapper S0 collision + view deleted_at filter

## Context
Diagnosis (closed): `COLUMN_MAP` in `services/ingestion/excel_parser.py` maps several source-file
column names onto the same DB field (e.g. both `source_itineraries` and `aa_itineraries` → `src_itineraries`).
`col_lookup` is a dict keyed by DB field built by iterating `df.columns` in file order, so whichever
column appears LAST in the file wins. Real supplier "Format B" files always place the `AA_*` columns
after the `SOURCE_*` columns, so `AA_*` (AI-rewritten output) always overwrote the real source text.
Confirmed blast radius: 46 rows across 2 batches (`a0b806f8`, `4bdd9b22`), already soft-deleted
(`deleted_at` set). 37/38 other batches are clean. No `tour_atoms` affected.

## F1.1 — Full audit of COLUMN_MAP same-target pairs

Grouped by DB field (`services/ingestion/excel_parser.py` COLUMN_MAP):

**Same-tier synonym pairs (no source vs. AA_* conflict, presumed intentional — a file uses one
variant, not several at once; left unchanged):**
- `tour_id_external` ← "tour id", "tour_id"
- `price_raw` ← "price_usd", "price"
- `inclusions` ← "inclusions", "includes"
- `exclusions` ← "exclusions", "excludes"
- `src_itineraries` bare synonyms ← "itineraries", "itinerary", "itinerary_summary" (all non-AA)

**Source vs. AA_* pairs (confirmed bug pattern — real "Format B" files carry both at once):**
- `src_name` ← "name", "source_name" (real) vs. "aa_name" (AA output)
- `src_subtitle` ← "subtitle", "source_subtitle" (real) vs. "aa_subtitle"
- `src_summary` ← "summary", "source_summary" (real) vs. "aa_summary"
- `src_highlights` ← "highlights", "source_highlights" (real) vs. "aa_highlights"
- `src_itineraries` ← "itineraries"/"itinerary"/"itinerary_summary"/"source_itineraries" (real) vs.
  "aa_itineraries" (AA output) — the exact column pair behind the 46-row corruption.

No other unexpected same-target pairs found. Did not stop/ask — the synonym group is unchanged
behavior (zero regression risk) and the source-vs-AA group is exactly what the diagnosis described.

## Decisions
- AA_* alias columns (`aa_name`, `aa_subtitle`, `aa_summary`, `aa_highlights`, `aa_itineraries`) are
  now unconditionally excluded from writing into `src_*` fields — not just deprioritized. Real/source
  columns are written first; AA_* columns are only used to fill a field if literally nothing else
  claims it, and even then they are NOT used — the field is left unset and a warning is logged. This
  removes the file-column-order dependency entirely (F1.2), independent of the F1.3 file-level reject.
- **Spec conflict, resolved with Nghiep (asked mid-implementation):** F1.3's marker group as written
  includes `AA_ITINERARIES`, but T1's mandatory tests 1–2 require a file with both
  `SOURCE_ITINERARIES` and `AA_ITINERARIES` to parse successfully (not reject) so the resolved value
  can be checked — mutually exclusive for the same file. Resolved: `AA_ITINERARIES` is deliberately
  **excluded** from the F1.3 file-level reject markers. It's covered entirely by F1.2's priority
  resolution instead, which already fully closes the diagnosed corruption vector on its own — a file
  legitimately carrying both columns still ingests correctly with the source value winning. F1.3 reject
  markers are `audit_status`, `publish_ready`, `fields_updated`, and any `dfs_*` column.
- Added T1.5 (Nghiep, mandatory): a file with `AA_ITINERARIES` and NO corresponding real source column
  (no `SOURCE_ITINERARIES`, no `ITINERARIES`) must never populate `src_itineraries` from `AA_ITINERARIES`
  — this is the exact shape that produced the original corruption and had no prior test coverage.
  Already-implemented behavior (leave the field unset + log `aa_alias_column_ignored`) satisfies it.
- **Known follow-up, explicitly out of scope for this PR (Nghiep):** a "Format A" file that carries
  AA_* columns but neither `AUDIT_STATUS`/`PUBLISH_READY`/`FIELDS_UPDATED` nor `DFS_*` still passes
  F1.3 and gets ingested — with this fix it will no longer corrupt `src_*` (AA_* never wins), but it
  can still create duplicate rows the same way today's bug does. That's `handler.py`'s dedup gap
  (P1.3/P1.5), a separate already-split-out PR — not touched here.
- Left the same-tier synonym group (F1.1 group 1) untouched: fixing an order-dependency that has no
  known bug and no failing test would be scope creep beyond the diagnosed incident.
- F2.1: added `rt.deleted_at IS NULL` to `acp_contract.v_trip_registry`'s WHERE clause (migration 090,
  CREATE OR REPLACE on top of migration 087's definition — no other view changes touched it in between).

## Changed
- `services/ingestion/excel_parser.py`: export-file guard + AA_*-never-wins-over-source resolution.
- `api/migrations/090_v_trip_registry_filter_deleted_at.sql`: `rt.deleted_at IS NULL` added.
- `tests/unit/test_excel_parser.py`: 4 new cases (T1) + Format B repro (T2).

## Tradeoffs
- Considered hard-failing (raise) on `AA_*`-alone-with-no-real-column instead of warn+skip. Chose
  warn+skip because F1.3 already hard-rejects the only real-world case this could fire from
  (`aa_itineraries` triggers file rejection outright); a lone `aa_name`/`aa_subtitle`/etc. without any
  export markers is unobserved in the data, so failing the whole row for it would be speculative.
- Did not touch `v_batch_stats` / `v_pipeline_summary` (F2.2) — proposal only, numbers below.

## F2.2 — v_batch_stats / v_pipeline_summary proposal (not changed in this PR)
Both (`shared.v_batch_stats`, `shared.v_pipeline_summary`) select from `silver_aa_internal.raw_tours`
directly with no WHERE clause at all — neither filters `deleted_at` today. Adding a
`raw_tours.deleted_at IS NULL` filter would drop row counts from **839 → 793** (exactly the same 46
soft-deleted rows). Proposal: yes, filter both the same way, for consistency with `v_trip_registry` and
because a batch/pipeline report that counts soft-deleted rows as if they were live is misleading — but
deferred to a follow-up PR per instruction (these are reporting views, not the pipeline input contract).
