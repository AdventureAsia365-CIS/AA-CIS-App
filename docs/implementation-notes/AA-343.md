## Round 3 — Part C: pipeline_runs stuck at 'ingesting' forever

### C1 — diagnosis re-confirmed
`handler.py:102-113` sets `status='ingesting'` at insert and never updates it again.
`source_repo.update_status(source_id, "done"/"failed", ...)` targets `raw_sources`, not
`pipeline_runs` — confirmed, and worse than assumed (see item 6 below).

### C2 — real `pipeline_runs.status` vocabulary (no CHECK/enum — free-text VARCHAR(50))
Grepped every `pipeline_runs` read/write in `api/`, `services/`, `shared/` (excluding tests):
- `services/ingestion/handler.py:102-113` — INSERT `status='ingesting'`.
- `api/routers/admin_pipeline.py:728-729` — `SET status='failed' WHERE ... AND status='ingesting'`
  (S1 retry-exhausted).
- `services/export/handler.py:93-97` — `SET status='completed', completed_at=NOW() WHERE ... AND
  status='ingesting'` (fires only once every tour in the batch reaches `pipeline_status='published'`).
- `admin_pipeline.py:3154-3155,3171,3194` — daily metrics `SUM(...)`, `WHERE status != 'ingesting'`.
- `admin_pipeline.py:3227-3230` (`last_run`) — `WHERE completed_at IS NOT NULL`.
- `admin.py:426-442,508-514` — tenant-facing dashboard, reads `pr.status`/`tours_total`/
  `tours_passed` for **every** `pipeline_runs` row, **no status filter at all**.
- `frontend/app/admin/tenants/page.tsx:242-253` — `STATUS_STYLE` badge map recognizes `ingesting`;
  unknown values fall back to a plain gray badge (`?? { bg: A.line2, col: A.muted2 }`) — confirmed
  `'ingest_failed'` won't break rendering, just shows unstyled (cosmetic, no UI changes made here).

**Real conflict found and resolved with Nghiep:** the existing convention treats `'ingesting'` as
the status for the batch's *entire* lifecycle (ingest→S1→export), only flipping to `'completed'`/
`'failed'` based on what happens later in S1/export. Setting `'completed'` right after ingest (as
originally asked) would have misrepresented an un-rewritten batch as done and permanently broken
`export/handler.py`'s `WHERE status='ingesting'` guard. **Resolved:** ingest success leaves
`status` **unchanged** (`'ingesting'`); ingest failure sets a **new** terminal status
`'ingest_failed'` with `completed_at` and a non-empty `error_message`.

### Item 3 — tours_passed/tours_failed conflict, resolved via new column (not reused)
`tours_passed` is fully **recomputed** (not incremented) to the published-tour count by
`services/export/handler.py:79-85` the moment any tour in the batch is exported, and is read
**unfiltered** by the tenant dashboard (`admin.py:508-514`) — writing an ingest-landed count there
would show tenants a misleading "N passed" before any S1 rewrite happened. `tours_failed` is
**incremented** by `admin_pipeline.py:663` per S1 quality failure — writing ingest-drop counts
there would permanently mix two different populations into one counter. **Resolved:** new
`shared.pipeline_runs.ingest_details JSONB` column (migration 091, file only, not run — see
`api/migrations/091_pipeline_runs_ingest_details.sql`), shape:
`{"rows_parsed": N, "rows_landed": N, "rows_dropped": N, "drops": [{"reason": str, "count": N,
"sample_ids": [...]}]}`. `tours_passed`/`tours_failed` are never touched by the ingest step —
verified by unit test (`tests/unit/test_aa343_ingest_status_fix.py`).

### Item 6 — `source_repo.update_status()` finding (not fixed, reported only per instruction)
Worse than "wrong table": `RawSourceRepository.update_status()` (`shared/repository/
raw_source_repository.py:33-39`) accepts `status` and `error` parameters but its SQL body only
ever does `SET row_count = COALESCE($2, row_count)` — **neither `status` nor `error` is written
anywhere**, and `silver_aa_internal.raw_sources` **has no `status` column at all** (confirmed
against Part A's `\d` output). Both call sites (`handler.py` success and failure paths) pass a
`status`/`error` argument that is silently discarded today. Left untouched per instruction (item 6:
"chỉ báo, không tự xoá").

### The actual root cause of the 14-row silent drop (P1.3) — different from the original assumption
The original bug report framed this as a dedup issue. It isn't: every parsed record is routed
either to `new_records` (→ `insert_batch`) or `upload_staging` (dedup match) — nothing is dropped
in that loop. The real mechanism: `RawTourRepository.insert_batch()`
(`shared/repository/raw_tour_repository.py`) looped `await self.insert(record)` with **no
per-record error isolation** — the first record whose INSERT raised (e.g. a value too long for a
`VARCHAR` column) aborted the **entire loop**, silently discarding every record after it (already-
inserted records stayed committed since there's no wrapping transaction). The exception then
propagated to `handler.py`'s `except Exception as e:` block, which called the (no-op, see item 6)
`source_repo.update_status(source_id, "failed", error=str(e))` — so the failure reason was
discarded twice over. This exactly explains "16/30 landed, error_message=NULL, no log of reason."

**Fix (not just logging — a real isolation fix, judged in-scope since it's not dedup logic):**
`insert_batch` now catches per-record, continues past a failing record, and returns
`(ids, failures)` with `identifier` (`tour_id_external` or `src_name`) + `reason` per failure.
`handler.py` groups failures by reason into `ingest_details.drops[]` (capped at 5 `sample_ids`/
group) and logs `ingest_rows_dropped` (structured, no longer silent). Dedup logic itself
(name+provider matching → `upload_staging`) is untouched.

### C4 — every ingest exit path
Restructured the `except Exception as e:` block: alongside the existing (no-op) `raw_sources` call
(kept, untouched), a new best-effort `UPDATE shared.pipeline_runs SET status='ingest_failed',
completed_at=NOW(), error_message=$2 WHERE batch_id=$1` runs inside its own nested try/except (so a
failure marking the failure doesn't mask the original exception) before re-raising. `batch_id_new`
is assigned as the very first statement inside the outer `try`, so it's bound for essentially any
exception that can occur in this function.

### ĐK2 — where rows_landed/rows_dropped should surface (proposal only, not implemented)
`GET /admin/upload-history` (`admin_pipeline.py:1493-1518`) is the exact backend for the Upload
History table on `/admin/upload`. Its `row_count` field (from `raw_sources.row_count`, the
*parsed* count) is what the frontend currently labels "TOURS PARSED" — this is the literal number
that reads "30" for `laos_biking_publish_ready.xlsx` while only 16 ever landed.

**Proposal:** join `shared.pipeline_runs` on `batch_id` in `get_upload_history()` and pull
`ingest_details->>'rows_landed'` and `ingest_details->>'rows_dropped'` (NULL for sources ingested
before migration 091 — pre-existing rows simply show nothing new, no backfill required for the UI
to degrade gracefully). Add two response fields (`rows_landed`, `rows_dropped`); frontend should
split "TOURS PARSED" into "PARSED / LANDED" with a dropped-count badge when `rows_dropped > 0`, so
a partial ingest is visible on the page that already shows this table, instead of only in a JSONB
column nobody queries. Not implemented this round (no endpoint/UI changes per instruction) —
**follow-up Linear issue created, see AA-343 comment for the link.**

### C6 — proposed backfill for the 3 stuck Laos `pipeline_runs` rows (NOT run)
```sql
-- 59a9f04a (LAOS.xlsx) — ingest itself succeeded cleanly (58/58 landed, still live rows).
-- status correctly stays 'ingesting' under the new design (not done through S1/export yet) —
-- only ingest_details is backfilled, reflecting what the new code would have written at ingest time.
UPDATE shared.pipeline_runs
SET ingest_details = '{"rows_parsed": 58, "rows_landed": 58, "rows_dropped": 0, "drops": []}'::jsonb
WHERE batch_id = '59a9f04a-7922-4242-bd27-a5bcd54b8d12' AND ingest_details IS NULL;

-- a0b806f8 (lao_biking_public_ready.xlsx, Format A) — ingest itself also succeeded cleanly at the
-- time (30/30 landed, matches raw_sources.row_count). Rows were later hard-deleted for content
-- corruption (unrelated to this bug, see Part B) — ingest_details reflects ingest-time reality,
-- not current row existence. status stays 'ingesting'.
UPDATE shared.pipeline_runs
SET ingest_details = '{"rows_parsed": 30, "rows_landed": 30, "rows_dropped": 0, "drops": []}'::jsonb
WHERE batch_id = 'a0b806f8-689a-4f78-90b1-5e36a29bb699' AND ingest_details IS NULL;

-- 4bdd9b22 (laos_biking_publish_ready.xlsx, Format B) — this is the one that actually FAILED under
-- the old code: insert_batch raised partway through (16/30 landed), the exception propagated, and
-- was silently discarded by the no-op raw_sources.update_status. Genuinely a failure, not a clean
-- ingest. completed_at/error_message are RETROACTIVE APPROXIMATIONS (the original error text was
-- never captured) — flagged explicitly in error_message, not fabricated as if it were real.
-- sample_ids are the 14 known-missing tour_id_external values from the original incident report.
UPDATE shared.pipeline_runs
SET status = 'ingest_failed',
    completed_at = started_at,  -- approximation: exact original failure time was never recorded
    error_message = 'RETROACTIVE BACKFILL (AA-343): original error text was discarded by the ' ||
                     'pre-fix no-op raw_sources.update_status call. Known fact: insert_batch ' ||
                     'aborted on the first per-record failure, 16/30 rows landed, 14 never attempted.',
    ingest_details = '{
        "rows_parsed": 30, "rows_landed": 16, "rows_dropped": 14,
        "drops": [{"reason": "unknown — pre-fix insert_batch discarded individual reasons",
                    "count": 14,
                    "sample_ids": ["tour-001","tour-003","tour-004","tour-006","tour-010",
                                    "tour-012"]}]
    }'::jsonb
WHERE batch_id = '4bdd9b22-ea41-4489-bcd6-24de54e545cb' AND status = 'ingesting';
```
