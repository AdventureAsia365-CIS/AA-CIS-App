# AA-564 — Build: AA-563's design (Groups 1-5)

Implements the design AA-563 (investigation, Done) produced. No new investigation here — every
architectural question was already answered with file:line evidence in AA-563's 2 Linear
comments; this file only records build-time decisions.

## Decisions

- **PR split**: Groups 1-3 (all Admin, `/admin/atom-curation`) in one PR (#340, merged) — they
  touch the same file (`page.tsx`) and the same two backend routers (`admin_atoms.py`,
  `admin_dashboard.py`), so splitting further would just fragment one coherent diff. Group 4.1
  (Tenant Portal rename) is a separate PR (#341) — different app surface, different files,
  genuinely independent per AA-564's own instructions.
- **1.3 (per-tour stats)**: added a one-line caption under the 5-card block ("Total atoms/
  Reviewed are for the selected Tour. High/Medium/Low ... stays platform-wide") rather than
  leaving the scope difference implicit — this exact confusion (a block that looks per-tour but
  isn't) is the bug being fixed, so leaving one field silently platform-wide with no label risked
  relitigating the same complaint later.
- **1.4 (SUPERSEDED tooltip)**: implemented as a native `title` attribute wrapping the existing
  `Badge`, not a change to the shared `Badge` component — scoped to the one place that needed it,
  no new prop on a component 10+ other call sites share.
- **2.1/2.2 (Slate JOIN + tenant scoping)**: while rewriting `list_slate()`, also fixed a
  pre-existing inaccurate copy reference (`SlateExplainerNote` pointed at a nonexistent
  `/portal/slate` route — the real route is `/portal/t7-planning`, confirmed both by AA-563's
  investigation and by grep here). Not a listed AA-564 item, but directly adjacent to the code
  being touched and the same class of "copy doesn't match reality" bug this whole epic chain has
  been fixing.
- **2.1 tour_name for Segment-based Subjects**: a Segment can legitimately span more than one
  tour (CONTEXT.md's own definition — "usually from different tours"), unlike a Route (always
  exactly one tour). `list_slate()`'s new query aggregates (`array_agg(DISTINCT ...)`) rather than
  assuming a single tour for the Segment case, joined into a comma-separated string for display.
- **3.1 recompute-on-`deleted`**: fires on `deleted` being included in the PATCH body at all (both
  `true` and `false`/restore), not only `deleted=true` as AA-564's text literally says — restoring
  an atom changes Segment eligibility (`WHERE NOT ta.deleted`) exactly as much as deleting one
  does, so triggering only one direction would leave the reverse case silently stale. Recorded as
  a deviation, not silently done.
- **3.1 extraction**: pulled the Segment→Ranking→Route 3-step chain out of
  `_run_a3_atomize_background()` into a new standalone `recompute_segment_score_route()`
  (`services/export/handler.py`) so both the delete-trigger path and the existing atomize path
  call the same code instead of duplicating it. `_run_a3_atomize_background()` itself is
  unchanged in behavior, just calls the extracted function now.
- **3.2 job/poll model**: no new job-status table. `POST /admin/atoms/atomize` is fire-and-forget
  (matches T9's `run_write_background()` precedent exactly — that pattern is "poll the resulting
  resource," not a separate job-status API, despite AA-564's text saying "reuse the pattern... "
  which could be read either way). The client polls `GET /admin/atoms/unatomized-tours` until the
  triggered tour(s) drop off the list.
- **3.2 sequential, not parallel**: "atomize all" runs tours one at a time in a single background
  task, not N concurrent tasks — `run_t5_atomize()` can issue one Bedrock call per itinerary day
  per tour; nothing caps how many tours "all" might mean, so parallel would risk a rate-limit
  burst with no such risk in the existing design.
- **4.1 (rename Slate → Social Content, Tenant Portal only)**: renamed every TENANT-facing string
  that names "Slate" by name — sidebar label (`Sidebar.tsx`), breadcrumb (`layout.tsx`), page H2
  (`PlanningTab.tsx`), `SlateTab.tsx`'s own `CardHead` + its loading-error empty state, and the two
  user-visible strings in `AngleGateTab.tsx` that referenced "the Slate" by name (its empty-state
  CTA and its resume-load error message). Left untouched: every internal comment/docstring that
  says "Slate" (CONTEXT.md's own glossary term, matches the DB/API naming — `SlateTab.tsx`'s own
  filename, `acp_shared.subject`, `GET /v1/slate`), and everything on the Admin side (Admin's
  `/admin/atom-curation` page still calls this section "05 · Slate" — Group 2's own explicit
  instruction NOT to rename Admin).

## Changed vs. AA-563's literal wireframe

- Admin Slate table: dropped the separate "Tenant" column from the wireframe's table sketch
  (channel/state/score/kind/topic/proposed) — once a single Tenant is selected via the new
  dropdown, every row is that same tenant, so the column would be constant/redundant. Not present
  in AA-563's own D.2.1 sketch either (it only shows the column drop implicitly).

## Should know before reading the diff

- `api/routers/admin_dashboard.py::list_slate()` changed its required query param from `tour_id`
  to `tenant_id` — this is exactly what AA-563 concluded was the bug (Slate is per-tenant, ADR-
  0003), not a new decision made here.
- `services/export/handler.py::recompute_segment_score_route()` is newly importable from other
  modules (previously this logic was private to one file) — used by `admin_atoms.py`'s
  `patch_atom()`. Existing tests patch `services.acp_contract.segment_matching.run_segment_matching`
  etc. at their origin module (not via `services.export.handler`), so the extraction doesn't
  break any existing test's patch target — verified by running the full pre-existing test suite.
- Live-verify (Playwright, real screenshots) for Groups 1-3/4.1 recorded separately in this file's
  "Live Verify" section once run against a real deploy, and posted to the AA-564 Linear issue.

## Groups 4.2/4.3/5 — stopped, awaiting confirmation

Groups 4.2 (merge Slate+Write into an inline-expand) and 4.3 (sync T4 My Catalog's layout with
Admin's Master Content) are **not implemented**. Both were investigated per AA-564's explicit
instruction and found to be substantial UI rewrites with real regression risk on business-
critical, previously-hard-won-correct pages (T8/T9's write wizard already fixed 3 real production
bugs across AA-497/500/522; T4's Catalog is the tenant's primary tour-management page). Per
AA-564's own escalation instruction ("nếu refactor phức tạp hơn dự kiến, DỪNG báo cáo qua comment
trước khi tiếp tục"), a stop-report with a concrete technical plan for both was posted to the
AA-564 Linear issue instead of pushing ahead. Group 5 (updating AA-556's description) depends on
4.2 being done, so it is deferred with it.
