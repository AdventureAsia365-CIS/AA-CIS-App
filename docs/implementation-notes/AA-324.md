# AA-324 — Prompt caching truly dead on satellite Bedrock calls

## Decisions
- Parent build-prompt's own directive: "STEP0 bắt buộc: xác nhận AA-518 đã giải quyết chưa —
  nếu rồi, không build, đề xuất Cancel." STEP0 confirms AA-518 (3-account per-stage config)
  did **NOT** resolve this — it changed model/role selection routing, not the satellite
  request-body construction where the real bug lives. Proceeded to build, not Cancel.
- STEP0 also found the issue's own **title hypothesis is wrong** (already flagged as
  unconfirmed in the 25/07 comment, ADR-2026-034): it is NOT "cache_control only works on
  acc2 Bedrock direct" (a platform/cross-account limitation). Confirmed via direct code read
  of `invoke_claude()` (the satellite call path) — 2 concrete, local, fixable bugs in
  `shared/llm_client/*`, nothing to do with cross-account IAM/STS at all:
  1. **Request side** (`bedrock_satellite.py::invoke_claude()`): `system` was sent as a
     PLAIN STRING. Bedrock's Anthropic-compatible InvokeModel body (the exact
     `"anthropic_version": "bedrock-2023-05-31"` shape this code uses, NOT the Converse API)
     supports the identical `cache_control` contract as the direct Anthropic API — `system`
     as a list of content blocks, each with `cache_control: {"type": "ephemeral"}`. A plain
     string is valid shape too, but Bedrock silently never caches it — no error. Matches the
     "code looks right, cache stays 0" symptom the issue itself observed exactly.
  2. **Response side** (`client.py::_call_bedrock_satellite()`): never read
     `cache_read_input_tokens`/`cache_creation_input_tokens` out of the satellite response's
     `usage` dict at all — `LLMResponse.cache_read_tokens`/`cache_write_tokens` always
     defaulted to 0 regardless of what Bedrock actually returned, independently of bug #1.
- Real-world relevance is HIGHER than the 25/07 comment's own "$4/month, only N7 matters"
  conclusion — that comment predates T7-T11 (AA-449 onward) existing. Live DB check (below)
  confirms virtually 100% of real recent S1/T2 generation calls (`generated_content.metadata`)
  already route through the satellite path (`model_used = "satellite-*"` on 51/51 checked
  rows) — this bug affects current real production content-writing traffic broadly, not a
  narrow legacy N7 corner. Did not attempt to re-estimate real $ savings (would need a real
  token-volume analysis across all satellite call sites, disproportionate to this pass) —
  flagged as stale in the Linear comment instead of silently re-asserting the old number.
- Built the fix rather than deferring: contained, 2-file change, no migration, no infra,
  directly reuses the existing `build_cached_system_prompt()` L1-cache helper (no new
  mechanism invented) — proportionate scope for a Medium-priority, well-diagnosed bug.

## Changed
- `shared/llm_client/bedrock_satellite.py::invoke_claude()` — `system` now wrapped via
  `build_cached_system_prompt()` (the same helper `_call_bedrock()`'s acc2-native T1 path
  already uses) instead of passed as a bare string.
- `shared/llm_client/client.py::_call_bedrock_satellite()` — extracts
  `cache_read_input_tokens`/`cache_creation_input_tokens` from the satellite response's
  `usage` dict, sets `LLMResponse.cache_read_tokens`/`cache_write_tokens` (previously always
  0). Mirrors `_call_bedrock()`'s own extraction exactly.
- `tests/unit/test_aa324_satellite_prompt_cache.py` — 4 new tests (request body carries a
  real cached content block; `system=None` still omits the field cleanly; response-side
  extraction reflects real usage; absent cache fields stay a real 0, not an error).

## Tradeoffs
- Did not add a minimum-token-count gate (H4 from ADR-2026-034) — that's a caller-content
  concern (how large the system prompt actually is), not something to hardcode into the
  low-level wrapper; S1/T9's system prompts (brand rules + schema instructions, ~6-8k tokens
  per the 25/07 comment's own N7 estimate) are almost certainly well above Anthropic's cache
  minimum already.
- Did not address H2 (5-min TTL expiry between calls) or H3 (prefix stability) — those are
  call-site/scheduling concerns (SQS FIFO grouping, etc., already covered by ADR-2026-034 for
  N7 specifically), not something this 2-file client-layer fix can or should touch.
- Did not re-verify N2/Batch's "closed, no caching applies" conclusion from the 25/07 comment
  — out of this fix's scope (Batch genuinely doesn't share cache across records by AWS
  design, unrelated to either bug fixed here).

## Should know
- **Real live DB evidence (pre-fix, this session)**: queried `silver_aa_internal.
  generated_content.metadata` for the 51 most recent rows carrying a `cache_read_tokens`
  key — **all 51 show `cache_read=0, cache_write=0`**, and **all 51 show
  `model_used LIKE 'satellite-%'`** — confirms both that virtually all real recent traffic is
  satellite (matching AA-329's finding acc2-native is blocked) and that caching has never
  actually engaged, consistent with bug #1 (request never even attempted to cache) rather
  than bug #2 alone masking a real cache hit.
- Live-verify (post-deploy): triggered a real rewrite through the actual domain, confirmed
  the resulting `generated_content.metadata.cache_write_tokens` is now non-zero on the first
  call to a given brand/system prompt — see Linear AA-324 comment for the real numbers.
- flake8 clean, full `tests/unit/` suite (1839 incl. these 4) passes, 0 regressions.
