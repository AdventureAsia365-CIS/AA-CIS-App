# AA-575 — Content Trace: sub-nav 01-06 disappears when navigating in, sort missing on most columns

## STEP0

01-05 are NOT separate Next.js routes. `frontend/app/admin/atom-curation/page.tsx` is ONE page
that implements 01 Atomize / 02 Segment / 03 Score / 04 Route/Hub / 05 Slate as client-side tab
state (`SectionKey`, `activeSection`). Its 01-06 "inner-sidebar" was JSX embedded directly in
that page's own render tree (`AtomCurationDashboardPage`) — never a shared layout or component.
`frontend/app/admin/tenant-activity/page.tsx` (06 · Content Trace) is a genuinely separate
route/page with its own independent render tree, which never had that inline markup at all. That
is the exact, sole root cause of the reported "sub-nav vanishes" bug — there was no shared layout
wrapping both pages, just one page's local markup that happened to also contain a real
`<a href="/admin/tenant-activity">` link out to the other page.

## Decisions

- **Extracted the inner-sidebar into a shared component**, `frontend/app/admin/_components/
  SocialContentSubNav.tsx`, rather than adding a Next.js route-group `layout.tsx`. A shared
  `layout.tsx` would require both pages to live under one route segment (they don't — 01-05 are
  tab state inside `/admin/atom-curation`, 06 is `/admin/tenant-activity`, a sibling route with no
  common parent segment besides `/admin` itself, which already has its own `layout.tsx` for
  auth/shell) and wouldn't solve the deeper issue that 01-05 aren't routes to begin with. A plain
  shared component both pages import is simpler and matches the existing pattern in this codebase
  (`AdminSidebar`, `adminUi.tsx` tokens are already shared this way).
- **Preserved the instant, no-reload tab-switch UX for 01-05 from atom-curation** (AA-554's own
  comments call this out as load-bearing — segment/score/route-hub each carry their own fetch
  state). `SocialContentSubNav` takes an optional `onSelectSection` callback: when present (only
  passed from atom-curation/page.tsx, which owns the tab state), 01-05 render as `<button>`s that
  call it — same-page state change, zero navigation. When absent (every other page, i.e. Content
  Trace today), 01-05 render as real `<Link>`s to `/admin/atom-curation?section=<key>`.
- **`?section=` query param, read once via `useSearchParams()`** on atom-curation's mount to pick
  the initial `activeSection` (falls back to `"atomize"` for a missing/invalid value via a
  `VALID_SECTIONS` allow-list — an unrecognized value would otherwise match none of the
  `activeSection === "..."` render checks and silently show a blank content column). This follows
  the exact existing convention in `frontend/app/(tenant)/portal/t4-pool/page.tsx` (wraps the
  page's default export in `<Suspense>`, same reason: `next build` fails prerendering an
  App-Router page that calls `useSearchParams()` without one) — verified with a real
  `next build` (prerenders cleanly, both routes stay static).
- **06 · Content Trace is always a real `<Link>`**, including when already on that page (harmless
  same-page nav) — there's no local tab state on that page for it to hook into, unlike 01-05 from
  atom-curation.
- **Content Trace's sub-nav sits inside the SAME scroll region as the table** (a
  `display:flex, gap:20` wrapper — `a527-dash-body`, matching atom-curation's own body shape —
  around `[SocialContentSubNav, content column]`), not as a sibling column outside it. Confirmed
  safe against AA-572's own sticky-`<thead>` fix (`reference_sticky_thead_needs_single_scroll_
  container` — a nested `overflow-x:auto` div breaks `position:sticky` on `<th>` by forcing
  `overflow-y` to compute to `auto` too): the new wrapper div sets no `overflow` property at all,
  so it doesn't become a second scrolling context — the existing `flex:1, minHeight:0,
  overflowY:"auto", overflowX:"auto"` div remains the one true scrolling ancestor. Verified live
  (test 07 of the pre-existing `aa572-content-trace-fixes.spec.ts` regression suite, unchanged,
  still passes after this restructuring).
- **The responsive media-query `<style>` block (`.a527-inner-sidebar` / `.a527-dash-body`,
  originally only in atom-curation/page.tsx) moved into `SocialContentSubNav.tsx` itself** — a
  React `<style>` tag is global (not scoped to its subtree), so defining it once inside the shared
  component covers both pages' wrapper `className`s without duplicating the block per-file.
- **Sort (AA-572 → AA-575): extended the exact same client-side mechanism to all 7 remaining
  columns** (Topic/Tenant/Tour/Channel/Angle chosen/Status/Published) instead of writing a
  per-column special case. `SortKey` grew from 3 to 10 values; a new `sortValue(row, key)` switch
  returns either a string (free-text/categorical columns, compared with `localeCompare`) or a
  number (Gate/Retry counts, the Created-at timestamp, and a new `PUBLISH_RANK` for Published).
  `toggleSort()`/the click-to-toggle-arrow UI were already generic over `SortKey` and needed no
  change.
- **Published gets a pipeline-order rank (`n/a` → 0, `pending_publish` → 1, `published` → 2),
  not an alphabetical string sort** — alphabetically "n/a" / "pending_publish" / "published"
  doesn't read as "progress toward live," which is what a human clicking this header actually
  wants.

## Changed

- `frontend/app/admin/_components/SocialContentSubNav.tsx` — new, the single shared 01-06 nav.
- `frontend/app/admin/atom-curation/page.tsx` — inline inner-sidebar JSX + `SECTIONS` const +
  local `SectionKey` type removed (now imported from the shared component); wrapped in
  `<Suspense>` for `useSearchParams()`; `activeSection`'s initial value now reads `?section=`.
- `frontend/app/admin/tenant-activity/page.tsx` — mounts `<SocialContentSubNav active=
  "content_trace" />` inside the existing scroll region; `SortKey`/`sortValue()`/`HEADERS` extended
  to all 10 columns (was 3).
- `tests/e2e/aa575-subnav-and-sort.spec.ts` — new, 13 tests (5 sub-nav, 7 new-column sort, 1
  regression check of AA-572's original 3 sortable columns).

## Tradeoffs

- Did not introduce a Next.js route-group `layout.tsx` — see Decisions above for why a shared
  component fits this codebase's actual route shape (01-05 = tabs, not routes) better than a
  layout would.
- Content Trace navigating to a 01-05 section is a real full page navigation (a fresh
  `/admin/atom-curation` mount with `?section=` read on mount), not a client-side transition that
  preserves atom-curation's already-fetched `summary`/`stats` state — acceptable because that's
  exactly how the pre-existing 06 link out of atom-curation already worked in the other direction
  (a plain `<a href>`, not a router push), so this doesn't regress anything, it only adds the
  missing reverse direction.

## Should know

- `SocialContentSubNav` is now the only place the 01-06 label list/order/icons live — a future
  07th section or a renamed label only needs editing there, not both pages.
- The `?section=` param only affects atom-curation's *initial* tab on mount; manually clicking
  01-05 there afterward does not update the URL (same as before this change) — a browser refresh
  on that page always lands back on whatever `?section=` (or the default `atomize`) says, not
  wherever the user last clicked.
