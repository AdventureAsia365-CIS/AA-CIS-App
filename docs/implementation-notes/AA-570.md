# AA-570 — content_piece.discarded_attempts

## Decisions
- Single `discarded_attempts JSONB NOT NULL DEFAULT '[]'` column directly on `content_piece`
  (migration 148), not a separate table — AA-570's own investigation found the real volume too
  small (66.7% of pieces have exactly 1 discarded attempt, ~2.4KB each, <$0.01/month even at
  50-tenant scale) to justify a child table's own indexes/migrations.
- No TTL/archival — same reasoning, confirmed in the investigation comment.
- Correctness detail not explicit in the build task but necessary for the field to mean what it
  says: `run_write_background()`'s gate-regression-guard (AA-528) can revert `content_text` back
  to attempt 1's output when attempt 2 regresses a gate. In that specific branch, attempt 1 is
  what's KEPT (not discarded) and attempt 2's own rewrite is the one thrown away — the discarded
  entry has to track whichever attempt actually didn't survive, not always "attempt N-1". See
  `discarded_attempt`'s own comment in `service.py` for the two capture points this needs.
- The discarded content_text/gate_ledger go through the same `strip_citation_tags()`/
  `deep_strip_citation_tags()` pass as the final persisted content — it's written to the same
  table, no reason a `[R:atom_id]` tag would be safe here and not there.
- `discarded_attempts` is deliberately NOT selected by any tenant-facing query (`fetch_piece()`,
  `fetch_latest_piece_for_request()`, `fetch_review()`, `fetch_review_list()`) — same exposure
  boundary AA-501 STEP0 §4 already draws for `gate_ledger`/`repair_log`. No UI reads it yet
  (matches AA-570's own investigation finding: no real consumer exists today).

## Changed
- `api/migrations/148_content_piece_discarded_attempts.sql` (new).
- `services/acp_content_writing/service.py`: `run_write_background()` captures the discarded
  attempt at the two points it can be determined (the gate-regression-guard revert branch, and a
  post-loop fallback for every other 2-attempt outcome); `_finalize_piece()` gains an optional
  `discarded_attempts` param (default `[]`, so the 2 other call sites — the exception handler and
  the buffer-retry path — need no changes) and persists it; `_row_to_dict()` reads it back
  defensively (`[]` when the calling query didn't select the column, same convention `flags`/
  `channel` already use).

## Tradeoffs
- No admin UI to browse discarded attempts — out of scope per the build task (storage only, no
  consumer requested yet).

## Should know
- 2 pre-existing tests in `test_aa499_content_writing_wiring.py`
  (`TestFinalizePiecePersistsEmbeddingAsPgvectorLiteral`) asserted `params[-1]` for the embedding
  literal — updated to `params[-2]` since `discarded_attempts` is now the true last SQL param.
