# AA-354 — Decimal/float TypeError in services/eval/regression.py:_detect_regression

Not an AA-352 or AA-353 change — a pre-existing bug in AA-289's original code, discovered while
running AA-353's live VERIFY (a real 20-tour golden-dataset eval run). Fixed as its own branch/PR
per explicit instruction not to fold this into AA-353 (already merged).

## Decisions
- Discovered live: the 20-tour golden-dataset run completed successfully end-to-end through the
  entire LangGraph pipeline for all 20 tours (confirmed by the log's last line:
  `eval_s1_old_tour_done idx=19 name=Gobi Desert Camel Traverse quality_score=10.0
  status=success`) — the crash happens strictly AFTER `run_s1_old_eval()` returns, inside
  `_detect_regression()`, called from `run_eval()`. Confirmed via a full traceback captured by
  self-daemonizing the script inside the ECS container (foreground `aws ecs execute-command`
  sessions die before a ~20-30 min run completes — see AA-353 implementation notes for the same
  observation applied to `eval-regression.yml`'s own SSM session).
- Root cause: `baseline["avg_quality_score"]` (via `_get_baseline`, straight from
  `conn.fetchrow()`) is a `decimal.Decimal` (Postgres NUMERIC column), while
  `current["avg_quality_score"]` (from `run_s1_old_eval()`'s `round(sum(...)/len(...), 3)`) is a
  plain Python `float`. `Decimal - float` raises `TypeError: unsupported operand type(s) for -:
  'decimal.Decimal' and 'float'`.
- Fixed at the read point (`_get_baseline`), not just the crash site (`_detect_regression` line
  297) — per explicit instruction to prefer converting nearest the source over a narrow patch,
  since any other future caller of `_get_baseline`'s result would hit the same mismatch
  otherwise. `_get_baseline` now returns a plain `dict` (was an `asyncpg.Record`, which is
  immutable and can't have a field reassigned in place) with `avg_quality_score` AND
  `avg_words_per_citation` (same NUMERIC-from-Postgres pattern, grepped for every usage — no
  current arithmetic on it, cast anyway for the same reason) cast to `float`. `gate_pass_count`
  is a Postgres INTEGER column → already a plain Python `int` via asyncpg, not affected.
- This bug is latent since AA-289 shipped `_detect_regression`'s s1_old branch — it only fires
  when a real PRIOR baseline row already exists for the pipeline (the very first run for a
  pipeline hits `if baseline is None: return False` before ever touching the Decimal). Given
  `shared.prompt_eval_runs` already had a 2026-07-23 baseline row before this session, it's
  plausible this branch has never actually completed successfully on a second run before now.

## Changed
- `services/eval/regression.py`: `_get_baseline()` — returns `dict` instead of `asyncpg.Record`,
  casts `avg_quality_score`/`avg_words_per_citation` to `float` right after fetch.
- `tests/unit/test_aa289_eval_regression.py`: 3 new tests —
  `test_get_baseline_converts_decimal_avg_quality_score_to_float`,
  `test_get_baseline_returns_none_when_no_prior_row`,
  `test_get_baseline_output_feeds_detect_regression_without_crash` (direct repro of the live
  crash, using the same threshold-crossing values).

## Tradeoffs
- `avg_words_per_citation` cast defensively even though no current code path does arithmetic on
  it — same source pattern as the field that actually crashed, cheap to fix now vs. waiting for
  a second live crash to find it.
- Did not touch `_write_eval_run`'s `baseline["avg_quality_score"]` passthrough into the INSERT
  (line ~334) — passing a `float` into an asyncpg NUMERIC-column parameter is safe (asyncpg
  accepts either), and the value was already `round()`-ed to 3dp before this fix, so there's no
  meaningful precision difference to worry about.
