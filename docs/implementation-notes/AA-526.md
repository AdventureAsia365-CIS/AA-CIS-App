# AA-526 — Atomize moves to A3, gỡ bỏ hoàn toàn khỏi luồng tenant

## Decisions

- **STEP0 correction #1 (before any code)**: the issue text cited `v1_tours.py:837` as where
  `run_t5_atomize()` runs automatically after tenant rewrite — that call site was already
  removed by AA-469 Việc 1 (23/08/2026). What actually needed removing was a SEPARATE, explicit
  tenant-triggered endpoint, `POST /v1/tours/versions/{version_id}/atomize` (My Catalog's
  "Atomize" button), invoked on-demand, not automatically. Confirmed by reading the current code,
  not assumed from the issue's own (stale) description.
- **STEP0 correction #2 (found mid-build, real regression risk)**: that same endpoint was ALSO
  the only trigger for Segment research + ranking + route-detection (AA-509/510/515) — deleting
  it outright (as the issue's literal wording implied) would have silently stopped Segments from
  ever being (re)built for any tour rewritten after this ships. Asked Nghiệp directly (3 options
  presented); chose "re-trigger on tenant rewrite" — Segment-matching + research/ranking/route-
  detection now fire from `_run_ranking_pipeline()`, moved into `trigger_rewrite()`'s own
  background flow (`api/routers/v1_tours.py`), same timing/UX as before.
- **STEP0 correction #3 (found mid-build, would have shipped broken)**: my first attempt also ran
  Segment-matching itself at A3, `owner_scope='platform'` — wrong. `acp_contract.atom_segment.
  tenant_id` is a real `UUID NOT NULL REFERENCES shared.tenants(tenant_id)` (migration 129); that
  call would have failed the FK/cast outright, and even fixed, `atom_ranking.py` reads Segments
  `WHERE asg.tenant_id = $1::uuid` for the calling tenant specifically — a "platform" Segment
  would be invisible to every real tenant's own ranking read regardless. Corrected per Nghiệp's
  own clarification: atoms are shared platform-wide, but Segments/Route/Ranking stay a
  PER-TENANT product built from them once a tenant picks/rewrites a tour — not a single global
  Segment set. `run_segment_matching()`'s own atom-read query now matches legacy
  `owner_scope = tenant_id` (kept working, 75 real rows existed at ship time) OR
  `owner_scope = 'platform' AND tour_id` in that tenant's own `tenant_tour_versions` — not
  indiscriminately every platform atom for every tenant.
- **A3 hook point**: `services/export/handler.py::process_export()`, right after step 3
  (`raw_tours.pipeline_status = 'published'`) — confirmed via the AA-438-03 audit + a fresh read
  of the current file that this is the real, live "tour enters Master Content Pool" moment (both
  real call sites, `admin_pipeline.py`/`v1_pipeline.py`, `await` it directly in their own request
  handler). Launched as a **fire-and-forget background task** (own connection, own lifecycle,
  strong-ref pattern), not awaited inline — a multi-day atomize run could otherwise add real
  latency to / risk an API Gateway 504 on the admin approve action, the same class of problem
  AA-466 already solved for T9's write endpoint.
- **`_SingleConnAsPool` adapter**, not a `run_t5_atomize()` rewrite: `process_export()` (Lambda-
  handler-style, one bare `asyncpg.Connection`, no pool) needed `run_t5_atomize()`'s
  `pool.acquire()` calls to work — reused that function (and `atom_extraction.py` beneath it)
  completely unchanged, per the issue's own instruction, via a thin shim yielding the same
  connection every `.acquire()` call. Safe because every real code path through
  `run_t5_atomize()` acquires-and-releases sequentially, never concurrently (that module's own
  docstring).
- **`_llm_log_tenant_id()` fix** (`services/acp_produce/tenant_pipeline.py`): a real, previously-
  latent bug this build surfaced — `record_call_with_pool(tenant_id=...)` casts `$1::uuid`; every
  pre-AA-526 caller always passed a real tenant UUID so this never mattered. `owner_scope=
  "platform"` is not a valid UUID literal — would have silently failed every A3 atomize LLM
  call's cost/usage log (caught by that function's own try/except, but a real, avoidable loss of
  visibility on a stage that now runs on every published tour). Fixed with a tiny UUID-format
  guard, `None` (no tenant attribution) for anything that isn't one.

## STEP0 correction #4 (found via real live-verify AFTER merge/deploy — PR #310)

**The A3 atomize trigger crashed on every single call, live, in production, before this fix** —
unit tests alone did not catch it (every existing test mocks `build_competitor_index()`, so none
exercised its real SQL). `services/acp_shared/competitor_index.py`'s queries cast
`tenant_id = $1::uuid` — that module's own docstring already correctly says it's "Only wired at
T5 (`owner_scope=tenant_id` atoms) — NOT at N2's platform-scope decompose", a distinction this
task's first pass missed applying to the NEW platform-scope caller. `owner_scope="platform"`
(8 chars) is not a valid UUID literal.

Confirmed via a real live-verify run (05/09/2026): a real HTTP `POST /admin/review-queue/{id}/
approve` → real `process_export()` → real background task → real log line:
`a3_atomize_failed error=invalid input for query argument $1: 'platform' (invalid UUID
'platform': length must be between 32..36 characters, got 8)`. Zero atoms were ever inserted for
any platform-scope tour before this fix — the entire A3 mechanism this issue exists to build was
non-functional despite passing all 9 unit tests and CI.

**Fix**: skip the competitor-index fetch entirely for a non-tenant `owner_scope` (both
`_atomize_per_day()` and `_atomize_whole_tour_legacy()`), using `score_distinctiveness()`'s own
documented empty-index "MED" fallback instead — not a workaround, exactly the behavior that
module's docstring already specified for platform-scope callers. 2 new regression tests
(`TestAtomizeSkipsCompetitorIndexForNonTenantScope`) assert `build_competitor_index` is never
awaited for `owner_scope="platform"`.

**Lesson**: mocking a collaborator at its Python call boundary (as every existing test here did)
verifies the CALLING code's logic but never exercises the collaborator's own real SQL — a
schema-level assumption (a column type, a cast) can only be caught by either reading the
collaborator's source directly (which this task's STEP0 should have done for `owner_scope` more
exhaustively, given `segment_matching.py`'s FK turned out to matter too) or by a real end-to-end
run against the real database. Live-verify is not a formality on top of a green test suite; on
this task specifically, it was the ONLY thing that caught a total-non-functional-feature bug.
