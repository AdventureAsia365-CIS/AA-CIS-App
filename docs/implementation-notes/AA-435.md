# AA-435 — Admin login JWT: drop JSON-body token + non-httpOnly duplicate cookie

## Re-verify (before touching code)

Read `docs/implementation-notes/AA-427-tenant-jwt-httponly-cookie.md`'s "Should know" section (the
source of this issue) + the real, current `/api/auth/login/route.ts` and `login/page.tsx` on a
fresh `origin/main` checkout (worktree built specifically for this, see "Should know" below).
Confirmed the finding is still accurate, unchanged since 22/08/2026: `/api/auth/login/route.ts`'s
admin branch returned `token: data.token` in its JSON response, and `login/page.tsx` copied that
into a plain (non-httpOnly) `document.cookie = cis_api_token=...`. `cis_admin_token` — the cookie
middleware.ts and `requireAdmin()` (`lib/auth-server.ts`) actually check — was already httpOnly
since AA-232; `cis_api_token` was a pure, redundant, client-readable duplicate of the same JWT.

## Decisions

- **Not a literal "make `cis_api_token` httpOnly"** — the issue text suggested that, but the real
  fix is to stop minting the redundant cookie at all. `cis_admin_token` already does the httpOnly
  job (since AA-232); adding a second httpOnly cookie with the same JWT would just be duplicate
  state for no benefit. Dropping `token` from the JSON response (which is what actually feeds
  `cis_api_token`) closes the leak with a smaller diff than AA-427's tenant fix needed.
- **Call-site audit before touching anything** (this is the part AA-427's own note didn't need,
  since tenant's fix started from a clean slate) — grepped every reader of `cis_api_token` across
  the frontend and classified each:
  - `frontend/app/(internal)/review/page.tsx` — **real, load-bearing**: 3 direct
    `fetch(${API_URL}/v1/pipeline/review-queue...)` calls with `Authorization: Bearer <token>`,
    cross-origin straight to the FastAPI backend, actually consumed by `_get_tenant()`
    (`api/routers/v1_pipeline.py`) via `_verify_jwt()`. This would have broken the moment
    `cis_api_token` stopped being set. **Fixed** — converted to the existing same-origin
    `/api/tenant/[...path]` proxy (already used elsewhere in the app for staff calls), which
    authenticates via the httpOnly `cis_admin_token` cookie server-side (`requireAdmin()`) and
    injects `X-Admin-Secret` itself. No new proxy route needed.
  - `frontend/app/(internal)/upload/page.tsx` — `getToken()` was only ever used as an
    existence-guard (`if (!token) return;`) in `fetchSources()`/`runPipeline()`, and as a fully
    unused parameter threaded into `uploadOne()`. Every actual `fetch()` in this file already goes
    through `/api/tenant/*` or `/api/admin/*` proxies. Left as-is the guards would have permanently
    short-circuited both functions once `cis_api_token` stopped being set (page silently stops
    loading sources / running the pipeline). **Fixed** — removed the dead guards/param entirely
    (not routed through a token check at all — the proxies already gate on the httpOnly cookie).
  - `frontend/app/(internal)/catalog/page.tsx` — `getToken()` feeds an `Authorization` header to
    `/api/tour-full/[id]/route.ts`, which **ignores the incoming header** and authenticates solely
    via `requireAdmin()` (httpOnly `cis_admin_token`). Already-dead code before this fix, no
    functional dependency — confirmed live below, **left untouched** (matches AA-427's own
    precedent of not touching adjacent dead code it happened to find).
  - `frontend/app/admin/pipeline/s1/page.tsx` — direct `fetch(${API_URL}/acp/s1/...)` calls,
    including a `?token=` query param on an SSE stream URL. Grepped the entire backend
    (`api/main.py`'s `include_router` list + every router file): **`/acp/s1/*` does not exist
    anywhere in the current backend** — only `v1_s1_from_atom_router` is registered, a different,
    newer route explicitly named to avoid colliding with "old S1". This page's backend calls are
    already 100% dead/broken regardless of this fix — confirmed via grep on origin/main, not fixed
    (pre-existing, unrelated bug; out of scope — flagging for a separate ticket if this page is
    still meant to be live).
  - Sidebar `logout()` (`InternalSidebar.tsx`, `AdminSidebar.tsx`) still try to
    `document.cookie = "cis_api_token=...max-age=0"` — now a harmless no-op (nothing to clear).
    Left as-is, no functional impact.
- **Content-role login branch untouched on purpose** — `login/page.tsx`'s cookie-setting is now
  guarded by `if (data.token)`, so it only fires when the backend actually returns one. Admin/
  reviewer logins no longer return `token` (this fix); the content-role branch
  (`/api/auth/login/route.ts`) still does (`{token: password, ...}`, unchanged) — that's a
  separate, already-flagged, already-accepted risk (AA-253's "content is unhardened by design"
  carve-out), not this issue's scope. The `if (data.token)` guard is what makes both cases correct
  with one line instead of branching on role.

## Changed

- `frontend/app/api/auth/login/route.ts` — admin/reviewer JSON response no longer includes
  `token`; only `{role, name, admin_id}`. `cis_admin_token` httpOnly cookie unchanged.
- `frontend/app/login/page.tsx` — `cis_api_token` cookie only set `if (data.token)` (now content-
  role only).
- `frontend/app/(internal)/review/page.tsx` — 3 direct-to-backend Bearer-token fetches → same-
  origin `/api/tenant/v1/pipeline/review-queue[...]` proxy calls; removed now-unused
  `getToken()`/`API_URL`.
- `frontend/app/(internal)/upload/page.tsx` — removed dead `getToken()`/`API_URL` + the token
  existence-guards in `fetchSources()`/`runPipeline()` + the unused `token` param on `uploadOne()`.

## Tradeoffs

- No new `/me`-equivalent endpoint (unlike AA-427's `/api/tenant/me`) — `cis_role`/`cis_user`
  stay plain, non-httpOnly cookies exactly as before. They're not secrets (role name + display
  name only), and 7+ existing call sites (`AdminSidebar.tsx`, `InternalSidebar.tsx`, `catalog`,
  `upload`, `review`, `brand` pages) already read them via `document.cookie` for UI display —
  converting all of those to a fetched `/me` was a much larger refactor than this issue asked for
  and orthogonal to the actual leak (the JWT), so left alone.
- Did not fix `catalog/page.tsx`'s or `s1/page.tsx`'s dead `getToken()` usages — no functional
  benefit (confirmed dead/already-broken respectively), smaller diff by leaving them.

## Should know

- **Found, not fixed (pre-existing, unrelated)**: neither admin sidebar's `logout()` clears
  `cis_admin_token` — it can't, that cookie is httpOnly, client JS was never able to clear it via
  `document.cookie = ...max-age=0`. This means clicking "Logout" today only clears the display
  cookies (`cis_role`/`cis_user`/`cis_api_token`) and redirects to `/login`, but the real httpOnly
  session cookie stays valid in the browser until its 24h expiry. This predates this fix entirely
  (`cis_admin_token` has been httpOnly since AA-232, long before AA-435) — not introduced or made
  worse here. AA-427 added a real server-side `/api/auth/tenant-logout` route for the equivalent
  tenant gap; admin has no equivalent. Flagging as a follow-up candidate, not fixing inline — this
  issue's literal scope is the JSON-body/duplicate-cookie leak, not session-lifecycle correctness.
- **Worktree hygiene**: the session that picked up this task found its previous git checkout
  (`fix/aa-518-llm-audit-followup`) 8 commits / 5 migrations behind `origin/main` (missing
  AA-514/AA-519, confirmed via `git rev-list --left-right --count HEAD...origin/main` and
  `api/migrations/` listing) — a stale-worktree situation the AA-520 backlog audit had just flagged
  as a live risk. Built this fix in a fresh `git worktree add ... origin/main` instead of continuing
  there; the stale branch's uncommitted, unrelated doc edits were left untouched, not discarded.
- `frontend/app/api/tour-full/[id]/route.ts` and `frontend/app/api/tenant/[...path]/route.ts` were
  already the correct pattern before this fix (both authenticate via `requireAdmin()`/httpOnly
  cookie, never a client-supplied token) — this fix's `review/page.tsx` change just brings that
  page in line with a pattern the rest of the app already used.
