# AA-531 — Blog gated by the wrong length threshold (shared with 7 short channels)

Linear: https://linear.app/aa-ecosys/issue/AA-531/t9bug-blog-bi-gate-chan-oan-vi-dung-chung-nguong-djo-dai-voi
Source: AA-525 Phần 13 (real data finding, 04/09/2026) — quoted verbatim in AA-531's description.

## STEP0 (confirmed against live code, 05/09/2026)

`services/acp_content_writing/quality_gates.py::gate_extreme_length()` (was lines 393-401,
`_MIN_CHARS`/`_MAX_CHARS` at 389-390 — line numbers matched the issue exactly, no drift) applied
ONE hardcoded pair (`_MIN_CHARS=20`, `_MAX_CHARS=6000`) to every channel unconditionally. Confirmed
channel-blind: the function took no `channel` parameter, and its only call site
(`run_quality_gates()`, line 770) passed just `length_check_text` with no channel argument, even
though `run_quality_gates()` itself already receives `channel` (used elsewhere in the same
function to gate the 3 blog-only DET gates and `gate_seo_surface`).

Real evidence (from AA-525 Phần 13 / this issue's own description): 3 real `content_piece` rows
for tenant `wanderlux-travel`, `channel='blog'`, held by `F4_extreme_length` at 6,679-7,266 chars
— all comfortably UNDER the real blog ceiling (2,200 words ≈ 13,000 chars per the origin repo
`aa-social-media`'s spec) but over AA-CIS-App's shared 6,000-char ceiling built for the 7 short
social channels.

## Changed

`services/acp_content_writing/quality_gates.py`:
- Added `_BLOG_MIN_CHARS = 4700` (~800 words) and `_BLOG_MAX_CHARS = 13000` (~2,200 words) —
  verbatim from the issue's own instruction (`~4,700-13,000 chars`), itself derived from the
  origin repo's real 800-2,200-word blog spec.
- Added `_length_bounds_for_channel(channel) -> (min_chars, max_chars)`: returns the blog pair for
  `channel == "blog"`, otherwise the original shared `_MIN_CHARS`/`_MAX_CHARS` pair unchanged
  (covers all 7 short channels AND an unrecognized/`None` channel, so an unexpected value fails
  exactly the same way it always did).
- `gate_extreme_length(content_text, channel=None)` — new optional `channel` kwarg, default
  `None` so every pre-existing direct call (both in tests and any other caller) keeps the exact
  old shared-band behavior unless it opts in by passing a channel.
- `run_quality_gates()`'s one call site now passes `channel` through:
  `gate_extreme_length(length_check_text, channel)`.
- `_MIN_CHARS`/`_MAX_CHARS` themselves are UNTOUCHED (still `20`/`6000`) — the other 7 channels
  get byte-identical behavior to before this change, per the issue's own instruction (§2: "7 kênh
  còn lại: giữ nguyên... chưa có bằng chứng cần đổi").

`tests/unit/test_aa450_quality_gates.py` — 6 new tests in `TestGateExtremeLength`:
- `channel=None` (the default) still fails at 7,000 chars — confirms the fix did not silently
  widen the default band for every existing non-blog caller.
- `channel='blog'` at 7,000 chars now PASSES (this is exactly the real wanderlux-travel shape).
- `channel='blog'` below the new 4,700-char floor fails (the issue's own "phụ lưu ý": blog had no
  real floor before, now it does).
- `channel='blog'` above the new 13,000-char ceiling still fails.
- `channel='blog'` mid-band (9,000 chars) passes.
- A named non-blog channel (`'facebook'`, not just `None`) also keeps the shared 20/6000 band —
  confirms the dispatch is "blog vs. everything else", not "blog vs. only None".

## Decisions

- Scope held strictly to the length threshold, per the issue's own explicit instruction (§4): did
  NOT touch FAQ requirements, H2 structure gates (`gate_structural_variance`/`gate_faq_dedup`), or
  anything else in the blog-only gate group.
- Threshold selection is a small helper function (`_length_bounds_for_channel`) rather than
  inlining an if/else directly in `gate_extreme_length()` — keeps `gate_extreme_length()` itself
  readable and gives the dispatch logic one clear, independently-testable seam (mirrors the
  existing "gate functions stay channel-agnostic where possible, dispatch decided by the caller"
  convention already used for the 3 blog-only DET gates in `run_quality_gates()` — though here the
  channel decision lives one level down, inside the gate itself, since F4 already existed for
  every channel and only its THRESHOLD needed to vary, not whether it runs at all).
- `channel` defaults to `None` rather than being made a required positional arg (unlike
  `run_quality_gates()`'s own `channel`, which AA-452 made required) — `gate_extreme_length()` has
  a real, still-valid usage without channel context (any code checking "is this empty/broken"
  generically), and making it required would have forced a channel argument onto every existing
  test/call site for no benefit. This is a narrower, single-function scope decision, not a
  precedent for other gates.

## Tradeoffs

- Did not generalize this into a full "per-channel gate config" system (e.g. a dict of channel ->
  thresholds for ALL gates) — no evidence any other gate needs per-channel tuning right now (per
  AA-525 Phần 13's own finding, this was specifically and only the length gate), and a bigger
  refactor risks touching code outside this issue's stated scope.
- Real blog-content evidence for the exact 4,700/13,000 boundary values comes from the issue text
  itself (ported from the origin repo's spec), not independently re-derived from a second source
  in this task — treated as authoritative per the issue's explicit instruction, not re-litigated.

## Should know

- `gate_extreme_length()`'s signature changed from `(content_text)` to
  `(content_text, channel=None)` — backward compatible (default keeps old behavior), but any new
  caller checking blog content specifically should now pass `channel="blog"` explicitly or it will
  silently get the wrong (too-narrow) band.
- Live-verify (see "Live Verify" section below, added once run against real dev RDS) re-runs
  `gate_extreme_length()` directly against the 3 real persisted `content_piece.content_text`
  values for `wanderlux-travel` blog pieces — confirms old threshold held them, new threshold
  passes them, no content rewrite needed.

**Important disclosure — a real finding, not silently omitted**: fixing `F4_extreme_length` does
NOT flip pieces 1 and 2 from `held` to `approved` on its own, and piece 3 was **never** actually
blocked by length at all (5,954 chars was already under the old 6,000-char cap). The FULL
persisted `gate_ledger` for attempt 2 of each piece (inspected directly, not just the single
`held_reason` summary field) shows:
- **Piece 1** (`8b2562a1`, 6,679 chars) — 7 gates failed in the real ledger: `F1_grounding`
  (the piece's own `held_reason` — a fabricated "5" not present in the atom source),
  `F4_extreme_length` (fixed by this PR), `F4_seo_surface` (keyword not in title/meta),
  `F5_atom_density`, `F3_structural_variance`, `F7_faq_dedup`, `F9_brand_voice`
  (SUMMARY_OFF_BRAND, real quoted phrases). `F1_grounding` runs BEFORE `F4_extreme_length` in
  `run_quality_gates()`'s fixed order, so it — not the length gate — is what `held_reason`
  surfaces; `F4_extreme_length` was a real, independent, ALSO-failing blocking gate on this piece,
  confirmed via the raw ledger, not inferred.
- **Piece 2** (`319bd3d8`, 7,260 chars) — 5 gates failed: `F1_grounding` (own `held_reason`,
  a fabricated "40"), `F4_extreme_length` (fixed by this PR), `F4_seo_surface`,
  `F5_atom_density`, `F3_structural_variance`.
- **Piece 3** (`22bf0d6f`, 5,954 chars) — `F4_extreme_length` already `passed=true` in the real
  ledger even under the OLD threshold (5,954 < 6,000) — this piece's `held_reason` was always
  `F4_seo_surface` alone (plus a failing `F3_structural_variance`), completely unrelated to
  length under either threshold.

None of these other 6 distinct failing gates (`F1_grounding`, `F4_seo_surface`,
`F5_atom_density`, `F3_structural_variance`, `F7_faq_dedup`, `F9_brand_voice`) are in this issue's
scope — the issue's own §4 explicitly excludes FAQ/H2-structure changes, and none of the others
were named at all. Per the coordinator's own explicit instruction this session, `F4_seo_surface`
in particular was confirmed but deliberately NOT fixed here (out of scope). These 3 specific
`held` rows will keep showing `status='held'` after this deploy (T10's architecture caps a piece
at 1 repair attempt — `attempt_number=2` here is already the final state for each of these 3
rows; nothing re-runs quality gates on an already-held row) — this PR's live-verify target was
always "does `gate_extreme_length()` itself now pass on their real content" (the issue's literal
instruction, confirmed word-for-word not requiring a content rewrite), not "do these 3 specific
historical rows flip to approved," which would need unrelated fixes to grounding/SEO-surface/
atom-density/structural-variance/FAQ-dedup/brand-voice this issue never asked for. The real,
durable effect of this fix is on every FUTURE blog write: a new attempt no longer gets an
extreme-length false-positive at the ~half-of-spec ceiling this issue found.
