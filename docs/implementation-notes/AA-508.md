# AA-508 — Atom identity content-hash + per-day fingerprint-skip + real UPSERT

Sub-issue #1 of epic AA-507 (T5-T11 redesign per aa-social-media, Ms. Thư). Segment (AA-509,
next sub-issue) needs a stable `atom_id` across re-runs to work at all — this is that
foundation. STEP0 evidence: `docs/claude_audit/AA-508-step0-atom-identity-investigation.md`,
`AA-508-step0b-upsert-vs-new-verification.md`.

## STEP0 addendum — FK/blast-radius enumeration (done before touching anything)

Grepped every migration for `REFERENCES.*tour_atoms` and every `atom_id`-bearing column.
**Zero DB-level FK constraints anywhere in this schema point at `acp_contract.tour_atoms
(atom_id)`** — confirmed via full grep, not inferred. `atom_id` is held as free app-level state
in:
- `acp_contract.tour_atoms.atom_id` — the PK itself (migration 079).
- `acp_shared.angle_gate_request.atom_id` — `TEXT NOT NULL`, no FK (migration 113).
- `acp_shared.acp_v2_slots.payload->'atom_ids'` — JSONB array, no per-item FK possible
  (migration 096).
- `acp_shared.content_piece` has no direct `atom_id` column — reaches it only indirectly via
  `angle_gate_request_id → angle_gate_request.atom_id`.

Migration 098's own comment independently confirms this was a deliberate prior decision ("No FK
to acp_contract.tour_atoms — grain is tour_id, not atom_id"), not an oversight this task is
the first to notice. Per the build prompt: **no `ON DELETE CASCADE` was added anywhere in this
change** — that stays a separate decision, not made here.

## Decisions

1. **`atom_id` formula adapted from the literal spec, not copied verbatim.** The build prompt's
   given formula (`f"{trip_code}|{day}|{normalise(place)}|{normalise(action)}"`) assumes
   `place`/`action` fields that do not exist in this schema — `atom_extraction.py`'s
   `SYSTEM_PROMPT` (AA-299, unchanged by this task) extracts one combined `text` field
   (the verbatim moment) plus a coarse `activity_type` enum, never split place/action pairs.
   Used `text` instead (it IS the place+action pair, just not split into two fields the way
   aa-social-media's extractor happens to return them). See `content_hash_atom_id()`'s own
   docstring (`services/acp_shared/atom_extraction.py`) for the full reasoning.
2. **Added `owner_scope` (tenant_id) to the hash input** — absent from the reference formula
   because that repo has no multi-tenant concept (one SQLite file per brand). `tour_atoms.
   atom_id` here is one GLOBAL primary key shared by every tenant that has ever rewritten a
   given `tour_id`; without owner_scope in the hash, two tenants' differently-worded rewrites of
   the same tour_id/day that happened to normalise to the same `text` would collide on that one
   PK and silently overwrite each other's row. Confirmed this is a real risk, not
   theoretical — `run_t5_atomize()`'s own pre-existing docstring already documents exactly this
   cross-tenant collision class for the OLD source_hash lookup.
3. **Dropped the `atom_` string prefix** on the new content-hash ids (kept only on the legacy
   whole-tour path's random ids, unchanged) — the build prompt's own literal formula has no
   prefix, and migration 079's original reason for the prefix (`[R:atom_id]` citation tag
   matching) doesn't actually require it: `ATOM_CITE_RE = re.compile(r"\[R:([^\]]+)\]")`
   (`services/acp_produce/atom_usage.py`) is fully generic, confirmed via grep before making
   this call.
4. **Fingerprint table keyed on `tenant_tour_version_id`, not `(tour_id, owner_scope)`** — per
   the build prompt's own given schema. A new tenant_tour_versions row is a genuinely new T4
   rewrite attempt that can reshuffle every day's wording even where the tenant asked for no
   change; STEP0b's own reference-repo measurement (forcing a re-read of unchanged content kept
   only 41% of prior atom_ids — the model re-worded the rest) means carrying a fingerprint over
   across versions would under-count what actually changed. A fresh version starts with zero
   fingerprint rows and reads every day once, same as a brand-new tour would.
5. **Days read SEQUENTIALLY, not concurrently** (deviation from aa-social-media's own 16-wide
   `ThreadPoolExecutor`). AA-418's own prior investigation (comment in
   `services/acp_produce/pipeline.py`, the AA-416 fix) found concurrent `invoke_claude()` calls
   unverified-safe on this codebase's Bedrock satellite setup (unverified acc3 quota under
   concurrency) — one call at a time keeps this inside the pattern already load-tested here,
   trading the reference repo's wall-clock speed for that. Explicitly not the reference repo's
   choice; this codebase's own precedent overrides it.
6. **Soft-delete, not hard-delete, for a day's atoms the current read no longer reproduces**
   (mirrors aa-social-media's `delete_missing()`, adapted to this table's existing convention —
   `tour_atoms.deleted`, already used by the admin PATCH soft-delete path, no hard-DELETE
   precedent on this table). Not explicitly requested by the build prompt's ordered steps, but
   added because an UPSERT alone, without this, would leave a day that shrank from 3 atoms to 2
   with 1 permanently-stale extra row and no mechanism to ever notice — the same gap STEP0b
   found already open (migration 084's own comment) for the whole-tour path. Confirmed live
   (see Live Verify below): the day-2 content-change run correctly soft-deleted the 2 stale
   day-2 rows from the prior read while creating 2 new ones, day-1 untouched.
7. **`starred` and `weight` are never touched by the UPSERT's `DO UPDATE SET`.** `starred` is a
   human curation flag (admin PATCH); `weight` is `content_metrics.py`'s own usage-log-derived
   learned value. Including either in the SET clause would silently erase both on every
   re-atomize that happens to touch that atom's row.
8. **`version_id` is optional, defaulting to `None`**, not a required new parameter. When
   omitted (or when `parse_canonical_itinerary_days()` can't parse the itinerary — returns `{}`,
   its own documented "cannot determine" signal, not "zero days"), `run_t5_atomize()` falls back
   to `_atomize_whole_tour_legacy()` — the pre-AA-508 function body, byte-for-byte, including its
   random `atom_` + uuid ids and whole-tour source_hash skip. This is what keeps
   `test_aa445_t5_distinctiveness.py` (both cases pass `itineraries=""`) passing unmodified —
   confirmed by running it, not assumed.

## Tradeoffs

- Sequential per-day LLM calls (Decision 5) means this codebase does NOT get the reference
  repo's "206 days in 69s" wall-clock number — a real tenant tour with many changed days will
  take roughly (changed days × one Sonnet call's latency) sequentially. Accepted because AA-418
  already found the alternative unverified-safe here; revisiting concurrency is a separate,
  explicit decision if wall-clock ever becomes a real complaint, not bundled into this task.
- The legacy whole-tour fallback path keeps its old gap (no cleanup of stale atoms when the atom
  count shrinks) unchanged — only the new per-day path got the soft-delete fix (Decision 6),
  since non-canonical content has no day boundaries to scope a cleanup query by. Not a
  regression; the old code already had this exact gap.
- No cleanup mechanism for atoms of a day number that disappears entirely from a SHORTENED
  itinerary (e.g. 10 days → 8). Investigated and deliberately not built: because the fingerprint
  table is version-scoped (Decision 4), a shortened itinerary in practice arrives as a NEW
  `tenant_tour_versions` row (T4 always creates a new version per rewrite), which starts with
  zero fingerprint rows and simply never asks for day 9/10 again — it does not need cleanup of
  an EXISTING version's rows the way aa-social-media's single-file-per-brand, edited-in-place
  itinerary model does. The OLD version's day-9/10 atom rows remain (same "old rows linger"
  precedent STEP0 already found pre-existing and unresolved, not a new regression from this
  task).

## Should know

- The one real call site (`api/routers/v1_tours.py::atomize_version()`) always has `version_id`
  in scope, so it always takes the new per-day path for any tenant whose T4 rewrite used the
  canonical itinerary format — which is every real T4 rewrite (T4 reuses T2's engine, `graph.py`
  `generate_node`/`_process_itineraries`, which always emits "Day N — Title\nBody"). The legacy
  fallback path is realistically only ever exercised by pre-AA-508 test fixtures or genuinely
  malformed/legacy content, not real traffic.
- `result["status"]` stays a 3-value contract (`success`/`failed`/`skipped`) at the endpoint
  boundary, same as before — a per-day run where SOME days fail and others succeed reports
  `"failed"` overall (with `result["days_failed"]`/`result["error"]` naming which), but the
  successful days' atoms and fingerprint rows are still committed and kept, not rolled back —
  confirmed live (see below). `atomize_version()`'s existing 502 + `escalate_t5_atomize_failure()`
  handling needed no changes to keep working correctly with this.
