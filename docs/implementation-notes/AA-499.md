# AA-499 — [AA-494 Decision 5] pgvector embedding for within/cross-tenant reuse

STEP0 was already answered by AA-520's audit (per this issue's own Linear description) — pgvector
v0.8.1 already installed (migration 041/AA-62), `content_piece.content_embedding vector(1536)`
already existed (migration 124) with 0 code reading/writing it. No infra-confirmation step needed
before starting.

## Decisions

- **Cross-tenant scope: relied on the already-Nghiệp-confirmed decision (Q6=B, 25/07/2026, AA-332
  origin, cited in AA-484's own Linear comment), did not re-ask.** This issue's own text says
  "cần xác nhận với Nghiệp, không tự suy diễn" about cross-tenant scope — but that confirmation
  already exists for the ONE cross-tenant use case this build enables (AA-484's blocking
  cannibalization gate). This build does NOT wire cross-tenant results into anything tenant-
  visible itself — `find_similar_pieces(cross_tenant=True)` is built as reusable infrastructure
  for AA-484 to consume, never called by any code in this issue. No new cross-tenant-facing
  behavior ships here, so nothing beyond the already-confirmed Q6=B needed re-confirming.
- **Consumption point (item 5's "T8 angle-gen or T7 atom-suggestion" choice): neither, built a
  third option — a non-blocking T10-adjacent flag.** Reasoned through both offered options:
  Decision 4 (AA-498) already covers "avoid repeating an angle for the SAME atom" via text
  history at ANGLE-GEN time, before any content exists to embed. Embedding similarity's real
  value is catching the DIFFERENT case — two DIFFERENT atoms for the same tenant converging on
  near-identical final content — which can only be checked AFTER a piece is written. Wired it as
  a `within_tenant_reuse` flag (ADR 0023's flag-not-block shape, same `content_piece.flags`
  column AA-519 built) appended in `run_write_background()` right after the gate loop concludes,
  `status == 'approved'` only — a pure metadata annotation on an already-decided outcome, not a
  new quality gate (`run_quality_gates()` is a synchronous, pool-free function; giving it DB+
  Bedrock access for one soft signal would be a bigger structural change than this issue's scope).
- **Threshold: reused 0.92 verbatim** (Nghiệp's own confirmed number for the cross-tenant
  BLOCKING gate, Q6=B) rather than inventing a second number for this softer, flag-only,
  within-tenant case — a shared threshold for the same underlying question ("is this a
  near-duplicate?") is more defensible than picking an arbitrary second one.
- **No new migration for the column** — `content_embedding` already existed (migration 124).
  **New migration 140** adds the missing ivfflat cosine index AA-484's own STEP0 comment already
  flagged as a real gap ("nếu chưa có index, query sẽ chậm dần") — added now, in the same build
  that starts actually populating the column, rather than deferred.

## Real, live finding that overrode this issue's own stated assumption

Migration 041/124's own comments both say "vector(1536) = Bedrock Titan Embed Text v2 output."
**Live-verify found this is wrong for this AWS account**: `aws bedrock list-foundation-models`
(checked on BOTH acc2 and acc3) shows Titan Embed is not offered at all — only
`cohere.embed-v4:0` (Cohere) is listed. Confirmed live: `invoke_model()` against
`amazon.titan-embed-text-v2:0` fails with `ValidationException: The provided model identifier is
invalid`. Switched to **Cohere Embed v4** (`us.cohere.embed-v4:0`, a cross-region inference
profile — the bare model id requires `INFERENCE_PROFILE` inference type, confirmed via
`aws bedrock get-foundation-model`), with `output_dimension: 1536` requested explicitly — same
class of "the plan assumed a model that turns out not to be available on this account" finding
this codebase has hit repeatedly for Anthropic/GPT models (AA-329/AA-351), now also true for
Titan Embed. **Lucky, not planned**: Cohere v4's requested output dimension still lands on
exactly 1536, so `vector(1536)` needed no change either way.

## Changed

- **New migration 140** — `idx_content_piece_embedding` (ivfflat, `vector_cosine_ops`, `lists=10`,
  same parameters migration 041's own 2 indexes use).
- **New** `services/acp_shared/content_embedding.py` — `compute_embedding()` (Cohere Embed v4,
  soft-fail on any error/malformed response → `None`) + `embedding_to_pgvector_literal()` (asyncpg
  has no `vector` codec — formats the Python list as pgvector's own text literal for an explicit
  `::vector` cast in SQL).
- **New** `services/acp_shared/piece_similarity.py` — `find_similar_pieces()`, the "shared
  mechanism, two call sites" migration 124's own column comment describes: `cross_tenant: bool`
  picks scope. No fixed threshold inside — the caller decides what counts as "too similar" (this
  build's own 0.92; AA-484 will bring its own call with its own confirmed threshold, currently
  the same number, but the function doesn't bake that in).
- `services/acp_content_writing/service.py` — `run_write_background()`: for `status='approved'`
  only, `compute_embedding(content_text)` (via `asyncio.to_thread`, same convention every other
  blocking Bedrock call here uses) → if a real embedding came back, `find_similar_pieces()`
  (within-tenant, excluding this piece, excluding same-atom matches) → a match ≥0.92 appends a
  `within_tenant_reuse` flag. `_finalize_piece()` gains `content_embedding` param, persisted via
  an explicit `$N::vector` cast.

## Tradeoffs

- Did not build any UI surfacing the new flag — `content_piece.flags` already has a real
  consumer contract from AA-519 (`gate_promises_an_option`'s own flag-not-block precedent); this
  adds one more flag value to that same, already-wired mechanism rather than inventing a new
  display path. No product ask for a dedicated UI treatment yet.
- Did not build a cross-account satellite fallback for the embedding call (unlike the Claude
  write/judge calls' AA-296/397 satellite chain) — Cohere Embed v4 is available NATIVELY on acc2
  (confirmed live, no "channel program accounts" block like Anthropic hits), so there's no known
  failure pattern to build a fallback for yet. Flagged for a future issue if one shows up.
- Did not backfill `content_embedding` for any pre-existing `approved` `content_piece` row — real,
  ongoing tech debt (existing approved pieces have no embedding, so they're invisible to
  `find_similar_pieces()` until they're rewritten or a backfill job runs) — out of this issue's
  own scope (item 4 only asks for "khi content_piece được approved" going forward), flagged not
  silently done.

## ⚠️ Real incident during live-verify — full disclosure

While testing `find_similar_pieces()` against real data, an early cleanup script scoped its
`DELETE FROM angle_gate_request` by `atom_id` instead of the exact `request_id` it had created.
`angle_gate_option`/`content_piece` both have `ON DELETE CASCADE` to `angle_gate_request`
(confirmed via `pg_constraint` after the fact) — the DELETE reported `DELETE 3` when only 1
throwaway row was expected, meaning **2 pre-existing `angle_gate_request` rows for a real atom
(`atom_00af646e46`, `wanderlux-travel`, created 30/08/2026) were deleted**, along with any
`angle_gate_option`/`content_piece` children they had (cascade — silent, no error either way).
Checked immediately after: `pg_constraint` confirms the cascade; a re-query for that atom shows 0
remaining requests. **What is NOT known**: whether those 2 rows had real generated content
(options/pieces) attached, or were themselves bare/abandoned test rows from an earlier session —
there is no way to recover this now (no soft-delete, no application-level audit log of the
deletion). This is a **dev-environment** table (`aa-cis-dev-db`), the tenant involved
(`wanderlux-travel`) is this codebase's own long-standing test fixture (used across dozens of
prior live-verify sessions, not a real paying customer), and the atom's own `owner_scope` traces
to that same test tenant — context that suggests low real-world consequence, but this is
context, not confirmation, and is stated as such, not as reassurance. **Fix applied
immediately**: the corrected script (used for the rest of this build's live-verify, including the
final integration check) tracks every created row's exact ID and deletes ONLY by that exact ID,
never by a broader match key. No further broad-match deletes were run. Nghiệp should decide
whether this atom's pre-08/30 history is worth investigating further (e.g., via RDS automated
backup / point-in-time recovery, if this warrants it) — flagged here, not silently absorbed into
"cleanup went fine."
