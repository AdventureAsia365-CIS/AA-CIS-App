## Tradeoffs

- The table's row 8 (Goal→Publish) is one row covering 6 pipeline stages, not 6 separate rows —
  every one of them shares the identical answer (tenant-owned, per-request, no cross-tenant
  mechanism except the one named F10 exception), so splitting them would add repetition without
  adding information. The issue's own "hoặc chia nhỏ nếu cần" gave room for this.

## Should know

- **The single most load-bearing new fact for the upcoming Admin/Tenant UI epic**: only 3 real
  cross-tenant mechanisms exist in the entire A0→T11 chain — the Master Content/Atom pool itself
  (the strongest form, a shared source, not a cache), the Search Demand cache, and Facts Entry's
  platform scope — plus one cross-tenant READ (not a cache), the F10 cannibalization gate.
  Everything else, including Segment/Score/Route/Hub/Slate/Subject, is 100% isolated per tenant.
  This directly answers the issue's own framing question: an admin monitoring UI needs a
  cross-tenant view for exactly those things (e.g. "how much has this keyword cost across every
  tenant") and a strictly per-tenant view for everything downstream of Segment — there is no
  middle ground to design for.
- `acp_contract.atomize_day_fingerprint` (migration 128) never had a `tenant_id` column even
  before AA-526 — its key (`tenant_tour_version_id`) was already an indirect tenant-scoping
  mechanism pre-AA-526 (one tenant's own rewrite-version UUID). Post-AA-526, that same column
  holds `generated_content.id` (a platform-wide A1 version id) for A3 atoms instead
  (`services/export/handler.py:246`) — correctly still no cross-tenant collision risk, but the
  column name is now a stale holdover worth knowing about if anyone touches this table again.
- Search Demand attribution (which tenant's research first bought a given cached row) is not
  tracked anywhere — flagged as a real consequence in ADR 0002, not built here (no current need).
