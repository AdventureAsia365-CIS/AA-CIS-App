# AA-498 — [AA-494 Decision 4] prior piece history in angle-gen prompt

STEP0 was already answered by AA-520's audit (see this issue's own Linear description) — no new
investigation needed. Confirmed live before writing code: `content_piece.content_summary`/
`content_embedding` (migration 124, 29/08) existed with 0 code reading/writing them; this build
is the first code anywhere to touch `content_summary`.

## Decisions

- **Summary generation timing: the SAME LLM call that writes the piece, not a second call.**
  Migration 124's own column comment already settled this ("generated by the same LLM call that
  writes the piece — near-zero marginal cost") — not re-decided here, just implemented.
- **Two extraction shapes, one per existing output contract.** The blog channel already returns
  a JSON envelope (AA-514) — added a `"summary"` key to it. The other 7 channels return plain
  text — added a trailing `===SUMMARY===\n<text>` marker line instead of restructuring their
  contract to JSON (a bigger, riskier change to 7 already-live channels for no real benefit).
  Both parsed by `generate.py` (`_parse_blog_envelope()`'s 3rd return value; new
  `_extract_summary()` helper for the marker). A single instruction block
  (`_SUMMARY_INSTRUCTIONS`) appended to `SYSTEM_PROMPT` covers both, so there's one place that
  explains the rule, not two.
- **Soft-fail everywhere, matching every other optional signal in this pipeline** (seo_meta
  fields, DFS/PAA `search_demand`): a missing/unparseable summary is `None`, never a reason to
  fail the write or hold the piece. Verified live twice — once as the common no-marker case in
  existing tests, once for real (Bedrock did produce a real summary both live-verify runs, no
  soft-fail path actually exercised live, but the code path is unit-tested).
- **Query joins via `content_piece.angle_gate_request_id` (always present), not
  `angle_gate_option_id`** (nullable, only populated since AA-497) — `angle_gate_request.atom_id`/
  `tenant_id` scope "same atom, same tenant"; a LEFT JOIN to `angle_gate_option` recovers the
  angle name where available. `tenant_id` is an explicit WHERE param even though `atom_id` alone
  already implies one tenant post-AA-475 (`owner_scope=tenant_id`) — matches
  `_fetch_atom_for_tenant()`'s own "never trust atom_id alone" convention elsewhere.
- **LIMIT 5** on the history query — a prompt-size guard, not a product decision; revisit with
  real usage data once atoms are realistically rewritten more than a handful of times.
- **No new migration.** Migration 124 already added both columns; this build only writes code
  that uses them.

## Changed

- `services/acp_content_writing/generate.py` — `_extract_summary()` (plain-text marker split),
  `_parse_blog_envelope()` gains a 3rd return value (`summary`). `write_content()`/
  `rewrite_with_feedback()` now return 4-tuples (`content, cost, seo_meta, summary`) instead of
  3-tuples — the one real breaking-shape change in this build, fixed at every call site (see
  Tests below).
- `services/acp_content_writing/prompts.py` — `_SUMMARY_INSTRUCTIONS` appended to `SYSTEM_PROMPT`
  (universal, all 8 channels); `_SEO_ENVELOPE_INSTRUCTIONS` gains a `"summary"` key.
- `services/acp_content_writing/service.py` — `run_write_background()` threads `summary` through
  the same "final attempt wins" convention `seo_meta`/`content_text` already follow;
  `_finalize_piece()` gains `content_summary` param, persisted in the existing UPDATE.
- **New** `services/acp_shared/piece_history.py` — `PriorPiece` dataclass + `fetch_piece_history()`.
- `services/acp_angle_gate/service.py` — `set_goal_and_generate()` calls `fetch_piece_history()`
  (same call site as `fetch_search_demand_signal()`, right before `generate_angles()`).
- `services/acp_angle_gate/generate.py`/`prompts.py` — `generate_angles()`/`build_user_prompt()`
  gain an optional `piece_history` param; SYSTEM_PROMPT gains one paragraph on how to use the
  block; omitted entirely when empty, same "no signal → no prompt noise" rule `search_demand`
  already set (AA-469 Việc 4).

## Tradeoffs

- Did not touch `content_embedding` (Decision 5, AA-499's own scope) — this build only populates/
  consumes `content_summary`.
- Did not backfill `content_summary` for any pre-existing `content_piece` row — there were 0 rows
  with a non-NULL value before this build (confirmed live), so there's nothing to backfill.
- `content_summary` is NOT added to `_row_to_dict()`'s whitelist — stays internal-only (never
  reaches any tenant-facing API response), matching the DB column's own "internal use only"
  framing. No product ask to surface it, so not exposed.
