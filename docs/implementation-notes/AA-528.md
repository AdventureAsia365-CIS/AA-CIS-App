# AA-528 — T9 gate-regression-guard (full rewrite breaking an already-passing gate)

## STEP0

Read `services/acp_content_writing/generate.py::rewrite_with_feedback()` (T9's attempt-2 call,
lines 179-217 at the time of this build) and its caller, `services/acp_content_writing/
service.py::run_write_background()` (the `for attempt in range(1, MAX_ATTEMPTS + 1)` loop,
`MAX_ATTEMPTS = 2`). Confirmed: attempt 2 is a full re-write from the same brief plus
`revision_feedback` (the first BLOCKING gate's own violation strings from attempt 1) — never a
targeted field patch. The loop keeps only the LATEST attempt's `content_text`/`gate_ledger`/
`seo_meta`/`summary` in scope (no memory of the previous attempt's own outcome once overwritten),
and only the FINAL attempt's full gate_ledger is ever persisted to `content_piece.gate_ledger` —
non-final attempts leave only a single-gate summary in `repair_log` (the first blocking failure
that triggered the retry), never their full ledger. This second fact matters for how this task's
live-verify works — see "Live-verify" below.

Also re-confirmed AA-537's finding still holds: `rewrite_with_feedback()` is untouched by AA-522/
526 — this bug and that refactor are independent, as the issue says.

## Decisions

- **Chose option (b) (revert-to-previous), not (a) (raise the attempt cap).** Both options were
  offered by the issue. (a) spends a real extra LLM call (cost) on every detected regression and
  still doesn't guarantee attempt 3 doesn't regress a *different* gate. (b) is free (both
  attempts' `gate_ledger`s are already computed by the time a decision is needed — this is a pure
  selection over data that already exists) and bounded (never more than the existing 2 attempts).
- **Regression is defined exactly as the issue's own proposal states it**: a BLOCKING gate that
  passed on the previous attempt and fails on this one. Implemented as a set difference between
  the two attempts' blocking-failing-gate-name sets (`cur_blocking_fail - prev_blocking_fail`).
  Deliberately does NOT treat "same gate still failing, different violation text" (case
  `319bd3d8`, below) as a regression on its own — the issue's own definition is pass→fail on a
  gate, not violation-content drift within an already-failing gate.
- **Revert condition adds one more term beyond the issue's literal example**: not just "any new
  regression", but "any new regression AND attempt 2 is not net-better on total blocking-failure
  count" (`len(cur_blocking_fail) >= len(prev_blocking_fail)`). This is the union of the issue's
  two illustrative phrasings — "1 gate pass→fail = regression" (option a's framing) and "revert
  if attempt 2 doesn't strictly improve (fails more gates)" (option b's framing) — combined so a
  rewrite that fixes 2 gates while breaking 1 new one (net improvement) is kept, not reverted.
  See `test_new_gate_failure_with_fewer_total_failures_does_not_revert` for this exact scenario.
- **Scope: `run_write_background()`'s own 2-attempt loop only.** `_run_buffer_retry_attempt()`
  (AA-498's separate one-shot buffer-retry mechanism, `service.py:618-682`) was read and
  deliberately left untouched — it's a different, already-reviewed design (Q5=C: "no retry of its
  own", writes to a brand-NEW `piece_id`, not the original held one) with no second attempt inside
  itself to compare against. AA-528 names `rewrite_with_feedback()`/T9's own loop specifically;
  extending the guard to the buffer-retry path (comparing against the ORIGINAL held piece's own
  ledger, fetched from a different row) would be a different, larger change outside this issue's
  scope.

## Changed

- `services/acp_content_writing/service.py`:
  - `run_write_background()`'s loop now snapshots the immediately-preceding attempt's own
    `content_text`/`gate_ledger`/`seo_meta`/`summary`/`embedding` into `prev_snapshot` right
    before a rewrite overwrites them.
  - After a failing attempt's `gate_ledger` is computed, a new block compares blocking-gate
    failures against `prev_snapshot` (when one exists). On a detected regression (see Decisions),
    it reverts every one of those fields back to the previous attempt's own values, appends an
    explicit `gate_regression_guard` entry to `repair_log` (audit trail — the attempt's OWN real
    failure entry is still appended first, unconditionally; the revert is a visible second entry,
    not a silent overwrite), and recomputes `first_failure` from the reverted (previous attempt's)
    ledger so the persisted `held_reason` matches what's actually being persisted.
  - Two `g["blocking"]` accesses use `.get("blocking", True)` (matching `quality_gates.py`'s own
    default) rather than a bare index — defensive against any gate_ledger entry that omits the
    key (this repo's own existing test fixtures for this file do, at `_failing_outcome()`).
  - Module docstring's "loop body itself is UNCHANGED [since AA-466]" line corrected — this is
    the first change to the loop's own decision logic since AA-466 moved it into a background task.
- `tests/unit/test_aa450_content_writing_service.py`: new `TestGateRegressionGuard` class, 4
  tests — modeled directly on the two real held pieces (see Live-verify), plus the "net
  improvement, no revert" and "approved attempt 2 never reaches the guard" edge cases.

## Tradeoffs

- The guard only ever sees FULL gate ledgers for attempts still in the SAME `run_write_background()`
  call (in-memory, never persisted per-attempt) — it cannot retroactively fix a piece already held
  under the old code (the issue's own scope explicitly excludes this: "Không cần xử lý retroactive
  5 piece đang kẹt held hiện tại", deferred to AA-495's full data reset).
- Reverting on a "same total count, different gate" trade (e.g., attempt 2 fixes gate A but
  breaks new gate B, count unchanged 1-for-1) DOES trigger a revert under this implementation
  (`new_regressions` non-empty, `cur >= prev` true when equal) — arguably conservative, but this
  was judged the safer default per the issue's own "ưu tiên an toàn hơn tốc độ" instruction on
  AA-535 and the general spirit of AA-528 (never trade a known problem for an unknown one).
- Case `319bd3d8` (same gate, different violation) is deliberately NOT reverted. Reverting there
  would not change the outcome (both attempts still fail F1_grounding — the piece is held either
  way) and would remove real audit signal (attempt 2's actual fabricated-number text) for no gain.

## Should know

- `MAX_ATTEMPTS = 2` is unchanged — this fix does not add a 3rd attempt. A piece that regresses on
  attempt 2 now ends up held with attempt 1's OWN content/reason (cleaner signal for a human or a
  future automated repair), not attempt 2's compounded one — but it is still held, not rescued
  into approved. The issue's own stated goal is exactly this: stop the mechanism from making a
  held piece WORSE, not guarantee every held piece becomes approvable.
- `prev_snapshot["embedding"]` is also reverted alongside content — AA-484/499's cannibalization/
  reuse checks run per-attempt on that attempt's own content, so persisting attempt 2's embedding
  next to attempt 1's content would have been a real, if minor, data-consistency bug.

## Live-verify

Real, unmocked `run_quality_gates()` was not re-run against these two pieces' original raw text
(the DB never persisted attempt 1's raw content_text for either — only the final attempt's, per
STEP0's finding above — and a fresh Bedrock call cannot deterministically reproduce either
piece's original failure). Verification instead uses the ACTUAL, unmocked `run_write_background()`
orchestration (only the two LLM-call functions `write_content`/`rewrite_with_feedback` are
stubbed to return fixed text — the same test-doubling convention this file's existing test suite
already uses for this exact function), fed the REAL gate names, REAL violation strings, and REAL
`held_reason` text copied verbatim from `acp_shared.content_piece` for both pieces (fetched live
via the S3-mediated ECS-exec pattern, real RDS, `aa-cis-dev-db`):

- **`8b2562a1-e812-4d67-87af-017172581d9d`** (blog, tenant `wanderlux-travel`): real stored
  `repair_log` shows attempt 1 failed only `F4_extreme_length` (7135 chars); the real, persisted
  `gate_ledger` (attempt 2's, the only one ever stored) shows attempt 2 STILL failing
  `F4_extreme_length` (6679 chars) plus a NEW `F1_grounding` failure never present before.
  `test_new_blocking_gate_failure_reverts_to_attempt_one` reproduces this exact shape (same 2
  gate names, same "1 failure → 2 failures, one new" pattern) through the real orchestration code
  — confirms the new code path reverts to attempt 1's content/ledger and persists
  `held_reason="F4_extreme_length: ..."`, not the compounded attempt-2 reason. Before this fix,
  the real persisted row shows the OLD behavior: `held_reason` was the NEW, worse
  `F1_grounding` failure, and `attempt_number=2`'s content (with the new problem) was what
  actually got persisted — exactly the bug this closes.
- **`319bd3d8-af9b-4820-8b90-695210138e17`** (blog, same tenant): real stored `repair_log` shows
  BOTH attempts failed `F1_grounding`, different violation text each time (attempt 1: numbers
  `['000','1']`; attempt 2: a different fabricated `'40'`). `test_same_gate_different_violation_
  does_not_revert` reproduces this shape — confirms the guard correctly does NOT revert here
  (same gate, not a new one), and attempt 2's own output is kept — matching this piece's real,
  unaffected outcome (still held on `F1_grounding`, just as it is live today).
