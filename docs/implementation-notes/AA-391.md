## Decisions

- **File location**: `tests/verify_scripts/aa391_e2e_orchestrator.py`, not the issue text's own
  suggested `scripts/e2e_test_orchestrator.py`. This repo's established convention for this exact
  kind of real-DB, real-Bedrock, non-CI verify script is `tests/verify_scripts/aaNNN_*.py`
  (ADR-2026-037) — AA-364/367/375/376/377/378 all used it. Following the existing convention
  rather than the issue text's guess, same STEP-0 discipline AA-377 itself modeled ("Slot
  phu thuoc run... khop dung signature slot_runner.py da viet").
- **Destination scoping mechanism**: filter the real `Trip` list (`fetch_trips()`) to
  `destination IN ('Laos', 'South Korea')` in Python, BEFORE calling the pure
  `compute_runway_map()`/`compute_quarter_plan()` functions — not via `specials` (force-include
  only, doesn't exclude other destinations) and not a bespoke SQL WHERE clause on
  `v_trip_registry` only this script uses. The script asserts after the fact that
  `quarter_plan.trip_ids` is a subset of the filtered trip_ids, so destination-scoping is a
  verified property of the run, not just an intention.
- **Gate A: skipped, not mocked.** `aa_internal` is confirmed live (STEP 1 of the script) to be a
  pre-existing `is_active=true` tenant — Gate A (`POST /admin/tenants/{id}/gate-a/approve`) exists
  to flip a brand-new tenant's `is_active` false->true during N1 onboarding. Nothing in
  `services/acp_planning/*.py` reads `acp_shared.tenant_onboarding`/Gate A state (confirmed by
  reading every N4-N6 module) — N4-N6 depend on `shared.tenants` and `quarter_plan_version`, not
  on onboarding status. Mocking a gate that isn't in the dependency path would be theater, not
  verification.
- **Gate B: real persisted path, not the in-memory bypass.** Prior verify scripts
  (`aa377_aa378_run_persist_verify.py`) set `quarter_plan.approved = True` directly in memory —
  sufficient for THEIR scope (proving persistence/slot-runner mechanics), but AA-391 explicitly
  asks to prove the real Gate B DB flow. This script calls the real
  `save_quarter_plan_version()` + `approve_quarter_plan_version(version_id, approved_by=
  "TEST_MODE_SCRIPT", pool)` — the exact same functions `POST /admin/quarter-plan` and
  `POST /admin/quarter-plan/{version_id}/approve` call. `approved_by="TEST_MODE_SCRIPT"` is
  written literally into the DB row per the issue's own explicit requirement (never a real name).
- **Gate C / BOFU-pricing**: neither has any code to interact with. Gate C (AA-365) is confirmed
  still 0% code (Backlog) — `deliver_packet()` has no Gate C call. BOFU/pricing classification
  does not exist anywhere in `services/acp_produce/*.py` or `services/acp_planning/*.py` (grepped,
  zero matches) — there is no gate to accidentally auto-approve. Both are recorded as real,
  reportable gaps for whoever builds AA-365 next, not silently worked around here.
- **N3 curation**: implemented as a TEST_MODE bulk auto-star (`UPDATE ... SET starred = TRUE`)
  across every live atom for the Laos/Korea trips, rather than a no-op. Reading
  `fetch_curated_atoms()`/`_eligible_atoms()` confirms `starred` is a weighting signal for N6, not
  a hard membership gate (only `NOT deleted AND NOT is_empty_marker` gates eligibility) — so this
  step is not strictly required for the chain to proceed, but auto-starring exercises the N3 step
  literally, as the issue text allows ("có thể auto-star/approve atom trong TEST_MODE nếu cần").
- **Week scope**: only week=1 of the current month is allocated+produced live. Real Bedrock
  Sonnet + Nova Pro judge + DataForSEO calls stack up fast across weeks x channels x repair
  rounds (AA-367.md's own baseline: up to 6 full attempts for ONE passing piece before repair_fn
  existed). This is a live-run cost-scope decision, not a code limitation — the same
  `allocate_and_persist_week()` mechanism covers weeks 2-4 unchanged.
- **No cleanup.** Every prior ADR-2026-037 verify script deletes its rows because those scripts
  used synthetic/hand-constructed fixtures or forced a single test slot. This script's entire
  purpose is producing real content for real Laos/South Korea tours under the real `aa_internal`
  tenant — the atoms, S1 content, quarter plan version, slots, pieces, and packet it creates are
  real production artifacts, left in place deliberately.

## Real-publish block — confirmed, not assumed

`grep -rniE "wordpress|wp[-_]?api|facebook.*graph.*api|instagram.*api|tiktok.*upload|publish_to|
send_to_tenant|social.*publish|cms.*publish" services/ api/` returns **zero matches** outside
docstrings/tests. `packets.py::deliver_packet()` — the only function anywhere that sets
`packets.status='delivered'` — only calls `write_usage_log()` (internal DB write) and updates
`packets.status`/`delivered_at`; no HTTP call of any kind. `set_publish_mode()` additionally
hard-blocks any `publish_mode` value other than `'propose_only'` via `PublishModeBlockedError`
(AA-364 decision, unrelaxed). This script never calls `set_publish_mode()`. Conclusion: there is
currently no code path in this repo capable of a real publish — nothing exists to comment out or
feature-flag. The script still asserts `publish_mode == 'propose_only'` on the final packet row as
a live, non-assumed check.
