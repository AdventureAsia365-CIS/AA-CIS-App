# AA-356 — entailment checker false-positive on structural day number (blocker for AA-353 resume)

Surfaced during AA-355's live VERIFY (S132, 01/08/2026): tour `608c5083` (22 atoms / 12 source
days) correctly got a `DAY 1:`...`DAY 12:` grouped atom pack and a correct "exactly 12 day-block(s)"
instruction — but the model responded by restructuring `aa_itineraries` into a list of
`{'day': N, 'title': ..., 'prose': ...}` dicts, which `OUTPUT JSON FORMAT` didn't declare. The
existing entailment checker then flattened each dict via `str(dict)` and flagged the bare day
number (`'day': 1` → novel_numbers=['1']) as an ungrounded numeric claim, failing all 3 retries
with `GroundingError`. Not an AA-355 bug per se — a pre-existing gap in how `s1_from_atom.py` feeds
text into the shared `services/acp_shared/grounding.py` checker, only exposed once AA-355 gave the
model day-structure to react to.

## Decisions
- **Did not touch `services/acp_shared/grounding.py` at all** (verified via `git diff --stat`,
  clean) — per the issue's explicit caution around ADR-2026-033's tested fabrication-detection
  logic (prior history: a threshold miss-tune once caused 7/11 missed violations + 56/96
  false-positives). The bug isn't in the number-detection regex — it's that `s1_from_atom.py` was
  feeding a Python dict's `str()` repr into it as if it were prose. Fixed entirely at that boundary.
- Both technical options from the issue turned out to be needed, but not as originally framed —
  instead of choosing "declare format" vs "harden checker", the actual fix is: (a) declare the
  `aa_itineraries` array-of-`{day, title, prose}` shape in `OUTPUT JSON FORMAT` (formalizes what the
  model already spontaneously produced), and (b) add `_itinerary_prose_texts()` — a boundary
  function in `s1_from_atom.py` that extracts only `title`+`prose` text for the citation/density/
  entailment gates, explicitly never passing the structural `day` int through. `grounding.py`'s own
  `_DAY_LABEL_RE` (which already exempts natural-language "Day N:" labels inside flat prose) is
  untouched and still does its job for the flat-string fallback path — my fix is orthogonal, at the
  s1_from_atom.py boundary, not a change to that regex.
- Kept `aa_itineraries` as a single consistent contract (always array-of-day-block, `day` nullable)
  rather than branching the OUTPUT JSON FORMAT by whether atoms are dated — simpler downstream
  parsing, and `_itinerary_prose_texts()` already has a flat-string fallback for models that don't
  comply, so there's no hard requirement on the model actually returning the array shape.
- Checked all downstream consumers before deciding this was low-risk to reshape:
  `services/acp_produce/judge_client.py`, `gates.py`, `brand_audit_node.py`, `judge_node.py` — none
  reference `aa_itineraries`. `api/routers/v1_s1_from_atom.py`'s `/generate` endpoint returns
  `result["content"]` straight through as JSON with no persistence to `generated_content`/
  `published_tours` (per the module's own docstring: "Runs PARALLEL to old S1... nothing here
  touches silver_aa_internal.generated_content or the old S1 tables"). No downstream code needed
  changes.
- Deliberately did NOT add a new deterministic day-count gate (comparing day-block count in the
  output against the DAY groups shown) even though the data is now available for it — out of scope
  per the issue ("KHÔNG mở rộng thêm ngoài phạm vi 2 việc trên").

## Changed
- `services/content_generation/s1_from_atom.py`:
  - `build_user_prompt()` — `OUTPUT JSON FORMAT`'s `aa_itineraries` now documents the
    `[{day, title, prose}]` array shape instead of a flat string.
  - New `_itinerary_prose_texts(val)` — extracts title+prose text only, from either the new array
    shape or a legacy flat string; never surfaces the `day` field as text.
  - `_flatten_gated_text()` and `_entailment_violations()` — both route `aa_itineraries` through
    `_itinerary_prose_texts()` instead of blind `str(v)` stringification.
- `tests/unit/test_aa306_s1_from_atom.py` — 10 new tests: `_itinerary_prose_texts` (array
  extraction excluding day, multi-block, flat-string fallback, empty/None), `_flatten_gated_text`
  excludes bare day number, `check_grounding` doesn't false-positive on the exact reported bug
  shape, **and** still catches a real fabricated number in day-block prose and in a day-block title
  (regression safety net for ADR-2026-033's actual job), `_entailment_violations` direct-call
  parity, and `build_user_prompt` declaring the new array format.

## Tradeoffs
- One test (`..._in_day_block_title`) initially failed for a reason worth recording: entailment
  only examines *cited* sentences (a sentence with no `[R:atom_xxx]` tag is never checked for novel
  numbers — nothing to validate it against). Fixed the test to put the citation tag on the same
  sentence as the fabricated number, matching how `_SENT_SPLIT_RE`/`CITE_RE` actually pair claims to
  citations elsewhere in this file. Not a code bug — a test-design correction.
