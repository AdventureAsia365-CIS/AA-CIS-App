# AA-370 — E1 Outline (deterministic) + E2 Draft (Sonnet acc1 satellite, batched)

## Decisions
- **`generation.py` is the module name**, not a new choice — `judge_client.py`, `pipeline.py`,
  `reliability.py`, `sweeper_lambda.py`, `packets.py`, `rule_adapter.py` all already forward-reference
  "E1-E5 generation" / `generation.py` by name as the anticipated writer module. Both E1
  (`build_outline`) and E2 (`generate_draft`) live in it together, matching those docstrings'
  grouping of "E1-E5 (the writer call that produces `piece.body_tagged`)" as one unit.
- **E1 does not call an LLM.** `Brief.required_h2s` + `Brief.atoms_by_section` (both already
  deterministic, built by AA-369's `compile_brief()`) are read as-is; the per-section `goal` is a
  template string (`"Cover N supporting fact(s) for '<title>'"` / FAQ variant / empty-atom variant).
  Verified in `test_build_outline_never_calls_bedrock` — `invoke_claude` is patched to raise if
  called at all.
- **Writer model is Bedrock satellite acc1 Sonnet, `model="sonnet"`** — confirmed as the closed
  decision (not a proposal) by re-reading AA-334 live via the Linear MCP tool before writing any
  code: AA-334 (the bake-off issue) is **Canceled** as of 06/08/2026 with an explicit sign-off note
  ("Nghiep xác nhận trực tiếp: Palmyra X5 không dùng được ... chuyển thẳng sang Bedrock satellite
  acc1 Sonnet, không qua bake-off"). Grepped `generation.py` for "Palmyra" after writing it — the
  only hits are in the module docstring explaining why it must never appear in code, not an actual
  usage.
- **Section batching is 2-3/call via a balanced chunker** (`_batch_sections`), not naive `chunks of
  3 with a possible trailing chunk of 1` — `divmod`-based sizing so e.g. 5 sections → `[3, 2]`, 7 →
  `[3, 2, 2]`, never a lone straggler batch. Directly implements the AA-353/357 lesson cited in the
  issue text ("tránh lặp lại lỗi kiến trúc compression đã sửa ở AA-353/357 cho S1").
- **Headings are inserted by code from the outline, never written by the model** — same principle
  AA-353 already applied to itinerary day-titles ("day-title formatting no longer trusted to the
  model"). The model is told to mark section boundaries with a machine-parseable
  `===SECTION:<title>===` line instead of writing a real heading; `generate_draft()` strips those
  markers and substitutes `## {outline_title}` itself.
- **`[F:fact_id]` is not offered to the model at all** — `Brief.facts_ids` is always empty (AA-369
  scope: no Facts pack exists anywhere in this repo) so the tag would have nothing real to
  reference. The system prompt explicitly says "Do NOT use [F:...] tags". `gates.py::TAG_RE` still
  matches both `R` and `F` (unchanged, no need to touch F1) — E2 simply never emits `F`.
- **Reused `services.content_generation.brand_standards.AA_BRAND_IDENTITY_PROMPT`** (S1's real brand
  rubric — voice, forbidden words, CTA line) as the base of the E2 system prompt instead of writing a
  second brand-voice text that could drift from it. Confirmed via grep this is the one real shared
  brand constant in the repo (`shared.tenant_brand_rules` is a DB table used by F9's audit judge, a
  different mechanism — not duplicated here either).
- **Retry: bounded, not a generic framework.** `_invoke_sonnet_with_retry` does up to
  `_MAX_INVOKE_ATTEMPTS = 3` attempts (1 original + 2 retries, per the issue's own "retry tối đa 2
  lần") with a short linear backoff (`2s * attempt`), then raises `DraftGenerationFailed` — mirrors
  AA-353's `_nudge_itinerary_day()` "exactly one attempt, caller never retries" shape, just with the
  attempt count the issue asked for instead of AA-353's 1.
- **Unparseable Sonnet output is treated the same as an invoke failure** — if the marker count in the
  response doesn't match the requested section count, `generate_draft()` raises
  `DraftGenerationFailed` rather than guessing a partial mapping or emitting an empty section body
  (issue text: "không viết section rỗng giả").

## Changed
- `services/acp_produce/models.py`: new `OutlineSection` model (`title`, `atom_ids`, `goal`) — E1's
  output type, placed next to `Brief` per this file's existing "shared types" convention.
- `services/acp_produce/generation.py` (new file): `build_outline()` (E1), `generate_draft()` (E2),
  `DraftGenerationFailed` exception, plus private helpers (`_batch_sections`, `_build_batch_prompt`,
  `_invoke_sonnet_with_retry`, `_parse_batch_response`, `_section_goal`).
- `tests/unit/test_aa370_generation.py` (new file, 12 tests): E1 no-LLM-call + goal templating, E2
  single/multi-batch happy path, retry-then-succeed, retry-exhausted, unparseable-response, empty
  outline, and 2 tests running the real `gates.py::gate_grounding()` (F1, unchanged from AA-298)
  directly against E2-shaped output — one grounded (passes), one with a fabricated number in a
  `[R:atom_id]`-tagged sentence (fails, same entailment check AA-298 already ships).

## Tradeoffs
- **`generate_draft()` is a synchronous function that blocks on `invoke_claude()`** (itself
  synchronous), same as `research.py::build_gap_statement()`'s existing pattern for the Haiku
  gap-statement call — not wrapped in `run_in_executor`. E2 does more sequential calls with bigger
  prompts than gap_statement's single small one, so the blocking window is longer; flagging this as
  a known cost of following the established pattern rather than introducing a new one unasked. If a
  future caller finds this blocks the event loop unacceptably, wrapping the batch loop in
  `asyncio.to_thread` is the straightforward fix — not done here since nothing in AA-370's scope
  asked for it and no real caller (the slot-runner/orchestrator) exists yet to measure the impact on.
- **Not wired into any real slot-runner.** AA-370's scope is E1+E2 only; there is still no orchestrator
  in this repo that calls `fetch_slot_atoms()` (AA-369) → `build_outline()` → `generate_draft()` →
  `Piece(...)` → `run_piece_through_produce_gates()` (AA-364) end-to-end for a real slot. `Piece`
  construction from `generate_draft()`'s return value is a one-line `Piece(piece_id=..., body_tagged=
  draft)` — deliberately not wrapped in a helper function here (would be a premature abstraction for
  a single line with no second call site yet).
- **AA-369's "overflow atoms all land on the last section" quirk (flagged in AA-370 STEP 0) is left
  unfixed**, on purpose: `build_outline()`'s explicit input contract is `Brief` alone (per the issue's
  own step-1 spec — atom_ids come "từ Brief.atoms_by_section[title] nếu có khớp"), and the overflow
  behavior is baked into `atoms_by_section` before `build_outline()` ever sees it, inside
  `research.py::compile_brief()` (AA-369, a different completed issue). Fixing it from *inside*
  `build_outline()` would mean either re-deriving atom-to-section assignment from the raw atom list
  (a different input contract than what the issue specified) or reaching into and editing AA-369's
  completed code under a different issue's scope — neither felt like "sửa dễ trong phạm vi E1" as the
  issue's own escape hatch worded it, so left as-is per that same instruction's fallback ("để nguyên
  và ghi lại đề xuất fix riêng"). **Proposed fix for a follow-up issue:** in
  `compile_brief()`'s `atoms_by_section` loop (`research.py` line ~284-287), replace `required_h2s[min(i,
  len(required_h2s) - 1)]` with a round-robin (`required_h2s[i % len(required_h2s)]`) or
  "assign each atom to the section it's already listed for in `required_h2s[1:4]`, spill the rest
  round-robin across the non-FAQ sections" — either avoids all overflow silently landing in FAQ.

## Should know
- `_batch_sections()` degenerate case: a 1-section outline produces one batch of size 1 (nothing to
  balance against) — this is fine, it's still exactly one Sonnet call for the whole draft in that
  case, not a violation of "avoid 1-call-whole-piece" (there's only 1 section total).
- `max_tokens` per batch is computed from `Brief.word_range`'s midpoint spread evenly across
  `len(outline)` sections, times the batch's own section count, with a `1.6` words→token multiplier
  and a 150-token headroom, clamped to `[512, 4096]` — the `4096` ceiling matches the existing
  JSON-truncation-bug fix ceiling already used elsewhere in this repo (`CLAUDE.md`: "max_tokens =
  4096 (NOT 2000)"), not a new number invented for this issue.
- `atom_text_by_id` (this module's own input type) is exactly the shape
  `pipeline.py::run_piece_through_produce_gates(text_by_id=...)` already expects, and
  `set(atom_text_by_id)` is its `valid_ids` — confirmed directly by running `gates.py::
  gate_grounding()` against real E2-shaped output in the two grounding tests, not just asserted from
  reading the regex.
- **Live smoke test WAS run** (06/08/2026, real Bedrock Sonnet acc1 satellite calls via S3-mediated ECS
  exec, real DB atoms — tour `b4d315a6-21cb-4d2b-9a2f-9d654388078a`, "Northern India: Riverside
  Safaris, Ancient Fortresses & The Taj Mahal", 6 live atoms). Run via a standalone verbatim-logic
  script (not `import services.acp_produce.generation` — that module is uncommitted/not deployed to
  the running ECS image; the script copies the exact E1/E2/F1 logic instead of patching the live
  container's app tree). Full evidence posted to the AA-370 Linear comment. Headline results:
  - E1: 5 sections, 0 Bedrock calls, and the documented AA-369 overflow quirk reproduced live —
    with 6 real atoms against 5 sections, the FAQ section absorbed 2 atom_ids (the overflow), exactly
    as flagged above.
  - E2: exactly 2 Sonnet calls (batches of 3 then 2 sections, per `_batch_sections`'s design), all
    `[R:atom_id]` tags, zero `[F:...]` tags, headings inserted by code matching the outline verbatim.
  - F1 grounding: **passed** (0 violations) on the real generated body; **failed correctly** (caught
    the injected `8342`) when a fabricated numeric claim was appended as a test.
  - Real cost: **$0.0187** for this slot's E2 (1829 input + 881 output tokens across the 2 calls) —
    under the $0.035–0.05 ballpark from STEP 0, using the same $3/$15-per-MTok reference rate (Bedrock's
    own exact per-token rate for this route is still not independently confirmed against AWS's pricing
    page — my one live-fetch attempt returned a stale page with no Sonnet 4.6 row — so treat this as a
    real-token-count-grounded estimate, not a Cost-Explorer-verified number).
  - Minor observed nuance, not a defect: `gate_grounding()`'s sentence-split regex doesn't split
    before a markdown link (`[text](url)` starts with `[`, not `[A-Z"'…]`), so the violation-message
    snippet for the injected test sentence showed the preceding CTA sentence's text rather than
    isolating just the fabricated one. Detection was still correct (right novel number flagged, gate
    still failed) — only the printed snippet's boundary was fuzzy. Inherited from AA-298's existing
    heuristic, not introduced here, not fixed here.
