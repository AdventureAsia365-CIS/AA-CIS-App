# AA-571 — Normalize raw_tours.country (SRI-LANDKA, OKINAWA)

## Decisions
- Mapping scope limited to exactly the 2 non-standard values Nghiep approved
  (`SRI-LANDKA`→`Sri Lanka`, `OKINAWA`→`Japan`) — the full 793-row `raw_tours` +
  74-row `published_tours` audit (posted as a Linear comment before any code) confirmed no
  other non-standard variant exists anywhere in either table, including a case/whitespace-
  normalized (`TRIM(UPPER(...))`) re-group that would have caught silent duplicates.
- Migration only touches `silver_aa_internal.raw_tours`. `gold_aa_internal.published_tours`
  has no `country` column of its own (confirmed via `information_schema.columns` — full
  23-column list, no `country`) — it always inherits country by joining `raw_tours.tour_id` at
  query time, so fixing the one source column fixes both tables with a single UPDATE. No
  separate gold-side statement is possible or needed.
- 9 `NULL`-country rows in `raw_tours` (5 of which are already published, all
  inactive/trashed) were deliberately left untouched — they are missing data, not a spelling
  variant, and are out of this issue's approved mapping scope. Flagged to Nghiep as a
  separate, undecided item.

## Changed
- `api/migrations/149_normalize_country_srilanka_okinawa.sql` — new migration, 2 UPDATE
  statements against `silver_aa_internal.raw_tours`.
- Applied live against `aa-cis-dev-db` via the standard S3-mediated ECS exec pattern
  (asyncpg, no psql/AWS CLI in the container). Verified before/after: `SRI-LANDKA`/`OKINAWA`
  count 0 remaining post-migration; `Japan` 103→104, `Sri Lanka` 18→24 (exact expected deltas,
  6+1=7 rows moved). Registered in `shared.schema_versions` (version `149`).

## Tradeoffs
- Considered backfilling the 9 NULL-country rows in the same migration for a "complete"
  cleanup pass, but that widens scope beyond the approved 2-row mapping and NULL isn't a typo
  — decided to leave it for a separate, explicit decision rather than silently fold it in.

## Decisions (round 2 — seed_builder redesign, S0 validation, NULL rows)
- **seed_builder.py landmark redesign (Việc 1)**: STEP0 catalog scan (real data, not guessed)
  found 36 of 104 real Japan tours mention "Okinawa" somewhere, and 24+ say it directly in
  their own title — a real, large cluster, not just the 1 originally mislabeled row. Kyoto/
  Osaka/Hokkaido had ZERO title-level hits in the same scan, so they were deliberately NOT
  added — would have been guessing ahead of evidence. `REGION_LANDMARKS` also covers Okinawa's
  own sub-locations found live in titles: Naha, Yanbaru, Iriomote, Miyako, and the real spelling
  variant "Yambaru" (with b) found in an actual title alongside "Yanbaru" (with n).
- Detection is **title-only** (`src_name`), not itinerary text, even though the task allowed
  either — the scan showed title alone already catches effectively the whole real cluster, and
  itinerary-based detection would risk false positives (e.g. a Tokyo-Kyoto-Osaka multi-city tour
  that stops at Nikko for one day should not be relabeled "Nikko").
- **CHECK constraint list (Việc 2A)**: sourced from AA's own legacy `countries` table (backup.sql,
  4 identical copies verified via md5sum) — 16 entries. Cross-checked against the 11 real active
  `raw_tours.country` values and found 2 mismatches, not just the 1 Nghiep flagged (South Korea) —
  **Taiwan (36 real rows) is also absent from the legacy list**. Both added per Nghiep's own rule
  (never exclude a value with real live data). Final list: 18 values. "Viet Nam" (backup.sql
  spelling) normalized to "Vietnam" to match `country_resolver.py`'s existing canonical spelling —
  using the legacy spelling verbatim would have created a brand-new variant in the one place meant
  to prevent exactly that.
- **9 NULL rows (Việc 3)**: proposed per-row via Linear comment (provider name + itinerary place
  names gave an unambiguous answer for all 9 — 8 Bhutan, 1 Sri Lanka). NOT backfilled — Nghiep's
  explicit rule: this is inference from other fields, not an obvious spelling fix like SRI-LANDKA/
  OKINAWA, so it needs his approval first.
- **TripPlanner correction**: the real TripPlanner repo (`~/projects/AA-TripPlanner-Web`, NOT
  under `~/projects/aa-cis/` — my earlier "no TripPlanner repo exists locally" claim in the first
  Linear comment was wrong, found by searching too narrow a directory) has the actual 2-line
  hardcode the original issue described (`backend/extraction/country_normalize.py`, explicitly
  referencing "Linear AA-571" in its own docstring). Not touched in this round — flagged in the
  Linear comment for a quick confirm, since it's a different repo outside this session's explicit
  3-item task list, even though it's now safely dead code (migration 149 cleaned the source).

## Decisions (round 3 — Việc 2B finish + Việc 3 backfill)
- **Việc 2B, Cách A** (Nghiep's explicit choice): unresolved country never blocks ingestion.
  Added `raw_tours.country_raw_unresolved TEXT` (migration 151) instead of reusing
  `review_status`/`review_notes` (migration 024, AA-44) — checked first and found those
  columns are set to their DEFAULT at ingest and never actually read or written anywhere else
  in the app (grepped `api/` + `services/`) — reusing an already-dead, differently-named
  lifecycle column for a new meaning would have been more confusing than a new, exactly-named
  one, not less.
- Found and fixed a real gap while wiring this up: `excel_parser.py` builds a `dict` per row,
  but `shared/repository/raw_tour_repository.py::insert()` uses a fixed, explicit column list
  in its `INSERT` — setting the dict key alone would have been a silent no-op. Added
  `country_raw_unresolved` to both the column list and the positional args.
- **Việc 3 backfill**: applied exactly as Nghiep approved (8 Bhutan, 1 Sri Lanka, by `tour_id`),
  no re-derivation — this round's job was to execute the already-approved table, not
  re-investigate it.

## Should know
- **STEP0 investigation-time discovery, not yet acted on**: `services/seo_intelligence/
  seed_builder.py::COUNTRY_NORMALIZE` already hardcodes the identical `SRI-LANDKA`/`OKINAWA`
  pair (AA-197, predates this issue) — but it maps `OKINAWA` to `"Okinawa, Japan"`, not bare
  `"Japan"`, deliberately keeping the more specific location for DataForSEO seed text (used by
  `build_seed()`, consumed by `admin_pipeline.py`, `v1_tours.py`, `allocator.py`,
  `segment_research.py`, and others). This is NOT the "TripPlanner PRD/code" hardcode the
  issue text refers to — no `AA-TripPlanner-Web` (or similarly named) repo exists locally to
  check its code directly; the issue's own reference is to the Notion PRD only. Removing
  `COUNTRY_NORMALIZE` now that the DB source is clean would be safe for the `SRI-LANDKA`
  branch, but would change SEO-seed behavior for the `OKINAWA` branch (losing the
  "Okinawa"-specific keyword targeting AA-251 cared about) — a real product tradeoff, not
  touched in this session, needs Nghiep's explicit call before deleting.
- **Real ingestion-time (S0) validation gap found**: `shared/country_resolver.py::resolve_country()`
  (AA-313) IS wired into ingestion (`services/ingestion/excel_parser.py:149`,
  `current["country"] = resolve_country(...)`) and its alias map already includes
  `SRI-LANDKA` → `Sri Lanka` — so a *new* Excel upload with that misspelling would already
  self-correct today. But `COUNTRY_MASTER["Japan"]` has no `OKINAWA` alias at all, and
  `excel_parser.py` unconditionally overwrites `country` with `resolve_country()`'s return
  value — for an unrecognized raw value that means the row's `country` silently becomes
  `NULL` on ingestion, not the original literal string. So today's live recurrence risk is not
  "another literal `OKINAWA` string" (the 1 existing row almost certainly predates AA-313 —
  the current ingestion code cannot reproduce that exact string) but **silent NULL country for
  any raw label `COUNTRY_MASTER` doesn't recognize** (new region names, further misspellings,
  etc.) — a broader and arguably worse failure mode than the original bug report assumed.
  Not fixed in this session — this is exactly the "prevention" design question Nghiep asked to
  see options for before any validation code gets written, see the Linear comment for the
  proposed options.
