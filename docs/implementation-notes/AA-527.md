# AA-527 — Admin Atom Curation page (replaces tenant-facing T6)

## Decisions

- **Access: admin-only**, not admin+reviewer+content. Asked Nghiệp directly (2 options
  presented) — curation here decides which atoms feed every tenant's social content, closer to
  a4-oversight/llm-usage's decision-quality tier than routine day-to-day content authoring.
  `frontend/middleware.ts` and the Sidebar's "ACP v2 — Setup & Approval" group (already
  admin-only) both reflect this.
- **No backend behavior change** — confirmed via AA-525 Phần 5 mục 3 before build:
  `api/routers/admin_atoms.py`'s list/summary/patch endpoints already resolve `owner_scope` via
  `_resolve_atom_owner_scope()` — a tenant JWT scopes to that tenant's own atoms (kept, unused by
  anything tenant-facing after AA-526, not removed for API stability), X-Admin-Secret (this
  page's own path) resolves to `owner_scope=None` — no filter, every atom across every scope.
- **One small, additive backend change**: `ta.owner_scope` added to the atom list SELECT, and
  `by_tour` now returns each tour's distinct `owner_scopes`. Not present before because no caller
  ever needed to tell owner_scopes apart (the tenant UI only ever saw its own). This page needs
  it: AA-526 left a real, currently-mixed dataset (new `owner_scope='platform'` atoms alongside
  75 pre-existing legacy tenant-scoped ones, still undeleted pending that issue's own open
  question) — silently mixing them here would be actively misleading to whoever curates, so each
  tour/atom gets a "Platform" or "Legacy tenant-owned" badge instead.
- **UI ported near-verbatim from the deleted `AtomsTab.tsx`** (git history, AA-509/AA-519's own
  Segment-grouping + atom-card + star/delete) — re-skinned onto `adminUi.tsx` tokens (this app's
  own admin design system) instead of the tenant portal's `ui.tsx`, and grouped by TOUR first (a
  new left rail, from `summary.by_tour`) since an admin curates across every tour platform-wide,
  not one tenant's own handful the way the old page did.
- **No new design pattern invented** for the tour-list/atom-panel split — matches this app's own
  established 2-column admin layout convention (e.g. this repo's a4-oversight page uses stacked
  sections; this page's own left-rail-plus-panel shape mirrors run-health/master-content's own
  filter-plus-list convention instead, closest fit for "pick a tour, see its atoms").

## Changed

- `api/routers/admin_atoms.py` — `ta.owner_scope` added to `_LIST_SELECT_COLS`; `by_tour_rows`
  query gains `array_agg(DISTINCT ta.owner_scope) AS owner_scopes`, exposed as `owner_scopes:
  string[]` per tour.
- `frontend/app/admin/atom-curation/page.tsx` — new page (this issue's own build).
- `frontend/app/admin/_components/AdminSidebar.tsx` — new nav item, admin-only group.
- `frontend/middleware.ts` — new `PROTECTED_ROUTES` entry, `roles: ["admin"]`.
- `tests/unit/test_aa300_admin_atoms.py` — updated 2 assertions/fixtures for the new column/
  field (a stale `"ta.owner_scope" not in query` check had to narrow to the filter-clause form
  specifically, since the SELECT now always includes it), added 1 new test for `owner_scopes`
  output.

## Tradeoffs

- `starred` has no real downstream effect in the current pipeline (confirmed via grep: no
  Segment/Ranking/Route module reads it — its one real consumer, the N6 allocator, was already
  deleted in a prior session's N4-N6 cleanup). Kept the star action anyway, unchanged from the
  old UI's behavior — removing it would be a bigger, separate product decision ("does curation
  even need a soft-approve distinct from hard-delete") this issue didn't ask for; flagged here
  rather than silently dropped or silently left ambiguous.
- Did not build a bulk multi-select/bulk-delete action (the old platform-wide `/admin/curation`
  page, deleted in AA-475, had one) — this issue's own text describes per-atom star/delete only;
  not assumed into scope.

## Should know

- Depends on AA-526 (atoms actually existing with `owner_scope='platform'`) — real data already
  live-verified there (108 real Sri Lanka atoms) before this page was built, so this page has
  real, non-empty data to show from first load.
- The "Legacy tenant-owned" badge is a direct, visible surface of AA-526's still-open data
  question (delete the 75 old atoms now / backfill later / new ticket) — this page doesn't
  resolve that question, just makes the mixed state visible and honest instead of silently
  blending 2 kinds of data.
- Live-verify plan (post-deploy): real X-Admin-Secret session, confirm the page loads real
  summary/by-tour data (the Sri Lanka tour's 108 real atoms should appear, tagged "Platform"),
  confirm a real star/delete PATCH round-trips correctly. Evidence posted to this issue's Linear
  comment once run.

## Bổ sung (05/09/2026, phiên 5) — 3 điểm kiểm tra STEP0 + khung dashboard 8-section (Phương án C)

Build prompt (`docs/claude_tasks/2026-09-05-phien5-aa527-aa532.md`) required 2 things: (a)
confirm 3 specific points about the already-built Atomize section, add what's missing; (b) wrap
the whole thing in an 8-section dashboard shell per Nghiệp's "Phương án C" decision. The Atomize
section's original build (PR #311, above) was NOT redone — only extended.

### STEP0 — 3 điểm kiểm tra, kết quả

1. **Filter/dropdown đầy đủ** — trước: tour/distinctiveness/unreviewed only. **Thiếu, đã bổ
   sung**: `owner_scope_class` (Platform / Legacy tenant-owned) and `lifecycle_stage` (active/
   phasing_out/retired) — both new optional query params on `GET /admin/atoms`. Segment isn't a
   separate filter dropdown — the existing UI already groups by Segment visually (`groupBySegment`
   ported from AtomsTab.tsx), which serves the same purpose without needing a 4th control.
2. **Tour active/inactive có atom** — **Đã có sẵn, chỉ chưa hiện**: `silver_aa_internal.
   raw_tours.lifecycle_stage` (migration 086, AA-301, `active|phasing_out|retired`) already exists
   and was never selected here. Added to both `GET /atoms` (per-atom) and `GET /atoms/summary`
   (`by_tour[].lifecycle_stage`), plus a badge/filter in the UI. Real live data (05/09/2026): all
   4 tours with atoms are currently `active` — no `phasing_out`/`retired` example exists yet to
   show the badge live, but the column, filter, and badge logic are real and correct (verified via
   a live `WHERE lifecycle_stage != 'active'` query returning 0 rows, matching the 4-tour "all
   active" state — did not flip a real tour's lifecycle_stage just to produce a demo row, that
   column drives other real features, e.g. AA-301's N4 Runway Map).
3. **Thống kê atom/tour dùng nhiều** — **Chưa tồn tại trước, xây được ngay (KHÔNG phải backlog)**:
   contradicts the issue's own premise that this might need a new field. `acp_shared.
   angle_gate_request.atom_id` (migration 113, AA-449) already links every T8/T9 write attempt
   back to its source atom — a plain `COUNT(DISTINCT request_id)` aggregate over EXISTING data,
   no migration needed. Added `usage_count` per atom (`GET /atoms`) and `used_atom_count` per tour
   (`GET /atoms/summary`). Live-verified against real data: atom `338e362c081d98d5` (SOUTHERN LAOS)
   really was written from 3 separate times — confirms this isn't a database column returning a
   trivial constant.

### Decisions (dashboard shell)

- **7 non-Atomize panels are read-only audit views, Atomize is the only one with actions** — per
  the build prompt's own point 5/6. No new mutating endpoint added anywhere except what already
  existed (Atomize's star/delete).
- **Write-Gate and Review (sections 06/07) share ONE dataset** (`GET /admin/a4/content-log`,
  AA-469/AA-501's existing endpoint) rendered as 2 different lenses — Write/Gate shows full
  per-attempt gate-ledger detail (why a piece held), Review shows a queue-style status/publish-
  readiness table. Chose this over building a second near-identical query: per AA-501's own
  earlier finding, "AA cần thấy MỌI THỨ tenant thấy, CỘNG THÊM chi tiết kỹ thuật" — content-log
  already IS the wide superset both views need, just rendered two ways.
- **New endpoints only for Segment/Score/Route-Hub/Slate** (`api/routers/admin_dashboard.py`) —
  the other 3 non-Atomize sections had no admin read-path of any kind before this (STEP0 confirmed:
  `v1_route_hub.py`/`v1_planning.py`/`v1_angle_gate.py` are all tenant-JWT-only, no admin-secret
  fallback, cross-tenant audit was impossible with them as-is). All 4 new endpoints are
  cross-tenant by design (same stance as `admin_a4.py`, STEP0/AA-437) — a Tour's Segment/Score/
  Route/Slate rows can in principle span more than one tenant (multiple tenants can each run T7
  over the same platform-shared atoms), so every endpoint returns every tenant's matching rows
  with `tenant_name` attached, not scoped to a single tenant.
- **`tour_id` added to `GET /admin/a4/content-log` and `GET /admin/a4/publish-log`** rather than
  building yet another endpoint — both already existed, both already had a `tenant_id` filter;
  `tour_id` follows the identical optional-param pattern (`content-log` filters on `agr.trip_id`,
  already joined for the `tour` display block; `publish-log` gains a conditional JOIN through
  `content_piece -> angle_gate_request` only when `tour_id` is actually passed, so the common
  no-filter case is unaffected).
- **Header "Tour" dropdown reuses `GET /admin/atoms/summary`'s existing `by_tour` list** — no new
  "list every tour" endpoint. Sections 02-08 all structurally depend on Atomize's atoms already
  existing (Segment/Route/Slate/Write-Gate/Review/Publish are all downstream pipeline stages), so
  any tour with T7-T11 data necessarily already appears there.
- **"All tours" is Atomize-only.** Sections 02-08's backend endpoints all require `tour_id`
  (Segment/Score/Route are Tour-scoped by schema; Slate/content-log/publish-log are cheap to scope
  to one tour but not designed here for a meaningful all-tenant-all-tour view). Selecting "All
  tours" in the header shows a "chọn 1 Tour cụ thể" prompt on those 7 panels rather than an error.
- **Hub grouping (Phần 12 mục 8) explicitly flagged backlog**, not silently omitted — `acp_contract
  .hub` has 0 rows in real live data (Route detection doesn't wire `hub_id` yet), so the Route/Hub
  panel shows `route.hub_name` (a plain text column, always populated) with a visible "backlog"
  note rather than an always-empty Hub column pretending to be complete.
- Used `<style>` (plain global CSS, not styled-jsx) for the one responsive rule needed (inner
  sidebar → horizontal tab row under 980px, per AA-530) — simplest option that works identically
  under this repo's Turbopack dev/build setup, no dependency on styled-jsx's scoping behavior.
- Did NOT invoke the `frontend-design` skill mentioned in the build prompt — it exists only as an
  installed marketplace plugin skill (`~/.claude/plugins/marketplaces/claude-plugins-official/
  plugins/frontend-design`), not in this session's active skill listing, so it can't be invoked by
  name. Followed the same brand tokens it would have pointed at anyway (adminUi.tsx's existing A.*
  palette — already AA's orange/dark-navy/Poppins-family tokens) since that source is already the
  actual design-token single-source-of-truth for every other /admin/* page in this repo.

## Tradeoffs (bổ sung)

- `usage_count`/`used_atom_count` count a DISTINCT `angle_gate_request_id`, not content_piece
  attempts — 2 write attempts (T10 retry) off the same T8 request count as 1 "use", since a retry
  isn't a second, independent decision to use that atom. Not filtered to `status='approved'`
  either — a `held` attempt still represents a real decision to try writing from that atom.
- Write-Gate/Review sharing one dataset (see Decisions) means both panels re-fetch the SAME
  `content-log` response independently rather than one shared cache — a deliberate simplicity
  choice at this data volume (tens of rows per tour), not a performance concern yet.
