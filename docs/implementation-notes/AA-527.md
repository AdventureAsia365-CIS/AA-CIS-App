# AA-527 — Admin Atom Curation page (replaces tenant-facing T6)

## Decisions

- **Access: admin-only**, not admin+reviewer+content. Asked Nghiệp directly (2 options
  presented) — curation here decides which atoms feed every tenant's social content, closer to
  a4-oversight/llm-usage's decision-quality tier than routine day-to-day content authoring.
  `frontend/middleware.ts` and the Sidebar's "ACP v2 — Setup & Approval" group (already
  admin-only) both reflect this.
- **No backend behavior change** — confirmed via AA-525 Phần 5 mục 3 before build:
  `api/routers/admin_atoms.py`'s list/summary/patch endpoints already resolve `owner_scope` via
  `_resolve_atom_owner_scope()` — a tenant JWT scopes to that tenant's own atoms (kept, unused by
  anything tenant-facing after AA-526, not removed for API stability), X-Admin-Secret (this
  page's own path) resolves to `owner_scope=None` — no filter, every atom across every scope.
- **One small, additive backend change**: `ta.owner_scope` added to the atom list SELECT, and
  `by_tour` now returns each tour's distinct `owner_scopes`. Not present before because no caller
  ever needed to tell owner_scopes apart (the tenant UI only ever saw its own). This page needs
  it: AA-526 left a real, currently-mixed dataset (new `owner_scope='platform'` atoms alongside
  75 pre-existing legacy tenant-scoped ones, still undeleted pending that issue's own open
  question) — silently mixing them here would be actively misleading to whoever curates, so each
  tour/atom gets a "Platform" or "Legacy tenant-owned" badge instead.
- **UI ported near-verbatim from the deleted `AtomsTab.tsx`** (git history, AA-509/AA-519's own
  Segment-grouping + atom-card + star/delete) — re-skinned onto `adminUi.tsx` tokens (this app's
  own admin design system) instead of the tenant portal's `ui.tsx`, and grouped by TOUR first (a
  new left rail, from `summary.by_tour`) since an admin curates across every tour platform-wide,
  not one tenant's own handful the way the old page did.
- **No new design pattern invented** for the tour-list/atom-panel split — matches this app's own
  established 2-column admin layout convention (e.g. this repo's a4-oversight page uses stacked
  sections; this page's own left-rail-plus-panel shape mirrors run-health/master-content's own
  filter-plus-list convention instead, closest fit for "pick a tour, see its atoms").

## Changed

- `api/routers/admin_atoms.py` — `ta.owner_scope` added to `_LIST_SELECT_COLS`; `by_tour_rows`
  query gains `array_agg(DISTINCT ta.owner_scope) AS owner_scopes`, exposed as `owner_scopes:
  string[]` per tour.
- `frontend/app/admin/atom-curation/page.tsx` — new page (this issue's own build).
- `frontend/app/admin/_components/AdminSidebar.tsx` — new nav item, admin-only group.
- `frontend/middleware.ts` — new `PROTECTED_ROUTES` entry, `roles: ["admin"]`.
- `tests/unit/test_aa300_admin_atoms.py` — updated 2 assertions/fixtures for the new column/
  field (a stale `"ta.owner_scope" not in query` check had to narrow to the filter-clause form
  specifically, since the SELECT now always includes it), added 1 new test for `owner_scopes`
  output.

## Tradeoffs

- `starred` has no real downstream effect in the current pipeline (confirmed via grep: no
  Segment/Ranking/Route module reads it — its one real consumer, the N6 allocator, was already
  deleted in a prior session's N4-N6 cleanup). Kept the star action anyway, unchanged from the
  old UI's behavior — removing it would be a bigger, separate product decision ("does curation
  even need a soft-approve distinct from hard-delete") this issue didn't ask for; flagged here
  rather than silently dropped or silently left ambiguous.
- Did not build a bulk multi-select/bulk-delete action (the old platform-wide `/admin/curation`
  page, deleted in AA-475, had one) — this issue's own text describes per-atom star/delete only;
  not assumed into scope.
