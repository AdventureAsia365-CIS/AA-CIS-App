## Decision needed from Nghiep before implementing

The minimum-viable button therefore can't just "pick an existing slot and call `run_slot_production()`" — nothing exists to pick yet. The real MVP chain for one click has to be:

1. Resolve tenant config (`fetch_tenant_planning_config` — markets/channels/capacity, same as `preview-slotgrid` already does).
2. `allocate_month_from_db(...)` — requires a Gate-B-approved quarter plan to already exist for that tenant/quarter (fails with `QuarterPlanNotApprovedError` otherwise — out of this issue's scope to create one).
3. `create_weekly_produce_run(pool, tenant_id, year, week)` → idempotent `run_id`.
4. `persist_slot_grid(pool, run_id, tenant_id, week, grid)` → idempotent Slot persistence (`ON CONFLICT DO NOTHING`).
5. `fetch_due_slots(pool, run_id)` → real due Slots for that week.
6. For each due slot → `run_slot_production(...)` → pieces (idempotent on retry, see #1 above).
7. Get-or-create a packet for `(tenant_id, year, week)` (`create_packet` has no `ON CONFLICT` — needs a catch/select-existing wrapper), `assemble_packet()` the passed pieces into it, `maybe_mark_packet_ready()`.
8. Return a result summary (pieces produced, per-piece status/held_reason, packet_id/status).

Then a second small screen/section: list packets with `status='ready'` + a Gate C approve action calling `confirm_ramp_transition()`.

This is a bigger build than "wire an existing button" — it's the first live wiring of N6 persist + N7 run + N8 assemble + Gate C approve, all in one PR. Confirmed with Nghiep to proceed on this exact shape before writing code.

## Decisions

- **Async 202+poll, not sync.** Confirmed live: the browser -> Vercel `/api/admin` proxy -> API
  Gateway (owq9as3wjl) -> ECS path has a hard 29s integration timeout. One real slot took 187.7s
  (see live-verify below) -- a sync endpoint would 504 on slot 1 every time. `POST
  /admin/produce/run` does the fast N6 part (allocate/create-run/persist-slots, DB+in-memory
  only, no LLM calls) synchronously and returns 202 immediately; the slow per-slot production
  loop runs as a FastAPI `BackgroundTask`. Reuses `acp_shared.acp_v2_runs.status`
  (allocated/producing/completed/failed) as the job-status field instead of a new table -- it
  already existed and was otherwise dead (nothing ever advanced it past `producing` before this).
- **Gate C is a thin wrapper, no new gate logic.** `POST /admin/produce/packets/{id}/gate-c/approve`
  calls the existing `trust_ramp.confirm_ramp_transition()` (AA-365) directly.
- **F8 "ends with CTA" facebook fix = Option A (fix the prompt), not Option B (reassign
  framework).** `hook_story_cta` is deliberately facebook's one dedicated framework
  (`constants.py` FRAMEWORK_TABLE, `("ANY", "facebook")` — same one-framework-per-channel
  pattern as tiktok/email) and its own rubric + name say "hook, story, CTA" — the framework
  assignment is correct. The bug was `adapt.py::_FACEBOOK_INSTRUCTIONS` never asking the model
  for a CTA phrase at all. Fixed the prompt instead of the framework assignment.

## Changed

- `api/routers/admin_produce.py` (new) — `POST /admin/produce/run`, `GET
  /admin/produce/run/{run_id}`, `GET /admin/produce/packets`, `POST
  /admin/produce/packets/{id}/gate-c/approve`. Wired into `api/main.py`.
- `services/acp_produce/adapt.py::_FACEBOOK_INSTRUCTIONS` — now explicitly requires a hook as the
  first sentence and the literal "Design This Journey" CTA phrase as the last sentence (before
  the HASHTAGS line, no blank line between them so both land in the same `\n\n`-paragraph
  `_ends_with_cta()` checks).
- `_produce_slots_background()` now calls `mark_slot_status(pool, slot.slot_id, "produced")` after
  each slot succeeds — a per-slot exception is caught, logged, and leaves that slot `status='due'`
  (eligible for retry) instead of either silently marking it produced or aborting every other due
  slot in the batch.

## Tradeoffs

- Holding one pooled connection for the entire per-slot production loop (`async with
  pool.acquire() as conn` wraps the whole `for slot in due_slots` loop in
  `_produce_slots_background`) — acceptable for a single manual admin trigger, not something a
  concurrent/multi-tenant version of this endpoint could get away with.
- Repair-prompt genericness (`repair.py`) was NOT touched — its violation messages are generic
  across all 9 gates and don't explain the *specific* CTA phrase/placement a facebook piece needs.
  With the base generation prompt now fixed, most facebook pieces should pass F8 on the first
  attempt without needing repair at all; if repair-time CTA failures turn out to still be common
  after this fix, that's a separate, broader repair-prompt-quality question, not this issue's scope.
- `acp_v2_runs` has no `month` column (only `year`+`week`, 1-4 SlotGrid week-of-month numbering) —
  a pre-existing schema gap, not introduced or fixed here. The endpoint takes an optional `month`
  input (defaults to the current calendar month) purely to compute the `SlotGrid`; `year`+`week`
  are what actually key the run/slot/packet rows, same as the existing schema.
