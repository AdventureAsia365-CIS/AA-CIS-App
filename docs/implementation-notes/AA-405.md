## Decision needed from Nghiep before implementing

The minimum-viable button therefore can't just "pick an existing slot and call `run_slot_production()`" — nothing exists to pick yet. The real MVP chain for one click has to be:

1. Resolve tenant config (`fetch_tenant_planning_config` — markets/channels/capacity, same as `preview-slotgrid` already does).
2. `allocate_month_from_db(...)` — requires a Gate-B-approved quarter plan to already exist for that tenant/quarter (fails with `QuarterPlanNotApprovedError` otherwise — out of this issue's scope to create one).
3. `create_weekly_produce_run(pool, tenant_id, year, week)` → idempotent `run_id`.
4. `persist_slot_grid(pool, run_id, tenant_id, week, grid)` → idempotent Slot persistence (`ON CONFLICT DO NOTHING`).
5. `fetch_due_slots(pool, run_id)` → real due Slots for that week.
6. For each due slot → `run_slot_production(...)` → pieces (idempotent on retry, see #1 above).
7. Get-or-create a packet for `(tenant_id, year, week)` (`create_packet` has no `ON CONFLICT` — needs a catch/select-existing wrapper), `assemble_packet()` the passed pieces into it, `maybe_mark_packet_ready()`.
8. Return a result summary (pieces produced, per-piece status/held_reason, packet_id/status).

Then a second small screen/section: list packets with `status='ready'` + a Gate C approve action calling `confirm_ramp_transition()`.

This is a bigger build than "wire an existing button" — it's the first live wiring of N6 persist + N7 run + N8 assemble + Gate C approve, all in one PR. Confirmed with Nghiep to proceed on this exact shape before writing code.

## Decisions

- **Async 202+poll, not sync.** Confirmed live: the browser -> Vercel `/api/admin` proxy -> API
  Gateway (owq9as3wjl) -> ECS path has a hard 29s integration timeout. One real slot took 187.7s
  (see live-verify below) -- a sync endpoint would 504 on slot 1 every time. `POST
  /admin/produce/run` does the fast N6 part (allocate/create-run/persist-slots, DB+in-memory
  only, no LLM calls) synchronously and returns 202 immediately; the slow per-slot production
  loop runs as a FastAPI `BackgroundTask`. Reuses `acp_shared.acp_v2_runs.status`
  (allocated/producing/completed/failed) as the job-status field instead of a new table -- it
  already existed and was otherwise dead (nothing ever advanced it past `producing` before this).
- **Gate C is a thin wrapper, no new gate logic.** `POST /admin/produce/packets/{id}/gate-c/approve`
  calls the existing `trust_ramp.confirm_ramp_transition()` (AA-365) directly.
- **F8 "ends with CTA" facebook fix = Option A (fix the prompt), not Option B (reassign
  framework).** `hook_story_cta` is deliberately facebook's one dedicated framework
  (`constants.py` FRAMEWORK_TABLE, `("ANY", "facebook")` — same one-framework-per-channel
  pattern as tiktok/email) and its own rubric + name say "hook, story, CTA" — the framework
  assignment is correct. The bug was `adapt.py::_FACEBOOK_INSTRUCTIONS` never asking the model
  for a CTA phrase at all. Fixed the prompt instead of the framework assignment.

- `api/routers/admin_produce.py` (new) — `POST /admin/produce/run`, `GET
  /admin/produce/run/{run_id}`, `GET /admin/produce/packets`, `POST

- `services/acp_produce/adapt.py::_FACEBOOK_INSTRUCTIONS` — now explicitly requires a hook as the
  first sentence and the literal "Design This Journey" CTA phrase as the last sentence (before
  the HASHTAGS line, no blank line between them so both land in the same `\n\n`-paragraph
  `_ends_with_cta()` checks).
- `_produce_slots_background()` now calls `mark_slot_status(pool, slot.slot_id, "produced")` after
  each slot succeeds — a per-slot exception is caught, logged, and leaves that slot `status='due'`
  (eligible for retry) instead of either silently marking it produced or aborting every other due
  slot in the batch.

## Tradeoffs

- Holding one pooled connection for the entire per-slot production loop (`async with
  pool.acquire() as conn` wraps the whole `for slot in due_slots` loop in
  `_produce_slots_background`) — acceptable for a single manual admin trigger, not something a
  concurrent/multi-tenant version of this endpoint could get away with.
- Repair-prompt genericness (`repair.py`) was NOT touched — its violation messages are generic
  across all 9 gates and don't explain the *specific* CTA phrase/placement a facebook piece needs.
  With the base generation prompt now fixed, most facebook pieces should pass F8 on the first
  attempt without needing repair at all; if repair-time CTA failures turn out to still be common
  after this fix, that's a separate, broader repair-prompt-quality question, not this issue's scope.
- `acp_v2_runs` has no `month` column (only `year`+`week`, 1-4 SlotGrid week-of-month numbering) —
  a pre-existing schema gap, not introduced or fixed here. The endpoint takes an optional `month`
  input (defaults to the current calendar month) purely to compute the `SlotGrid`; `year`+`week`
  are what actually key the run/slot/packet rows, same as the existing schema.

## Gate audit — week=2 real-data failures vs Ms. Thu's aamc/gates.py (15/08/2026, investigation only)

Week=2 run (`aa_internal`, run_id `e64befb4-...8754`): 0/9 pieces passed, 4 failure types. Read
Ms. Thu's `aamc/gates.py` side by side and pulled the real `acp_deliver.pieces` rows (body_tagged +
gate_ledger + repair_log) for every held piece. No code changed. Findings, per gate:

- **F5 "missing" — confirmed a numbering artifact, not missing coverage.** aamc's F5 =
  `gate_brief_compliance()`. This repo's F4 = the same check (word count/keyword/H2/internal-link),
  same logic, just renumbered — the module docstring already says AA-372's own Linear text jumps
  F4→F6 with no F5 in its scheme (route-to-sellable keeps aamc's F6 label). Also confirmed aamc's
  F2 (atom density) and F10 (AI-detector signal logger) are the only two genuinely-not-ported
  pieces, and both are called out as deliberately out of scope in the docstring already — nothing
  new here, prior session's conclusion holds, now with the actual line-by-line diff behind it.

- **F1_grounding (1/9, real CloudWatch HARD-FLOOR alarm fired) — mechanical regex bug, NOT a
  fabrication.** Piece `slot_b30a9406...`: flagged numbers `['2000', '52']` as unsupported by the
  cited atom. Traced to the actual body: those numbers come from an FAQ block (`**Q: What is the
  52 hour rule...**` / `**Q: Can someone live for $2000 a month...**`) — real, honestly-answered
  "the given fact does not address this" Q&A, not a claim the piece makes. Root cause:
  `_SENT_SPLIT_RE = r"(?<=[.!?])\s+(?=[A-Z\"'‘’“”])"` doesn't match `*` (markdown bold), so it
  fails to split before `**Q:` — confirmed by direct regex test, `re.split` returns 1 part across

  `[R:atom_...]` citation from the itinerary paragraph 150+ chars earlier, and the numeric-entailment
  check (`find_novel_numeric_claims`, `services/acp_shared/grounding.py`) blames that citation for
  numbers that actually belong to an unrelated FAQ answer. Same failure class as the old AA-325
  false-positive pattern (citation-matching bug), not a new fabrication. Ms. Thu's aamc F1 doesn't
  have this exact bug because it never implements numeric entailment at all (the module docstring's
  "P0-1 bug" — her version's own docstring comment "numbers must come from corpus: any digit
  sequence not present in corpus text is suspect" is dead text, no code backs it); it also
  paragraph-splits (`\n\n`) rather than sentence-splits, which would have kept this FAQ block
  correctly isolated. Real operational concern: the fired alarm's own description
  ("HARD FLOOR=1.0, fabrication risk, investigate immediately") reads as certain-fabrication
  severity for what turned out to be a parser artifact — worth revisiting the alarm's framing
  separately from the regex fix itself.

- **F3_structural_variance (2/9) — genuine content gap, not a gate bug.** Byte-for-byte the same
  heuristic as aamc's F4 (own docstring: "Direct port... no B10/B12 baggage"), so there's no

  Confirms AA-404's existing "needs real data to calibrate" tracking with the data it was waiting

  fix.

  `_FACEBOOK_INSTRUCTIONS` doesn't constrain the source material to one atom when drafting from a
  multi-atom blog piece), not a judge-reliability issue — do not apply the CTA fix's "make it
  deterministic" pattern here, there's no positional proxy for "stays on one atom."

- **F9_brand_seo_audit_social (5/9, most common failure) — likely a genuine, still-uncalibrated

## F1_grounding regex fix (15/08/2026) — merge-bug shipped, disclaimer-sentence issue tracked separately

**Fixed**: `services/acp_produce/gates.py::_SENT_SPLIT_RE` now tolerates up to 2 markdown-bold
asterisks (`\*{0,2}`) immediately around the sentence-boundary whitespace, so `**Q: ...**\nA: ...`
FAQ markers (`faq.py::render_faq_section()`'s real format) correctly split as their own sentences
instead of merging into whatever preceded them. This was the mechanism behind the real week=2
CloudWatch alarm (`aa-cis-dev-acp-grounding-score-floor`) — an itinerary sentence's legitimate
citation was getting merged across the FAQ boundary and blamed for a later FAQ answer's numbers.

**Tested**:
- Two new unit tests in `tests/unit/test_aa298_gates.py`: one proves the fixed gate passes a body
  shaped exactly like the real held piece (citation on an earlier, plain-punctuation-bounded
  sentence, FAQ block with `**Q:`/`A:` markers after); a companion test module-patches
  `_SENT_SPLIT_RE` back to the pre-fix pattern on the *same* body/ids to prove the reproduction is
  real (it fails pre-fix, both `'52'` and `'2000'` flagged) — not a tautological always-passing test.
- Full `tests/unit/` suite: 1213 passed, 0 regressions.
- Re-ran `gate_grounding()` against all 9 real week=2 pieces (not just the alarm piece) with the
  patched module: 8/9 show zero change (no new splits, no new violations — confirms the fix doesn't
  just move the bug elsewhere in this corpus). `flake8` clean on both changed files.

**Known residual, not fixed here (AA-409)**: the alarm piece (`slot_b30a9406...:blog`) still shows
one violation post-fix — `'52'` on the FAQ sentence *"A: The given fact does not address the
52-hour rule; it describes a Day 2 visit to the Demilitarised..."* — but now for the correct,
narrower reason: this sentence legitimately carries its own citation (for the "Day 2 DMZ visit"
clause) while also restating the disclaimed number from its own question. `find_novel_numeric_
claims()` has no concept of negation — an honest "does not address X" still trips the check. This
is a different bug than the merge (confirmed: the merge fix's own regression test isolates this
exact shape and shows it resolved when the disclaimer sentence carries no citation of its own — the
residual only appears when a citation and a disclaimed number share one sentence). Not in this PR's
scope per Nghiep's decision (15/08) — tracked as AA-409, with 3 candidate fix directions already
noted there (split on `;` clause boundaries, exempt text after "does not address"/"the given fact"
phrasing, or restructure how FAQ "unknown" answers cite atoms).

**Also found, not fixed here**: markdown *links* (`[text](url)`) and `##` headings also don't match
`_SENT_SPLIT_RE`'s lookahead — same class of gap as the `**` case, just not what fired this
alarm (no real citation in the corpus so far sits directly against a link/heading boundary). Noted
in the regression test's docstring; worth folding into AA-409 or its own follow-up rather than
silently forgotten.

**Also confirmed, separately tracked (AA-408)**: `services/content_generation/s1_from_atom.py:55`
has its own independent copy of the identical pre-fix `_SENT_SPLIT_RE` (not imported from
`gates.py`) — same merge bug likely reproducible there. Deliberately not touched in this PR (S1 is
a different pipeline, out of this issue's scope).

**Alarm-wording suggestion (not made in this PR — infra/Terraform, separate concern)**: the fired
alarm's description text — *"HARD FLOOR=1.0, fabrication risk, investigate immediately"* — reads as
certain-fabrication severity. This incident was a parsing artifact, not a fabrication, and the
wording gave no room for that possibility. Suggest softening to something like *"grounding-check
