# AA-461 — fix `quarter.fetch_atoms_by_trip()` filtering by `raw_tours.tenant_id` instead of `tour_atoms.owner_scope`

## STEP0 — did T7 (AA-448) already fix this?

No. T7 built a **separate, parallel** function (`services/acp_planning/tenant_pool.py::fetch_tenant_atoms_by_trip()`)
that routes around the bug for its own read-only `/v1/planning/slot-grid` endpoint — its own
module docstring says so explicitly ("Replaces `quarter.fetch_atoms_by_trip()` for T7 — ...").
It never touched `quarter.py`. `quarter.fetch_atoms_by_trip()` — used by `plan_quarter()` /
`compute_quarter_plan()`, i.e. N5/N6 quarter-plan allocation (`POST /admin/quarter-plan`,
`/admin/quarter-plan/preview`, `admin_atoms.py`'s slot-grid preview) — still had the original
`JOIN raw_tours ON ... WHERE rt.tenant_id = $1` bug at the exact line (279) the issue named.

## Decisions

- Fixed `quarter.fetch_atoms_by_trip()` in place (not a second parallel function) — N5/N6 is the
  last real caller of this bug, no reason to keep two copies once both are correct. Matched
  `tenant_pool.fetch_tenant_atoms_by_trip()`'s established shape exactly: query columns
  unprefixed (no more `raw_tours` JOIN needed at all), `str(tenant_id)` passed explicitly rather
  than relying on asyncpg's implicit UUID→text param coercion (owner_scope is free-text per
  ADR-2026-038 Hướng B, not a UUID FK).
- Did not add `owner_scope IN ('platform', tenant_id)` — `tenant_pool.py`'s own docstring already
  traces this: AA-440 floated it as a *possible* fix shape but it was never built anywhere,
  including AA-444's Marketplace aggregate. Following the real shipped precedent, not the
  unbuilt alternative.

## Real impact confirmed live (before fix)

Real tenant `test-agency` (`9fb0a3db-59aa-468a-a082-ded01ac50bee`) has 15 real T5 atoms
(`owner_scope = 9fb0a3db-...`) rewritten from the shared-pool tour "Route A: Tokyo Bay"
(`raw_tours.tenant_id = aa_internal`). The buggy query returned **0** atoms for this tenant;
every real tenant is in the same situation, since **no tenant in this database directly owns a
`raw_tours` row today** — `raw_tours.tenant_id` is `aa_internal` for every row (confirmed via
live query against `shared.tenants` × `raw_tours`/`tour_atoms`) — `/v1/tours/pool` only ever
offers tours from the `aa_internal` shared pool. So this bug was not an edge case: it made N5/N6
quarter planning blind to **every** real tenant's T5 atoms, unconditionally.
