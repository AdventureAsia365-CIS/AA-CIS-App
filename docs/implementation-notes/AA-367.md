## Decisions

- **Ready threshold**: `>=1` assigned piece with `status='passed'` advances `assembling` ->
  `ready`. Explicitly a **minimum viable threshold, not a confirmed business rule** — Linear
  AA-367's own verify checklist ("packet có ≥1 piece 'passed'") is the only source; comment left
  in `maybe_mark_packet_ready()` flagging this for revisit.
- **"delivered" mechanism**: status/`delivered_at` marker only (no AA-365 yet) — confirmed
  correct scope, nothing further added.
- **Slot-runner gap**: NOT built here. Tracked as AA-375. This issue's verify uses a test-only
  glue script (`tests/verify_scripts/aa367_real_piece_chain.py`) that hand-assembles a `Slot`
  from real DB atom/tour data and calls the real C1-E5/F1-F9 functions with zero mocking.
- **`set_publish_mode()`/`ALLOWED_PUBLISH_MODES_UNTIL_F6`**: untouched, per explicit instruction.

## Changed

- `services/acp_produce/packets.py`: added `assemble_packet()`, `maybe_mark_packet_ready()`,
  `PacketNotReadyError`, `deliver_packet()`. `deliver_packet()` calls `write_usage_log()`
  (AA-361) BEFORE flipping `packets.status` to `'delivered'` — ordering matters: a
  `write_usage_log()` failure leaves the packet retriable at `'ready'` rather than stuck
  `'delivered'`-but-unlogged (its own `status != 'ready'` guard blocks re-entry once delivered).
- `tests/unit/test_aa367_packets.py`: 10 new unit tests for the above (mocked db/pool).
- `tests/verify_scripts/aa367_real_piece_chain.py`: new, test-only, not run by pytest/CI.

## Tradeoffs / real findings surfaced along the way (out of scope, not fixed here)

- **`brand_rubric_text` has no real production source.** `pipeline.py`'s F9 call expects the
  caller to supply it (pre-fetched, like F1's `text_by_id`) — nothing in the codebase actually
  fetches a tenant's real brand rubric for this parameter yet. The verify script initially passed
  a one-line test-fixture placeholder (copy-pasted from `test_aa364_pipeline.py`'s own fixture)
  and F9 consistently flagged real content as `GENERIC_AI_WORDING`/off-brand — switching to the
  real `AA_BRAND_IDENTITY_PROMPT` constant (the same text E2/E3/E4's own system prompts already
  use) fixed this. Worth a real ticket: F9's `brand_rubric_text` needs a real fetch path, same
  gap class as the missing slot-runner.
- **E2's draft prompt doesn't reliably satisfy F3's variance directives** (e.g. "include >=1
  one-sentence paragraph") even though `Brief.variance_directives` is passed into the prompt
  verbatim — real Sonnet output didn't comply in 2/2 live attempts. Not fixed here (would mean
  editing `generation.py`'s prompt, out of scope).
- **E3's facebook adapt prompt doesn't reliably end with a CTA**, which F8's `hook_story_cta`
  rubric requires ("ends with CTA") — real output failed this in 2/2 live attempts. Not fixed
  here (would mean editing `adapt.py`'s prompt).
- **F6's blog CTA-substring check** (`cta_target` must appear verbatim in `body_tagged`) is very
  unlikely to be satisfied by real E2 output, since the E2 system prompt never instructs the
  model to literally embed the raw CTA URL in prose — only lists it as context. Real blog pieces
  held on F6 in both live attempts for this reason (in addition to F3/F4).

None of the three items above were fixed in this issue — they're prompt-engineering gaps in
E2/E3 (AA-368's own deliverable), flagged for a follow-up, not silently patched here.

## Gaps found during live verify (out of scope, NOT fixed here — reporting only)

1. **No real slot-runner** (AA-375, confirmed, not built here — see STEP 0 findings above).
2. **`brand_rubric_text` has no real production fetch path** — nothing in the codebase supplies
   it from a tenant's actual brand rules table; callers (including this verify script, initially)
   have to know to reuse `AA_BRAND_IDENTITY_PROMPT` themselves. Worth a real ticket.
3. **E2/E3 prompts don't reliably satisfy F3/F4/F6(blog-CTA)/F8(social-CTA)** — real generated
   content held on these in the large majority of live attempts (blog: 6/6; facebook: 5/6).
   Likely root cause below (#4), not a prompt-wording nit on its own.
4. **`run_piece_through_produce_gates()` still hardcodes `max_repairs=0`** (`pipeline.py`,
   `_repair_not_available()`) — its own docstring's justification ("repair requires E1-E5
   generation infra, not yet built") is now STALE: E1-E5 (AA-368) exists. Without a real
   `repair_fn` wired in, a real piece that fails any DET/LLM gate has no path back to `passed`
   except a full fresh regeneration — which is why this verify needed 6 attempts (5 of them
   fully run) to get 1 passing piece. This is the most load-bearing finding from this verify:
   packets will rarely fill with real content until repair is wired. Recommend a follow-up issue
   (repair_fn wiring into `pipeline.py`, using E1-E4's own regenerate functions) — not attempted
   here, well outside AA-367's own scope.
