# AA-573 — Login stuck on "Connecting..." indefinitely

## STEP0 — root cause (confirmed by reading code, then reproduced live)

`frontend/app/login/page.tsx`'s `login()` had two independent problems, both
present since the page's original commit (`c5c35a5`) — not a regression:

1. **No double-submit guard.** Both `<input>`'s `onKeyDown` handlers called
   `login()` unconditionally on Enter, with no `loading` check (unlike
   `tenant-login/page.tsx`, which already had `!loading` on its one input).
   A double-Enter (or Enter racing the button click) fired **two** concurrent
   `login()` runs → two `POST /api/auth/login` → two `router.push("/admin/
   dashboard")`. Live-reproduced locally: before the fix, a scripted
   double-`Enter` press produced exactly 2 POSTs and 2 `GET /admin/dashboard`
   fetches — the same "2 lần gọi /login" pattern Nghiệp's Network-tab
   evidence showed.
2. **No `finally { setLoading(false) }` on the success path.** `router.push`
   is fire-and-forget — it doesn't return a promise the code awaits. The
   code's only path back to `loading=false` was the `catch` block or the
   `!res.ok` branch. If the client-side transition to `/admin/dashboard`
   ever failed to complete for *any* reason, the button was stuck at
   "Connecting..." with **no recovery path but a manual refresh** — this is
   the deterministic mechanism behind the reported symptom, regardless of
   what actually triggers a stalled transition.

**What can stall the transition**: `middleware.ts`'s `verifyAdminToken()`
re-verifies the JWT that was *just* issued, via its own uncached
`POST /auth/verify-admin` round trip — the identical uncached-round-trip
shape `docs/implementation-notes/AA-551.md` already diagnosed and fixed for
`/api/admin/*` BFF proxy calls (`lib/auth-server.ts`'s `requireAdmin()`), but
middleware.ts is a separate module and never got that fix. Under any
transient latency between the freshly-set cookie and this next request, the
verify call can lose the race and redirect back to `/login` — matching the
Network-tab evidence (`dashboard` fetch → 307 → a second `login` fetch → 200).

## Fix

`frontend/app/login/page.tsx`:
- `login()` now returns early `if (loading) return;`.
- Both `onKeyDown` handlers gained `!loading` (mirrors `tenant-login`).
- Post-login navigation changed from `router.push(...)` to
  `window.location.href = ...` — a real browser navigation instead of a
  client-side App Router transition, so whatever the server ultimately
  serves is what renders (no more silently-stuck client transition state),
  and `useRouter`/`router` were removed as now-unused.

`frontend/lib/auth-server.ts`:
- Exported `adminVerifyCache`/`tenantVerifyCache` (previously module-private)
  so `middleware.ts` can share them.

`frontend/middleware.ts`:
- `verifyAdminToken()`/`verifyTenantToken()` now check the shared cache
  before making their own `/auth/verify-*` round trip, and populate it on a
  successful verify — closes the actual race, not just the visible symptom.

## Changed vs. original ask

Issue asked to "fix so UI auto-redirects after 200". The literal ask is
satisfied by the `page.tsx` change alone. The `middleware.ts`/`auth-server.ts`
change goes one layer deeper (closes the race that can *cause* a stalled
transition in the first place) — included because STEP0 traced the stall
mechanism there and AA-551 already established this exact cache-sharing
pattern as the fix for the same class of bug; leaving it out would fix the
symptom (permanent stuck UI) but leave the underlying bounce-back-to-/login
race live.

## Tradeoffs

- `window.location.href` costs a full page reload instead of an SPA
  transition on every login (one-time cost per session, not a hot path) —
  traded for eliminating an entire class of Next.js client-router edge cases
  around server-driven redirects during a transition.
- Did not add a client-side timeout/watchdog on `loading` as a second safety
  net — the full-navigation fix removes the condition that caused the stall,
  and an artificial timeout would just paper over the symptom rather than a
  cause.

## Should know before reading the diff

- `tenant-login/page.tsx` was NOT changed — it already guarded double-submit
  (`!loading` on Enter, `disabled={loading}` on the input) and already had
  `finally { setLoading(false) }`, so it does not exhibit the "stuck forever"
  symptom even though it shares the same underlying middleware race. Live-
  verified working end-to-end regardless (see Live Verify).
- Credentials used for live-verify: `e2e-test-admin` / `e2eTest2026!` (staff,
  reused across many prior sessions' e2e specs) and a freshly-generated API
