# AA-425 — [A/T-T2-T5] Tenant Rewrite → QA Gate → Tour Pool → Atomize

Implemented per the updated plan (AA-425 Linear comment, 21/08, after AA-426's finding): no temp
trigger endpoint — extended the flow that already runs when `PoolTab.tsx`'s "Rewrite" button calls
`POST /pool/{id}/rewrite` (`v1_tours.py:179` → `_do_rewrite_and_save()` closure). T1 (the trigger
UI/endpoint) is out of scope for this issue — it already exists, just needs a relabel later.

## Decisions

- **Where T3/T5 got spliced in**: inside `_do_rewrite_and_save()` (`v1_tours.py`), right after T2's
  existing rewrite call, NOT inside `_rewrite_tour()` itself (`v1_pipeline.py:82`) — even though
  Nghiep's comment named that file:line. `_rewrite_tour()` is a shared primitive also called by
  admin's generic `/admin/run-tour` (Lane A1, no tenant_id, no atomize) — adding tenant-specific T3
  QA / T5 atomize logic there would incorrectly fire for admin batch content generation too.
  `_do_rewrite_and_save()` is already tenant-only (it's the closure inside the tenant-facing
  rewrite endpoint), so that's where the extension actually belongs. Flagging this since it's a
  literal deviation from the file:line named in the decision comment, even though the *intent*
  ("wherever T2 currently ends, in the tenant flow") is followed exactly.
- **New module `services/acp_produce/tenant_pipeline.py`** holds T3 (`run_t3_qa_gate`,
  `escalate_t3_failure`) and T5 (`run_t5_atomize`) — kept out of `v1_tours.py` to avoid that file
  growing further and to make T3/T5 independently testable.
- **T3 structural check** reuses `validate_node`'s own verdict — `result["failure_codes"]`, already
  computed by T2's own graph run (`validate` node, `graph.py:448`) — instead of re-invoking
  `validate_node` a second time on identical content. Satisfies "reuse validate_node" without
  redundant computation.
- **T3 grounding check** reuses `find_novel_numeric_claims()` (`services/acp_shared/grounding.py`)
  but, unlike `s1_from_atom.py`'s citation-keyed `check_grounding()`, compares each rewritten
  sentence against the WHOLE T2-input corpus (`tour_dict.values()`), not a specific cited atom's
  text. `graph.py`'s free-writing engine (what T2 uses, per the issue) produces no `[R:atom_id]`
  citations to key a per-citation check off of the way `s1_from_atom.py`'s atom-assembly engine
  does — that's a genuinely different (and not yet wired into T2) engine, not reused here per the
  issue's explicit choice of `content_generation/graph.py`.
- **T3 repair loop is NOT `services/acp_produce/gates.py::run_gates()`** — confirmed by reading it:
  that function is typed around N7's `Piece` object (`piece.body_tagged`/`gate_ledger`/
  `repair_count`), a much richer domain object than a tour dict. Adapting it would mean
  constructing a fake `Piece`, not really reusing it. Reimplemented the same gate-then-repair
  SPIRIT (bounded rounds, re-check everything after each repair) at T3's actual scale.
  `TENANT_QA_MAX_REPAIRS = 2` is a new, separate constant from `acp_produce.models.
  REPAIR_TOTAL_MAX` (=3, N7's unrelated budget) per Nghiep's explicit naming guidance.
- **`shared.tenant_atom_state`-vs-`acp_contract.tour_atoms` distinction (AA-422) matters here**:
  T5 writes to `acp_contract.tour_atoms` with `owner_scope = tenant_id`, NOT to
  `tenant_atom_state` — that table is per-tour state (starred/cooldown/usage_log), not where atom
  content lives.
- **Idempotency fix in `run_t5_atomize` vs. the admin path it's adapted from**
  (`v1_atoms.py::_decompose_inline`): the `source_hash` lookup that decides "skip, source
  unchanged" is scoped to `(tour_id, owner_scope)` together, not `tour_id` alone. The admin path
  never needed this (owner_scope was always `'platform'`) but two different tenants rewriting the
  same underlying `tour_id` would otherwise read each other's most-recent atom row.
- **Migration 107**: `tenant_tour_versions` gets `qa_status`/`qa_repair_count`/`qa_checked_at`
  (decision a — checked live schema first via ECS exec, confirmed no existing QA column, ALTERed
  rather than a new table). `review_queue.generated_content_id` (FK to
  `silver_aa_internal.generated_content`, the admin/N4 pipeline's own table) made nullable — a
  tenant-rewrite escalate has no such row and forcing an unrelated id in would violate the FK.
  Added `tenant_tour_version_id` (real FK back to the source row) and `escalate_detail jsonb` (the
  issue's mandated `{check_id, field, description, source_span, suggested_fix}` shape) — decision
  (b) said reuse `review_queue`, this is the minimum ALTER needed to actually do that.
- **T5-failure handling (decision c)**: confirmed — a T5 failure does not roll back T2-T4; the tour
  stays in `tenant_tour_versions` (already QA-passed, valid for the tenant to see/use), only the
  atomize step itself failed. Logged (`tenant_atomize_done` with `t5_status`), no persisted
  failure-state column and no retry scheduler built — the issue's own text calls this a future,
  separate concern ("atomize retry riêng"), not something this issue builds.
- **Anti-GC fix on the background task**: added a module-level `_background_tasks` strong-ref set
  in `v1_tours.py`, mirroring `admin_pipeline.py`'s existing AA-223 pattern (that file's own
  comment explains why: `asyncio.create_task()` alone only holds a weak ref, so an unreferenced
  task can be GC'd mid-flight). The pre-AA-425 code fired-and-forgot with no ref at all; T3's
  repair loop + T5 add real additional async work on top of T2, so this bug's odds of firing went
  up meaningfully by touching this code — fixed while here rather than left as a now-more-likely
  landmine.

## Changed

- New: `services/acp_produce/tenant_pipeline.py` (T3 QA gate + T5 atomize).
- New: `api/migrations/107_aa425_tenant_qa_gate.sql`.
- `api/routers/v1_tours.py`: `_do_rewrite_and_save()` now runs T3 (self-repair, max 2 rounds) after
  T2 succeeds; on pass, runs T5 (atomize); on fail, escalates to `review_queue` instead of T5.
  `qa_status`/`qa_repair_count`/`qa_checked_at` now written on every completed rewrite. Added
  `_background_tasks` strong-ref set (anti-GC).

## Tradeoffs

- `tenant_pipeline.py` imports helper functions (`_build_user_prompt`, `_source_hash`,
  `_strip_json_fence`, `_SYSTEM_PROMPT`) directly from `api/routers/v1_atoms.py` — a services-layer
  module reaching into an api-layer router file. Architecturally these helpers would better live in
  a shared `services/` module, but moving them touches working, unrelated admin-atomize code beyond
  this issue's scope — importing them where they already live is the smaller, safer change.
