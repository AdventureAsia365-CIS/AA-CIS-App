## Tradeoffs

- **Việc B.3 (merge evaluation)**: considered introducing a shared `shared/llm_client/
  openai_direct.py` helper both `judge_node.py` (S1) and `judge_client.py::invoke_judge_gpt41()`
  (N7) would call, to DRY the ~15 duplicated lines of `openai.OpenAI(...).chat.completions.
  create(...)` construction. **Decided against it, for now**:
  1. `judge_client.py`'s own docstring and a real test
     (`test_judge_client_module_never_imports_generation_or_writer_modules`) enforce an explicit
     isolation guarantee (ADR-2026-014/027 L3) via import-graph structure, not just convention.
     A shared helper wouldn't *break* that guarantee (it's about not importing the writer's own
     prompt-building modules, not about generic provider clients) but it does add a new shared
     surface between two modules whose separateness is a deliberate, tested property — the risk/
     reward is asymmetric for a genuinely temporary state.
  2. This is explicitly a TEMPORARY stand-in (task's own point 5) pending GPT-5.6 unblocking.
     Investing in a shared abstraction for a state everyone expects to change again is premature
     — better to revisit consolidation once the two pipelines' judge backends actually settle
     long-term (see Việc C: a DB-driven model-select design would make this question moot by
     routing both through one config-driven call site anyway).
  3. The two call sites aren't even the same shape today — `judge_node.py` goes through
     `LLMClient.generate(model_tier="gpt-4.1")` (part of the general multi-provider client),
     while `judge_client.py::invoke_judge_gpt41()` is a deliberately separate direct
     `openai.OpenAI()` construction (chosen in AA-351-03 specifically to avoid `LLMClient`'s
     Bedrock-first fallback chain). Merging them would mean either giving `LLMClient` a
     Bedrock-skip mode or accepting the fallback-chain behavior in the N7 judge, both bigger
     changes than this task asked for.

## Việc C — Model-select design (NOT built, design only)

### 1. Schema — `shared.llm_role_config` (would be migration 135)

```sql
-- 135_llm_role_config.sql
CREATE TABLE shared.llm_role_config (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    role          TEXT NOT NULL CHECK (role IN ('writer', 'judge')),
    provider      TEXT NOT NULL CHECK (provider IN ('anthropic-bedrock', 'openai-direct')),
    model_id      TEXT NOT NULL,   -- writer: 'sonnet' | 'haiku' (matches invoke_claude()'s own
                                    -- model= param). judge: 'gpt41' (matches JUDGE_MODEL's own
                                    -- values) -- literal strings the existing code already
                                    -- understands, not new vocabulary.
    account_route TEXT CHECK (account_route IN ('acc1', 'acc3') OR account_route IS NULL),
                                    -- writer only: which satellite account to try FIRST.
                                    -- NULL for judge (OpenAI direct has no AWS account routing).
    is_active     BOOLEAN NOT NULL DEFAULT true,
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_by    TEXT NOT NULL,   -- admin user id/email, same convention as content_piece's
                                    -- reviewed_by (AA-241)
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Exactly one active config per role at any time.
CREATE UNIQUE INDEX uq_llm_role_config_active_role
    ON shared.llm_role_config(role) WHERE is_active;

INSERT INTO shared.schema_versions (version, applied_at, description)
VALUES (135, now(), 'llm_role_config — admin-selectable writer/judge model')
ON CONFLICT DO NOTHING;
```

**Append-only history, not in-place UPDATE** — a model switch is INSERT new active row +
UPDATE previous active row for that role to `is_active = false`, in one transaction. Mirrors
this repo's existing Gate A/B row-lock convention (`services/acp_planning/quarter.py` — "same
row-locked approve, reject re-approval pattern"), and gives a free audit trail (who changed the
judge model and when) without a separate audit table.

**Seed data** (2 rows, one per role, `is_active = true`, `updated_by = 'system-seed-aa518'`):
```sql
('writer', 'anthropic-bedrock', 'sonnet', 'acc3', true, ...)
('judge',  'openai-direct',     'gpt41',  NULL,   true, ...)
```
— matches what's live today exactly, so shipping the migration changes nothing until an admin
actually touches the UI.

### 2. Real reconciliation gap found while re-reading `client.py` — flagging before designing edit points

`request.model_tier` ("haiku"/"sonnet") is currently an intentional **per-call-site** choice —
different callers pick haiku for cheap/fast tasks and sonnet for premium editorial quality; it
is not one global "the admin's chosen model" knob today. So a single "writer" admin row cannot
cleanly override every caller's `model_tier` without contradicting that existing design intent.

What a global "writer" row **does** map cleanly onto: **which satellite account is tried
first** — `account_route` (acc3 vs acc1). That part genuinely is one hardcoded global order
today (`generate()` always tries T1.5a=acc3 before T1.5b=acc1, at both the sonnet and haiku
tiers) — a real, single knob, useful for a real scenario (acc3 having an outage or losing
access — flip to acc1-first without a code deploy). `model_id` for the writer role is scoped
narrower than "judge" role's: it's the tier used **only when a caller passes no explicit
`model_tier`** (`DEFAULT_MODEL_TIER`'s current job) — most call sites already pass one
explicitly and stay unaffected.

Judge is cleaner — `JUDGE_MODEL` is already exactly one global string today
(`"nova_pro"`|`"gpt56"`|`"gpt41"`), so the judge row is a direct 1:1 replacement, no
reconciliation needed on that side.

**Scope decision, following the build prompt's own framing** ("Chỉ 2 nhà cung cấp thật khả dụng
hôm nay: Claude... và GPT...") — the UI's Judge dropdown offers **GPT options only** (GPT-4.1
available; GPT-5.6 Sol/Terra/Luna shown blocked, not hidden). Nova Pro stays fully functional in
code (still the deep fallback / manually settable via `model="nova_pro"`) but is **not** a
dropdown option in this v1 design — flagging this explicitly in case Nghiệp wants it included.

### 3. Concrete edit points (for the future BUILD pass, not done now)

New module `shared/llm_client/role_config.py`:
```python
@dataclass
class RoleConfig:
    provider: str
    model_id: str
    account_route: str | None

def get_active_config(role: str) -> RoleConfig:
    """DB-backed, 30s in-memory TTL cache (mirrors shared/secrets.py::_get_cached, just a much
    shorter TTL — this is admin-facing, wants near-live effect, not secret-rotation-rare).
    On any DB error: log + return the last good cached value if one exists, else a hardcoded
    safe default (writer: sonnet/acc3; judge: gpt41) -- never let a config-read failure break
    the writer or judge gate. No cross-process invalidation channel (Redis pub/sub etc.) --
    the TTL alone is enough at current scale (desired_count=1) and degrades gracefully if that
    ever changes (each task independently re-reads within its own window, no coordination
    needed)."""
```

### 2. Real STEP0 finding: `stage` had to be call-site granular, not "A0/A1/T2"-phase granular

The build prompt's own example list ("A0, A1, T2, T5, T7, T8, T9...") doesn't map onto real code
structure. `services/content_generation/graph.py` (the S1 rewrite graph — `s1_generate`/
`s1_judge`/`s1_brand_audit`/`s1_flag_fix`/`s1_itinerary_nudge`) is the **identical code** whether
triggered by an admin A1 batch-rewrite (`admin_pipeline.py`) or a tenant T2 self-service rewrite
(`v1_tours.py::trigger_rewrite()` → `v1_pipeline.py::_rewrite_tour()`) — there is no code-level
"A1 vs T2" branch to hang two separately-configured model rows off of. What DOES differ per call
is `tenant_id` (`None` for A1, real for T2) — captured in `llm_call_log.tenant_id`, not in
`llm_role_config`. Config is keyed to the call site (`s1_generate`); usage/quality is keyed to
the call site AND the tenant. This is the one real, disclosed deviation from the build prompt's
own example stage names — the proposed SCHEMA (columns/types) needed no change, only which
strings go in the `stage` column.

**T7 has zero LLM call sites** — `v1_planning.py::get_slot_grid()` is pure read-only (confirmed
both by this STEP0 and the earlier AA-451 implementation notes) — so there is no `t7_*` stage;
not an omission.

### 3. Schema — as shipped, migration `137_llm_role_config_and_call_log.sql`

### 4. `shared/llm_client/role_config.py` + `call_log.py` — the read/write/log plumbing

- **Cache**: in-process dict, 20s TTL (`role_config.py::_CACHE_TTL_SECONDS`), `invalidate(stage)`
  called by `PATCH /admin/llm-config/{stage}` right after a successful DB write. This app runs
  `desired_count=1` (confirmed live, CLAUDE.md) — one process, so an in-process cache + explicit
  invalidate is a complete solution, not a partial one; no cross-process broadcast (Redis pub/sub
  etc.) needed at current scale. `get_stage_config_sync()` is what every non-`async def` call site
  uses (the majority — S1's graph nodes, all 5 N7 writer/judge functions, T5, s1_from_atom) via
  `asyncio.run()` — safe because every one of those already runs inside `asyncio.to_thread()`
  from its own async caller (AA-416's convention), so no event loop is already running on that
  worker thread. `get_stage_config()` (async) is used directly by `t8_angle_gen`'s `async def
  generate_angles()`.
- **Never breaks the writer/judge on a DB hiccup**: `SAFE_DEFAULTS` (a hand-kept dict, matches
  the seed exactly) is the final fallback; a stale cache entry is preferred over SAFE_DEFAULTS
  when the DB read itself fails (stale-but-real beats a hardcoded default).
- **`shared/llm_client/pricing.py`** (new): `BEDROCK_SONNET`/`BEDROCK_HAIKU`/`COST_TABLE`/
  `calc_cost()` relocated out of `client.py` (still re-exported there, zero breakage) so Mechanism-
  B call sites (which never imported `client.py`) can price a call without a heavier/circular-
  risking import.
- **`call_log.py`**: `record_call()` (async, opens its own short-lived connection — used by call
  sites with no `pool` in scope), `record_call_with_pool()` (async, reuses an open
  `asyncpg.Pool` — used by `t5_atomize`/`t8_angle_gen`, whose async callers already have one),
  `record_call_sync()` (the sync wrapper, same `asyncio.run()`-inside-`to_thread()` reasoning as
  above). All 3 swallow every exception and log a warning — a logging failure must never break
  the LLM call it's recording.

### 5. `shared/llm_client/client.py::generate()` — stage-aware now

`LLMRequest` gained `stage: Optional[str] = None`. `model_tier`'s pydantic default changed
`"haiku"` → `None` (grep-confirmed every real call site already set it explicitly before this
change, so the old default was already dead weight everywhere — see §6). `generate()`: `tier =
request.model_tier or (stage_cfg.model_id if stage_cfg else DEFAULT_MODEL_TIER)` — an explicit
per-request tier (AA-237's opt-in haiku→sonnet auto-upgrade, still fully intact) always wins over
the stage default, exactly mirroring `model_tier`'s pre-existing relationship with the
`DEFAULT_MODEL_TIER` env var. `account_route` (when the stage config says `"acc1"`) swaps which
satellite is tried FIRST in the T1.5a/T1.5b and T2.5a/T2.5b legs — the other account is still
tried second either way, so acc3-down resilience is unchanged, only the *order* is now admin-
controllable per stage (closing round-1's own "real, single, useful knob" finding).

### 7. Wireframe — "LLM Models" tab, added to the existing `/admin/settings` page

New tab in the existing `TabBar` (`frontend/app/admin/settings/page.tsx` — `pipeline` / `brand` /
`seo` / `tenant` already exist; `models` added as the 5th), not a new route — avoids the
"new admin page needs a middleware allow-list entry" gotcha entirely by reusing an already-
allow-listed route (`feedback_new_admin_page_middleware_allowlist` memory).

**Layout**: 16 rows grouped under 5 sub-headers matching the call-site groupings in §1 (S1
rewrite pipeline · T5 atomize · T8 angle generation · T9 write + T10 judge · N7 production
pipeline), each row: stage name (mono, e.g. `s1_generate`) + a short human label ("S1 — Content
generate", "N7 — E2 draft", ...) + role badge (writer/judge/validate, color-coded) + a model
`<select>` (options from `GET /admin/llm-config`'s own `options` field per row — judge rows show
GPT-4.1 selectable, GPT-5.6/Nova Pro shown with a "Blocked"/"Not recommended" pill and their real
reason, never hidden, per the build prompt's own "hiện nhãn 'chưa dùng được, lý do X'"
requirement) + an account `<select>` (acc3/acc1, only rendered for `provider='claude'` rows) +
last-updated (relative time + `updated_by`).

**Flow**: changing either dropdown marks that row "dirty" (a small unsaved-changes dot, Save
button enabled only for dirty rows — no bulk-save, one stage at a time, matching "đổi model ảnh
hưởng toàn hệ thống" being a deliberate, singular action) → click Save → confirm dialog (Card-
styled modal, not a native `confirm()`) showing the from→to diff explicitly ("s1_generate: Claude
Haiku 4.5 (acc3) → Claude Sonnet 4.5 (acc3)") → Cancel reverts the dropdown, Confirm calls `PATCH
/admin/llm-config/{stage}`.

**States**: row shows a small `Spinner` next to Save while the PATCH is in flight; on success the
row's "current" values update in place + a green "Đã lưu" toast (auto-dismiss); on error the
dropdown reverts to the last-known-good server value (never left showing an unsaved, unconfirmed
edit) + a red inline error message naming what failed, dismissible.
