# AA-518 — LLM/API audit follow-up: dead secret cleanup + judge unification + model-select design

Follow-up to the STEP0 4-channel LLM/API audit (02/09/2026, see memory
`project_aa519_llm_api_audit_02sep.md`). 3 parts: A (delete dead credential), B (unify judge on

## Decisions

- **Việc A**: `get_anthropic_key()` deleted outright, not just left dead. Confirmed 0 callers
  app-wide (grep across the whole repo, including tests) before removing. Matches
  `feedback_check_all_callers_before_deleting_shared_function` / `feedback_dead_code_deletion_
  needs_package_level_check` memory discipline — checked every reference, not just the obvious
  one.
- **Việc A infra**: the ECS secret injection is Terraform-managed (AA-CIS-Infra), not
  hand-editable via a one-off `register-task-definition`. Applied Terraform directly this
  session (Nghiệp's explicit go-ahead, twice — the classifier blocked `terraform apply` both
  times it ran real infra mutation and needed a fresh approval each time, not a standing grant).
  Order matters: registered the new task def revision → pointed the service at it → confirmed
  rollout COMPLETED + `/health` 200 → **only then** soft-deleted the actual Secrets Manager
  secret (7-day recovery window). Deleting the secret before the task def stopped referencing it
  would have broken any new container launch in between.
- **Việc B.1**: `invoke_judge_gpt41()` already existed (AA-351-03) and already mirrors
  `judge_node.py`'s exact client construction — the ask to "dùng đúng đường gọi có sẵn ở
  judge_node.py làm mẫu" was already satisfied by existing code. Only the *default* needed to
  change (`"nova_pro"` → `"gpt41"` in `invoke_judge()`), not new plumbing.
- **Việc B.2**: set `JUDGE_MODEL=gpt41` explicitly in the ECS task def (not just relying on the
  code default) so the pin is visible directly in `describe-task-definition` output, not buried
  in source. Exposed as a real Terraform variable (`judge_model`, default `"gpt41"`) in both
  `modules/ecs` and `accounts/aa365`, plus a `terraform.tfvars` line — matches this repo's
  existing convention of explicit pass-through for every other var, not relying on defaults
  alone.
- **Việc B.3 — do NOT merge the two judge call paths into one shared OpenAI wrapper** (see
  Tradeoffs below for the reasoning).

## Tradeoffs

- **Việc B.3 (merge evaluation)**: considered introducing a shared `shared/llm_client/
  openai_direct.py` helper both `judge_node.py` (S1) and `judge_client.py::invoke_judge_gpt41()`
  (N7) would call, to DRY the ~15 duplicated lines of `openai.OpenAI(...).chat.completions.
  create(...)` construction. **Decided against it, for now**:
  1. `judge_client.py`'s own docstring and a real test
     (`test_judge_client_module_never_imports_generation_or_writer_modules`) enforce an explicit
     isolation guarantee (ADR-2026-014/027 L3) via import-graph structure, not just convention.
     A shared helper wouldn't *break* that guarantee (it's about not importing the writer's own
     prompt-building modules, not about generic provider clients) but it does add a new shared
     surface between two modules whose separateness is a deliberate, tested property — the risk/
     reward is asymmetric for a genuinely temporary state.
  2. This is explicitly a TEMPORARY stand-in (task's own point 5) pending GPT-5.6 unblocking.
     Investing in a shared abstraction for a state everyone expects to change again is premature
     — better to revisit consolidation once the two pipelines' judge backends actually settle
     long-term (see Việc C: a DB-driven model-select design would make this question moot by
     routing both through one config-driven call site anyway).
  3. The two call sites aren't even the same shape today — `judge_node.py` goes through
     `LLMClient.generate(model_tier="gpt-4.1")` (part of the general multi-provider client),
     while `judge_client.py::invoke_judge_gpt41()` is a deliberately separate direct
     `openai.OpenAI()` construction (chosen in AA-351-03 specifically to avoid `LLMClient`'s
     Bedrock-first fallback chain). Merging them would mean either giving `LLMClient` a
     Bedrock-skip mode or accepting the fallback-chain behavior in the N7 judge, both bigger
     changes than this task asked for.

## Việc C — Model-select design (NOT built, design only)

### 1. Schema — `shared.llm_role_config` (would be migration 135)

```sql
-- 135_llm_role_config.sql
CREATE TABLE shared.llm_role_config (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    role          TEXT NOT NULL CHECK (role IN ('writer', 'judge')),
    provider      TEXT NOT NULL CHECK (provider IN ('anthropic-bedrock', 'openai-direct')),
    model_id      TEXT NOT NULL,   -- writer: 'sonnet' | 'haiku' (matches invoke_claude()'s own
                                    -- model= param). judge: 'gpt41' (matches JUDGE_MODEL's own
                                    -- values) -- literal strings the existing code already
                                    -- understands, not new vocabulary.
    account_route TEXT CHECK (account_route IN ('acc1', 'acc3') OR account_route IS NULL),
                                    -- writer only: which satellite account to try FIRST.
                                    -- NULL for judge (OpenAI direct has no AWS account routing).
    is_active     BOOLEAN NOT NULL DEFAULT true,
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_by    TEXT NOT NULL,   -- admin user id/email, same convention as content_piece's
                                    -- reviewed_by (AA-241)
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Exactly one active config per role at any time.
CREATE UNIQUE INDEX uq_llm_role_config_active_role
    ON shared.llm_role_config(role) WHERE is_active;

INSERT INTO shared.schema_versions (version, applied_at, description)
VALUES (135, now(), 'llm_role_config — admin-selectable writer/judge model')
ON CONFLICT DO NOTHING;
```

**Append-only history, not in-place UPDATE** — a model switch is INSERT new active row +
UPDATE previous active row for that role to `is_active = false`, in one transaction. Mirrors
this repo's existing Gate A/B row-lock convention (`services/acp_planning/quarter.py` — "same
row-locked approve, reject re-approval pattern"), and gives a free audit trail (who changed the
judge model and when) without a separate audit table.

**Seed data** (2 rows, one per role, `is_active = true`, `updated_by = 'system-seed-aa518'`):
```sql
('writer', 'anthropic-bedrock', 'sonnet', 'acc3', true, ...)
('judge',  'openai-direct',     'gpt41',  NULL,   true, ...)
```
— matches what's live today exactly, so shipping the migration changes nothing until an admin
actually touches the UI.

### 2. Real reconciliation gap found while re-reading `client.py` — flagging before designing edit points

`request.model_tier` ("haiku"/"sonnet") is currently an intentional **per-call-site** choice —
different callers pick haiku for cheap/fast tasks and sonnet for premium editorial quality; it
is not one global "the admin's chosen model" knob today. So a single "writer" admin row cannot
cleanly override every caller's `model_tier` without contradicting that existing design intent.

What a global "writer" row **does** map cleanly onto: **which satellite account is tried
first** — `account_route` (acc3 vs acc1). That part genuinely is one hardcoded global order
today (`generate()` always tries T1.5a=acc3 before T1.5b=acc1, at both the sonnet and haiku
tiers) — a real, single knob, useful for a real scenario (acc3 having an outage or losing
access — flip to acc1-first without a code deploy). `model_id` for the writer role is scoped
narrower than "judge" role's: it's the tier used **only when a caller passes no explicit
`model_tier`** (`DEFAULT_MODEL_TIER`'s current job) — most call sites already pass one
explicitly and stay unaffected.

Judge is cleaner — `JUDGE_MODEL` is already exactly one global string today
(`"nova_pro"`|`"gpt56"`|`"gpt41"`), so the judge row is a direct 1:1 replacement, no
reconciliation needed on that side.

**Scope decision, following the build prompt's own framing** ("Chỉ 2 nhà cung cấp thật khả dụng
hôm nay: Claude... và GPT...") — the UI's Judge dropdown offers **GPT options only** (GPT-4.1
available; GPT-5.6 Sol/Terra/Luna shown blocked, not hidden). Nova Pro stays fully functional in
code (still the deep fallback / manually settable via `model="nova_pro"`) but is **not** a
dropdown option in this v1 design — flagging this explicitly in case Nghiệp wants it included.

### 3. Concrete edit points (for the future BUILD pass, not done now)

New module `shared/llm_client/role_config.py`:
```python
@dataclass
class RoleConfig:
    provider: str
    model_id: str
    account_route: str | None

def get_active_config(role: str) -> RoleConfig:
    """DB-backed, 30s in-memory TTL cache (mirrors shared/secrets.py::_get_cached, just a much
    shorter TTL — this is admin-facing, wants near-live effect, not secret-rotation-rare).
    On any DB error: log + return the last good cached value if one exists, else a hardcoded
    safe default (writer: sonnet/acc3; judge: gpt41) -- never let a config-read failure break
    the writer or judge gate. No cross-process invalidation channel (Redis pub/sub etc.) --
    the TTL alone is enough at current scale (desired_count=1) and degrades gracefully if that
    ever changes (each task independently re-reads within its own window, no coordination
    needed)."""
```

`shared/llm_client/client.py`:
- `generate()` (top of method, before the `if tier == "sonnet":` branch) — resolve
  `primary_account, fallback_account` from `get_active_config("writer").account_route` instead
  of the hardcoded `"acc3"` then `"acc1"` literals currently baked into the T1.5a/T1.5b (lines
  ~80-100) and T2.5a/T2.5b (lines ~110-130) blocks. Replace those 4 literal `"acc3"`/`"acc1"`
  strings with the resolved variables.
- `tier = request.model_tier or DEFAULT_MODEL_TIER` (line 58) — change the fallback source from
  the `DEFAULT_MODEL_TIER` env var to `get_active_config("writer").model_id` (env var stays as
  the safe default if the DB read itself fails).

`services/acp_produce/judge_client.py::invoke_judge()`:
- `model = model or os.environ.get("JUDGE_MODEL", "gpt41")` → `model = model or
  get_active_config("judge").model_id` (env var + `"gpt41"` stay as the fallback chain if the DB
  read fails).

`services/content_generation/judge_node.py` — **the real open question, not resolved here**:
today this builds `LLMRequest(model_tier="gpt-4.1", ...)` and calls `LLMClient.generate()`,
which understands Bedrock tiers and `"gpt-4.1"` but NOT `"nova_pro"`/`"gpt56"` — those only
exist inside `judge_client.py`'s separate `invoke_judge()`. Making S1's judge (this file) and
N7's judge (`judge_client.py`) actually share one admin-controlled row means either (a) teaching
`LLMClient` to also support `nova_pro`/`gpt56` tiers, or (b) having this file call
`judge_client.invoke_judge()` directly instead of going through `LLMClient` (not an isolation
violation — that guarantee is about not importing the *writer's* modules, and this is S1's own
judge calling N7's judge client, not the writer). Either is real code work with its own testing
surface on a currently-stable production judge — **deferred to the BUILD pass**, flagging now so
it isn't a surprise later: shipping the DB table alone does NOT yet make the two pipelines'
judges actually share one control unless this piece is also done.

### 4. Wireframe

Interactive click-through mockup (no backend, fake state transitions only):
https://claude.ai/code/artifact/c2312d56-b3b2-4f41-a8ae-e3776457c19a

Layout: 2 stacked role cards (Writer / Judge), each showing the current active config, an
inline expandable option list restricted to confirmed-available options (radio-style, one
selection), an explicit Save button (not autosave — this affects the whole platform), a confirm
dialog before applying (shows the from→to diff explicitly), and loading/success/error toast
states (one Judge option is wired to always "fail" in the demo, specifically to show what the
error state looks like). Blocked models (GPT-5.6 Sol/Terra/Luna) stay listed in the dropdown
with a "Blocked" pill and their real reason, never hidden — per the build prompt's explicit
requirement. Palmyra X5 is the deliberate contrast case noted in the footer: permanently
rejected models don't appear at all (different from a temporarily-blocked one), and the wireframe
calls that distinction out explicitly rather than leaving it implicit.
