# AA-521 — Admin logout doesn't clear httpOnly `cis_admin_token`

## Decisions
- Mirror AA-427's `/api/auth/tenant-logout` shape exactly: one server route,
  `response.cookies.set(name, "", { path: "/", maxAge: 0 })` per cookie, POST
  only, `{ ok: true }` body. No new abstraction needed for one more cookie set.
- New route clears all 4 admin-session cookies (`cis_admin_token`, `cis_role`,
  `cis_user`, `cis_api_token`) server-side, not just the httpOnly one — makes
  the route the single source of truth for "log this session out" instead of
  splitting the clear between a client loop (display cookies) and a server
  call (the real one). Sidebar callers no longer need their own
  `document.cookie` loop at all.
- Scope widened beyond the issue's literal ask: `frontend/app/(internal)/
  _components/InternalSidebar.tsx` had the byte-identical bug. Reviewer-role
  sessions (the `/upload`, `/review`, `/catalog`, `/brand` content-team
  pages) go through the same `/auth/admin-login` JWT flow as admin and carry
  the same httpOnly `cis_admin_token` cookie — leaving that sidebar
  unfixed would have left the exact same vulnerability open via a different
  entry point. Fixed both call sites with the same new route.

## Changed
- New: `frontend/app/api/auth/admin-logout/route.ts`.
- `frontend/app/admin/_components/AdminSidebar.tsx` — `logout()` now
  `async`, calls the new route (best-effort, `try/catch` swallowed) before
  `router.push("/login")`.
- `frontend/app/(internal)/_components/InternalSidebar.tsx` — same change,
  same new route (reviewer/content sessions).

## Tradeoffs
- Client-side clear removed entirely rather than kept as defense-in-depth —
  the server route already clears the same cookie names, and keeping a
  redundant client loop around risked the two lists drifting apart again.
  If content-role's `cis_api_token` cookie shape ever changes, there's now
  one route to update, not three.
- Did not touch `verifyAdminToken()`/middleware.ts — no server-side token
  revocation list added. A stolen JWT used directly (e.g. replayed via curl
  with the raw cookie value, bypassing the browser) is still valid until
  natural 24h expiry; this fix only closes the "same browser after logout"
  vector the issue described. Out of scope — would need a revocation table,
  not asked for here.

## Should know
- `cis_admin_token` is the only real credential (JWT, verified server-side
  each request); `cis_role`/`cis_user` are client-writable display cookies
  with no proof value on their own — clearing them alone (the old behavior)
  still let `verifyAdminToken()` accept a hand-set `cis_role=admin` cookie
  paired with the still-valid old JWT if an attacker also still had that
  cookie value (e.g. shared/left-open browser). That's the actual exploit
  this closes.
- content-role login (`login/route.ts`'s early-return branch) never sets
  `cis_admin_token` at all — only reviewer/admin do, via the shared JWT
  path. The route clears it unconditionally regardless (a no-op delete of an
  absent cookie is harmless), so one route covers all three roles.
