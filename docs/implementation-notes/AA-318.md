# AA-318 (gộp AA-289) — Log full prompt + prompt versioning

## Decisions

- **Followed Nghiệp's 03/09/2026 decision verbatim**: log full prompt text (option 1 of the
  4 originally listed), tied to prompt versioning, no conditional/debug-flag gating (that was
  option 3, not chosen). Read AA-289 first as instructed — it turned out AA-289 (Done, PR #94)
  already built most of the "versioning" half: a `prompt_version` (`sha256[:8]` of the system
  prompt) computed per generation call, persisted into `generated_content.metadata` (S1-old) /
  `acp_contract.s1_from_atom_runs` (S1-from-atom), plus a whole separate `shared.
  prompt_eval_runs` table (migration 089) for the on-demand Golden-Tours regression gate. So
  this task's real remaining gap was narrower than the original issue text implied: (a) the
  full-prompt-content logging genuinely never existed, (b) a real bug meant the versioning data
  that DOES exist was unreadable through its own UI (see next bullet).
- **Real bug found and fixed, not just the logging gap**: `api/routers/admin_pipeline.py::
  get_tour_history()` (backs `TourDetailPanelV2.tsx`'s "Rewrite History" tab) selected a bare
  `gc.prompt_version` column. Grepped every migration — that column has never existed on
  `silver_aa_internal.generated_content` (only `metadata->>'prompt_version'`, a JSONB field, by
  AA-289's own deliberate design — see `_build_generated_metadata()`'s docstring). Every real
  call to this endpoint would raise `UndefinedColumnError`. This is squarely in scope: it's the
  read-path for the exact prompt-versioning feature this issue is about, and it directly blocks
  "khả năng verify prompt version qua thời gian" through the UI (the actual outcome AA-318 asks
  for), not a tangential find.
- **Both pipelines get the full-prompt log**, not just S1-old (`graph.py`) which the original
  gap report named. `services/content_generation/s1_from_atom.py` already computes its own
  `prompt_version` (AA-289) but never logged the prompt at all, length or content — same gap,
  sibling pipeline. Added the equivalent `logger.info("llm_prompt_built", ...)` there too, for
  consistency and because a future S1-from-atom prompt bug would otherwise hit the identical
  "can't observe the request" wall AA-314 hit for S1-old.
- **Confirmed safe to log in full (STEP0, decision item 2)**: grepped `prompts.py` + `graph.py`
  + `s1_from_atom.py` for `os.environ`/`SECRET`/`API_KEY`/`password`/`credential` — zero matches.
  Both prompts are built purely from static instruction text, brand rules (the tenant's own
  brief, already visible to them elsewhere in the product), and tour/atom content (also
  tenant/admin-visible elsewhere). No secret material can reach these log lines.
- **`prompt_version` included in the same log line** as the full prompt text (decision item 3/4
  — "kết hợp" both needs with one mechanism) — a specific logged prompt can be tied back to
  `generated_content.metadata.prompt_version` (and now the Rewrite History UI) without a
  separate correlation step.
- **UI**: added a "Prompt" column to the Rewrite History table — `HistoryRow.prompt_version`
  was already a typed field on the frontend interface but never rendered anywhere (dead field).
  Shows the short hash as a mono pill; an admin scanning this column for a version-to-version
  change IS the actual regression signal this issue's "quan sát prompt version qua thời gian"
  goal describes. No new endpoint/data needed — the field was already being fetched, just never
  displayed (compounding the fact the backend column it read never resolved anyway).
- **Did not add a NEW dedicated versioning table** — AA-289's `prompt_eval_runs` already covers
  the "structured comparison over time" need decision item 4 raises as a fallback ("nếu cần...
  cân nhắc thêm 1 bảng DB riêng"); building a second one would duplicate it without a new need
  identified.

## Changed

- `services/content_generation/graph.py::generate_node()` — the `llm_prompt_built` log call
  gains `system_prompt_text` (full), `user_prompt_text` (full — this is the field that would
  have let AA-314's original verification actually read the Highlights section in CloudWatch),
  and `prompt_version`. `prompt_len` kept unchanged for backward compatibility with any existing
  CloudWatch query/dashboard built against it.
- `services/content_generation/s1_from_atom.py::generate_s1_from_atom()` — new `llm_prompt_built`
  log call (previously logged nothing about the prompt at all), same shape, once per retry
  attempt (system prompt is stable across retries within one call; user prompt varies with the
  atom pack + feedback).
- `api/routers/admin_pipeline.py::get_tour_history()` — `gc.prompt_version` → `gc.metadata->>
  'prompt_version' AS prompt_version`. Real bug fix, not a refactor.
- `frontend/app/admin/_components/TourDetailPanelV2.tsx` — new "Prompt" column in the Rewrite
  History table.
- Tests: `tests/unit/test_aa318_prompt_log_versioning.py` (new) — `structlog.testing.
  capture_logs()` asserts both pipelines' `llm_prompt_built` events carry real prompt content
  (not just a length), plus 2 tests pinning the `get_tour_history()` fix (one exercising the
  actual returned shape, one a direct regression guard on the SQL string itself so a future
  edit can't silently reintroduce the bare-column bug). Full `tests/unit/`: 1777 passed, 0 new
  failures. Frontend: `tsc --noEmit` clean, `next build` succeeds.

## Tradeoffs

- Logging full prompt text on every real LLM call meaningfully increases CloudWatch log volume/
  cost versus the pre-existing length-only line — this was the exact tradeoff the original gap
  report flagged as needing Nghiệp's decision, and the 03/09/2026 decision explicitly chose
  "log full" (option 1) over "log conditionally" (option 3), so no opt-in/debug-flag gating was
  added. `/ecs/aa-cis-dev`'s CloudWatch retention is 14 days (per prior audit), which bounds how
  long this extra volume persists.
- `prompt_version`'s own definition is unchanged from AA-289 (hash of the system prompt only,
  not including the variable user-prompt/tour-data portion) — this task didn't revisit that
  scope; it's the correct granularity for "did the PROMPT TEMPLATE change" (AA-289's own stated
  purpose), separate from per-tour content which is expected to vary every call regardless.

## Should know

- The "Prompt" column added to Rewrite History shows the version an admin can already read from
  `generated_content.metadata` — this task did not add any NEW prompt_version computation or
  change what gets hashed, only fixed the read path and surfaced it in the UI that was already
  fetching (but silently dropping) the field.
- Not live-verified against real deployed CloudWatch (would need a real `/admin/run-tour` call
  post-deploy to confirm the full prompt actually appears in a live log line, matching AA-314's
  own original verification need this issue traces back to) — the structlog capture-based unit
  tests directly assert the log call's kwargs, which is the same guarantee a live CloudWatch
  read would confirm, minus the actual AWS round-trip. No DB/infra state changed by this PR.
