# AA-494 — Build Step 1: choose_angle() unset-others prerequisite fix

**Scope of this PR:** ONLY the `choose_angle()` bug fix identified as AA-494's mandatory
prerequisite (Decision 3 of `docs/claude_tasks/AA-494-design-atom-angle-piece-reuse.md`).
No schema changes, no status-value redesign, no other part of AA-494's design. See that
design doc for the full plan this is step 1 of.

## Decisions

- Fixed via an explicit second `UPDATE ... SET chosen = false WHERE request_id = $1 AND
  idx != $2` in the same transaction as the existing `SET chosen = true`, rather than a
  single `SET chosen = (idx = $2) WHERE request_id = $1` statement. Kept as two
  statements so the existing "no angle option idx=N for this request" existence check
  (via the first statement's `UPDATE 0` result) stays intact unchanged — a single
  combined statement would always report a row count equal to however many options
  exist for the request, losing that specific error signal.
- Did not touch the `status == 'pending_choice'` guard at the top of `choose_angle()`.
  That guard is what makes this bug currently harmless (nothing can call `choose_angle()`
  a second time for the same request in the live code path today) — loosening it is
  explicitly Decision 3's job, a separate future PR, not this one.

## Changed

- `services/acp_angle_gate/service.py::choose_angle()` — added the unset-others UPDATE.
- `tests/unit/test_aa449_angle_gate_service.py`:
  - `TestChooseAngle::test_happy_path_sets_chosen_and_approved` — updated
    `conn.execute.side_effect` from 2 to 3 items (the new unset call is now a 3rd
    `execute()` call) and added an assertion that the unset call fired with the correct
    `(request_id, idx)` args.
  - New `TestChooseAngle::test_choosing_twice_unsets_previous_choice` — the build task's
    required "exercise `choose_angle()` twice" test. The existing status guard blocks a
    real second call today, so this test uses a new stateful fake connection
    (`_StatefulAngleOptionConn`) that tracks `angle_gate_option.chosen` state directly
    across two calls (resetting `request_status` back to `pending_choice` between them,
    simulating a future loosened guard) — verifies only the most-recently-chosen idx
    ends up `chosen=True` after the second call. This is a data-state assertion, not a
    call-count assertion, since that's what the bug actually was.

## Tradeoffs

- The new test double (`_StatefulAngleOptionConn`) is a different mocking style than
  this file's existing `AsyncMock` + `side_effect` convention. Necessary because the
  bug is about final DB state across 2 sequential calls, which a call-count/args-only
  mock can't express — accepted the inconsistency in mocking style for a meaningfully
  stronger test rather than force-fitting the existing pattern.
- No migration, no live schema touch — this is a pure logic fix, matches the build
  task's explicit requirement.
