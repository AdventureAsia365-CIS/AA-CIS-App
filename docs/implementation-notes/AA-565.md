## Wireframe v2 (2026-09-08) — direction reversal after Claude Chat feedback

Claude Chat's answers to wireframe v1's 3 questions came back as a bigger change than a simple
pick, not "sync with Admin's columns" anymore — tenant-specific column set, one row per tour
(latest version only, version history hidden from UI but NOT deleted from DB), Save + Save as
New Version merged into one button, VersionHistory no longer rendered in the tenant drawer
(component itself untouched — Admin still uses it). Full detail + wireframe v2 posted as a
Linear comment; superseded wireframe v1's columns/filters (v1's Score/Version columns and
Country/Score/Version dropdown question are now moot — decided against).

### Real finding while investigating the Save-merge instruction (`saveEdit()` in `CatalogTab.tsx`, `PATCH /v1/tours/versions/{id}` in `api/routers/v1_tours.py:908-957`)

- The header "Save" button and the footer "Save as New Version" button were **already 100%
  identical** before this task — both wired to the same `onClick={saveEdit}`, same request body
  (`action: "edit"`). Merging the two BUTTONS is risk-free by itself.
- But the backend's `action == "edit"` branch **always `INSERT`s a brand-new
  `tenant_tour_versions` row** (`status='pending'`, `edit_source='tenant_edit'`) — it never
  `UPDATE`s the existing row. So every existing "Save" click today, under either button label,
  already silently creates a new pending version. Claude Chat's stated intent for the merged
  button ("ghi đè/cập nhật thành phiên bản mới nhất, KHÔNG tạo 2 bản song song") describes
  in-place overwrite semantics that **do not exist anywhere in the current code** — achieving it
  is a backend behavior change (UPDATE instead of INSERT), not a frontend button merge. Flagged
  back to Claude Chat as an open question rather than assumed.
- Separately, a real pre-existing bug found in passing (not part of this issue's scope,
  disclosed for awareness): `saveEdit()`'s success handler (`CatalogTab.tsx:231`) never updates
  `selected`/`detail` to the `new_version_id` the backend returns — unlike `doAction()`
  (`CatalogTab.tsx:213`), which does `setDetail(upd); setSelected(upd)` on approve/reject. So
  immediately after a Save, `selected.id` still points at the pre-edit version; a subsequent
  "Add to Catalog"/"Request New Version" click PATCHes that stale old-version id, not the
  freshly-created pending one. Superseded by wireframe v3 below (Add to Catalog removed
  entirely) — bug moot, no longer needs a separate decision.

## Wireframe v3 (2026-09-08) — direction reversal #2, larger scope: drop version/approval concept entirely from tenant UI

Claude Chat's Decision 1 replaces the whole Save-merge question: no manual approval step at
all ("Add to Catalog" removed), no visible status vocabulary (Queued/In Catalog/Ready to
Review/New Version Requested, "AI Generated" language) anywhere in tenant UI, "Request New
Version" kept but renamed away from "version," and pending/generating tours show inline
loading in place of a status badge. Decision 2 (the stale-`selected`-id bug) is now moot — the
action that triggered it (`doAction("approve")`) no longer exists in the tenant UI.

### STEP0 finding 1 — streaming vs. polling for the write flow

- No real SSE exists anywhere live in this codebase for any tour-write flow. Repo-wide search
  for `EventSource`/`text/event-stream` found exactly one frontend usage —
  `frontend/app/admin/pipeline/s1/page.tsx:345`, pointing at `/acp/s1/run/{run_id}/stream` — and
  that backend route no longer exists (`api/main.py` doesn't register any ACPv1 router; AA-477
  tore ACPv1 down). Dead code, not a reusable template.
- The tenant write flow itself (`POST /v1/tours/pool/{id}/rewrite`,
  `api/routers/v1_tours.py:385-692`) is fire-and-forget: inserts a `pending` row, fires
  `asyncio.create_task()`, returns immediately with `"message": "Rewrite started — check My
  Catalog in ~30 seconds for results"`. `CatalogTab.tsx`'s existing 5s poll is the only consumer.
  100% polling, confirmed by reading the actual code, not inferred.
- The shared Bedrock client (`shared/llm_client/client.py:177-225`) does call
  `invoke_model_with_response_stream()` — but only to dodge an HTTP idle-timeout (AA-224); it
  fully accumulates every chunk into one string before returning (`content = "".join
  (content_parts)`). No caller anywhere receives incremental text today.
- Real infra risk for building genuine SSE: this codebase already hit a documented ~29s API
  Gateway REST integration timeout on other long-LLM-call endpoints while the backend kept
  working past it (AA-452's T8/T9 `/write` finding) — the same API Gateway (`4ylo382khg`) fronts
  this rewrite endpoint too. A held-open SSE response is subject to the same ceiling unless
  routed around the gateway. Separately, the text that would stream live is the PRE-QA-gate raw
  draft — the actual final content only exists after T3's QA gate + up to N auto-repair rounds
  (`run_t3_qa_gate`), which can silently change what was just shown.
- **Option A — build real SSE**: new streaming method on the shared LLM client (parallel to the
  existing one — too many other callers depend on today's accumulate-then-return contract to
  modify it directly), a new backend SSE endpoint, a decision on showing the pre-repair draft
  live vs. only starting the stream after QA clears, and validating the API Gateway doesn't kill
  the connection past ~29s. Multi-day, cross-cutting — a separate ticket, not foldable into this
  wireframe.
- **Option B — recommended**: keep the exact existing 30s-background-job + 5s-poll mechanism;
  change only the tenant-facing visual — an inline "Writing your tour…" loading placeholder
  where the content will land (table row + drawer body), instead of a status badge. Zero backend
  risk, ships inside this issue.
- Recommending Option B unless Nghiệp explicitly wants to fund Option A as its own ticket.

### STEP0 finding 2 — backend version/status ownership, Admin impact

- No DB schema change needed. `gold_aa_internal.tenant_tour_versions` keeps `status`/
  `version_number` exactly as today (INSERT-only on edit/rewrite, never UPDATE) — Admin's own
  reads (`api/routers/admin.py:434-477,702-706`, `api/routers/admin_pipeline.py:3332-4365`) pull
  directly from this same table for tenant-oversight views and want the FULL per-row history,
  not "latest only" — confirmed by reading those queries, none of them collapse to one row per
  tour. These live in different router files from the tenant endpoints (`v1_tours.py`) with no
  shared code path, so leaving the table alone keeps Admin provably unaffected.
- Repo-wide grep confirms nothing outside display ever filters on
  `tenant_tour_versions.status = 'approved'` — dropping the tenant UI's "Add to Catalog" call
  (`PATCH /versions/{id}` action=approve) is safe to just stop calling; no backend deletion
  needed, endpoint can stay dormant/available.
- **Real gap found, needs confirmation**: today's "Request New Version" (`doAction("reject")`)
  ONLY sets `status='rejected'` — it never calls the rewrite-trigger endpoint, and nothing else
  in the codebase consumes `status='rejected'` to kick one off either. So the existing feature is
  already a dead end: it shows "🔄 New version requested" but no version is ever actually
  requested from the AI. The quota-confirm dialog's "This will use 1 rewrite credit" text is
  also untrue today — `_check_and_consume_rewrite_quota()` only runs inside `trigger_rewrite()`,
  which `reject` never calls. Renaming the button without fixing this makes the mismatch worse
  (the new name implies real action even more directly than the old one). Recommending: wire
  the renamed button to actually call `POST /pool/{id}/rewrite` for that tour (same endpoint
  Browse Pool's first write uses, same real quota check) — a real behavior fix, not just a
  rename, flagged for explicit confirmation before building.
- `NextStepGuide.tsx` is keyed entirely by the old status vocabulary ("AI is writing…", "add to
  your catalog", "New version requested") — cannot be reused verbatim under the new no-status/
  no-AI-language direction; needs a full copy rewrite or removal, not a straight port.

### Real bugs found by this build's own Playwright live-verify (fixed, not just noted)
- **isAiWriting scope bug (would have shipped broken)**: naively treating any `status==='pending'`
  row as "still writing" would have (a) shown a false "Writing your tour content…" screen
  immediately after every manual Save, and (b) kept the 5s poll running forever for any tenant
  who ever clicked Save once — confirmed via reading `update_version()`'s edit branch
  (`api/routers/v1_tours.py:932-957`), which inserts `status='pending'` for tenant self-edits too
  and never advances it. This is a **pre-existing bug in the code this build replaced** (the old
  polling condition had the same unscoped `status==='pending'` check) — not introduced by this
  build, but fixed here since `isAiWriting()` already had to define this boundary precisely.
- **"✓ Saved" confirmation was flashing then disappearing** — found live during this build's own
  Playwright test 3. Root cause: the openGroup-sync `useEffect` reloads `detail` whenever
  `openGroup.id !== detail.id`; since `saveEdit()` always creates a NEW version row, `fetchList()`
  picking that up immediately triggered `loadDetail()`, which unconditionally resets `saveOk` to
  false at its start — stomping the just-set `true` within the same render pass. Fixed by having
  `saveEdit()` point `detail.id` at the backend's returned `new_version_id` *before* calling
  `fetchList()`, so the sync effect sees `detail` already current and skips the reload.

## Decisions (wireframe phase)

- **Overlay drawer, not a squeezed 2-column grid.** Admin's table needs ≥7 columns (checkbox,
  #, Tour Name, Country, Score, Version, Status, Actions) to match Admin fidelity. The current
  `CatalogTab` 2-col grid gives the list only 300px once a row is selected — nowhere near enough
  for a real table without truncating columns to the point of losing the parity the issue asks
  for. Chose: table always full-width; opening a row slides in a right-side drawer over it,
  reusing the exact overlay mechanics Admin's own `TourDetailPanelV2.tsx` already uses (fixed
  backdrop `rgba(0,0,0,0.4)` + fixed panel `top:0/right:0/bottom:0`) — not a new UI concept,
  an existing one already proven in this codebase.
- **Drawer width 700px fixed (not Admin's 70vw).** Admin's 70vw suits its wide before/after
  compare table; Tenant's content (text fields, highlights, itinerary) reads better at a fixed
  ~700px than at a viewport-relative width that gets very wide on large monitors.
- **Backdrop click-to-close only when NOT dirty.** Admin's backdrop has no dirty-guard (it's
  view-only). Tenant's drawer holds unsaved edits, so backdrop click added as new convenience but
  gated: closes only if `!dirty`; a dirty drawer still requires the explicit ✕ (unchanged from
  today — no regression risk, no silent data loss).
- **Row grouping is an open question, not decided** — see "Needs approval" below. Confirmed via
  `api/routers/v1_tours.py:697-751` that `GET /v1/tours/my-versions` returns **one row per
  version** (`gold_aa_internal.tenant_tour_versions`), not one row per original tour — the
  current card-list already reflects that flat shape. Grouping by `tour_id` with a nested
  "▸ Versions" expand (to actually reuse `VersionHistory`-style rendering the way Admin's
  version sub-row does) is a bigger structural change than a pure re-skin, so it's presented as
  an option, not baked into the one recommended wireframe.
- **No StatCards row added.** Admin's 4 StatCards (Total Tours/Avg Quality/Total LLM Cost/
  Pipeline Runs) are out of scope — the issue asks for table+filter+panel layout sync only,
  not a stats dashboard for the tenant page. Explicitly excluded to avoid scope creep.

## Tradeoffs

- Overlay drawer vs. persistent 2-column: drawer wins on table fidelity but means the tenant
  can't see table + editorial panel side-by-side simultaneously (today's 2-col grid does allow
  that, cramped as it is). Flagged explicitly in the Linear wireframe post for a real decision,
  not assumed.
- Grouped-by-tour rows would cut list clutter for tenants with multiple self-rewrite attempts on
  the same tour, and lets `VersionHistory`-style markup double as both the table's nested
  expand AND the drawer's existing version switcher — but it's a heavier change than the issue's
  literal ask ("bảng thật thay card-list"), so left as an explicit choice rather than default.

## Should know

- `GET /v1/tours/my-versions` has NO backend grouping/aggregation by tour — any "group by tour"
  table variant is 100% client-side reshaping of the same flat response, no API change needed.
- `country`/`duration`/`quality_score`/`version_number` are already present in the `Version`
  shape returned today, so Admin-style Country/Score/Version dropdown filters (beyond the
  mandatory Status dropdown) are pure client-side additions, no backend change — proposed as an
  optional parity bonus in the wireframe, not mandatory.
- Every existing tenant interaction (dirty/save, Save as New Version, Request New Version +
  quota-confirm dialog, Add to Catalog, CSV/XLSX multi-select export, 5s poll while any row is
  `pending`, `?tour_id=` deep-link banner, QA-auto-pass badge, version switch via
  `VersionHistory`) must survive the re-skin verbatim — enumerated in full in the Linear comment
  as a live-verify checklist for when code actually starts.
