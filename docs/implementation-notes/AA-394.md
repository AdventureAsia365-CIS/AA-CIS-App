# AA-394 — TEST_BACKFILL for acp_deliver.tenant_tour_pages (87 Laos+South Korea tours)

STEP 0 (investigation, no code) found `acp_deliver.tenant_tour_pages` (migration 078, AA-302)
has been empty since creation — ADR-2026-030 decided AA should host a real per-tenant
white-label tour page there, but that "+1-2 sprint landing page engine" was never built
(tracked as AA-395, not started). This issue's own scope, per Nghiep's explicit instruction,
is a temporary, non-production backfill to unblock testing — not AA-395 itself.

## Decisions

- **Script location**: `tests/verify_scripts/aa394_*.py`, not `scripts/`. Checked both before
  choosing: `scripts/` is a legacy grab-bag (old patch instructions, stray JSON exports, no
  consistent naming) while `tests/verify_scripts/aaNNN_*.py` is the actively-used,
  ADR-2026-037-sanctioned convention for exactly this kind of real-DB, real-Bedrock, non-CI
  script — AA-364/367/375/376/377/378/391/392 all use it. Deviates from the issue text's own
  illustrative `scripts/2026-08-09_*.py` example; following the repo's real established
  convention instead, same STEP-0 discipline prior sessions in this repo have used.
- **No date-prefixed filename**: the established `aaNNN_*.py` convention uses the issue number,
  not a date, as the prefix (matches every existing file in the directory). The run date/scope
  the issue text asked for lives in each file's own header docstring instead (more durable than
  a filename — a file gets copy/reused across dates, as this one explicitly is meant to be).
- **Two files kept separate** (backfill vs. verify), matching the issue's own ask and the
  natural boundary: the backfill script is meant to be re-run for future destinations before
  AA-395 exists; the verify script is a one-off proof against a specific already-persisted slot
  set and depends on the backfill having run first.

## Changed

- New `tests/verify_scripts/aa394_backfill_tenant_tour_pages.py` — seeds
  `acp_deliver.tenant_tour_pages` with one shared, live, but non-tour-specific URL for every
  tour matching a tenant + destination filter. Idempotent (`ON CONFLICT ... DO UPDATE`).
- New `tests/verify_scripts/aa394_verify_f6_gate_pass.py` — re-runs real, already-persisted N7
  slots through `run_slot_production()` with a freshly-computed `cta_target`, proving F6 clears
  post-backfill. Fixes a real bug found while first running this ad hoc (before it was
  committed): `Piece.gate_ledger` holds `GateResult` Pydantic objects, not dicts — the original
  ad hoc version called `.get("gate")` on them and crashed with `AttributeError` after the real
  Bedrock/Nova Pro work had already finished (no wasted spend, just a broken post-processing
  loop). Fixed to use `g.gate`/`g.passed` attribute access; the version committed here has this
  fix applied and was not re-run against Bedrock again (would cost real money for a
  print-formatting fix with no new information — the DB re-read already had the ground truth).
- No production code changed. No migration. `docs/implementation-notes/AA-394.md` (this file).

## Real result (09/08/2026, live dev DB, S3-mediated ECS exec, no code changes to app itself)

- `acp_deliver.tenant_tour_pages`: 0 → 87 rows (57 Laos + 30 South Korea, tenant `aa_internal`),
  `url = https://aa-cis.lumiguides.it.com/` for every row (confirmed live HTTP 200 before use).
- Root cause turned out one step earlier than F6 itself: `services/acp_planning/allocator.py:193`
  (`cta = t.trip_url if t.url_alive else None`) meant every N6 slot got `cta_target=None` while
  the table was empty, so `research.py::compile_brief()` rejected with `no_cta_target` before any
  `Piece` was ever created — F6 never got a chance to run. Same root cause AA-394 already
  diagnosed, one step earlier in the chain than STEP 0 had mapped.
- Verify: re-ran the 3 real persisted N7 slots (blog/facebook/tiktok, South Korea tour
  `c9fb02ef-8db5-4849-a12e-e9718935039e`) with real Bedrock Sonnet 4.6 + Nova Pro judges +
  DataForSEO. **9 real pieces produced (was 0). `F6_route_to_sellable` passed=True on 9/9**,
  confirmed via independent re-read of `acp_deliver.pieces.gate_ledger`. All 9 still ended
  `status=held` — on `F3_structural_variance` / `F8_framework` / `F9_brand_seo_audit_social`,
  pre-existing E2/E3 prompt-quality gaps already documented in `AA-367.md`, unrelated to F6.
- Only 1 of 87 tours was run through real production, to limit real Bedrock/Nova Pro/DataForSEO
  spend — the other 86 were backfilled but not exercised end-to-end this session.

## Tradeoffs

- These 9 real `held` pieces and the 6 `acp_v2_runs`/`acp_v2_slots` rows from this + the prior
  AA-391 session are left in place, not cleaned up — matches AA-391's own established
  convention ("No cleanup ... real production artifacts"), not an oversight.
- The backfilled rows are indistinguishable from a real landing-page-engine's output by schema
  alone (no dedicated "is this real" column exists — migration 078 has none). Recognizable in
  practice by every row sharing the identical `url` and `published_at` cluster — documented
  explicitly in both scripts' own docstrings so a future reader isn't misled.

## Should know

- This is temporary, non-production data. It will be superseded by AA-395 (the real per-tenant
  landing page engine, ADR-2026-030) when that lands — do not build further on top of this
  backfill as if it were real, and do not point real tenant-facing review (Gate C) at content
  produced against these URLs.
- `aa394_backfill_tenant_tour_pages.py` is written to be reused for a different destination
  batch before AA-395 exists (edit `TENANT_ID_TEXT`/`DESTINATIONS`/`TEST_URL` at the top) — that
  was Nghiep's explicit reason for keeping it in the repo rather than discarding it.
