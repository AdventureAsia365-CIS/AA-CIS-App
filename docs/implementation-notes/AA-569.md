# AA-569 — My Content: view/edit/save/export, no gate leak

## Decisions
- The wizard's "done" popup shows only when a write started THIS session actually finishes
  (inside `pollPiece`'s success branch) — never when resuming an already-finished piece via the
  `latest-piece` effect. A tenant reopening a done request shouldn't get a popup for nothing that
  just happened.
- Popup wording is identical for approved and held ("Your content is ready") — no status-specific
  language, since any wording split risks hinting at *why* a piece landed in one bucket or the
  other.
- Edit/Save/Export are gated on `content_text !== null` on the frontend, mirroring the backend's
  own `status IN ('approved', 'held')` gate on the PATCH/export endpoints exactly — a `processing`
  piece has nothing real yet, a `failed` piece has no content_text worth keeping.
- HTML export uses the `markdown` PyPI package (added to requirements.txt) rather than a
  hand-rolled parser — T9's blog prompt (AA-452) already writes real `##`/`**` markdown syntax,
  so a real parser is correct where a naive replace-based one would break on edge cases.
- Export downloads are built client-side (fetch -> Blob -> `<a download>`) rather than relying on
  the API responding with `Content-Disposition: attachment`, because `/api/tenant/[...path]/
  route.ts` (the tenant proxy) only forwards `Content-Type` from the upstream response, not other
  headers — a plain `<a href>` to the export endpoint would just open the file inline instead of
  downloading it.

## Changed
- `AngleGateWizard.tsx`: removed the inline result card (full `content_text` + `attempt_number` +
  raw `held_reason`) — replaced with a `WriteDonePopup` + a minimal always-visible confirmation
  line, both linking to `/portal/t10-review?piece={id}`.
- `ReviewList.tsx` / `t10-review/page.tsx`: removed the `maxWidth: 720` cap; added `?piece=`
  auto-expand+scroll (needs a `<Suspense>` boundary around `<ReviewList/>`, same as
  `t8-angle-gate/page.tsx`'s existing pattern for `useSearchParams()`); added inline
  Edit/Save (textarea + PATCH) and Export (text always, +HTML for `channel === "blog"`).
- `services/acp_content_writing/service.py`: added `channel` to `_FETCH_PIECE_QUERY`/
  `_row_to_dict()` (needed by the export endpoint to decide HTML eligibility); added
  `update_piece_content_text()`.
- `services/acp_content_writing/export.py` (new): `render_content_text_to_html()`.
- `api/routers/v1_content_writing.py`: `PATCH /pieces/{piece_id}`, `GET /pieces/{piece_id}/export`.
- `services/acp_shared/audit_log.py`: new `TenantAuditAction.CONTENT_PIECE_EDITED`.

## Tradeoffs
- No rich-text/WYSIWYG editor — a plain `<textarea>` (matches the rest of the portal's `Field`
  component convention). The task asked for "textarea/rich-editor"; a WYSIWYG editor for markdown
  is a real scope increase (new dependency, HTML<->markdown round-trip risk) not justified by
  what was actually requested.
- Export filename is built client-side from the angle name (slugified), not returned by the
  backend — the backend endpoint returns bare content (text/plain or text/html), no
  `Content-Disposition` (see Decisions above on why that header isn't usable through the proxy
  anyway).

## Should know
- The old wizard card's "Change angle" / meta row (Angle/Goal/Channel summary) is unchanged —
  only the block that showed `content_text`/`attempt_number`/`held_reason` was removed.
- `fetch_piece()`'s response shape gained one new key (`channel`) — additive, no existing caller
  reads a fixed key list that would break.
