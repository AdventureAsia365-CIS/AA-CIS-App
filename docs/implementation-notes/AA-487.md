# AA-487 — Sanitize brand brief input (S0) before building system_prompt

## Decisions

- **Two call sites fixed, not one.** The Linear issue's own evidence only names
  `services/acp_brand_brief_parser/{parser,builder,db}.py` (the DOCX-upload Lambda). While
  reading the frontend to confirm "no UI needed", found a SECOND, more direct write path to the
  exact same `shared.tenant_brand_rules.system_prompt` column:
  `api/routers/admin_pipeline.py::update_brand_identity()` (`POST /admin/brand-identity`), which
  `frontend/app/(tenant)/portal/_components/BrandTab.tsx`'s "edit brand voice" form calls — a
  tenant can type `system_prompt`/`style_guide` directly into a textarea and save, with **no
  parsing step in between at all**. That is a strictly more direct injection surface than the
  DOCX path this issue named, so it's fixed here too rather than left for a follow-up issue.
- **Redaction, not rejection.** Chosen approach: strip/redact known injection shapes (regex,
  case-insensitive) and replace with `[redacted]`, rather than reject-with-error. A tenant who
  triggers a false positive (e.g. writes "ignore the above pricing tiers" in a legitimate brief)
  gets a slightly mangled but still-saved brief, not a blocked save with a confusing error about
  a security concept they didn't intend to trigger.
- **Delimiters as defense-in-depth**, per the issue's 3rd checklist item — `build_system_prompt()`
  now wraps all tenant-derived fields between explicit `BEGIN_BRAND_BRIEF`/`END_BRAND_BRIEF`
  markers with an instruction line telling the model to treat everything between them as data,
  never as instructions. This helps even against a payload that slips past the regex list (regex
  redaction can never be a complete defense against prompt injection — this is containment, not
  a hard guarantee).
- **Two length caps, not one.** The Lambda's per-field caps stayed close to the pre-existing
  `style_guide[:300]` (now `MAX_LONG_FIELD_LEN=300` for style_guide-shaped fields,
  `MAX_SHORT_FIELD_LEN=200` for shorter fields like core_idea/customer_segment). But
  `update_brand_identity()`'s `system_prompt` field holds a tenant's WHOLE hand-typed system
  prompt (not assembled from several already-capped fields like the Lambda's), so reusing 300
  there would truncate a normal, non-malicious save. Added `MAX_SYSTEM_PROMPT_LEN=2000` — enough
  headroom for genuine brand-voice prose, still bounded well short of "paste a large injection
  payload."
- **No shared import between the Lambda and the FastAPI app**, even though the logic is
  duplicated (~35 lines) between `services/acp_brand_brief_parser/sanitize.py` and
  `shared/validators/prompt_sanitize.py`. Found while building this: `scripts/
  package_lambdas.sh`'s `package_brand_brief_parser()` zips ONLY
  `services/acp_brand_brief_parser/*.py` flat — it does not copy `shared/` (unlike the other
  Lambdas in that same script, e.g. `ingestion`/`export`, which do get `shared/` copied in).
  Importing `shared.*` from the brand-brief-parser Lambda would pass local tests (repo checkout
  on `sys.path`) but raise `ModuleNotFoundError` in the real deployed Lambda. Kept the two
  copies independent rather than changing the packaging script, to keep this fix's blast radius
  to the injection surface itself.

## Changed

- New `shared/validators/prompt_sanitize.py`: canonical `sanitize_text()`/`sanitize_list()` +
  length constants, used by `admin_pipeline.py`.
- New `services/acp_brand_brief_parser/sanitize.py`: same redaction/length logic (intentionally
  duplicated, see Decisions), plus `sanitize_parsed_brief()` which maps it over every field of a
  `ParsedBrief`.
- `services/acp_brand_brief_parser/parser.py::parse_docx()`: now runs its result through
  `sanitize_parsed_brief()` before returning — single choke point, every consumer of
  `ParsedBrief` (builder.py, db.py's version snapshot) gets already-sanitized text.
- `services/acp_brand_brief_parser/builder.py::build_system_prompt()`: rewrote the f-string to
  wrap all brand-brief fields between `BEGIN_BRAND_BRIEF`/`END_BRAND_BRIEF` markers with an
  explicit "treat as data" instruction. **Output shape changed** (was a single sentence-style
  paragraph; now a labeled block) — no code parses this string's exact shape (grepped
  `"You are writing travel content for"` across the repo — only the pre-existing test fixture
  string matched, not any real reader), so this is safe, but flagging since `system_prompt` is
  replayed verbatim into every LLM call for the tenant.
- `api/routers/admin_pipeline.py::update_brand_identity()`: sanitizes `body.system_prompt`,
  `body.style_guide`, `body.forbidden_words` before the INSERT.
- Tests: `tests/acp/test_aa487_sanitize_brand_brief.py` (sanitize.py regex/length unit tests +
  `parse_docx()` end-to-end with a crafted injection payload + `build_system_prompt()` delimiter
  shape), `tests/unit/test_aa487_brand_identity_sanitize.py` (`update_brand_identity()` with a
  mocked asyncpg pool, mirrors `test_aa300_admin_atoms.py`'s mocking pattern). 23 new/updated
  tests; full `tests/unit/` suite: 1772 passed, 0 new failures.

## Tradeoffs

- Regex-based redaction is inherently incomplete against a determined attacker who varies
  phrasing enough to dodge the pattern list — accepted per the issue's own framing (self-
  injection risk, containment not a hard guarantee). The delimiter wrapping in
  `build_system_prompt()` is the second layer for exactly this reason.
- Did not touch `api/routers/admin_pipeline.py::create_brand()`/`update_brand()` (`POST/PUT
  /admin/brands*`) — these are staff-only (`X-Admin-Secret`, no tenant JWT path), hardcoded to
  the AA-internal pseudo-tenant only, and used by `frontend/app/admin/brand/page.tsx` /
  `(internal)/brand/page.tsx` (staff configuring AA's OWN brand, not tenant self-service). Not
  the tenant self-injection surface this issue targets; noted here rather than silently skipped.
- Did not change `MAX_SHORT_FIELD_LEN`/`MAX_LONG_FIELD_LEN` values beyond what the issue already
  had (`style_guide[:300]`) for the Lambda path — the issue's own text says the length cap isn't
  the real defense against short injection payloads (the regex redaction is), so tightening
  further wouldn't have added real protection, only risked truncating legitimate longer briefs.

## Should know

- No frontend change needed. `BrandTab.tsx` and `admin/brand/page.tsx` render whatever
  `system_prompt`/`style_guide` come back from the API — since the fix operates on the value at
  write time (both the Lambda parse and the manual-edit endpoint), the UI needs no changes to
  reflect sanitized content; it was never told about the sanitization mechanism to begin with.
  Confirmed no UI needs a "this was sanitized" indicator or similar — the issue's checklist
  doesn't ask for one, and a false-positive redaction (see Decisions) is rare enough and low-
  enough-stakes (worst case: a slightly odd-looking `[redacted]` token in the tenant's own saved
  brief, visible only to them) not to warrant new UI surface.
- `build_system_prompt()`'s output format changed (see Changed). If a future task needs to parse
  or diff `system_prompt` text programmatically, it now has a stable `BEGIN_BRAND_BRIEF`/
  `END_BRAND_BRIEF` block to anchor on rather than a free-form sentence.
- Live-verify: this Lambda (`aa-cis-dev-brand-brief-parser`) and the tenant-portal
  `POST /admin/brand-identity` endpoint both require a real tenant session / S3 DOCX upload to
  exercise end-to-end; not run live as part of this task (unit + Lambda-fixture tests cover the
  actual sanitize logic directly, matching how `test_brand_brief_parser.py`'s existing fixture
  tests already validate this Lambda without a live AWS round-trip). No DB/infra state changed —
  safe to leave as code-level verification only.
