# AA-556 — Tenant-facing "Cut" button for Slate proposals

## Decisions

- **Stopped before coding** on the one open question the issue's own AA-564 Nhóm 5 note flagged:
  disable "Cut" when the same row's `AngleGateWizard` is expanded (`isExpanded`)? Posted the exact
  race mechanism (traced in `SlateTab.tsx`'s `pick()` handler — `onExpand()` sets `isExpanded=true`
  synchronously while `onPicked()`'s refetch is still in flight, so there's a real window where
  `isExpanded && subject.state === "proposed"` both hold) to the Linear issue as a comment, per the
  explicit instruction to ask there rather than decide unilaterally.
- Nghiệp + Claude Chat's confirmed reply: check whether `cut_subject()` re-reads live DB state
  before answering — if yes, disabling is UX polish only; if no, it's a backend bug to fix first
  (not to be self-patched without confirming the approach). Read `cut_subject()`
  (`services/acp_shared/slate.py:582-614`): it always `SELECT`s the real `state` from
  `acp_shared.subject` at call time and never accepts a client-supplied state — same guard shape
  as `pick_subject()`. Posted this finding back to Linear before touching any UI code.
- Built as confirmed: Cut button next to "Chọn viết" in the same `state === "proposed"` block,
  disabled while `picking || isExpanded || cutting` — purely to avoid a harmless same-row 409/UI
  flicker, not a data-safety guard (none needed — the backend already re-checks live state).
- `variant="danger"` (existing `Btn` variant in the tenant portal's `ui.tsx`, red-soft) to visually
  distinguish it from the primary "Chọn viết" action, matching the one-way/no-undo framing.
- `window.confirm()` gate before the POST — same shape the issue asked for, same pattern this
  portal doesn't otherwise use a custom modal for single irreversible actions.
- Error handling mirrors `pick()`'s own FE-audit-#2 rule exactly: a failed cut() never calls
  `onPicked()` — only a confirmed 200 refetches the Slate — with the same manual "Refresh" link on
  failure.

## Changed vs. original requirement

- None — built exactly what the issue asked (Cut button + confirm + admin note removal +
  live-verify), after the required stop-and-confirm on the disable-condition question.

## Tradeoffs

- Considered an optimistic UI removal (drop the row immediately on click) instead of waiting for
  `onPicked()`'s refetch — rejected to stay consistent with `pick()`'s existing, deliberate
  "only a confirmed success changes what's shown" rule (FE audit #2, AA-511) rather than
  introducing a second update strategy on the same page.
