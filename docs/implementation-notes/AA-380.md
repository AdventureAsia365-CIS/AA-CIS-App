# AA-380 — ECS task role thiếu cloudwatch:PutMetricData, App side (live verify)

This note covers the AA-CIS-App half (live verify: a real Piece through the real gate stack,
CloudWatch datapoint confirmation, cleanup). The Terraform half (IAM policy change) lives in
AA-CIS-Infra's own `docs/implementation-notes/AA-380.md`.

## STEP 0/1 — root cause + emit point (recon, before Terraform fix existed)

- `modules/ecs/main.tf::aws_iam_role_policy.ecs_task_policy` (AA-CIS-Infra) never had
  `cloudwatch:PutMetricData` — only `s3:*`, `secretsmanager:GetSecretValue`, `sqs:*`, `logs:*`,
  `bedrock:InvokeModel*`. Every `emit_piece_metrics()` call since AA-362 shipped (05/08/2026) was
  silently swallowed by its own try/except (`services/acp_produce/metrics.py:96-97` logs
  `cloudwatch_emit_failed` and returns — by design, "a CloudWatch outage must never fail the
  actual N7 pipeline"). No datapoint had ever been written.
- `emit_piece_metrics()` is called **once per Piece**, at the very end of
  `run_piece_through_produce_gates()` (`services/acp_produce/pipeline.py:186`), unconditionally —
  after `_persist_piece()`, regardless of whether the piece ended `passed` or `held`. Confirmed by
  reading `run_gates()` (`services/acp_produce/gates.py:520-537`): every gate in the stack is
  always evaluated in full each round (no early break on first failure — only the round stops when
  `max_repairs=0`), so `F1_grounding` always lands in `piece.gate_ledger` as long as the piece
  clears `apply_output_rules_to_piece()` first. `grounding_score` is only emitted when
  `F1_grounding` is present in the ledger (`piece_metric_data()`); `piece_passed`/`piece_held`/
  `repair_count` are always emitted once the piece reaches a terminal status.

ratio is legitimately 100%. `treat_missing_data="notBreaching"` means it self-clears once the
1-hour evaluation window rolls past this single datapoint with no further data. The SNS
subscription (`aa-cis-dev-acp-alerts`) is in a confirmed (non-`PendingConfirmation`) state, so this
likely sent Nghiep a real "N7 piece held-rate above 20%" email — a genuine, expected side-effect of
running this verify, not a production incident. This is itself further proof the whole
