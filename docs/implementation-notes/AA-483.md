# AA-483 — Race condition in process_export() batch completion check

## Decisions

- **STEP0 confirmed the described shape**: `sync_batch_completion()` (`services/export/
  handler.py`) was a genuine check-then-write split — a `SELECT COUNT(*)` (pending non-terminal
  tours) followed, in Python, by a conditional `UPDATE ... status = 'completed'`. No lock,
  no single atomic statement, exactly as the issue's STEP0 asked to verify.
- **Went with the issue's own 2nd suggested fix (single atomic UPDATE), not row locking.**
  `UPDATE shared.pipeline_runs SET status='completed', completed_at=NOW() WHERE batch_id=$1 AND
  status='ingesting' AND NOT EXISTS (SELECT 1 FROM raw_tours WHERE batch_id=$1 AND
  pipeline_status NOT IN (...)) RETURNING 1` — the check and the write happen inside one
  statement, under one MVCC snapshot with the target row locked by Postgres itself. This closes
  the gap by construction rather than by adding an application-level lock (`SELECT ... FOR
  UPDATE`) that a future edit could accidentally drop.
- **Found a second, more consequential problem while fixing the first**: `process_export()`'s
  ACP-S1 manifest/EventBridge fanout (`if pending == 0:` block — uploads a manifest to S3 and
  fires an EventBridge event) was gated on the SAME racy `pending` read. Two concurrent
  completions of the same batch could each independently observe `pending == 0` and each fire
  the fanout — a real double-fire risk (title-referenced in AA-476's own issue title: "...3
  double-fire ingestion..."), not just a redundant, harmless status UPDATE. Changed
  `sync_batch_completion()` to return `(pending, just_completed)` — `just_completed` is `True`
  only for whichever single caller's atomic UPDATE actually matched a row — and re-gated the
  fanout on `just_completed` instead of `pending == 0`. This directly fixes the double-fire
  risk, not just the status-flip race the issue's title names.
- **`pending` is kept, now purely informational** (logging/observability), not a completion
  signal for any caller — `mark_tour_rejected()` already discarded the return value entirely and
  needed no change beyond the new tuple shape being compatible with that.
- **Did not add a periodic backfill/self-healing job** (the issue's own 4th checklist item,
  explicitly framed as "cân nhắc" / optional, not "phải làm"). The atomic UPDATE closes the
  specific race by construction, so a backfill job's marginal value for THIS bug class is now
  low. A periodic scan would still have real, separate value for a genuinely different failure
  mode — a tour whose pipeline crashes mid-flight and never reaches ANY terminal state (never
  calls `process_export()` or `mark_tour_rejected()` at all, so nothing ever triggers a
  completion check for its batch) — but that is a distinct problem from the race this issue
  investigates, and building new infra (EventBridge schedule, Terraform) for it wasn't
  confirmed in scope. Flagging as a real, separate follow-up recommendation rather than building
  it speculatively.

## Changed

- `services/export/handler.py::sync_batch_completion()` — status-flip is now one atomic
  `UPDATE ... WHERE NOT EXISTS(...) RETURNING 1` instead of a separate SELECT + conditional
  UPDATE. Return type changed from `int` (pending count) to `tuple[int, bool]`
  `(pending, just_completed)`.
- `services/export/handler.py::process_export()` — the ACP-S1 fanout's guard changed from
  `if pending == 0:` to `if just_completed:`.
- Tests: `tests/unit/test_aa476_batch_completion.py` updated (`FakeConn` now distinguishes the
  pending-count `fetchval` from the atomic-flip `fetchval` by SQL content; assertions updated
  for the new tuple return and the `mark_tour_rejected` test's changed evidence trail — the
  status flip is no longer visible in `conn.executed` since it moved from `execute()` to
  `fetchval()`). New `tests/unit/test_aa483_batch_completion_race.py`: proves the flip SQL is a
  single atomic statement (not read-then-write), and proves `process_export()`'s fanout is
  correctly skipped when `pending == 0` but `just_completed is False` (the exact double-fire
  scenario) and correctly runs end-to-end when `just_completed is True` — the latter with the
  full ACP-S1 side-effect chain (S3 manifest upload, EventBridge publish, `write_run_context_
  stage`) explicitly mocked, not relying on the code's own try/except to silently swallow an
  unmocked real AWS call. Full `tests/unit/`: 1776 passed, 0 new failures.

## Tradeoffs

- No new migration — `shared.pipeline_runs`'s schema is unchanged, only the SQL statement shape
  that reads/writes it changed.
- `tours_passed`'s own UPDATE (recomputed via a separate `SELECT COUNT(*) WHERE pipeline_status
  = 'published'`) is still a non-atomic, separately-committed statement, same as before — left
  untouched because it's a display/reporting counter, not a completion-decision input; a
  momentarily-stale `tours_passed` under concurrency (already possible pre-this-fix) has no
  correctness consequence, unlike the status flip and fanout gate this task fixes.
- The atomic UPDATE approach means a batch whose LAST tour arrives via `mark_tour_rejected()`
  (not `process_export()`) still correctly triggers the flip (same shared function, same atomic
  statement) — but `mark_tour_rejected()`'s call site never looks at `just_completed` (no
  fanout is triggered from the reject path, matching existing/AA-476 behavior — a rejected tour
  was never meant to trigger the ACP-S1 manifest fanout).

## Should know

- No frontend change — this is a pure backend race-condition fix. No new field, no API response
  shape change (`process_export()`'s own returned dict, and every existing endpoint, are
  unchanged), no new UI-visible state. Confirmed no dashboard reads `pipeline_runs.status`'s
  update mechanism directly (only the end value, which behaves identically, just correctly now).
- Not live-verified against real concurrent traffic (would need 2+ tours in the same batch
  reaching terminal state within milliseconds of each other, a real timing-dependent scenario
  hard to force deterministically in a live environment) — correctness rests on the atomic SQL
  statement's own guarantees (a single `UPDATE ... WHERE ...` is inherently race-free under
  Postgres's MVCC + row-locking model) plus the unit tests proving both branches of
  `process_export()`'s new gating logic. No DB/infra state changed by this PR; nothing to
  observe live yet.
