## Decisions (from Nghiệp, 30/08/2026, restated here as the source of truth for this build)

- **Architecture: 2 separate pages, no toggle** — tenant JWT vs x-admin-secret, different data
  shapes, matches existing AA/Tenant split precedent (STEP0 §6).
- **Tenant page is STRICTER than the existing T8 wizard** — the wizard's end-of-flow card already
  shows `held_reason`; the new `/portal/t10-review` page does NOT (deliberate divergence, not an
  oversight — Nghiệp confirmed explicitly). No `gate_ledger`/`repair_log`/`held_reason` anywhere
  in the tenant-facing response, enforced at the SQL SELECT level, not just hidden in the UI.
- **Admin content-log widens to be the widest of the two views** — everything tenant sees, plus
  full gate/retry/error detail, plus a tenant filter, plus publish-status join. No route change.
- **No LLM cost/token tracking this task** — split to AA-505 (separate issue, not touched here).
- **DFS/PAA becomes a real snapshot column**, not a live re-fetch — persisted at
  `set_goal_and_generate()` time, both new endpoints read the snapshot, never call
  `fetch_search_demand_signal()` live for display purposes again.
- Route slug confirmed: `/portal/t10-review`, sidebar entry "Review" between "Write Content" and
  "Publish".
- "Điểm" for AA resolved as gate pass-count (e.g. "7/9") as a summary, WITH full per-gate detail
  still shown (name/pass-fail/violation) — not a replacement for it.

## Changed vs. original STEP0 proposal

- STEP0 proposed one new tenant endpoint (`GET .../requests/{request_id}/review`, per-request).
  The build task's own UI spec ("Danh sách bài viết theo channel") needs a LIST across all of a
  tenant's pieces, which a per-request endpoint alone can't serve — added a second endpoint,
  `GET /v1/content-writing/reviews`, that returns every request's latest piece with full context
  embedded (no gate/repair/held fields, same contract as the per-request one). The per-request
  endpoint is kept too (built exactly as specified) for a future direct-link use case; the
  `/portal/t10-review` page itself only calls the list endpoint today.
- Migration number is 127 (STEP0 didn't know the number yet, correctly deferred it).

## Decisions made during build (not fully specified by the build task)

- `dfs_paa_snapshot` placed on `angle_gate_request` (not `content_piece`) — `set_goal_and_generate()`
  calls `fetch_search_demand_signal()` exactly once per request; AA-497's reopen/re-choose/re-write
  cycle never re-calls it, so one snapshot per request is correct for every piece written under it.
- `ready_state` is a 3-value enum (`ready`/`in_progress`/`not_ready`) derived from
  `content_piece.status` (`approved`→ready, `processing`→in_progress, `held`/`failed`→not_ready).
  Never exposes the raw status value to the tenant.
- Content text is shown for `approved` AND `held` pieces (held keeps real writer output visible,
  per migration 115/118's own precedent) — hidden for `processing`/`failed` (no real text exists).
- Admin's `gate_pass_count`/`gate_total_count` are a computed summary alongside the full
  `gate_ledger` (not a replacement) — per Nghiệp's explicit "cần xem chi tiết được" requirement.
- Admin's tour/atom context uses a plain SQL JOIN (`silver_aa_internal.raw_tours` via
  `agr.trip_id`, `acp_contract.tour_atoms` via `agr.atom_id` + `owner_scope`), not the tenant's
  own branded `fetch_tenant_trips()` helper — AA doesn't need the tenant's rewritten display name,
  raw tour identity is enough for oversight, and this avoids a per-tenant-scoped Python call in a
  cross-tenant endpoint. The tenant-facing endpoints DO use `fetch_tenant_trips()` (their own
  branded name), matching the build task's explicit instruction to reuse it there.
- The tenant list endpoint (`fetch_review_list()`) calls `fetch_tenant_trips()` at most ONCE for
  the whole list (not per row) — avoids N+1 for a tenant-scoped call that IS available once.
- Admin's existing `publishStatusColor()` (for `publish_log.status`) and the new content-log
  `publish_status` field share no vocabulary (`published`/`failed`/`unpublished` vs.
  `published`/`pending_publish`/`n/a`) — kept as two separate color-mapping functions
  (`contentPublishStatusColor` for the new one) rather than overloading one function for two
  different value domains.

## Tradeoffs

- The admin list endpoint now returns EVERY `content_piece` row (not just held/failed) per
  Nghiệp's explicit "AA cần thấy MỌI THỨ tenant thấy" instruction — this is a real behavior/volume
  change from AA-469 Việc 5's original scope (a lesson log now doubles as a general audit view).
  Fine at current data volume; if the tenant base grows significantly, this endpoint's `limit`
  param (already existed, max 500) is the lever to revisit before adding real pagination.
- Two independent SQL queries (`admin_a4.py`'s content-log, `acp_content_writing/service.py`'s
  `fetch_review_list()`) duplicate the same angle/atom option_id-first join logic rather than
  sharing an abstraction — matches this codebase's existing precedent (`v1_publish.py`'s
  `/pending` and `admin_a4.py`'s content-log already each keep independent SQL), not a new
  inconsistency.

## Should know

- `content_piece` has been NOT-1-row-per-request since migration 125 (AA-497) — every new query
  in this change picks the latest by `created_at`, never `attempt_number`.
- `dfs_paa_snapshot` is NULL for every request created before migration 127, and for any
  tripless atom (no `seo_context` to snapshot) — both endpoints/UI handle NULL by simply omitting
  the DFS/PAA section, not erroring.
- Neither new tenant endpoint nor the widened admin endpoint touches LLM cost/token tracking —
  explicitly out of scope, split to AA-505.
- T10's automatic gate logic and T11's publish logic are UNCHANGED by this task — pure read/UI
  addition.
