## STEP0 findings (real schema + real endpoint code read, 2026-09-09)

### 1. Angle (cả 3 angle đã sinh, không chỉ angle chọn) — ✅ FULLY sufficient
`acp_shared.angle_gate_option` (migration 113) stores exactly 3 rows per request (idx 0-2):
`name`, `why_it_works`, `formula_fit`, `best_final_style`, `recommended` (LLM's own top pick),
`chosen` (tenant's actual pick) — two separate booleans, both real columns.
`GET /admin/a4/content-log` (`api/routers/admin_a4.py:504-512`, built by AA-561 "3a") already
returns ALL 3 as a JSON array (`angles`), ordered by `idx`, each carrying `chosen`/`recommended`.
No gap, no new backend work needed — just render the array with the `chosen` one visually marked.

### 2. Gate (lý do lỗi cụ thể từng lần, không chỉ count) — ✅ FULLY sufficient
`content_piece.gate_ledger` (JSONB) is a real array of `{gate, passed, violations: list[str],
repairable, blocking}` per gate that ran on the FINAL attempt — `violations` holds real,
specific text (e.g. `services/acp_content_writing/quality_gates.py:245`:
`f"sentence states {novel} not present in the content seed: '{quoted}'"`), never just a count.
`content_piece.repair_log` (JSONB) additionally carries one entry per FAILED attempt-round:
`{attempt, gate_targeted, violations, repairable}` (`service.py:503-506`) — the specific gate
+ specific violation text that caused that round to fail, not a bare tally.
`GET /admin/a4/content-log` already selects both `gate_ledger` and `repair_log` in full, plus
computes `gate_pass_count`/`gate_total_count` as a convenience summary (not a replacement).
No gap.

### 3. Retry (nội dung gì đã đổi mỗi lần) — ⚠️ PARTIAL, real but not literal "diff"
`repair_log` gives the REAL, specific reason each retry round happened (`gate_targeted` +
`violations` text, often quoting the exact offending phrase — see gate_grounding() above) — this
is genuinely NOT a bare count, and matches the issue's "lý do lỗi cụ thể" bar for the trigger
side.
**What is NOT available**: the actual resulting content text of each attempt. Traced the write
loop (`service.py:429-556`): `content_text` is a single variable overwritten every loop
iteration; only the FINAL attempt's value (`content_text` after the loop, whichever one
ultimately got persisted as `approved`/`held`) is ever written to the DB
(`_persist_piece`/`_hold`, line ~603). An intermediate attempt's full text (e.g. attempt 1's
prose, if attempt 2 supersedes it) is discarded in-process and never written anywhere — not to
`content_piece`, not to `repair_log`, not to `shared.llm_call_log` (migration 137 — that table
logs tokens/cost/`quality_signal`, never the generated text itself). Confirmed structural, not a
query gap: there is no column/table this data could be read from even with a new query, because
the value itself was never persisted.
**So**: the accordion CAN honestly show, per retry round: which gate blocked it + the exact
violation text that was fed back to the LLM as rewrite instructions ("what was wrong, told to the
writer"). It CANNOT show an actual before → after prose diff for that round ("what the writer
actually changed in response") — that specific data was never captured.

### Bonus corroboration (matches AA-558's 2026-09-07 finding, still current)
`frontend/app/admin/tenant-activity/page.tsx:18-19,59-60` confirms **06 Write/Gate and 07 Review
already call the exact same endpoint** (`GET /admin/a4/content-log`) — same rows, just re-framed
under two tab labels. 08 Publish calls `GET /admin/a4/publish-log` (separate table
`acp_shared.publish_log`, joinable by `piece_id`). Merging into one table is not just UI
convenience — it removes a real, byte-identical data duplication.

### Minor note (not a blocker, needs one small confirm): status terminology
Issue's UI spec lists filter values "Draft/Held/Approved/Published". Real
`content_piece.status` CHECK constraint (migration 118) is
`processing | approved | held | failed` — no `draft` value exists, and `published` is not a
`content_piece.status` value at all, it's a derived cross-table fact (a matching
`acp_shared.publish_log` row with `status='published'`) — `content-log`'s own
`_publish_status()` helper already computes this the same way. Proposed mapping (will apply
unless Nghiệp says otherwise when confirming the retry question below): filter UI shows the 4
real states as **Processing / Approved / Held / Failed**, plus a separate **Published** filter
that's really `status='approved' AND publish_status='published'` — not a fifth status value.

## Build (09/09/2026)

### Decisions
- Route stays `/admin/tenant-activity` (unchanged URL, per the issue's own requirement #1).
- Sidebar nav item relabeled "06 · Content Trace" (was "06-08 · Content Trace") and restyled to
  the exact same button look as 01-05 in `atom-curation/page.tsx`'s inner nav list — no more
  border-top divider/different padding setting it apart. It is still a real `<a>` navigation (not
  an inline tab) since 06 now stays genuinely on its own page — that part of AA-557 H.15's
  original design was already correct and untouched.
- Backend: extended `GET /admin/a4/content-log` (`api/routers/admin_a4.py`) rather than building a
  new endpoint — it already had 90% of what the merged page needs (tenant filter, full angle
  array with `chosen`, `gate_ledger`/`repair_log` with real violation text, source lineage). Added:
  `status`/`channel`/`published`/`date_from`/`date_to` query filters; `content_text` now selected
  in FULL (was `LEFT(cp.content_text, 280)`) so the row-click accordion needs no second per-piece
  fetch; `retry_count` (`len(repair_log)`); `topic` (real proxy: the atom's own text, falling back
  to the T8 goal — `content_piece` has no title/topic column, confirmed STEP0, never fabricated);
  `publish_external_url`/`publish_published_at` added to the SELECT (folds 08 Publish's own
  endpoint into this one call — the merged page never calls `/publish-log` at all).
- `GET /admin/a4/publish-log` itself was left untouched (not deleted) — `admin_a4-oversight`'s own
  Cross-Tenant Oversight page still reads it independently; out of this issue's scope to touch.
- Tenant dropdown reuses the existing `GET /admin/tenants` (already used by `/admin/tenants`) —
  no new endpoint for a 4-tenant list.
- "Angle đã chọn" column reads `angles.find(a => a.chosen)?.name` client-side (data already on the
  row, matching the "no second fetch" principle the old `PieceLineageCard` established) — not a
  new backend field.

### Changed vs. original requirement
- Issue's UI spec listed status values "Draft/Held/Approved/Published" — built as the real
  `content_piece.status` values (Processing/Approved/Held/Failed) + a separate Published filter,
  per STEP0's own flagged terminology correction (posted in the Linear comment, no objection from
  Nghiệp before build).

### Tradeoffs
- Considered adding pagination to `content-log`; skipped — real row count today is 13 total across
  all tenants (confirmed live), `limit=200` default already covers every real row with headroom.
  Revisit if/when tenant volume grows.
- `auditPanels.tsx`'s old `WriteGateSection`/`ReviewSection`/`PublishSection`/`PieceLineageCard`/
  `useContentLog`/`useTourScopedFetch`/`CrossLinkNote`/`PickTourPrompt` were deleted outright
  (not deprecated-in-place) — confirmed via grep that nothing else in the frontend imported them;
  the merged page's own `ContentTraceTable`/`ContentTraceAccordion` replace them with a genuine
  table+accordion (SlateTab.tsx/AA-564 SubjectRow pattern — one shared `expandedId`, at most one
  row open) rather than the old page's 3-tab layout.

### Should know (reviewer)
- Real HTML `<table>` with a second `<tr><td colSpan={10}>` per row for the accordion (not
  `AuditTable`, which has no room for an inserted expand-row) — `Fragment` with an explicit `key`
  wraps each row pair; a shorthand `<>` fragment inside `.map()` cannot carry a `key` and was
  caught before commit.
- 30 backend unit tests now cover this endpoint (16 pre-existing + 14 new for the AA-568 filters/
  fields), all passing; full suite 1922 passed / 2 pre-existing unrelated failures (missing
  `OPENAI_API_KEY` in this sandbox, nothing to do with this change).
