## Decisions

- Gap 1 "who can create a pending plan": no new role gate. `/admin/quarter-plan/create` sits
  under the existing `/admin/quarter-plan` middleware prefix (`roles: ["admin"]`) — same as
  Gate B review itself. **The system has no separate Trang/Nghiep role today** (only
  admin/reviewer/content/tenant) — flagged to Nghiep in the final report, not invented here.
- `TripScore` is additive on the `QuarterPlan` pydantic model — `quarter_plan_version.payload`
  is `JSONB` (migration 092), so no migration needed for this field; old persisted rows without
  it just default to `[]` on read.
- New read-only `POST /admin/quarter-plan/preview` endpoint (no persist) powers the live
  checkbox override UI; the existing persisting `POST /admin/quarter-plan` is only called once,
  on final "Create Quarter Plan for Review".
- Preview endpoint (`admin_atoms.py`) now checks `fetch_approved_quarter_plan()` first and only
  falls back to the in-memory `admin-preview-demo` auto-approve path when no approved version
  exists for the tenant/year/quarter — this is what makes Gap 1's full chain (create → Gate B
  approve → N6 reads the real version) observable end to end from the existing Preview screen,
  with no new N6 "production" endpoint needed.

## Round 4 (2026-08-13) — Nghiep's real-browser walkthrough, 3 follow-ups

Not new bugs — Nghiep verified the create → approve → preview chain end to end in the real
browser (something STEP 0 flagged as still needing a live pass) and found 3 UX gaps that are a
direct continuation of the same "chuỗi thao tác rời rạc" problem this issue was already fixing.

### Việc 1 — History tab (view v1..vN, not just the newest)
- No endpoint listed every version for a tenant/year/quarter — `GET
  /quarter-plan/{tenant}/{year}/{quarter}` only ever returns the latest (`ORDER BY version_no DESC
  LIMIT 1`). New `GET /quarter-plan/{tenant}/{year}/{quarter}/history` (`api/routers/admin.py`)
  returns every version, newest first, **including the full plan payload per row** — not just
  summary fields — so the frontend never needs a second round-trip per row.
- `frontend/app/admin/quarter-plan/page.tsx`: new `TabBar` (Pending / History, reusing
  `adminUi.tsx`'s existing `TabBar` — not a new component) on the list screen. History tab is its
  own tenant/year/quarter selector (same shape as the Create Plan page's picker, since the
  underlying endpoint is scoped to one tenant/quarter — there's no cross-tenant "all history"
  query, matching how the endpoint itself is scoped) + a version table. Clicking a row builds
  `VersionDetail`/`PendingItem` directly from the already-fetched payload and reuses the exact
  same `DetailView` the Pending tab uses — no new detail UI, per Nghiep's "reuse DetailView"
  instruction.
- Decision: put History in a tab on the same page rather than a new `/admin/quarter-plan/history`
  route (Nghiep's stated preference to avoid an extra nav hop). No `middleware.ts` change needed —
  it's the same `/admin/quarter-plan` prefix, already gated.

### Việc 2 — sticky container regression + scope extension
- Found while implementing this round: PR #140's round-3 sticky fix (`position: sticky` on the
  Create button) was **silently dropped** by the later `ba383d8` "N4-N6 UI Phase 2" commit, which
  rewrote `create/page.tsx` from a pre-round-3 base. `origin/main` (post both merges) still had it
  correctly, but it's worth flagging: a big feature commit landing on a stale local branch is how
  this kind of regression slips through — checked `git merge-base`/`git log --graph` against
  `origin/main` before starting this round specifically because of that risk.
- Per the actual ask: merged the pre-submit button and the post-submit "created" banner into ONE
  sticky container that swaps its children by `createdVersionId` state, instead of two separate
  blocks (one sticky, one a plain `Card` appended after it — which reproduced the exact
  scroll-to-find problem the round-3 fix was meant to solve, just one screen-state later).

### Việc 3 — Approved → Preview link
- Added a "View in Slot Grid Preview" button on `DetailView`'s approved-status block, linking to
  `/admin/curation/preview`. Deliberately a **plain navigation link**, not a tenant-scoped deep
  link with `?tenant_id=`/year/quarter query params: `GET /admin/atoms/preview-slotgrid` (the
  endpoint Preview calls) hardcodes `today.year`/`(today.month-1)//3+1` for its quarter — it does
  not read year/quarter from the URL at all — so passing a specific version's year/quarter through

## Round 5 (2026-08-13) — Preview version investigation + create-page field audit

### Việc 1 — CONCLUSION: NO BUG. Live DB + live API evidence below.

Nghiep's report (v6 created with 8 different trips than v5, approved, Preview's summary cards
"looked the same" after Recompute) was treated as a serious bug report, not a false alarm, and
investigated against the real live DB/API (AWS was live this session — ECS running, RDS
`available`), not code-reading alone.

**Evidence gathered** (read-only S3-mediated ECS exec — `acp_shared.quarter_plan`/
`quarter_plan_version` for `tenant_id=00000000-0000-0000-0000-000000000001` (aa_internal),
year=2026, quarter=3):
- `quarter_plan.current_version_id` = `98af1ff5-...` = v6's `version_id`. Confirmed correct — not
  stuck on v5 or an older version.
- **v1 through v6 are ALL `approval_status='approved'`** in `quarter_plan_version` — approving a
  new version does NOT flip older versions back to a non-approved status, it only moves
  `quarter_plan.current_version_id` (this is `approve_quarter_plan_version()`'s actual, correct
  behavior — see `services/acp_planning/quarter.py:364-379` — not a bug, but worth knowing since it
  means "approval_status='approved'" alone never identifies the live version; only
  `current_version_id` does).
- Called `GET /admin/atoms/preview-slotgrid` directly via `curl` from inside the running ECS
  container (real deployed code, not a re-derivation) — its `quarter_plan.trip_ids` **exactly
  matched v6's 8 trip_ids from the DB, byte for byte** (`MATCH: True`). `demo_params.demo_mode`
  was `False` ("Reading a real Gate B-approved quarter plan"), confirming the real-DB path was
  taken, not the in-memory demo fallback.
- **Root cause of the visual "looks the same"**: v5 and v6 only share 3 of 8 trips (5 actually
  differ), but `destination_shares` is `{"South Korea": 1.0}` for BOTH versions, and both have
  the same trip COUNT (8). Read `frontend/app/admin/curation/preview/page.tsx`'s "Quarter plan"
  summary card (line ~311, pre-round-5): it renders only `Q{quarter} {year} — {trip_ids.length}
  trips` + a destination-shares bar chart — **it never rendered individual trip names or ids**, so
  two versions with the same count and same 100%-single-destination split are visually
  indistinguishable on that card regardless of which 8 trips are actually selected. Slot cards
  further down show channel/funnel-stage/keyword/atom-count, not trip name either. This is exactly
  the mechanism Nghiep's own hypothesis in the round 5 brief predicted ("output slot pattern
  giống do cùng destination") — confirmed with real data, not assumed.
- Also relevant: `runway_cell_count` (36, shown in the first summary card) is computed by
  `runway_map()` from the tenant's full trip/atom pool for the market, independent of which trips
  a specific quarter plan version selected — it would read identically across ANY version for the
  same tenant/year/markets, by design (N4 Runway Map is destination-level staging, not
  per-quarter-plan-version). Not a bug; a different concern than "which version is this."
- **No code fix needed for Việc 1** — the version-tracking mechanism (`current_version_id`,
  `fetch_approved_quarter_plan`, the live `preview-slotgrid` endpoint) all read correctly end to

### Việc 4 — create-page trip-selection field audit (investigation only, no UI changes)

Read `services/acp_planning/quarter.py:109-189` (`_score_reason`, `compute_quarter_plan`) to get
ground truth for every field on `/admin/quarter-plan/create`'s trip rows, then pulled v6's full
`trip_scores` array (763 rows — one per non-retired trip, not just the 8 chosen) from the live DB
to check real distributions rather than guessing.

| Field on screen | What it actually is | Notes |
|---|---|---|
| Trip name / Destination | `Trip.name` / `Trip.destination` | As shown, no surprise. |
| Numeric score (e.g. 1.73/0.73/0.00) | `TripScore.score` — a **composite**: `runway_fit*0.4 + richness*0.3 + distinctiveness_score*0.3 + (1.0 if forced else 0)`. Not a single metric. | Max for a non-forced trip is 1.0; forced trips can reach up to 2.0 (the +1.0 bonus is why 1.73 > any possible non-forced score). |
| "Manually added" reason text | Shown **exactly when** `forced=True`, i.e. the trip's name/destination fuzzy-matched one of the `specials` strings (populated when a human clicks the checkbox to add a trip N5 didn't auto-select). `_score_reason()` checks `forced` first and short-circuits — the 3-way score breakdown below is never computed/shown for a forced trip. | |
| "FORCED" badge | **The exact same `forced` boolean** as "Manually added." | Confirmed by reading both code paths — `create/page.tsx`'s `{t.forced && <Badge>forced</Badge>}` and `_score_reason`'s `if forced: return "Manually added"` both key off `TripScore.forced`. Currently the UI shows **two separate labels for one field** on the same row — redundant, not two different concepts. |
| "High runway fit (BOFU/MOFU window this quarter)" reason text | One of 3 possible labels, meant to name whichever of `{runway_fit*0.4, richness*0.3, dist*0.3}` is numerically largest for that trip (`max(contributions, key=...)` over a 3-entry dict). | **CONFIRMED BUG, not a placeholder illusion** — evidence: of the 763 trips in v6's live payload, 594 (78%) show this exact text, and of those, **562 have `runway_fit=0.0`** (real example: Bhutan trips "THIMPHU FESTIVAL" etc., `runway_fit=0.0, richness=0.0, distinctiveness_score=0.0`, reason still "High runway fit..."). Root cause: when all three weighted contributions tie at exactly `0.0` (the common case — most trips have neither a BOFU/MOFU runway window nor curated atoms yet), Python's `max()` on a dict returns the **first** key in insertion order, and `"High runway fit..."` happens to be listed first in `_score_reason`'s `contributions` dict (`quarter.py:117`). The label is not just uninformative for these rows, it is **factually the opposite of true** (claims high runway fit when the value is the minimum possible, 0.0). |
| "Rich atom pool" / "High-distinctiveness atoms" reason text | Same mechanism, chosen correctly when they ARE the max non-tied contributor — 136 trips in the same payload show "Rich atom pool" legitimately (their `richness*0.3` really was the largest term). | Not buggy on their own — only the tie-at-zero case is wrong. |

**Proposals (not built, per instructions — Nghiep to decide):**
1. Fix `_score_reason()`'s tie-break: add a 4th branch for the all-zero case (e.g. return
   `"No runway/atom signal yet this quarter"` instead of defaulting to the misleading first key).
   Small, isolated fix — same function, no schema/API change.
2. Collapse "FORCED" badge + "Manually added" reason text into one indicator — they're the same
   field shown twice today.
3. Relabel the bare numeric score as `"Score: 1.73"` or similar (Nghiep's own suggestion) so it
   doesn't read as an unexplained raw number; optionally a tooltip breaking down the 3 weighted
   components + forced bonus.
4. Given 763 rows is the full non-retired trip pool (not just the 8 shown as selected today's UI
   already filters to what fits capacity_posts_per_week+1 via `max_trips`, so the create page
   itself isn't the 763-row view) — no table-simplification action needed there specifically, but
   worth Nghiep knowing the reason-label bug (item 1) affects the majority of rows a reviewer scans
   before deciding to manually add/remove a trip.

## Tradeoffs

- No new role gate for "who can create a pending plan" — the system has no Trang/Nghiep
  distinction today (only admin/reviewer/content/tenant), so `/admin/quarter-plan/create` sits
  under the same `roles: ["admin"]` prefix as Gate B review itself. Building a real
  Trang-vs-Nghiep role split was explicitly out of scope (decision #1) — flagged here, not
  invented.
- Gap 1's create-plan UI does not let a user edit markets/channels/capacity inline — those come
  read-only from the tenant's Planning config (Gap 3). Splitting "which trips" from "what
  campaign parameters" keeps each screen single-purpose; changing parameters mid-preview would
  also silently invalidate the score list shown, which seemed more confusing than a link to
  Tenants > Planning.
- `TripScore.reason` is a single dominant-factor label (e.g. "Rich atom pool"), not the full
  breakdown (`runway_fit`/`richness`/`distinctiveness_score` are still returned as separate
  fields in the API response for anyone who wants the raw numbers — the create-plan UI shows the
  numeric `score` plus the label, not a 3-column breakdown, to keep the checklist scannable).
- `excluded_trip_ids` exclusion is enforced by removing a trip from consideration entirely
  before ranking (never entering `eligible`), not by ranking it and then filtering — this means
  an excluded trip's capacity slot is backfilled by the next-highest-scoring eligible trip,
  which is the expected "remove and let the algorithm re-fill" behavior, not "leave a gap."
- Preview-slotgrid's real-vs-demo branch check (`fetch_approved_quarter_plan` first) adds one
  extra DB round-trip on every Preview page load/Recompute click even when no approved plan
  exists (the common case for a fresh tenant). Accepted — this is a low-traffic admin preview
  endpoint, not a hot path, and the alternative (a separate flag/endpoint) would fragment the
  single source of truth for "is there a real plan" logic that `allocate_month_from_db` already
  owns.
