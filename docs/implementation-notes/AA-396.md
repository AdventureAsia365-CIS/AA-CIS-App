# AA-396 — repair notes-chain fix + leak-guard against reasoning-leak corruption

Follow-up to the AA-396 investigation (all 9 real N7 pieces held after exhausting
`max_repairs=3`). Two concrete, evidenced bugs fixed here; the broader held-rate problem
(F8 "ends with CTA" judge reliability, F3/F4 threshold calibration, the shared
`max_repairs` budget across simultaneous multi-gate failures) is **not** addressed by
this PR — see Should-know.

## Decisions

- **Fix 1 and fix 2 shipped together, not as separate issues.** Both are instances of the
  same root problem (repair works with insufficient/wrong context on LLM-judged gates,
  AA-382's territory) surfacing at two different points in the same flow — the gate side
  (notes dropped before repair ever sees them) and the repair side (repair actively
  misreads the vocabulary it's given). Splitting them into separate PRs would just mean
  reviewing the same real failure data twice.
- **Fix 2a: renamed the 4 colliding failure codes, did not just patch the prompt.**
  Confirmed via grep that `BRAND_SEO_FAILURE_CODES`/`SOCIAL_SEO_FAILURE_CODES` (gates.py)
  have zero cross-module consumers — no other file imports these lists or matches on
  these literal strings outside `gates.py` itself. The S1 pipeline's own
  `_CODE_FIELD_MAP` (`content_generation/graph.py`) and `flag_fix_node.py` have an
  **identical**, entirely separate copy of `SUMMARY_OFF_BRAND`/`HIGHLIGHTS_TOO_GENERIC`/
  `ITINERARY_STRUCTURE_WEAK`/`META_INCOMPLETE_SENTENCE`/`DFS_INTENT_UNDERUSED`/
  `GENERIC_AI_WORDING` mapped to real `generated_content` DB columns
  (`seo_title`/`aa_highlights`/`aa_itineraries`/`seo_meta`) — a real prior-art vocabulary
  that N7's F9 rubric was evidently copy-pasted from without noticing N7 has no such
  discrete fields (everything lives in `piece_body` prose). Renaming removes the
  exact-string collision at its source (permanent) rather than relying on a prompt
  disclaimer the repair LLM has to correctly prioritize every time (band-aid, and the
  disclaimer competes for attention with the failure-code list itself). Only renamed the
  4 codes piece 7's own leaked text named explicitly (`SEO_TITLE_WEAK`,
  `META_INCOMPLETE_SENTENCE`, `HIGHLIGHTS_TOO_GENERIC`, `ITINERARY_STRUCTURE_WEAK` →
  `BODY_OPENING_TITLE_WEAK`, `BODY_SUMMARY_LINE_INCOMPLETE`,
  `BODY_EXPERIENCE_DETAILS_TOO_GENERIC`, `BODY_DAY_FLOW_STRUCTURE_WEAK`) — left
  `SUMMARY_OFF_BRAND`/`GENERIC_AI_WORDING`/`DFS_INTENT_UNDERUSED` alone even though they
  also collide with S1's vocabulary, since they were not implicated in the real
  confusion (piece 7's leaked reasoning never mentioned them, and pieces 2/3/6/9's
  repeated `SUMMARY_OFF_BRAND`/`GENERIC_AI_WORDING` failures show no sign of the same
  "this must be a separate field" misreading) — staying evidence-based rather than
  renaming everything that happens to also collide.
- **Fix 2b: guard lives inside `repair_piece()`, raises the existing `RepairFailed`.**
  Considered adding a new `Piece.status` value for "repair sanity-check rejected" but
  explicitly told not to invent a new state category — `RepairFailed` already *is* "what
  exists for repair attempt failed" (AA-376 built it for Sonnet-invoke exhaustion,
  `run_gates()` already catches it and holds via `_hold(piece, first_failure)`). Reusing
  it means the guard needed zero changes to `gates.py::run_gates()`.
  - **Known consequence, called out explicitly since it doesn't match a literal reading
    of the ask:** raising from inside the retry loop (not retried further) means
    `run_gates()` holds the piece **immediately** with the *original* failing gate's
    `held_reason` (e.g. `F9_brand_seo_audit: ...`), not a custom "sanity check failed"
    message, and per `run_gates()`'s existing, already-documented semantics
    (`piece.repair_count` is only incremented on a `repair_fn` call that *returns*),
    `repair_count` does **not** increment for a rejected attempt — same as any other
    `repair_fn` exception (e.g. Sonnet exhausted retries). This is the correct behavior
    per the existing design (a repair attempt that produced garbage shouldn't count as a
    "real" attempt that legitimately used up budget), but it means a guard trip ends the
    repair loop for that piece outright rather than consuming one of three rounds and
    trying again. Did not touch `run_gates()`'s counting logic — that's shared, load-
    bearing code well outside today's two-bug scope. The sanity-check message itself is
    preserved in the `gate_repair_fn_failed` warning log (`error=str(e)`) for debugging.
  - Guard is a narrow phrase-match against the **first paragraph/prefix only** (real leak
    precedes real content, confirmed against piece 7's actual data), not a general
    reasoning-detector — deliberately biased toward missing edge cases over
    false-flagging legitimate content, per the explicit instruction to keep this
    conservative.

## Changed

- `services/acp_produce/gates.py`:
  - New `_format_audit_reason(failure_codes, notes)` helper — folds `notes` in alongside
    `failure_codes` (previously `or`'d, so `notes` was silently dropped whenever any
    `failure_codes` existed, which is nearly always). Used by both
    `gate_brand_seo_audit()` and `gate_brand_seo_audit_social()`.
  - `BRAND_SEO_FAILURE_CODES`: 4 codes renamed (see Decisions). `SOCIAL_SEO_FAILURE_CODES`
    unchanged (no collision — its codes are `SUMMARY_OFF_BRAND`/`CTA_MISSING_OR_WEAK`/
    `HOOK_WEAK`/`GENERIC_AI_WORDING`/`FACT_CHECK_MANUAL_CHECK`, none of piece 7's 4).
- `services/acp_produce/repair.py`:
  - New `_LEAK_SIGNAL_RE` / `_looks_like_leaked_reasoning()` — checked against the first
    ~500 chars up to the first `\n\n` only.
  - `repair_piece()`: after a successful Sonnet invoke, runs the guard before returning;
    raises `RepairFailed` (not silently returning the corrupted text, not retrying) if it
    trips.
- Tests (all mocked, no live Bedrock/DB calls, matching each file's existing convention):
  - `tests/unit/test_aa298_judge.py`: notes-preservation test for the blog F9 gate.
  - `tests/unit/test_aa372_gates.py`: notes-preservation test for the social F9 gate.
  - `tests/unit/test_aa376_repair.py`: prompt carries the fuller notes-inclusive reason
    string through to Sonnet; leak-guard positive case using piece 7's actual leaked text
    reconstructed verbatim from `docs/implementation-notes/AA-391-report-data.json`
    (confirms `RepairFailed` + exactly 1 invoke call, no wasted retries); leak-guard
    negative case — legitimate travel content that genuinely discusses "itinerary...
    structure" does not trip the guard.

## Tradeoffs

- Renaming `BRAND_SEO_FAILURE_CODES` values changes what the F9 judge (Nova Pro) is
  asked to emit and what gets written to `acp_deliver.pieces`/audit records going
  forward — verified this is safe (list has no other consumers), but any external
  dashboard or manual query someone might already be running against the old code
  strings (`SEO_TITLE_WEAK` etc.) in raw `held_reason`/`gate_ledger` text would need to
  switch to the new names. No such consumer exists in-repo as of this fix.
- The `notes`-inclusion fix makes `held_reason` strings longer (codes + `--` + judge
  prose) — acceptable since `held_reason` is operator/reviewer-facing text, not a
  parsed/matched value anywhere in the codebase (confirmed: only `_hold()` constructs it,
  nothing pattern-matches on its exact old shape).

## Should know

- **This does not close AA-396.** Per the original investigation report: F8's "ends with
  CTA" judge reliability (reproduced across 3 separate runs now — AA-367, AA-376,
  AA-396), F3/F4 threshold calibration against real writer output, and the shared
  `max_repairs=3` budget starving pieces with multiple simultaneous gate failures (piece
  1's class) all remain open, unresolved, out of scope for this PR. AA-396 itself should
  stay in its current status until those are separately investigated/fixed — do not treat
  this PR as evidence the held-rate problem is solved.
- Even with fix 1, `notes` is a single LLM-written sentence, not the full rubric or
  worked examples — AA-376's own live-verify already showed that a single repair call
  fixing one flagged dimension of F9 can genuinely introduce a *new* one, even with
  reasonably rich context. This fix improves what repair has to work with; it does not
  guarantee convergence within 3 rounds on a piece with a genuinely multi-dimensional
  brand/SEO problem.
- Did not re-run the AA-376 live-verify script or any new production N7 run as part of
  this fix (explicitly out of scope per the task) — these fixes are verified by unit test
  only. A live re-verify against real Bedrock/Nova Pro would be the natural next step
  before calling AA-396 resolved.
