## Decisions

- **`quality_signal` is real and per-stage, never a placeholder** (the 02/09/2026 S171 decision
  this build prompt opened with). Every one of the 16 call sites logs something ACTUALLY computed
  at that call site — a real judge score/pass-fail where a judge exists (`s1_judge`,
  `s1_brand_audit`, `t10_judge`, `n7_judge`), or a real, honest heuristic where none does
  (`t5_atomize`: atoms actually extracted this call; `s1_itinerary_nudge`: did the nudge land
  inside clamp; `t8_angle_gen`: angles generated + avg PAA answers matched; `n7_gap_research`:
  did it produce a real comparison statement; `n7_draft`/`n7_faq`: sections/items parsed vs.
  requested; `n7_adapt`: required channel markers present; `n7_repair`: leaked-reasoning rejected
  or not; `s1_generate`/`s1_atom_writer`: JSON parsed / output length). No stage was found where
  literally nothing measurable exists — every one of the 16 got a real signal, not a fallback
  `{}`.
- **`t9_write`'s own row is a SHALLOW heuristic (output length), not the T10 gate result** —
  deliberate split, not an oversight: `t10_judge`'s own 2 rows (one per gate, `gate_framework`/
  `gate_brand_voice`) carry the REAL, meaningful pass/fail for that same piece. Considered logging
  `t9_write` with the deferred T10 outcome instead (richer signal) but rejected it — it would have
  required changing `write_content()`/`rewrite_with_feedback()`'s return tuple shape (currently
  `(content_text, cost_usd, seo_meta)`, unpacked by name in ~10 existing tests across 2 test
  files), a real regression-risk for a signal that already exists elsewhere in a cleaner, more
  attributable form (the judge's own row, not the writer's row wearing the judge's result).
- **Judge-stage rows (`t10_judge`, `n7_judge`) always log `tenant_id=NULL`**, even for a real
  tenant's T9/T10 run — `gate_framework()`/`gate_brand_voice()`/`gates.py`'s 3 gate functions
  take only `content_text`/rubric text as parameters, by design (both files' own docstrings:
  "gate functions stay channel-agnostic"). Threading tenant identity into 5 functions whose whole
  design point is staying context-free was judged the wrong trade for this task — the SAME
  piece's `t9_write` row (which does carry `tenant_id`/`angle_gate_request_id`) sits right next
  to it in `llm_call_log`, joinable by `created_at` proximity if per-tenant judge-cost ever
  becomes a real requirement.
- **Cost pricing for judge calls uses `pricing.calc_cost()` against whatever `model_used` the
  judge backend reports** — accurate for the real production default (`gpt-4.1`, in
  `COST_TABLE`); an approximation (falls back to Sonnet-tier rates) for a manual `nova_pro`/
  `gpt56` override via `JUDGE_MODEL` env var, which is NOT the shipped default. Acceptable for an
  observability log, explicitly not treated as a billing-grade number.

## Tradeoffs

- **Tree query computes an "ok_rate" by OR-ing 8 differently-named boolean keys across the 16
  stages' `quality_signal` shapes** (`passed`/`landed_in_clamp`/`meta_landed_in_band`/
  `required_markers_present`/`produced_statement`/`json_parsed`/`output_parsed`/`status='pass'`)
  rather than one uniform "success" field. Considered normalizing every stage's `quality_signal`
  to always include a top-level `"ok": bool` key instead — rejected: it would have hidden the
  actual, stage-specific signal (e.g. "3 items requested, 2 parsed" is more informative than a
  bare `false`) behind a lossy boolean at write time, for a convenience only the READ side (this
  one aggregation query) needs. The OR-list is uglier SQL but keeps every stage's own log row
  fully self-describing.
- **`t5_atomize`'s quality_signal (`atoms_extracted`) and `t9_write`'s (`output_len_chars`) are
  numeric, not boolean** — the tree query surfaces these as separate `avg_atoms_extracted`/
  `avg_output_len_chars` columns rather than trying to force them through the same "ok_rate"
  machinery. The monitoring UI shows whichever of (`ok_rate`, `avg_atoms_extracted`,
  `avg_output_len_chars`, or just `call_count`) is actually non-null for that stage — not every
  leaf renders the same shape, by design (matches the build prompt's own "tự đề xuất cấu trúc hợp
  lý" latitude).

## Should know

- **Cost/quality numbers only exist from the moment this PR deploys forward** — `llm_call_log`
  starts empty; every dollar this codebase has ever spent on LLM calls before this task is real
  but permanently unrecoverable (matches AA-434's own original finding: the old code computed
  cost in memory and discarded it, nothing to backfill from).
- **A1/T2 spend through the 5 `s1_*` stages is NOT tenant-attributable** — see AA-518.md §6's
  "Known, disclosed gap". The monitoring tree will show these under a synthetic `tenant_id=NULL`
  → `"aa_internal"` bucket regardless of whether the underlying call was actually an admin A1 run
  or a tenant T2 rewrite — a real, disclosed limitation of this round, not silently swept under
  the tree UI's own "aa_internal" label.
- Live-verify (real UI model change → real LLM call → real DB row, cache-invalidate check, tree
  matches DB, regression on an untouched stage) is below, once run.
