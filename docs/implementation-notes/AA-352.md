# AA-352 — itinerary_day column on tour_atoms + LLM self-extraction at N2 decompose

## Decisions
- Migration number: 093 (092 = AA-320 quarter_plan, already exists — confirmed by listing
  `api/migrations/` before creating the file, not assumed).
- `shared.schema_versions` is confirmed a single global table used by every schema's migrations
  (acp_contract via migration 090, acp_shared via migration 092) — no per-schema convention exists
  to diverge from, so 093 uses the same `shared.schema_versions` INSERT as its predecessors.
- No new LLM call — `itinerary_day` is added to the existing Sonnet extraction contract inside
  `_decompose_inline()` (one invoke_claude per tour, unchanged call count).
- `AtomRecord` (`services/acp_planning/models.py`) intentionally NOT touched. It is already a
  narrow projection of `tour_atoms` — it omits `activity_type`, `emotional_hook`, `season_note`,
  `media`, `human_seam_notes`, `owner_scope`, timestamps, `source_hash`, `is_empty_marker` today.
  Per AA-350, N5/N6 planning has no requirement to read `itinerary_day` yet (that's AA-306/
  S1-from-atom's future concern) — adding it here would be scope creep against an already-deliberate
  narrow model, not a trivial add-for-free.
- No backfill of the 300 existing atoms (30 tours) — explicit instruction, `itinerary_day` stays
  NULL for all pre-093 rows.

## Changed
- `api/migrations/093_tour_atoms_itinerary_day.sql` (new): `ALTER TABLE acp_contract.tour_atoms
  ADD COLUMN itinerary_day SMALLINT NULL` + column comment.
- `api/routers/v1_atoms.py`:
  - `_SYSTEM_PROMPT`: added `itinerary_day` to the JSON contract, with explicit "return null if
    unclear, never guess" instruction matching the prompt's existing never-pad/never-invent voice.
  - Response parsing: reads `atom.get("itinerary_day")`, tolerant of the key being absent or null
    (matches existing `.get()` pattern used for `emotional_hook`/`season_note`).
  - INSERT statement (real-atom branch): added `itinerary_day` column + `$14` placeholder.
  - Empty-marker branch INSERT: NOT changed — a marker row is not a real atom, has no day to record
    (column stays at its NULL default there, consistent with every other atom-shaped column already
    absent from that INSERT).

## Tradeoffs
- `itinerary_day SMALLINT` (not `INTEGER`) — matches `visual_potential SMALLINT` sibling column and
  the actual value range (1–99 realistically); no functional difference at this scale, chosen for
  schema consistency only.
- Prompt asks the model to map `"DAY 01"` / `"Day 12"` free-text labels to an integer itself rather
  than a regex pre-pass — this was STEP 0's finding (labels too inconsistent to parse reliably) and
  Nghiep's explicit decision this session, not re-litigated here.
- Left `content_generation/s1_from_atom.py` and `acp_planning/quarter.py` untouched — both use
  named-column SELECTs (verified by grep, see Should know) and are unaffected by an additive nullable
  column; wiring them to actually *read* `itinerary_day` is out of scope (AA-306 territory).
