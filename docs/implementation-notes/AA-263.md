# AA-263 — [CIS][S1] Tách node editor độc lập — STEP0 verdict: KHÔNG build

## Decisions
- STEP0 (mandatory per the issue) read `services/content_generation/graph.py` +
  `flag_fix_node.py`/`judge_node.py`/`brand_audit_node.py` directly, node by node, to confirm
  which node(s) actually mix "revise" into "validate/score" TODAY — not assumed from the
  issue's 06/07/2026 description.
- **Verdict: the substantive architectural goal ADR-2026-020 asks for is already satisfied.**
  `flag_fix_node` (AA-133/134/135, migration 050 — shipped well before this issue's own
  creation date, confirmed via `git log --diff-filter=A` on that migration) already IS the
  separate "editor" node: it's the ONLY node in the whole S1 graph that makes an LLM call
  whose purpose is to rewrite content fields (`LLMClient().generate()` with `FIX_SYSTEM`,
  writing back into `current_content`/`generated`). Every other node
  (`validate_node`/`judge_node`("llm_judge")/`brand_audit_node`/`revalidate_node`) is a pure
  scorer — confirmed by reading each one fully: they build `issues`/`fired`/`score`/
  `brand_audit_status`/`quality_score` and return them, never rewrite `generated` content via
  an LLM call. `revalidate_node` just re-invokes `validate_node`+`judge_node` (pure re-score,
  no independent edit logic).
- The issue's own premise text ("S1 hiện gộp việc revise vào validate_node/llm_judge — cần
  tách 1 node editor độc lập") does not match the graph as it exists — and confirmed via
  `git log` it didn't match it even AT THE TIME the issue was written: `flag_fix_node` was
  committed **2026-05-29** (migration 050, `git log` date, PR #3), over 5 weeks before this
  issue was created (**2026-07-06**). Not something that drifted since — the premise appears
  to have been already-stale when filed.
- **One real, narrow, technically-accurate gap found** (not the substantive gap the issue is
  about): `validate_node` (`graph.py` lines ~501-542) does an inline, DETERMINISTIC (regex-
  only, no LLM) itinerary text-format normalization — stripping markdown bold, normalizing
  day-separator dashes, collapsing blank lines — before scoring. Strictly read, this is
  `validate_node` "sửa" (editing) something, a narrow violation of ADR-2026-020's "validate
  node = chấm điểm, không sửa" principle. But this is pure text/whitespace formatting cleanup
  with no LLM call, no brand-voice/factual content change, and no cost/latency delta (no new
  LLM call) — categorically different from, and much lower-stakes than, the "add an editor
  LLM-call node" architecture change the issue and its Consequences section describe (cost/
  latency delta from a new LLM call, full CI→Deploy→UAT→Prod pipeline).

## Changed
Nothing. No code touched — this is a STEP0-only investigation record, same class of outcome
as AA-324's "AA-518 didn't resolve it, but investigate rather than assume" and AA-310's
"prerequisite unmet, don't force it."

## Tradeoffs
- Chose NOT to build a full new "editor" node given STEP0's finding that one already exists
  and does the job (`flag_fix_node`) — building a second, redundant editor node into the
  shared A1+T2 production S1 graph, with the full heavy pipeline (CI→Deploy Dev→digest
  verify→UAT Preview→wait for manual merge→Deploy Prod) this issue itself specifies for a
  real architecture change, would be real production risk for zero real architectural gain.
- Chose NOT to build the narrow itinerary-format-normalization extraction either (moving
  those ~40 lines out of `validate_node` into a tiny separate node) — while real and
  technically accurate, it's a cosmetic ADR-compliance nicety with no functional/cost/latency
  motivation, doesn't match what this issue's own Consequences section anticipated building
  (an LLM-call editor node), and isn't what was asked for. Flagging it as an optional, much
  lower-risk future cleanup rather than building it unasked, to avoid scope-creeping a
  "should I build this too" decision into an issue whose real premise didn't hold.
