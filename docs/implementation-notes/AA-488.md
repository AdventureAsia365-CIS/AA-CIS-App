## STEP 0

Re-audited (not trusted blind) the 4 code locations the original AA-488 issue pointed at —
`services/ingestion/handler.py::process_file()`, `api/routers/admin_pipeline.py::ingest_s3()`
dry_run branch, `frontend/app/admin/upload/page.tsx` Step 4 commit UI, and the `upload_staging`
table (migration 052). All 4 line-number references in the issue matched the real code exactly.

Confirmed: `process_file()` had exactly ONE dedup layer against the DB (`raw_tours`, by
normalized `(src_name, provider)`) — no dedup between rows within the SAME uploaded file. Two
rows in one file with an identical key, neither already in `raw_tours`, both query the DB before
either is inserted, so neither sees the other as "existing" — both land in `new_records` and both
get inserted, producing duplicate `raw_tours` rows from a single upload.

## Decisions

- Split AA-488 into 2 PRs (Nghiep's call, presented as a tradeoff): Gap 1 touches only
  `handler.py`'s insert-time loop; Gap 2 spans 3 layers (dry_run preview, Commit response,
  frontend) and is a different concern (response/UX accuracy for the "nothing new happened"
  state, not insert semantics). No shared diff hunks between the two.
- In-file duplicate handling (Nghiep's call): drop silently, keep the FIRST occurrence, record
  the dropped row in `ingest_details.drops` via the existing `_summarize_drops()` grouping with a
  new `reason='duplicate_in_file'` — reused the mechanism AA-343 already built for insert
  failures, no new table/enum/schema needed. Rejected alternative: routing in-file dupes into
  `upload_staging` (that table's `matched_tour_id` FK models a match against an EXISTING
  `raw_tours` row, which an in-file dupe is not — would need a schema/semantics change for a
  case the drops mechanism already covers for free).

## Changed

- `services/ingestion/handler.py::process_file()`: added `seen_keys` (set of normalized
  `(src_name, provider)` tuples assigned to `new_records` this run) and `in_file_drops` (list).
  A record whose normalized key is already in `seen_keys` is dropped with
  `reason='duplicate_in_file'` and `continue`s — never reaches the DB-existence query, never
  reaches `upload_staging`. `seen_keys` is populated only in the `else` branch (no DB match) — a
  record that DOES match an existing DB row still routes to `upload_staging` unchanged.
  `_summarize_drops(insert_failures + in_file_drops)` merges both drop sources into one
  `ingest_details.drops` list/log line. `rows_dropped` in the function's final return dict was
  also updated to `len(insert_failures) + len(in_file_drops)` — this was NOT updated in the first
  pass (only the logger call and `ingest_details` write were), caught by the first unit test
  failing (`result["rows_dropped"] == 0`, expected `1`).

## Tradeoffs

- First-occurrence-wins with no tie-break logic (e.g. "keep the row with more complete fields")
  — matches the existing DB-dedup path's behavior (`ORDER BY ingest_at DESC LIMIT 1`, i.e.
  whichever exists first also wins there), so this doesn't introduce a new dedup philosophy,
  just extends the existing one to the in-file case.
- Did not touch Gap 2's dry_run preview (`admin_pipeline.py`), which has the identical
  DB-only-dedup gap on the preview side (`duplicate_names` set built only from `raw_tours`) — a
  file with in-file dupes will still show BOTH rows as "ready" in the Step 3 preview screen, and
  only find out one was dropped after committing (Step 4). Deliberately out of scope for PR-1 per
  the 2-PR split; PR-2 will address the preview-side gap.

## PR-2 — Gap 2 (frontend false-success tick)

### Decisions

- Scope confirmed with Nghiep before coding, beyond the original 3rd decision point (per-file
  circle+text only): also fixed the aggregate "Done! Tours are ready for rewrite in S1." banner
  and the post-commit toast, both of which show the identical unconditional-success bug for the
  same root cause (`written===0 && staged===0`) a few lines away from the piece already approved.
  Rejected alternative: fix only the per-file row, leave banner/toast as a documented known gap —
  rejected because it would ship a half-fixed UX (row says "no new tours" in amber, banner right
  below still says "Done!" in green for the same file).
- No backend change in this PR — `CommitResponse` already carries `tours_written`/`tour_count`/
  `tours_staged`, everything needed is already in the response the frontend receives. Confirmed
  by reading `interface CommitResponse` (`frontend/app/admin/upload/page.tsx`) before writing any
  fix.
- Reused `A.gold` for the "no new tours" state (existing token, already means "in-
  progress/attention" elsewhere on this page — e.g. the `committing` spinner) rather than adding
  a new color token. Toast component only supports `type: "success" | "error"` — kept
  `type="success"` for the new wording rather than adding a third toast type, since this is a
  wording fix, not a new visual category.
- Deliberately did NOT touch `admin_pipeline.py`'s `dry_run` preview branch (the `duplicate_names`
  set there is built only from the DB, same underlying gap as Gap 1 but on the PREVIEW side — a
  file with in-file duplicates still shows both rows as "ready" in the Step 3 preview screen).
  That is a genuinely separate, still-open gap from what was scoped as "Gap 2" — noted here as a
  known follow-up, not silently rolled into this PR.

### Changed

`frontend/app/admin/upload/page.tsx`:
- Added `AlertCircle` to the lucide-react import.
- `doCommit()`: tracks `anySuccess`/`anyNewTours` across the `Promise.all` of per-file commits.
  When no file has staged rows (the existing "go to Step 5 review" branch) AND at least one
  commit succeeded but none wrote or staged anything new, shows
  `"No new tours — every row already exists in the catalog."` instead of the old unconditional
  `"Tours saved to database successfully"`. If ALL commits failed outright (`anySuccess` false),
  falls through to the original wording unchanged (that's a different, pre-existing gap —
  error-path toast wording — not this task's scope).
- Added `fileHasNoNewTours(fs)` helper + `allDoneFilesHaveNoNewTours` derived value (near the
  existing `allDone` computation).
- Step 4 per-file row: circle background/icon is now `A.gold`/`AlertCircle` instead of
  `A.green`/`CheckCircle` when `status==="done"` and the file wrote nothing new; text becomes
  `"No new tours (all duplicates)"` instead of `"0 tours saved"`.
- Step 4 aggregate banner: split the single `allDone && dupBatchIds.length===0` block into two —
  one (new) shows the amber "No new tours" message + only an "Upload More Files" button when
  EVERY done file wrote nothing new; the other is the original green "Done! ... Go to S1 Rewrite"
  banner, now gated on `!allDoneFilesHaveNoNewTours` so it no longer fires for an all-empty
  commit.

### Tradeoffs

- `allDoneFilesHaveNoNewTours` is all-or-nothing across every committed file in one batch — a
  batch with 2 files where file A has real new tours and file B has none still shows the GREEN
  "Done!" banner (correct — something real did get saved), with file B's own row correctly shown
  amber individually. Only when EVERY file in the batch wrote nothing does the banner switch.
  This matches the same granularity choice already implicit in the existing `dupBatchIds`/Step-5
  routing logic (also all only cares in aggregate whether ANY file had staged rows).
- Toast wording change only fires when `anySuccess && !anyNewTours` — a batch that's a mix of
  "some real writes" and "some empty" still gets the original "success" toast (matches the
  banner's same all-or-nothing choice, for consistency between the two aggregate signals).
