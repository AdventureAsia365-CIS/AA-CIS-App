# AA-532 — route_detection.py: versioning replaces DELETE+INSERT-whole

## Decisions

- **Versioning, not delete-then-diff-then-selective-update** (Nghiệp's own chosen direction,
  05/09/2026) — simpler and provably correct vs. trying to compute a smart mapping between old
  and new Route boundaries when Segments shift.
- **Route identity = (tenant_id, tour_id, first_day, last_day)** — the same 4 fields that already
  made `route_id` deterministic (AA-510). Per identity, a run either leaves the current row alone
  (content byte-identical), supersedes it and inserts a new version (content changed), supersedes
  it with no replacement (identity no longer produced at all), or inserts a fresh version-1 row
  (identity never existed before).
- **`route_id` stays unsuffixed for v1** (`{tenant}:{tour}:{first}-{last}`, unchanged format,
  every real existing `subject.route_id` reference keeps resolving with zero backfill) and gains
  a `:v{n}` suffix starting at v2 — guarantees global PK uniqueness across every version ever
  written without touching the v1 naming convention AA-510 already established.
- **Column names**: `version INT NOT NULL DEFAULT 1` + `superseded_at TIMESTAMPTZ NULL` (NULL =
  current). Considered `is_current BOOLEAN` instead of `superseded_at IS NULL` — picked the
  timestamp because it's strictly more informative (when it stopped being current) for the same
  storage cost, and matches this repo's own precedent (`unpublished_at`, `resolved_at`, etc. — a
  nullable timestamp as the "is/was" flag, not a separate boolean).
- **No-op when unchanged** ("tránh version rác mỗi lần chạy", the issue's own "cân nhắc") — a
  content-equality check (`ordered_segment_ids`, `hub_id`, `hub_name`, `score`) against the
  current row skips the write entirely for an identity nothing changed about. Verified live: a
  real re-run against WanderLux's real SOUTHERN LAOS route wrote nothing (`routes_unchanged: 1`,
  `routes_written: 0`), confirming this isn't just a returns-early-in-theory path.
- **`old_hubs` (hub-family matching) now reads CURRENT routes only** (`r.superseded_at IS NULL`)
  — a superseded row lying around forever must not keep contributing to "which tours does this
  Hub cover" once it's no longer the real answer.
- **Every OTHER reader of `acp_contract.route` updated to filter `superseded_at IS NULL`**
  (STEP0 grep found 7 total reader files) — `v1_route_hub.py` (tenant Route/Hub picker),
  `services/acp_shared/slate.py` (both Slate candidate-listing queries), `admin_atoms.py`'s
  Segment "part of Route" badge. The 3 exceptions, deliberately unchanged: `acp_angle_gate/
  service.py` and `slate.py::fetch_slate()`'s `LEFT JOIN ... ON r.route_id = s.route_id` (a
  Subject resolving its OWN specific route_id, current or superseded, is the correct behavior —
  arguably an accuracy IMPROVEMENT post-fix, since that row no longer disappears); `slate.py`'s
  `_atom_and_tour_for_pick()` (same — resolves one already-known route_id, not "current routes").
  The new admin dashboard's own Route/Hub audit panel (AA-527, `admin_dashboard.py`) also
  deliberately does NOT filter — showing version history is that panel's whole point.
- **`create_route_pick()` now also filters `superseded_at IS NULL`** — picking a route_id that
  still exists as a row (never deleted) but has since been superseded must return `None` ("pick
  again"), same signal as a route_id that never existed, not a silent stale snapshot.

## Changed

  2 partial indexes (`idx_route_current_identity` — at most 1 current row per identity, a real
  constraint not just an application convention; `idx_route_tenant_current`). **Applied live**
  (05/09/2026, S3-mediated ECS exec).
- `services/acp_contract/route_detection.py` — `run_route_detection()` rewritten (diff against
  current rows instead of DELETE+INSERT-whole); `old_hubs` query gains `r.superseded_at IS NULL`;
  `create_route_pick()`'s SELECT gains the same filter.
- `api/routers/v1_route_hub.py` — `list_routes()`/`list_hubs()` gain the filter.
- `services/acp_shared/slate.py` — `_fetch_route_candidates()`/`_fetch_segment_hub_map()` gain
  the filter; `fetch_slate()`'s docstring updated (its "stale-but-harmless NULL" scenario is now

- `api/routers/admin_atoms.py` — the Segment "part of Route" LATERAL join gains the filter.
- `tests/unit/test_aa532_route_versioning.py` — new, 6 tests covering all 4 diff outcomes
  (new/unchanged/changed/removed identity) + the `old_hubs` filter + `create_route_pick`'s guard.

## Tradeoffs

- Content-equality check does NOT compare `first_day`/`last_day` (they're part of the identity
  key itself, so by construction they're always equal when a row is being compared at all) —
  only `ordered_segment_ids`/`hub_id`/`hub_name`/`score`. If a future change needs first_day/
  last_day to be independently mutable within one identity, this would need revisiting (not the
  case today — the whole point of the identity key is that a boundary change IS a different
  identity).
- Did not build any UI/tooling to browse a Route's full version history beyond the admin
  dashboard's own Route/Hub panel (AA-527) — no dedicated "history" endpoint, no pruning/
  retention policy for old versions. Superseded rows accumulate forever by design (never
  deleted); a real cleanup policy is a separate decision this issue didn't ask for.
- `routes_written`'s meaning changed (now "rows newly inserted this run", not "every current
  row after a full rebuild") — the one caller (`v1_tours.py`, log-only) doesn't assert on it, so
  this is disclosed here rather than treated as a breaking-change concern.

## Should know

- **The bug was real, not hypothetical** — confirmed via `pg_constraint` (`subject_route_id_fkey`,
  `confdeltype = 'a'`, i.e. NO ACTION) AND by literally running the OLD (currently-deployed)
  `run_route_detection()` against the real WanderLux tenant (which has a real `picked` Subject,
  `cfff38d7-a9e6-4811-b8e2-d8e299feb6e1`, referencing a real Route,
  `...:4bf83a2c-cec0-4127-ac82-1a26fbbd48a3:1-5`) — it raised
  `ForeignKeyViolationError: ... violates foreign key constraint "subject_route_id_fkey"`, exactly
  as predicted. The transaction rolled back automatically; no real data was touched by that
  reproduction.
- **Live-verify, real WanderLux tenant, real Subject, this branch's fixed code** (via `cis-tunnel`
  — not yet deployed, see PR): `run_route_detection()` on the same tenant/data raised nothing,
  returned `{routes_written: 0, routes_superseded: 0, routes_unchanged: 1, ...}` (correctly a
  no-op — nothing about that Route's content had changed since it was last detected), the Route
  row is untouched (`version: 1, superseded_at: null`), and the Subject still resolves its real
  `hub_name`/`first_day`/`last_day` through the join. Ran a second time immediately after —
  identical no-op result, confirming idempotency.
- **The "supersede + new version" path itself is proven by unit test, not by a second live
  mutation** — deliberately did not force a real content change in production data (e.g.
  editing real `atom_ranking` rows) just to manufacture a demo version-bump; the 6 unit tests
  (`test_aa532_route_versioning.py`) cover that path directly against a mocked pool, including
  the exact assertion that the old row is `UPDATE`d (never `DELETE`d) and the new row's `route_id`
  carries the `:v2` suffix.
- Migration 144 is already applied live on the real dev RDS (idempotent, `ON CONFLICT DO
  NOTHING`) — this PR and AA-527's (PR #312, not yet merged) are mergeable/deployable in either
  order with no DB-side coordination risk; AA-527's own dashboard queries against `version`/
  `superseded_at` will work correctly whenever that PR deploys, since the column already exists.
