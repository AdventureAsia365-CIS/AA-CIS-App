# AA-559 — Semantic tenant activity logging (login/pick Slate/write/rewrite)

## STEP0 findings

`acp_shared.audit_log` (migration 030) columns: `id, tenant_id VARCHAR(50), actor VARCHAR(64),
action VARCHAR(64), resource_type VARCHAR(32), resource_id TEXT, details JSONB, created_at`.
Migration 021 later added `actor_type acp_shared.audit_actor_type` (enum: `hitl_reviewer`,
`tenant_admin`, `tenant_reviewer`).

The issue's own "Bối cảnh" claims only 2 historical action types
(`trip_reallocation_suggestion`, `agency.onboard`) exist. Grep found **5 real pre-existing
call sites**, not 2:
- `agency.onboard` — `api/routers/admin.py` (create_tenant)
- `agency.offboard` — `api/routers/admin.py` (offboard_tenant) — issue's own audit missed this one
- `hitl.gate3_social.{status}` — `api/routers/v1_social.py` (batch_review)
- `publish_mode_transition` — `services/acp_produce/trust_ramp.py` (confirm_ramp_transition)
- `trip_reallocation_suggestion` — `services/acp_planning/trip_reallocation.py`
  (confirm_trip_reallocation)

All 5 are raw inline `INSERT INTO acp_shared.audit_log ...` — no shared helper existed. None of
the 5 write `actor_type` except where the row is a HITL-reviewer decision; the one existing
tenant-self-service row (`trip_reallocation_suggestion`, `actor=f"tenant:{tenant_id}"`) already
leaves `actor_type` NULL — the same convention this issue's 6 new rows follow, since none of the
3 enum values describe an ordinary tenant action.

None of the 5 existing call sites were touched.

## STEP0 correction found by live-verify (real bug in the first version of this build)

The first version of this build added the `tenant.login` log to
`api/routers/auth.py::tenant_login()` — the function that visually looks like the real
`POST /auth/tenant-login` handler (same file the module docstring documents the flow in, same
name, imported by `TenantLoginRequest`/`TenantLoginResponse`). It is not. `api/routers/auth.py`
declares an `APIRouter` (`router = APIRouter(prefix="/auth", ...)`) but that `router` object is
**never `app.include_router()`'d** — `api/main.py` only imports individual helpers/models from
it (`_hash_api_key`, `_create_jwt`, `verify_jwt`, the two `TenantLogin*` models, etc.) and
**redeclares the real, live route directly on `app`** at `api/main.py:155`
(`@app.post("/auth/tenant-login", ...)`). `api/routers/auth.py::tenant_login()` has **zero
callers anywhere in the codebase** — confirmed via grep before treating it as fixed — genuinely
dead code, not just an unlikely path. This exact class of bug happened once before in this repo
for the sibling admin-login routes: commit `0edb073` ("fix: mount admin auth endpoints in
main.py — router was never included [AA-232]").

First live-verify run (real login against the deployed API, described below) confirmed this the
hard way: the real `/auth/tenant-login` call succeeded and returned a valid JWT, but querying
`acp_shared.audit_log` afterward found zero `tenant.login` rows anywhere in the table. Root-
caused to the dead-code issue above (not a swallowed exception — no
`tenant_login_audit_log_failed` line in CloudWatch either, meaning the code path was simply
never reached). Fixed by moving the exact same log call into `api/main.py::tenant_login()` (the
real handler) and reverting `api/routers/auth.py::tenant_login()` back to its original, unedited
form — editing genuinely dead code only to satisfy a test would have been misleading. The
`TestTenantLoginAuditLog` unit tests were rewritten to call `api.main.tenant_login()` directly
(same pattern every other router test in this repo already uses: call the endpoint function,
mock its DB param) instead of `api.routers.auth.tenant_login()`. Re-verified live after
redeploy — see Live Verify below.

## Decisions

- **New shared helper** (`services/acp_shared/audit_log.py`, `write_audit_log()` +
  `TenantAuditAction` constants) — not a new table. The issue explicitly says no new table
  without a clear technical reason (none found: current volume is low, existing indexes on
  `(tenant_id, created_at)` and `(action, created_at)` already fit the new query shape). A
  helper *is* new, but 6 near-identical INSERTs justify extracting the one that was about to be
  duplicated a 6th time — same "3 similar lines" threshold, not speculative.
- **"start write" mapped to `POST /v1/content-writing/.../write` (T9), not T8's `choose_angle()`.**
  The issue's own parenthetical calls this "bắt đầu wizard T8 Angle Gate" — imprecise T-stage
  labeling, consistent with this repo's known pattern of loosely-worded issue text (AA-554 cited
  a nonexistent "ADR-0014"). AA-450's LIVE STATE record confirms T8+T9 are ONE continuous
  frontend wizard with no separate T9 route — "start write" is the tenant-visible action of that
  wizard actually starting to write, i.e. the `/write` call, not the earlier angle-choice step.
- **6th log point added beyond the literal minimum 5**: `content_piece.finished`, in
  `_finalize_piece()` (services/acp_content_writing/service.py) — covers all 3 of its call
  sites (main loop, exception-handler fallback, buffer-retry) in one place. The issue's own
  minimum list cites `_insert_placeholder_piece()` for "content viết xong" ("content finished
  writing"), but that function runs BEFORE any LLM call — it creates a `status='processing'`
  placeholder, not finished content. Logging only there would mislead a future Activity UI into
  showing "content written" before gates have even run. Kept `_insert_placeholder_piece()`'s own
  log too (`content_piece.created`, satisfies the issue's literal code pointer) and added
  `content_piece.finished` as the real completion signal — both are real, distinct events, not
  redundant. This is exactly the kind of "phát hiện điểm quan trọng khác" the issue's own point 2
  invites.
- **`cut_subject()` NOT logged.** Issue explicitly says this can wait for AA-556 (the Cut button
  is backend-only today, 0 UI callers, per AA-554's own decision record) — adding it now would
  be logging an event no real tenant can ever trigger yet.
- **Failure mode: fail-closed (same connection/transaction) for 5 of 6 points**, matching the
  established convention all 5 pre-existing call sites use (audit row written in the same unit
  of work as the real state change, failure propagates). **Exception: `tenant.login`**
  (api/routers/auth.py) is wrapped in try/except, logged-and-continued on failure. Login has no
  pre-existing DB write of its own to be atomic with (pure SELECT + JWT mint) — this is the one
  call site where a brand-new write is being added to a hot, security-critical path with nothing
  else guarding it; failing every tenant login because an audit INSERT hiccuped would be a worse
  outcome than one missing Activity-feed row.
- **`actor` string**: `f"tenant:{tenant_id}"` for all 6, matching the one existing tenant-self
  precedent (`v1_planning.py`'s call into `confirm_trip_reallocation()`). No per-user identity
  exists yet (tenants are single API-key/JWT principals, not multi-user) — `actor_type` stays
  NULL, `details` carries anything action-specific.

- `services/acp_shared/slate.py` — `pick_subject()`: audit row inside the existing transaction.
- `api/routers/v1_content_writing.py` — `write()`: audit row after `start_write()` succeeds.
- `services/acp_content_writing/service.py` — `_insert_placeholder_piece()` (created) and

  assessment). Real estimated added volume: login (per tenant session, ~daily at most),
  pick/write/finish/rewrite (per tenant content action, realistically low-tens/day per tenant

  tenant count grows materially; `audit_log` has no TTL/purge mechanism today (AA-558's own
  finding, unchanged by this issue).
