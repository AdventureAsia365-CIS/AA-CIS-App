# AA-177 — [SEC-01] Container + Lambda image scanning + SBOM in CI

## Decisions
- **Scoped to `AA-CIS-App` only** — `AA-ACP-App` is repo-policy abandoned (0 traffic since
  09/07/2026, per this repo's own `CLAUDE.md`), not worth scanning. `AA-ACP-Core` is not
  present on this machine (`~/projects/AA-ACP-Core` doesn't exist here) — cannot be touched
  this round. `AA-CIS-Infra`'s ECR enhanced scanning toggle (Inspector, the issue's own
  "layer thứ 2" alternative) also not built this round — proportionate to the time budget for
  this pass in a very long issue chain; flagged as a real remaining item, not silently
  dropped.
- **Rolled out in MONITOR MODE (report-only), not blocking, for the NEW Trivy container scan.**
  STEP0 found 5 real, pre-existing vulnerabilities in `requirements.txt` via `pip-audit`
  this session (`chromadb` x2 with NO fix version available yet; `pytest`/`python-dotenv`/
  `langchain` WITH fixes available) — could not pre-verify the CONTAINER image's own real
  Trivy findings locally (no working `docker`/`trivy` binary available in this sandboxed
  environment to test against). Shipping an unverified blocking gate straight into the
  REQUIRED `Docker Build Check` job risked breaking CI for every concurrent PR (multiple other
  sessions are actively merging into this same repo today) the moment this merged — matches
  this issue's own explicit "tránh CI noise spam" principle: a scanner nobody has reviewed
  real findings from yet should not silently start blocking every merge. Flipping to
  `exit-code: 1` for CRITICAL/HIGH (`--ignore-unfixed`, matching the issue's own severity-gate
  ask) is a real, deliberate, low-effort follow-up once someone reviews one real CI report.
- **Did not touch the existing `pip-audit` job** (already covers item 2, Lambda/dependency
  scan, for `requirements.txt` + `services/acp_brand_brief_parser/requirements.txt` — found
  already built, just non-blocking `|| true`) — same reasoning: 5 real pre-existing findings
  would immediately break CI if flipped to blocking without review.
- Verified real GitHub Action versions via `gh api` before pinning — my first-guess version
  numbers for both `aquasecurity/trivy-action` and `anchore/sbom-action` turned out stale/
  nonexistent; corrected to the real latest tags (`v0.36.0`/`v0.24.2`) confirmed to exist.

## Changed
- `.github/workflows/ci.yml`, `docker-build` job: added a Trivy image scan step
  (`aquasecurity/trivy-action@v0.36.0`, `severity: CRITICAL,HIGH`, `exit-code: "0"` — report
  only) + a syft SBOM generation step (`anchore/sbom-action@v0.24.2`, CycloneDX JSON,
  auto-uploaded as a GitHub Actions artifact via `artifact-name`).

## Tradeoffs
- No new required/blocking check — `docker-build` (the existing required check) still passes
  purely based on the image building successfully; the new steps append visible output/
  artifacts without changing pass/fail. Chose this over adding a SEPARATE, non-required job
  (which would show as an alarming red X on every PR while still not actually blocking
  anything) — appending to the existing job keeps the new signal visible in the same log
  without a confusing "failed but not required" status.
- `pip-audit`'s Lambda/main dependency scan stays exactly as-is (unchanged, still `|| true`) —
  a real severity-based gate for THAT tool specifically is a separate, smaller follow-up
  (`pip-audit`'s own output has no native severity field the way Trivy's does — would need
  either a CVSS lookup step or switching that job to `trivy fs` as the issue itself suggests
  as an alternative, to get a comparable severity-gate mechanism).
