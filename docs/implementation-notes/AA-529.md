# AA-529 — Facts Entry source for T9 (facts table + content_seed integration)

## STEP0 findings (05/09/2026)

- No `facts`-equivalent table exists anywhere in the schema (`to_regclass('acp_shared.facts')` and
  `to_regclass('shared.facts')` both `None`, confirmed live). `grep`-wide confirmed the only prior
  reference to a "Facts pack" is documentation acknowledging it doesn't exist
  (`services/acp_produce/research.py`, `services/acp_content_writing/generate.py`/`prompts.py`).
- T9's real content_seed builder is `services/acp_content_writing/service.py::start_write()`. It
  computes ONE `atom_text` string (either a single atom's `text`, or — for a Route/Blog pick with
  >1 Segment — the joined text of every Segment's representative atom via
  `_fetch_route_segments()`). That same `atom_text` is used for THREE things downstream:
  1. `content_seed` passed into `prompts.py::build_user_prompt()` (what the model actually reads)
  2. `atom_text` passed into `quality_gates.run_quality_gates()` → `gate_grounding()` (F1) and
     `gate_banned_patterns()` (F2)/`gate_promises_an_option()`
  3. Nothing else — it is not persisted anywhere itself.
- `gate_grounding()` (`services/acp_content_writing/quality_gates.py`) delegates to
  `services.acp_shared.grounding.find_novel_numeric_claims()` — a pure numeric-token check: every
  digit-sequence in a sentence must appear somewhere in the union of the cited source texts, or
  the sentence is flagged. It does **not** parse citation tags at all for this check — tags only
  matter to `gate_atom_density` (F5, blog-only, checks *some* tag exists in a word window).
- Citation tag convention: `TAG_RE = re.compile(r"\[(?:R|F):([^\]]+)\]")` — **already accepts `F:`
  identically to `R:`**, confirmed in `quality_gates.py` (comment: "gates.py's TAG_RE additionally
  accepts F: (non-atom fact citations...)"). Only the `blog` channel currently ever emits any tag
  at all (`prompts.py::_BLOG_FORMAT_INSTRUCTIONS`/`_BLOG_FORMAT_INSTRUCTIONS_ROUTE`, only ever
  instructs `[R:{atom_id}]`) — the `[F:...]` half of that regex was pure latent/unused capacity
  until this issue.
- Live-repro'd the exact reported bug: piece `c771a4d5-48bb-47c0-bb31-0c6de5bb3741` /
  `7ca09d4b-4c09-4a13-bbb8-971ad73f090c` (tenant `wanderlux-travel` =
  `a1b2c3d4-0001-4000-8000-000000000001`, `angle_gate_request` `4d316f9a-e3eb-45bf-beaf-602fbf4c0bd4`,
  channel=`instagram`, atom_id=`1ae1b84dd422d3b6`). The atom's own text is "Don Det and Don Khone
  islands — cross the French colonial-era bridge" — **zero digits** — so any price/day-count
  claim the writer makes is guaranteed to fail F1_grounding; both real attempts opened on a
  "$100..." claim and both held, exactly as the issue describes.
- `shared.tenants.tenant_id` is `UUID` (confirmed via `information_schema.columns` and via the
  live query above returning a real `UUID(...)` value) — the issue's own sketch used
  `tenant_id TEXT NULL REFERENCES tenants(tenant_id)`; built against the REAL live type (UUID)
  instead, see Decisions below.
- Latest migration on `main` at start: 144 (`144_route_versioning.sql`) → this issue is 145.

## Decisions

1. **Table location: `acp_shared.facts`, not `shared.facts`.** The issue's own two sketches don't
   commit to a schema prefix. `acp_shared` is where every other T7-T11 pipeline entity this table
   directly serves already lives (`angle_gate_request`, `angle_gate_option`, `content_piece`) —
   `shared.*` is reserved for platform-wide tenant/plan config (`tenants`, `tenant_brand_rules`),
   a different kind of thing. Facts is pipeline content, not tenant config.
2. **`tenant_id UUID`, not `TEXT`.** The issue's schema sketch wrote `tenant_id TEXT NULL
   REFERENCES tenants(tenant_id)` — but `shared.tenants.tenant_id` is actually `UUID` (every
   recent migration FKs to it as UUID, e.g. migration 117/129/131/115). Built against the real
   live column type, not the sketch's placeholder type.
3. **`fact_id` format mirrors `atom_id`**: `TEXT PRIMARY KEY`, application-generated as
   `f"fact_{uuid.uuid4().hex[:10]}"` — same convention `tour_atoms.atom_id` already uses
   (migration 079's own header explicitly ties that format to citation-tag use, which applies
   identically here).
4. **One `provenance TEXT NOT NULL` column**, not separate `written_by`/`source_note` columns —
   the issue's own plain-language ask is "nguồn dẫn (ai viết, dựa trên gì)" as one idea, not two
   structured fields; a free-text field ("Admin Nghiep, based on the published rate card,
   09/2026") satisfies "kept verifiable" without inventing structure the issue never asked for.
   Kept `NOT NULL` — a Facts Entry with no stated source defeats the entire point of this table
   (verifiability, per the issue's own stated goal).
5. **Citation convention reused as-is, not reinvented**: `[F:<fact_id>]`, parsed by the SAME
   `TAG_RE` that already (silently) accepted it. No gate code changes needed for tag parsing —
   only `prompts.py` needed to actually start telling the model this option exists.
6. **Facts merged into the SAME `atom_text` variable in `service.py`**, not threaded as a wholly
   separate pipeline. Concretely: `start_write()` fetches facts once, formats them into a labeled
   block (`format_facts_block()`, same `[Fact id=<id>]` labeling shape
   `_fetch_route_segments()`'s own `[Moment id=<id>]` already established for atoms/segments), and
   that block is passed as an explicit `facts_text` argument end-to-end (context dict → `generate.py`
   → `prompts.py::build_user_prompt()`). Two places consume it:
   - **Prompt visibility**: `build_user_prompt()` appends the FACTS block after whatever CONTENT
     SEED text it already builds (flat atom text, or — for a multi-Segment Route/Blog pick — the
     joined `[Moment id=...]` blocks) — covers every existing branch, not just the flat case.
   - **Grounding gate**: `service.py` builds a `grounding_text = atom_text + "\n\n" + facts_text`
     used ONLY as the `atom_text` argument to `run_quality_gates()` (gate_grounding/
     gate_banned_patterns/gate_promises_an_option) — the prompt's own `content_seed` arg is left
     as the plain `atom_text` (facts are appended separately inside `build_user_prompt()`, see
     above) so there's no double-inclusion of the facts block in what the model reads.
   This was chosen over a wider refactor (e.g. a formal "sources: list[Source]" abstraction like
   the origin repo's real 4-source system) because the issue explicitly says: "không cần port
   nguyên xi 4-loại-nguồn của repo gốc, chỉ cần thêm 1 loại nguồn mới" — the smallest change that
   makes Facts a real, cited, gate-passing source, reusing every existing seam (labeled-block
   convention, TAG_RE, strip_citation_tags()) rather than adding new ones.
7. **Read-only integration, no write-side service/route in this issue.** The issue is explicit:
   "Đây là 1 phần UI cần đưa vào epic thiết kế Admin/Tenant sắp tới, KHÔNG tách riêng issue UI
   này — chỉ backend/schema xử lý trong issue này trước." No `POST /v1/facts` (or admin
   equivalent) was added. The one real Facts row needed for this issue's own live-verify was
   inserted directly via SQL (S3-mediated ECS exec pattern), not through any app code path — this
   is explicitly a stand-in for the future UI's own write path, not a precedent for how tenants/
   admins will create facts in production.
8. **RLS enabled with a scope-aware policy**, matching `content_piece`/`angle_gate_request`'s own
   convention (`ENABLE ROW LEVEL SECURITY` + a `tenant_isolation`-style policy), extended for the
   platform/tenant split: `USING (scope = 'platform' OR tenant_id::text =
   current_setting('app.tenant_id', true))`. Confirmed (matching this codebase's existing pattern
   elsewhere) that the app's connection pool does not actually set `app.tenant_id` for this
   pipeline's queries — RLS here is the same defense-in-depth convention `content_piece`/
   `angle_gate_request` already carry, not the actual enforcement boundary; the real boundary is
   `fetch_facts_for_writing()`'s own explicit `WHERE scope='platform' OR (scope='tenant' AND
   tenant_id=$1)` filter, same as every other tenant-scoped query in this codebase.

## Changed

- New migration `api/migrations/145_acp_shared_facts.sql` — `acp_shared.facts` table.
- New `services/acp_content_writing/facts.py` — `fetch_facts_for_writing()` (platform + own-tenant
  facts) and `format_facts_block()` (labeled prompt block).
- `services/acp_content_writing/prompts.py::build_user_prompt()` — new optional `facts_text`
  param, appended to whichever CONTENT SEED text was already built; both blog format-instruction
  blocks (`_BLOG_FORMAT_INSTRUCTIONS`/`_BLOG_FORMAT_INSTRUCTIONS_ROUTE`) gained one bullet each
  telling the model `[F:<fact_id>]` is the citation tag for a FACTS-sourced detail.
- `services/acp_content_writing/generate.py::write_content()`/`rewrite_with_feedback()` — new
  optional `facts_text` param, passed straight through to `build_user_prompt()`.
- `services/acp_content_writing/service.py::start_write()` — fetches facts once, stores
  `facts_text` in `context`; `run_write_background()` and `_run_buffer_retry_attempt()` pass it
  into every write/rewrite call and fold it into the grounding-gate's `atom_text` argument.

## Tradeoffs

- Facts are re-fetched fresh on every `start_write()` call (no caching) — same "no cache, cheap
  query, correctness over micro-optimization" choice this codebase already makes for
  `fetch_brand_rubric_text()`/`fetch_brand_audience()` on the same request path. A tenant/admin
  editing a fact takes effect on the very next write, with no invalidation logic needed.
- No pagination/limit on facts fetched per tenant — acceptable for the realistic volume of a
  hand-curated table (platform facts + one tenant's own), same assumption `fetch_tenant_trips()`
  already makes for a tenant's trip list.
- `stated_on` is a plain nullable `DATE`, not enforced against `body`'s own content — a Fact can
  go stale with no automatic expiry check. Out of scope: the issue asks for a citable source, not
  a freshness/expiry system.

## Should know (for the reviewer)

- The reported blocked piece is `channel='instagram'` — the SIMPLE, non-Route, non-blog case
  (flat `atom_text`, no citation tags emitted at all for this channel). The Facts merge into
  `atom_text` fixes this exact case directly: a Fact whose body contains "100" makes
  `find_novel_numeric_claims()` see "100" as already-cited, no tag needed for a non-blog channel
  (`gate_grounding` doesn't require tags, only that the number appear in the source text).
- For a blog piece with a multi-Segment Route pick (the one case where the model sees LABELED
  moments instead of a flat blob), Facts are appended as their own `[Fact id=...]` block AFTER the
  moments — this is the one path this build actually had to extend `prompts.py` itself for (not
  just `service.py`), since that branch ignores the flat `content_seed` argument in favor of a
  moments-only render.
- Live-verify evidence (real Bedrock, real RDS, real HTTP) is appended below once the migration is
  applied and a real Facts row is written for `wanderlux-travel`.
