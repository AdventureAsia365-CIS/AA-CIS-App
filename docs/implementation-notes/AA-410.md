# AA-410 — acp_v2_runs/acp_v2_slots missing `month`

## Root cause (recap, already confirmed before this session started)

AA-404's real N7 retrigger (3rd run, 15/08/2026) hit a hard block: every one of aa_internal's
15 `acp_shared.acp_v2_slots` rows (week 1-4/2026) was already `status='produced'`, and
`POST /admin/produce/run` for week=1..4 was a guaranteed no-op — not "no more work this month",
but a structural bug:

- `acp_shared.acp_v2_runs` (migration 096) has `UNIQUE(tenant_id, year, week)` and **no `month`
  column at all**. `week` is SlotGrid's own week-of-month numbering (1-4), not ISO week.
- `create_weekly_produce_run(pool, tenant_id, year, week)` (`allocator.py`) never took a
  `month` param — every calendar month's week-1 run collapses onto the SAME row.
- `persist_slot_grid(pool, run_id, tenant_id, week, slot_grid)` never read
  `slot_grid.month` either, even though `SlotGrid.month` was always right there on the object.
- Independent second bug, same family: `_deterministic_slot_id(tenant_id, week, trip_id,
  channel)` was missing `year` — the original AA-377 spec (migration 096 header comment,
  `AA-377.md` Decision #3) documented `sha256(tenant_id|year|week|tour_id|channel)`, but the
  shipped hash was `tenant_id|week|trip_id|channel`. Combined with the month gap above, this
  meant `ON CONFLICT (slot_id) DO NOTHING` could silently swallow a different month's slot for
  the same (tenant, week, trip, channel) — not just a blocker today, a time bomb for every
  future month.

## Decisions

- **One migration (103) for both tables**, mirroring migration 096's own precedent — `acp_v2_slots.run_id`
  FKs into `acp_v2_runs`, so splitting the two across migrations risks a broken intermediate
  state where one table has `month` and the queries joining them don't line up yet.
- **Backfill via real timestamps, not a hardcoded default.** All 4 existing `acp_v2_runs` rows
  (aa_internal, year=2026, week=1-4) were created 15/08/2026 — confirmed live before writing
  the migration. `EXTRACT(MONTH FROM created_at)` backfills the true value (8) for those rows,
  same convention migration 099 (`shared.tenants.posts_per_week`) used for its own backfill.
  `acp_v2_slots.month` backfills via a join to its parent run (`run_id`) rather than its own
  `created_at` — a run and its slots are always written in the same `allocate_month()` call, so
  the run's month IS the correct value; no reliance on wall-clock proximity between the two
  writes.
- **`_deterministic_slot_id()` field order**: `tenant_id|year|month|week|trip_id|channel` —
  inserts `year` (always missing) and `month` (new) right after `tenant_id`, keeps the
  originally-documented order of the rest unchanged to minimize blast radius on anything that
  might reason about the hash format.
- **No new UNIQUE constraint on `acp_v2_slots`.** Its only real dedup key is the `slot_id` PK
  itself (a hash) — adding `month` as a plain column (for the row to be self-describing,
  matching the existing convention that `week` is already denormalized onto both tables) is
  enough; the hash fix in `_deterministic_slot_id()` is what actually closes the collision.
- **`acp_v2_runs`'s old 3-column index (`idx_acp_v2_runs_tenant`) dropped, not widened.** The
  new `UNIQUE(tenant_id, year, month, week)` constraint auto-creates its own supporting index,
  and no live call site queries `acp_v2_runs` by a `(tenant_id, year, week)` prefix without
  `month` — keeping the old index would just be redundant index maintenance.

## Changed

- `api/migrations/103_acp_v2_runs_slots_month.sql` — new, additive: `month SMALLINT NOT NULL`
  (backfilled) on both tables, `acp_v2_runs`'s UNIQUE constraint re-scoped to include it.
- `services/acp_planning/allocator.py`:
  - `_deterministic_slot_id()` — new `year`, `month` params, both now in the hash.
  - `make_slot()` (inside `compute_slot_grid()`) — passes `year`/`month` (already in closure
    scope) into `_deterministic_slot_id()`.
  - `create_weekly_produce_run()` — new `month` param, INSERTs/SELECTs it, `ON CONFLICT`
    target widened to `(tenant_id, year, month, week)`.
  - `persist_slot_grid()` — reads `slot_grid.month`, writes it on every slot row.
  - `allocate_and_persist_week()` — passes its own `month` param through to
    `create_weekly_produce_run()` (it already had `month` in its own signature since AA-378;
    only the pass-through was missing).
- `api/routers/admin_produce.py` — `trigger_produce_run()` passes the resolved `month` (already
  computed: `body.month or date.today().month`) into `create_weekly_produce_run()`;
  `get_produce_run()` and the trigger response both now surface `month` for observability.
- `tests/unit/test_aa377_aa378_run_slot_persist.py` — updated every call site for the new
  signatures; added `test_different_year_different_id` / `test_different_month_different_id`
  (hash-level), `test_different_month_same_week_gets_different_run_id` (run-level),
  `test_same_week_different_month_no_longer_collides` (persist-level) — each targets one of the
  two independent bugs directly, not just the happy path.

## Tradeoffs

- `acp_deliver.packets` (migration 094, ISO year+week) is **explicitly untouched** — migration
  096's own header comment already documents that packets use a different, non-colliding week
  numbering (ISO week already disambiguates months within a year across ~52 distinct values) —
  reconciling the two week schemes was an out-of-scope decision then and still is now.
- Existing `slot_id` values for the 15 already-produced rows are **not regenerated** — they keep
  their pre-fix hash format (missing year, effectively month-blind). This is safe: those rows
  are already `status='produced'`, never re-persisted, and the fix only changes what NEW
  `allocate_month()` calls compute going forward. Regenerating old ids would just be churn with
  no observable benefit.
- `acp_deliver.packets` lookup in `get_produce_run()` (keyed on `tenant_id, year, week`) was
  deliberately left alone for the same ISO-week reason above — not a missed call site.

## Should know

- **This does NOT touch `acp_v2_slots`'s existing 15 rows' `slot_id` values** — only their new
  `month` column is backfilled. A human comparing old vs. new slot_ids for the same
  (tenant, week, trip, channel) will see the hash format changed going forward; that's expected,
  not a regression.
- Verify block below confirms the migration actually ran on the real dev DB and that a
  cross-month insert that used to be blocked now succeeds — this was checked live, not just
  unit-tested.
