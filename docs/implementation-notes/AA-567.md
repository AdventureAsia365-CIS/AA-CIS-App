# AA-567 — pick_subject() owner_scope bug (platform atoms never resolved)

## STEP0 — confirmed a real bug, not an intentional isolation boundary

Read `docs/adr/0001-atoms-platform-wide-segments-per-tenant.md`, `docs/adr/0003-segment-score-
route-hub-will-become-platform-wide.md`, and `CONTEXT.md`'s cross-tenant ownership table before
touching any code, per the issue's explicit instruction. All three independently confirm:

- Atom (`tour_atoms.owner_scope`) has been platform-wide, by design, since AA-526 — "Accepted"
  status in ADR-0001, no open question about it. Atoms hold AA's own neutral, brand-agnostic
  rewrite text (AA-535) — "no tenant voice to justify per-tenant grouping" (ADR-0001's own
  words).
- `CONTEXT.md`'s row 2 states plainly: "every tenant's Segment build reads the SAME
  `acp_contract.tour_atoms` rows... `WHERE ta.owner_scope = 'platform'`" — i.e. every OTHER
  consumer of this exact table already reads platform atoms universally. `pick_subject()`'s
  `_resolve_representative_atom()` was the only place that didn't.
- The ADRs' actual open question (Segment/Score/Route/Hub being per-tenant) is a DIFFERENT
  column entirely (`atom_segment.tenant_id`, a real enforced FK) — unrelated to this bug. That
  question stays open (AA-542, tracked separately); this fix does not touch it.

**One real near-miss found during STEP0**: `services/acp_planning/tenant_pool.py`'s own
docstring (AA-448, T7) explicitly argues for `owner_scope = tenant_id` ONLY, matching
`v1_marketplace.py`'s Marketplace atom-count convention — and explicitly floats
`owner_scope IN ('platform', tenant_id)` as a "possible fix shape" it deliberately did NOT
adopt. Read this closely before concluding it contradicts AA-567's fix: T7/Marketplace answer a
different question ("how many atoms has this tenant personally produced via their own T5
rewrite" — a planning-capacity metric) than `pick_subject()` does ("what atom does this
Slate-eligible Segment/Subject resolve to, so the tenant can write about it"). T7's convention is
intentional and untouched by this fix; `pick_subject()`'s was not, and is fixed.

## Changed

`owner_scope = $N` → `owner_scope IN ('platform', $N)` in every atom-resolution query on the
Slate→pick→Write→Review path (kept tenant-owned atoms acceptable too, unchanged from before —
this is additive, not a narrowing):

- `services/acp_shared/slate.py::_resolve_representative_atom()` — both the Segment-pick and
  Route-pick branches (the bug's own point of discovery, AA-564).
- `services/acp_angle_gate/service.py::_fetch_atom_for_tenant()` (T8) — re-fetches the SAME
  atom_id `pick_subject()` already resolved; would have re-rejected it with the old filter.
- `services/acp_content_writing/service.py`: `_fetch_atom_text()` (T9 write), `_fetch_route_segments()`
  (T9 Gap A Route walk — literally the same query slate.py's Route branch uses, just applied
  per-Segment across a whole walk), `_fetch_atom_context()` (T10 review, single request),
  `fetch_review_list()`'s own `LEFT JOIN` (T10 review list — this one degraded silently, no
  error, just NULL atom_* columns for every platform-atom-backed row).

**Deliberately NOT touched** (confirmed different, unrelated to this bug):
- `services/acp_planning/{quarter,tenant_pool}.py` (T7) — the Marketplace-matching convention
  above.
- `services/acp_produce/tenant_pipeline.py` — T5's own write path (a tenant's own rewrite
  atomize), a different pipeline entirely.
- `services/acp_shared/content_metrics.py::rollup_atom_weights()` — found the exact same
  `owner_scope = $N` pattern here too, but it reads through `acp_deliver.pieces`/`acp_v2_slots`
  (the older N7/N8 flywheel-delivery pipeline, not T7-T11), where the atoms flowing through are
  plausibly already tenant-owned by construction (a tenant's own previously-published content).
  Flagging as a related, NOT verified, NOT fixed finding — out of AA-567's explicit T8/T9/T10
  scope, and touching it would need its own investigation into whether N7/N8 is still live.
