# AA-361 [N8-1] — usage_log write-back + atom.weight update proposal

## STEP 0 finding (05/08/2026)

Confirmed via direct read of the 4 files below:

- `services/acp_produce/models.py::Piece` (piece_id, body_tagged, status, gate_ledger,
  repair_count, held_reason) has **no explicit atom_ids field**. This is NOT a blocker: every
  atom a piece actually used is already recorded in its own `body_tagged` as a `[R:atom_id]`
  citation tag — the same convention `services/acp_produce/gates.py::gate_grounding()` (F1)
  and `services/content_generation/s1_from_atom.py::CITE_RE` already rely on for the SAME
  purpose (closed-world + entailment checks). Parsing each piece's own `body_tagged`
  independently is not a guessed heuristic — it's the established citation mechanism, and it
  is naturally piece-scoped (no shared/union atom-id collection needed anywhere), which is
  exactly what avoids bug B8 (see below). No new Piece field, no migration.
- `acp_contract.tour_atoms.usage_log`/`.weight` columns already exist (migration 079, JSONB
  `'[]'` / NUMERIC `1.0` defaults) and are READ by `quarter.py:162` (big-rock atom selection —
  `not a.usage_log`) and `allocator.py:66` (`w = a.weight * starred_mult * distinctiveness_mult`).
  Nothing in the repo writes `usage_log`; nothing updates `weight` post-curation. Confirmed by
  grep — 0 write sites for either column outside migration/insert (`test_aa299_atom_insert.py`
  inserts `weight` once at atom-creation time only).
- Bug B8 (`docs/AI-gent-for automation works/aa-marketing-v2/aamc/delivery.py:41-49,66-74` —
  gitignored dead prototype code, never imported by the real app, confirmed via `git grep
  aamc` = 0 hits outside `docs/`) confirmed exactly as described: `used_atom_ids` is built as
  the UNION of every atom cited across ALL pieces' briefs (lines 44-50), then every
  `status == "passed"` piece gets a usage_log entry for every id in that UNION (lines 68-77) —
  not just its own atoms. Real implementation avoids this by construction: `atom_ids_cited()`
  takes exactly one `Piece` and parses only that piece's own `body_tagged`.

## Decisions

- New module `services/acp_produce/atom_usage.py` (not a new file under `acp_planning/`,
  since usage-log write-back is a Produce/N7-output concern, matching where `Piece` itself
  lives) — `atom_ids_cited()` (pure), `build_usage_entries()` (pure, B8-safe core logic),
  `write_usage_log()` (async DB wrapper) — same pure-computation/async-wrapper split already
  used by `compute_quarter_plan()`/`plan_quarter()` and `compute_slot_grid()`/`allocate_month()`.
- `ATOM_CITE_RE = re.compile(r"\[R:([^\]]+)\]")` — R-only, deliberately narrower than
  `gates.py`'s `TAG_RE` (which also accepts `F:` fact citations per its own docstring "the
  atom/fact set"). `usage_log` lives on `tour_atoms` rows only; an `[F:...]` id is never a row
  in that table, so including it would either silently no-op the UPDATE or need an extra
  filter against a real atom-id set this function doesn't otherwise need.
- One usage_log entry per (atom, piece) pair, deduped within a piece (an atom cited twice in
  the same piece's body counts as "used once by this piece", not twice) — matches the
  semantic `quarter.py:162` actually needs (`not a.usage_log` = "has this atom EVER been used
  by ANY passed piece", not a citation-occurrence counter).
- `channel_by_piece_id: dict[str, str] | None` param on both `build_usage_entries()` and
  `write_usage_log()` — optional because the current `Piece` model has no `channel` field
  (unlike the research build's richer `Piece`). Entry omits the `channel` key entirely when
  not supplied, rather than writing `null`. N8-4 (Weekly Packet, AA-364, separate issue) will
  have real channel context at assembly time and can pass it in without any change to this
  function.
- `write_usage_log()` appends via `usage_log = usage_log || $2::jsonb` (JSONB concat), one
  `UPDATE` per atom, inside one transaction for the whole call — no new column, no migration.

## Changed (vs. issue text)

- None — scope matched the issue as written once STEP 0 confirmed the tag-parsing mechanism
  was sufficient (issue explicitly allowed either outcome: "if Piece truly cannot know which
  atoms belong to it, report it as a blocker" vs. proceeding).

## Tradeoffs

- Did NOT add a redundant `atom_ids` field to `Piece` that would just cache what
  `atom_ids_cited()` derives on demand — would be a second source of truth that could drift
  from `body_tagged` after a repair round rewrites it. Re-parsing is O(1) regex over already
  in-memory text, not worth the drift risk for the write-back path.
- Did NOT implement any `weight` UPDATE (explicit issue constraint) — see proposal below,
  unconfirmed pending Nghiep's decision.

## Should know (weight-update proposal — NOT implemented, awaiting confirmation)

Current `allocator.py:66` computes atom priority ENTIRELY at read time, never persisted:
`w = a.weight * (1.5 if starred else 1.0) * {"HIGH":1.5,"MED":1.0,"LOW":0.6}[distinctiveness]`.
Short-horizon repeat-avoidance already exists structurally (`used_this_month` set + B7 fix +
`cooldown_until`) — the gap `usage_log` is meant to close is a LONGER-horizon one: after
cooldown expires, a HIGH-distinctiveness atom used 5 times last quarter should still rank
below one never used, so content doesn't cycle through the same "greatest hits" atoms forever.

Two implementation shapes, with a recommendation:

1. **(Recommended) Read-time multiplier, no persisted write to `weight` at all.** Add a 4th
   factor to the existing `allocator.py:66` line: `* usage_decay(a.usage_log, today)`, computed
   fresh from `usage_log` on every call — exactly how `starred`/`distinctiveness` already work
   today (also computed live, never written back). Zero migration, zero risk of compounding
   decay, and it trivially satisfies "don't UPDATE weight" as an architecture property, not
   just a promise.
2. Persist a decayed value into `weight` itself at `write_usage_log()` time. Rejected as
   default: `weight` currently holds a human-curated base value (set once at atom-curation
   time, migration 079 default 1.0). Overwriting it with `base * decay` and then decaying
   AGAIN next time compounds indefinitely — the atom's weight would ratchet toward 0 and never
   recover, unlike option 1 where an atom used long ago naturally regains full weight as
   `usage_decay()` decays back toward 1.0 with time. Only viable with a NEW `base_weight`
   column (immutable, human-set) so `weight` becomes a derived/cached column recomputed fresh
   from `base_weight` each time, never from its own prior value — extra migration + write path
   for no benefit `allocator.py` doesn't already get from option 1, unless some OTHER consumer
   needs `weight` pre-decayed outside the allocator (none identified in this repo today).

Proposed formula for `usage_decay(usage_log, today)` (option 1):

```
effective_uses = sum(
    exp(-ln(2) * days_since(entry.date, today) / RECENCY_HALF_LIFE_DAYS)
    for entry in usage_log
)
usage_decay = DECAY_PER_EFFECTIVE_USE ** effective_uses
```

Each usage entry contributes ~1.0 to `effective_uses` right after it happens and decays
toward 0 with a half-life, so old uses stop being held against the atom instead of applying a
flat, permanent penalty. `DECAY_PER_EFFECTIVE_USE` (e.g. 0.85) and `RECENCY_HALF_LIFE_DAYS`
(e.g. 60) are **unverified placeholders** — no real N7 usage data exists yet to tune them
against (same situation as `SWEEPER_SLA_HOURS` in AA-298, flagged the same way there: don't
treat a placeholder constant as final without real production data). Alternative simpler
shapes considered and rejected: flat `weight / (1 + count)` (decays too fast for one popular
atom, no recency recovery) and a hard exclusion after N uses (duplicates what
`cooldown_until`/`used_this_month` already do structurally, and would make a real HIGH atom
permanently ineligible rather than just lower-priority).
