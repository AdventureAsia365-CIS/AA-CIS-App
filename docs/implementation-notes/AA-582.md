# AA-582 — Fix JWT-tenant JOIN bug + narrow Playground allowlist

## Decisions

- Two-round investigate already established: `GET /v1/tours/{tour_id}` and the JWT-tenant
  branch of `GET /v1/tours/{tour_id}/full` queried `gold_aa_internal.published_tours` by
  `tenant_id`, but that column is always the `aa_internal` sentinel — never a real per-tenant
  value — so any real tenant JWT always got 404. Fix: scope both through
  `gold_aa_internal.tenant_tour_versions` instead, mirroring the pattern `v1_marketplace.py`
  (AA-444) already uses correctly.
- `get_tour_full()` has 2 auth branches (admin `X-Admin-Secret` vs. tenant JWT) sharing one
  query. Only the JWT-tenant branch was buggy — the admin branch's sentinel-based lookup into
  the shared `aa_internal` reference pool is intentional (see `v1_marketplace.py`'s own
  `INTENTIONAL` comment) and must not change. Branched the query on `is_admin` instead of
  unifying it, to avoid touching the admin path's behavior at all.
- Playground `ALLOWED_PATHS` (`frontend/app/api/playground/proxy/route.ts`) was broader than
  `endpoints-config.ts`'s displayed endpoint list — `"/v1/tours"` (`.startsWith()`, incidentally
  matching `.../full` too) and `/^\/v1\/tours\/[\w-]+$/` let a logged-in tenant reach the buggy
  bare/`.../full` routes directly via devtools/curl, never through any UI button. Default choice
  per Nghiệp's activation prompt: narrow the allowlist down to exactly what the UI shows today
  (`/v1/tours/my-versions`, `/v1/tours/versions/:id`, `/v1/webhooks`) rather than officially
  exposing the now-fixed `/v1/tours/:id`/`.../full` through the Playground — no stated product
  need to add them, and the bug this issue exists to fix is specifically "proxy allowlist wider
  than UI," so re-widening it without a UI entry would reintroduce the same class of gap.

## Changed

- `api/routers/v1_tours.py`:
  - `get_tour()` — query rewritten to `JOIN gold_aa_internal.tenant_tour_versions ttv ON
    ttv.published_tour_id = pt.id WHERE pt.id = $1::uuid AND ttv.tenant_id = $2::uuid`.
  - `get_tour_full()` — branched: `is_admin` keeps the original sentinel-based query unchanged;
    the `elif credentials` (JWT-tenant) path now uses the same `tenant_tour_versions` JOIN.
- `frontend/app/api/playground/proxy/route.ts` — `ALLOWED_PATHS` narrowed to the 3 exact paths
  `endpoints-config.ts` displays, removing the two over-broad patterns.

## Tradeoffs

- Did not add `/v1/tours/:id`/`.../full` to `endpoints-config.ts` even though the backend bug is
  now fixed and it would be technically safe to expose — no product ask for it, and the
  Playground's existing 2 endpoints already cover tenant tour access (list + version detail).
  Can be added later as its own small UI change if wanted.
- Did not touch `RawTourRepository`/legacy `/tours` routes — that's AA-585's scope, different
  file (`api/main.py`), unrelated bug class (no auth at all, vs. this issue's wrong-tenant-scope
  bug on an already-authed route).

## Should know

- Live DB-level verify (via S3-mediated ECS exec against real RDS, before any code was deployed):
  ran the NEW query directly against real data — tenant "WanderLux Travel" owns published tour
  "Delights of Sri Lanka" via `tenant_tour_versions`. New query found it; the OLD query (same
  params) found nothing, confirming the original bug was real. New query against a published tour
  that tenant does NOT own (`tenant_tour_versions` has no row for that pair) correctly returned
  nothing — no cross-tenant leak introduced by the fix.
- Playground allowlist logic verified with a standalone Node script mirroring the exact
  `isAllowed()` function: old exploitable paths (`/v1/tours/:id`, `.../full`, bare `/v1/tours`)
  now correctly rejected; both UI-displayed endpoints and `/v1/webhooks` still pass.
- `tests/ -k "tours or marketplace"` (83 tests) pass locally with no regressions.
- Full production HTTP live-verify (real tenant JWT via generate-key + tenant-login, real
  Playground proxy calls) done post-merge/post-deploy — see the Linear comment on AA-582 for that
