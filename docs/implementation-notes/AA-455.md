# AA-455 bước 1 — A4 force-unpublish + tenant self-unpublish + publish_log

Two prior STEP0 rounds (AA-455-00 T11 investigation, AA-455-01 A4 force-unpublish investigation)
established the design; this is the real build. Linear AA-455 updated 24/08/2026 (post-STEP0-01)
locked: Option 2 for tenant self-unpublish (build both AA and tenant actions now, same PR), and
confirmed the schema/endpoint/PR-shape can't be split across two PRs.

## Decisions

- **Single PR, not split** — per AA-455-01's own §8 finding (re-confirmed, not re-derived, in the
  Linear issue's own STEP0-bước-1-hoàn-tất update): a force-unpublish action cannot exist without
  the `publish_log` table, so migration + both mutating endpoints + FE section ship together.
- **`unpublished_by` format**: single `TEXT` column, `"admin:<id>"` / `"tenant:<id>"` prefix —
  chosen over a separate `unpublished_by_role` enum column because Nghiep's own Linear update text
  gave this exact prefixed-string example, and it matches migration 115's own minimalism
  precedent (no extra column beyond what's needed for the same information).
- **New router `v1_publish.py`**, not folded into `v1_content_writing.py` — `publish_log` is its
  own resource (T11's, once T11 exists), not T9/T10's. Mirrors migration 115's own reasoning for
  not denormalizing parent fields onto a child table: a distinct resource gets its own place.
- **Tenant self-unpublish ownership check** copies `v1_competitors.py:187`'s exact shape —
  `WHERE publish_id = $1 AND tenant_id = $2 AND status = 'published'`, 404 (not 403) whether the
  row doesn't exist or belongs to another tenant — no cross-tenant existence leak (AA-445-02
  lesson, re-applied, not re-derived).
- **`admin_a4.py`'s new endpoints reuse `verify_admin_secret`** unchanged — same auth dependency
  the file's existing 2 endpoints already use, no new auth mechanism introduced.
- **FE: third section on the same `/admin/a4-oversight` page**, not a new route — per STEP0 §4/§7,
  confirmed again this session (middleware.ts's `/admin/a4-oversight` prefix entry already covers
  it; a new route would repeat the exact 307 bug AA-384/388/405/437 each independently hit). No
  middleware.ts edit made — deliberately, and verified nothing broke (see Live Verify below).
- **`publish_log` migration ships now, ahead of T11's own write path** (bước 2, a separate future
  task) — same "column/table exists before its real writer" pattern as AA-450's
  `angle_gate_request.cta` existing before AA-451 wired a writer into it. Deploys against an empty
  table in production; this session's own live-verify used manually-inserted test rows (see
  below), since there's no real T11 producer yet.
- **RLS added to `publish_log` for schema consistency with `content_piece`, not as the real
  isolation boundary** — confirmed by grep (no `app.tenant_id` SET anywhere in `api/`/`services/`)
  that `content_piece`'s identical RLS policy is already inert; real isolation in this codebase is
  the explicit `WHERE tenant_id = $N` every query carries, which both new endpoints use.

## Tradeoffs

- Building tenant self-unpublish now (Option 2) rather than deferring to T11 bước 2, per Nghiep's
  explicit decision — means this "force-unpublish tối thiểu" issue ships a slightly larger surface
  than its own title suggests. Traded off against having to re-migrate `unpublished_by`'s shape
  later if Option 2 had been picked after the fact.
- No tenant-facing `GET /v1/publish-log` (list) — out of scope for this issue (STEP0-01 flagged
  this explicitly: a tenant list endpoint serves no real purpose until T11 bước 2 actually writes
  rows a tenant would want to see). `DELETE` only.
- Kept RLS on the new table even though it's confirmed inert — for schema parity with
  `content_piece`, not because it does anything today. Flagging so a future reader doesn't assume
  it's load-bearing.
