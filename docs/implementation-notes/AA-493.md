# AA-493 — Persist stop_reason/finish_reason from LLM response (Bedrock + OpenAI)

## Decisions

- **Destination confirmed via STEP0, per the issue's own instruction**: `shared.llm_call_log`
  (migration 137, AA-518/AA-505) already exists as the "bảng log LLM call chung" the issue asks
  to check for. Added `stop_reason TEXT` (nullable) to that table (migration 141) instead of a
  new table or a column on `generated_content`/`tenant_tour_versions` — `shared/llm_client/
  call_log.py::record_call()`/`record_call_with_pool()` is the single write path for every
  confirmed real call site, so one column there reaches all of them through that shared function.
- **Real scope is 4 raw-call implementations, not 1**, found while tracing every call site (the
  issue's own text named only `shared/llm_client/client.py`):
  1. `shared/llm_client/client.py` (`_call_bedrock` streaming, `_call_bedrock_satellite`,
     `_call_openai`) — the one the issue named.
  2. `shared/llm_client/bedrock_satellite.py::invoke_claude()` — Mechanism-B call sites (T5
     atomize, N7 draft/adapt/faq/repair/research, S1's atom writer) call this DIRECTLY, not
     through `client.py`. Different response shape too: non-streaming `invoke_model()`, so
     `stop_reason` is a top-level payload key, not nested in a `message_delta` event like
     `client.py`'s streaming parser.
  3. `services/acp_produce/judge_client.py` — N7's judge (F8/F9, `gates.py`) AND T10's judge
     (`quality_gates.py`) both call this, completely bypassing `client.py`. 3 backends, 3
     different field names/locations for the same concept: Nova Pro's `invoke_model` response
     and the real Converse API (GPT-5.6 Sol) both use top-level `stopReason` (camelCase);
     OpenAI (GPT-4.1, the shipped default per AA-518) uses `choices[0].finish_reason`.
  4. `services/content_generation/brand_audit_node.py` — its own direct `openai.OpenAI()` call,
     not routed through `client.py` either.
  All 4 are fixed — leaving any one out would have left a large fraction of real calls (every
  judge call, every Mechanism-B writer call) still silently discarding this field, which is
  exactly the gap the issue is about.
- **15 call sites threaded through individually** (grep-confirmed list of every
  `record_call`/`record_call_sync`/`record_call_with_pool` invocation) rather than changing the
  log functions' signatures to accept the whole response object — kept consistent with how
  `model`/`tokens_in`/`cost_usd` are already passed as separate scalar kwargs at every one of
  these call sites, not a smaller diff than the alternative but a more consistent one.
- **STEP0 confirmed both event schemas before writing any code** (task's own checklist item):
  read `shared/llm_client/client.py`'s existing streaming test fixture
  (`tests/unit/test_aa224_streaming_fallback.py`) — it already modeled `message_delta`'s
  `delta.stop_reason` correctly (the code just wasn't reading it); similarly
  `test_aa351_judge_gpt41.py`'s `_nova_response()` fixture already included a `stopReason` key
  the code wasn't reading. Confirms the AA-341/AA-493 finding was a pure "field exists in the
  response, code ignores it" bug, not a stale/incorrect assumption about the API shape.
- **Frontend UI updated** (`frontend/app/admin/llm-usage/page.tsx`, the AA-505 cost/quality
  dashboard reading `shared.llm_call_log`) per this task's own instruction to keep any affected
  UI in sync — this is the one real UI surface that reads this table. Added a `truncated_count`
  aggregate (`COUNT(*) FILTER (WHERE stop_reason = 'max_tokens')`) to the `/llm-usage/tree` rollup
  SQL, an amber "N bị cắt (max_tokens)" badge per stage-branch (shown only when > 0), and a
  page-level "Bị cắt (max_tokens)" stat card. Also added `stop_reason` to the flat
  `/llm-usage/calls` SELECT (no frontend consumer of that endpoint exists yet — grep-confirmed —
  so this is data-completeness only, not a UI change).
- **South Korea Cycling case (issue's optional item 3)**: not investigated — that tour's original
  run predates this fix by weeks; `stop_reason` was never captured for any historical call, so
  there is no `shared.llm_call_log` row (or any other row) that could retroactively confirm or
  rule out truncation for that specific run. Flagging as explicitly not resolved rather than
  silently dropped — the issue itself already framed this as "n=1, chưa kết luận" and optional.

## Tradeoffs

- No behavior change to `max_tokens` itself (explicitly out of scope, per the issue's own
  constraint — AA-341 Khoản 4 stays open, separate issue).
- `truncated_count` in the `/tree` rollup only counts `stop_reason = 'max_tokens'` exactly —
  rows written before migration 141 (or by a call site somehow still not threading it through)
  have `stop_reason IS NULL` and are correctly excluded, not miscounted as either truncated or
  clean. This means the dashboard's truncation rate will under-report until enough new calls
  accumulate after this migration applies — accepted, since over-reporting (treating NULL as
  truncated) would be actively misleading.
- Did not add a per-call `stop_reason` column to the `/llm-usage/calls` flat list's frontend
  rendering, because no frontend page currently consumes that endpoint (confirmed via grep) —
  only the backend SELECT was updated, so the data is there the moment a consumer is built.

## Should know

- `record_call_sync()` needed zero code changes — it's a thin `**kwargs` forwarder to
  `record_call()`, so every one of its ~10 call sites picked up the new parameter automatically
  once passed; only the call sites themselves (not the sync wrapper) needed editing.
- The Nova Pro judge backend's response is technically `invoke_model()`, not the real Bedrock
  Converse API, despite having an `"output"/"message"` wrapper shape that looks like it — but it
  happens to also carry a top-level `stopReason`, confirmed against the live code before relying
  on it (see `judge_client.py`'s inline comment on this).
- Migration 141 is NOT applied live as part of this task (matches this repo's "a PR carrying a
  migration should NOT be auto-merged" convention) — `stop_reason` will read as `None`/absent
  everywhere until Nghiệp (or CI on merge) applies it and the app redeploys. All new tests mock
  the DB layer, so they pass regardless of live migration state; no live HTTP/DB verify was run
  for this reason — nothing to observe live yet.
