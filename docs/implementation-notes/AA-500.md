# AA-500 — `fetch_trips()` reads the tenant's own T1→T5 pipeline, not the unfiltered platform catalog

## Decisions

1. **Data source: `gold_aa_internal.tenant_tour_versions` ⋈ `raw_tours`/`published_tours`, not
   `v_trip_registry`.** STEP0 (this session) found `v_trip_registry`/`raw_tours.tenant_id` is
   100% `aa_internal` live (793/793, 763/763 rows) — no B2B ingestion pipeline ever writes a
   `raw_tours` row for another tenant. `v_trip_registry` is the correct source for T1
   pool-browsing (`v1_tours.py`), never for per-tenant planning. The real per-tenant "which
   tours has this tenant rewritten" signal is `tenant_tour_versions.tenant_id` (T1→T4) — the
   same source `tenant_pool.fetch_tenant_trips()` (AA-448, already shipped) already uses for T7.
   The new `_TRIP_ROW_QUERY` in `runway.py` is byte-identical to `tenant_pool.py`'s
   `_TENANT_TRIP_QUERY`.

2. **Duplicated, not shared, with `tenant_pool.fetch_tenant_trips()`.** `tenant_pool.py` already
   imports `_row_to_trip` from `runway.py`; reusing `tenant_pool`'s query function from `runway.py`
   would create a circular import. Matches this codebase's own existing precedent —
   `quarter.fetch_atoms_by_trip()`'s AA-461 fix duplicated `tenant_pool.fetch_tenant_atoms_by_trip()`'s
   query rather than restructure the import graph; same call made here for consistency.

3. **No atom-existence gate on the trip list.** The new query returns every tour the tenant has
   *rewritten* (`tenant_tour_versions`), regardless of whether it has been *atomized* yet
   (`tour_atoms`) — matching `tenant_pool.fetch_tenant_trips()` and `v1_marketplace.py`'s
   `_MARKETPLACE_QUERY` (which LEFT JOINs the atom aggregate and COALESCEs to 0 rather than
   filtering it out — "a rewritten tour with no atoms yet is a real, useful gap signal ... not
   noise to filter out", per that module's own docstring). Live-verified: `wanderlux-travel` has
   8 rewritten tours but only 2 with real `tour_atoms` rows — `fetch_trips()` returns all 8.
   **Flagging explicitly**: the build prompt's live-verify checklist item ("đối chiếu số tour trả
   về với số tour thật sự có tour_atoms cho tenant đó") could be read as expecting equality
   between the two counts (8 vs 2 here) — this implementation deliberately does NOT enforce that
   equality, to stay consistent with the two already-shipped precedents above. If the intent was
   actually "only tours with atoms are eligible", that's a follow-up decision, not implemented
   here — flag to Nghiep on review.

4. **`aa_internal` gets an empty trip list, by design, not a special-cased branch.** Live DB
   check: `aa_internal` has ZERO `tenant_tour_versions` rows and ZERO `tour_atoms` rows under its
   own tenant_id — it has never gone through the T1→T5 tenant-rewrite flow on its own master
   catalog (it IS that catalog, not a rewriter of it). A first design considered branching
   `fetch_trips()` so the platform tenant keeps reading `v_trip_registry`; **Nghiep explicitly
   rejected that** — aa_internal should behave exactly like any other tenant (rewrite a tour via
   the portal like anyone else, if/when N4-N6 planning is needed for it) rather than get special
   code. Confirmed no crash: `compute_quarter_plan()`/`compute_slot_grid()` already handle empty
   `trips`/`trips_by_id` gracefully (dict `.get()` with `None` fallback, `or 1` divide guards) —
   verified both by reading the source and by a real live run (see "Live Verify" below).

## Changed

- `services/acp_planning/runway.py::fetch_trips()` — full query replacement (was: unfiltered
  `SELECT ... FROM acp_contract.v_trip_registry`, no params; now: tenant-scoped
  `tenant_tour_versions` ⋈ `published_tours` ⋈ `raw_tours`, `$1` = `tenant_id`). `_row_to_trip()`
  unchanged — the new query's SELECT list is column-for-column identical to the old one, so no
  caller-visible shape change.
- `tests/unit/test_aa301_runway.py` — replaced the AA-323-round-6 "reads full catalog, no
  filter" assertion with two tests: the new query shape/param, and the "no
  `tenant_tour_versions` rows → empty list, not an error" contract.
- No changes to `compute_runway_map()`, `quarter.py`, `allocator.py`, or any router — all three
  existing callers (`runway.runway_map()`, `quarter.plan_quarter()`, `allocator.allocate_month()`)
  already call `fetch_trips(tenant_id, pool)` with the identical signature; none needed edits.

## Tradeoffs

- Duplicating the tenant-scoped trip query (vs. importing `tenant_pool.fetch_tenant_trips()`
  directly into `quarter.py`/`allocator.py`, retiring `runway.fetch_trips()` entirely) keeps the
  change small and matches an already-accepted pattern in this codebase, at the cost of two
  copies of the same SQL that must be kept in sync if the join ever changes (same tradeoff
  `quarter.fetch_atoms_by_trip()`/`tenant_pool.fetch_tenant_atoms_by_trip()` already accepted).
- Not gating on atom existence (Decision 3) keeps `fetch_trips()`'s contract simple and matches
  precedent, but means a tenant can have "eligible trips" in N5/N6 scoring that carry zero atoms
  (scored via `richness=0`, `dist` defaults) — already true today for T7's own `fetch_tenant_trips()`
  path, so not a new class of state, just now also true for N5/N6.

## Follow-up (same day, 2026-09-01) — "Cách B": atom-existence gate

PR #271 merged and deployed (task def `:179`) with Decision 3 above (no atom-existence gate).
Post-merge live-verify passed identically to pre-merge. Nghiep then reviewed and **overrode
Decision 3**: `fetch_trips()` must additionally require >=1 real `tour_atoms` row, not just a
`tenant_tour_versions` row.

**Reason (Nghiep)**: Slate (T7, AA-511) shows/recommends by ATOM (through Segment/Route), not by
tour. A rewritten-but-not-yet-atomized tour has zero atoms for Slate to use — surfacing it in
`fetch_trips()` is pure noise (a tenant clicks into it and finds nothing). Filter at the source
in `fetch_trips()`, not pushed down into Slate's own logic.

**Changed**: `_TRIP_ROW_QUERY` gained `WHERE EXISTS (SELECT 1 FROM acp_contract.tour_atoms ta
WHERE ta.tour_id = rt.tour_id AND ta.owner_scope = $2 AND NOT ta.deleted AND NOT
ta.is_empty_marker)` — same existence filter `tenant_pool._TENANT_ATOM_QUERY`/
`v1_marketplace._MARKETPLACE_QUERY`'s atom aggregate already use, applied here as a hard gate
via `EXISTS` instead of a LEFT JOIN + COALESCE. `fetch_trips()` now binds two params:
`tenant_id` (`$1::uuid`, `tenant_tour_versions.tenant_id`) and `str(tenant_id)` (`$2`,
`tour_atoms.owner_scope` — free-text column, matches `tenant_pool.py`'s own str-cast convention).

**Deliberate divergence, not a bug to reconcile**: `tenant_pool.fetch_tenant_trips()` (T7's own
query) and `v1_marketplace._MARKETPLACE_QUERY` (AA-444) both still keep a 0-atom rewritten tour
in their results (LEFT JOIN + COALESCE to 0) — that is still the *correct* behavior for their own
purposes (a tenant's own Marketplace/T7 view legitimately wants to show "you rewrote this, it
still needs atomizing" as a gap signal). Only N4-N6's `runway.fetch_trips()` — feeding
atom-driven Slate — needed the hard gate. Do not copy this `EXISTS` filter onto the other two
queries, or drop it from this one, without re-confirming which caller's semantics are actually
being asked for.

**Live-verify** (ephemeral file-copy onto the running ECS task, real RDS, reverted after):
- `wanderlux-travel`: `fetch_trips()` → exactly **2** (was 8) — cross-checked byte-for-byte
  against a direct `SELECT DISTINCT tour_id FROM tour_atoms WHERE owner_scope = ... AND NOT
  deleted AND NOT is_empty_marker` query: **identical tour_id sets**, not just matching counts.
  `plan_quarter()` still runs clean (2/2 trips chosen, no crash) — `runway_map()` now returns 0
  cells for this tenant (both remaining trips lack qualifying PERIOD data for a cell to compute;
  not a regression from this change, a pre-existing property of those 2 specific trips).
- `aa_internal` / `exploreasia-co`: both `fetch_trips()` → 0, cross-check against `tour_atoms`
  also 0 — matches (both had 0 either way, before and after this follow-up).
- Cross-tenant isolation reconfirmed disjoint across all three.
