# AA-466 — /write → async (202 Accepted + poll)

## Decisions

- Scope narrowed to `/write` only. `/goal` stays synchronous (1 LLM call, self-recovers via
  `pending_goal` on parse failure, comfortable margin under the 90s gateway ceiling AA-465 set) —
  Nghiep confirmed during STEP0 design review. The `client.generate()` missing-`asyncio.to_thread()`
  gap found in `/goal` during STEP0 is tracked as a separate, smaller issue — not fixed here.
- `content_piece` (migration 115) reused as the job-status table — no new job table. Placeholder
  row inserted with `status='processing'` at request time, updated in place when the background
  task finishes (approved/held) or errors (failed).
- New `content_piece.status` value `'processing'` (in-flight) AND `'failed'` (real system error in
  the background task, distinct from `'held'` — a valid business outcome with real content). `held`
  is never used for a system failure.
- `angle_gate_request.status` untouched — T8/T9 stay 2 separate API surfaces/data models, per the
  existing design (AngleGateTab.tsx's own comment). No new intermediate value added there.
- Background task launched via `asyncio.create_task()` + module-level strong-ref set +
  `add_done_callback()` — the pattern `api/routers/v1_tours.py::trigger_rewrite()` (AA-425) already
  uses, NOT the bare `asyncio.create_task()` `v1_s4_blog.py` uses (that file's own comment flags the
  GC risk of an unreferenced task).
- Poll endpoint: reused `GET /v1/content-writing/pieces/{piece_id}` unchanged — no new GET route.
- FE poll ceiling 180s / interval 3s — independent of the 90s gateway timeout (that ceiling applies
  only to the LLM call itself; POST /write now returns in ms, and each poll GET is a single-row read
  that never approaches 90s). Backend keeps running past 180s if the FE gives up watching.

## Changed

- **PR1 (migration)**: `api/migrations/118_content_piece_processing_failed_status.sql` —
  `content_piece.status` CHECK constraint gains `'processing'`/`'failed'`, `content_text` gets a
  `DEFAULT ''`.
- **PR2 (backend)**: `services/acp_content_writing/service.py::write_and_check()` split into
  `start_write()` (sync pre-flight, unchanged 404/409/422 contract, inserts a `'processing'`
  placeholder) + `run_write_background()` (the write/rewrite + T10-check loop, body unchanged,
  now `UPDATE`s the placeholder via the renamed `_finalize_piece()` instead of inserting a final
  row). `api/routers/v1_content_writing.py::write()` returns `202` immediately and launches the
  background task via `asyncio.create_task()` + a module-level strong-ref set (mirrors
  `v1_tours.py::trigger_rewrite()`, AA-425). `GET /pieces/{piece_id}` unchanged. Updated 4 test
  files that called the old `write_and_check()` directly (`test_aa450_content_writing_service.py`,
  `test_aa450_v1_content_writing.py`, `test_aa450_event_loop_not_blocked.py`,
  `test_aa452_t10_nine_gates.py`) — same coverage, now targeting `start_write()`/
  `run_write_background()` separately, plus new tests for the `failed` status path.
- **PR3 (frontend)**: `AngleGateTab.tsx` — `writeContent()` now polls
  `GET /pieces/{piece_id}` (3s interval, 180s ceiling) instead of using the POST response
  directly. `ContentPiece.status` extended with `processing`/`failed`. New UI branches: a
  poll-ceiling banner (not an error — background keeps running) and a `failed` branch with a
  Retry button.

## Tradeoffs

- `GET /v1/content-writing/pieces?request_id=` (list-by-request) was NOT built — if the FE gives up
  polling (tab closed, ceiling hit and not retried), the tenant has no way back to a finished piece
  except the `piece_id` held in React state. Accepted as a known gap, left for a follow-up ticket —
  full STEP0 design reasoning already recorded in the AA-466 Linear comment.
- `content_piece.held_reason` reused to carry the system-error message on `status='failed'` rather
  than adding a new column — avoids schema sprawl for a single TEXT field with the same "why it
  didn't reach approved" meaning in both cases.
