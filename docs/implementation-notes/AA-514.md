# AA-514 — [T10] Gate "promises an option" + SEO surface + structural variance route-aware

## Decisions

- **SEO surface = real architecture fork, asked directly (AskUserQuestion), Nghiệp chose full
  port.** `gates/shape.py::seo_surface()` needs structured `Piece.seo_title`/`meta_description`/
  `slug`/`keyword` fields the origin's writer always produces — `acp_shared.content_piece` had
  none, and T9's writer output has always been one plain-text blob. Full port means: migration
  136 (3 new columns) + blog-channel T9 output becomes a JSON envelope (`{seo_title,
  meta_description, slug, body}`) instead of plain text. Non-blog channels' output contract is
  completely unchanged (still plain text) — confirmed by test and live-verify.
- **Corrected premise (not an architecture stop): "auto-fix tối đa 3 lần"** does not describe a
  mechanism T10 needs to build. T10 already has one flat, uniform `MAX_ATTEMPTS=2` retry loop
  applied to ANY `repairable=True` gate — F2_banned_patterns already participates in exactly
  this, not a separate "3 rounds" counter. `gate_seo_surface()` joins the SAME existing loop
  (`repairable=True`), matching what "banned patterns hiện nay hoạt động thế nào" actually is.
- **`gate_promises_an_option()` resolved without a new migration/table** (unlike SEO surface) —
  the origin precomputes "is this Atom offered" into a separate `offered_moments` table; AA-CIS
  scans the SAME `atom_text`/Segment text T9 already holds in memory, inline, at gate-check
  time — no new persisted classification needed for a single-piece check. `channels=None` (every
  channel gets this gate, not just blog) — matches the origin exactly, and required no schema
  change since it needs only text already in context.
- **`keyword`** (for SEO-surface's keyword checks) reuses T8's own already-snapshotted
  `dfs_paa_snapshot.related_keywords[0]` (AA-501, migration 127) — no new DataForSEO call.
- **F3 route-aware variance** reuses AA-513's own per-sentence citation tags (already carries
  each Segment's own id) — no new data needed, purely a smarter grouping of existing H2 sections
  by which Segment's id dominates each one.

## Changed

- Migration 136: `content_piece.seo_title`/`meta_description`/`slug` (nullable, blog-only).
- `quality_gates.py`: `gate_promises_an_option()` (new, never `repairable`, every channel) and
  `gate_seo_surface()` (new, `repairable=True`, blog-only, thresholds ported verbatim from
  `gate-thresholds.toml`) added to the ledger; `gate_structural_variance()` gains optional
  `route_segments` for a route-aware variance check (falls back to the original generic H2 check
  when absent/single-segment, byte-identical to before); `run_quality_gates()` wires all 3 in.
- `prompts.py`: blog channel's output contract becomes a JSON envelope
  (`_SEO_ENVELOPE_INSTRUCTIONS`); `keyword` param added.
- `generate.py`: `write_content()`/`rewrite_with_feedback()` return a 3rd value (`seo_meta`,
  all-None for non-blog); `_parse_blog_envelope()` parses the JSON (json-repair fallback, raises
  `SeoEnvelopeError` on a genuinely malformed response — never silently falls back to treating it
  as plain text).
- `service.py`: `start_write()` resolves `keyword`; `run_write_background()`/`_finalize_piece()`/
  `fetch_piece()` thread the 3 SEO fields through persistence and read-back.

## Tradeoffs

- Did not extend `fetch_review()`/`fetch_review_list()` (admin/tenant review-queue reads) to
  surface the 3 new SEO fields — out of this ticket's scope (T10 gate behavior, not the review
  UI), and no page consumes them yet.
- Did not port the origin's "claim support" gate (verifies a cited sentence shares a distinctive
  word with the SPECIFIC id it cites) — neither AA-513 nor AA-514's own text asks for it; flagged
  as a real, separate follow-up if per-tag accuracy (not just presence) ever needs checking.
