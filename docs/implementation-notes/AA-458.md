# AA-458 [T11 PR2] — list endpoint + real publish + /portal/t11-publish complete

The final piece of T7→T8→T9→T10→T11. Depends on AA-457 (credentials layer) + AA-459 (IAM fix) +
AA-460 (false-positive fix), all merged and live-verified before this task started.

## Decisions

- **`WordPressAdapter.create_post()` now reads `content.status` instead of hardcoding `"draft"`**
  — `BlogContent.status` was already a declared dataclass field (default `"draft"`), just never
  read; using it directly means `services/acp_s4_blog/cms/publisher.py` (the only existing
  caller) needs zero changes — it never sets `status` explicitly, so it keeps getting the
  default. Chosen over adding a brand-new parameter (which the task's own text floated as a
  fallback) because the field already existed — using dead infrastructure that's already there
  beats adding a second, redundant way to say the same thing.
- **The AA-460 lesson applied inside the adapter itself**, not duplicated in the router: after
  a 200/201, `create_post()` now requires `content-type` starting `application/json` AND a
  parseable body AND both `"id"` and `"link"` present (real WordPress post shape) before
  returning a `CMSPostResult` — anything else raises `RuntimeError` with a clear message. The new
  `POST /v1/publish-log/{piece_id}/publish` endpoint never re-checks response shape itself; it
  just catches whatever `create_post()` raises and records that as the failure. One place owns
  "is this really WordPress," matching the same principle AA-460 established for
  `test_wordpress()` (routed through one shared classifier, not parallel logic).
- **List query matches the task's own literal SQL shape** (`LEFT JOIN ... AND pl.status =
  'published'`, filter `pl.publish_id IS NULL`) rather than a more elaborate
  "most-recent-attempt" LATERAL join — simpler, and a piece with a prior `'failed'` or
  `'unpublished'` publish_log row still correctly reappears as pending (both are legitimately
  retryable states), not just a piece with zero rows at all.
- **List + publish both filter `channel = 'blog'` explicitly** — `angle_gate_request.channel`
  can be any of T8's 8 real channels, but T11 is blog-only scope (AA-456/AA-458's own framing
  throughout). A `facebook`/`tiktok`/etc. approved piece must not appear in "ready to publish"
  or be publishable through this endpoint — not explicitly spelled out in the task's numbered
  steps, but directly implied by "blog-only" everywhere else in this effort; flagging the
  reasoning here rather than silently adding it.
- **Post title sourced from `angle_gate_option.name`** (the tenant's chosen angle, `chosen =
  true`) — `content_piece` itself has no title field (confirmed by reading migration 115).
  Migration 115's own comment explicitly endorses this shape ("no denormalized
  cta/channel/goal/angle_name columns... callers join back when they need them") — this is the
  designed-for way to get contextual fields, not a workaround. Falls back to `"Untitled"` if
  somehow no chosen option exists (defensive, shouldn't happen given T8's own invariants).
- **`content_html` = `content_piece.content_text` verbatim, no markdown→HTML conversion** — the
  writer produces real markdown (`## ` headings, `**Q:**/**A:**` FAQ pairs, per AA-452) but this
  task's scope is wiring the publish pipe end-to-end, not building a markdown renderer.
  WordPress's own `wpautop` will still paragraph-wrap it reasonably; headings just won't render
  as real `<h2>` tags. Flagged as a real, deliberate simplification — a legitimate follow-up if
  nicer rendering is wanted later, not silently glossed over.
- **Retry semantics**: a piece with an existing `status='failed'` publish_log row gets that row
  UPDATEd in place on the next attempt (no accumulating duplicate failure rows); a `'published'`
  or `'unpublished'` row is left untouched and a fresh publish attempt creates a brand new row —
  preserves that older row's real `unpublished_at`/`unpublished_by` audit trail (AA-455's whole
  reason those columns exist) rather than destroying it on re-publish.
- **Publish failure is a `200` response with `success: false`**, not a 4xx/5xx — mirrors
  `test_wordpress()`'s own established pattern exactly (the HTTP request itself succeeded; the
  domain-level publish attempt is what failed, and that's recorded + returned in the body).
- **`_get_secret()` duplicated in `v1_publish.py`** rather than imported from
  `v1_integrations.py` — matches this codebase's own existing precedent
  (`v1_integrations.py` itself duplicated `publisher.py::_get_cms_creds()` for the identical
  reason: avoid a cross-router import for one small, stable helper function).
- **Frontend**: `PublishPendingList` stays visible even when WordPress isn't connected — Publish
  buttons disable with STEP0 §12's exact copy ("Connect WordPress to publish") rather than
  hiding the whole list, so a tenant always sees what they have ready regardless of connection
  state. Sidebar entry added in NAV1 (`Send` icon, "Publish" label) — deliberately withheld in
  AA-457 per that PR's own scope note ("route wasn't functionally complete yet"), added now that
  it is.

## Tradeoffs

- No markdown-to-HTML conversion (see Decisions above) — real, acknowledged gap, not scope creep
  to fix here.
- SEO meta fields (`seo_title`/`seo_meta`) both just reuse the angle name / are left empty —
  `content_piece` has nothing more specific to offer, and building real SEO-meta generation
  wasn't asked for.
