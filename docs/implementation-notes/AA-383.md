# AA-383 — acp-brand-brief-parser Lambda: INSERT branch missing brand_name

## Context correction (important)

The Linear issue was written 08/08/2026 and describes the intended fix as "use `body.name` as
default" (mirroring what `create_tenant()` did at the time). That is now **wrong** — AA-471
(28/08/2026, this same session, PR #245) found that using `body.name`/a tenant's own name as
`brand_name` was itself the root cause of a separate bug: every reader
(`fetch_brand_rubric_text()`, `_resolve_brand_rule()`, AA-198's multi-brand convention since
migration 044) looks up the tenant's primary brand row via `WHERE tenant_id = $1 AND
brand_name = 'default'`. AA-471 changed `admin.py`'s seed INSERT to the literal `'default'`
sentinel. This task follows that corrected pattern, not the issue's original description.

The issue's "10/11 tenants missing a row" figure was also stale — queried live via S3-mediated
ECS exec (28/08/2026): **3 active tenants total** (aa_internal, wanderlux-travel,
exploreasia-co), **all 3 already have a `tenant_brand_rules` row** (post migration 121/122
cleanup + AA-471's restore). So this bug currently has **zero live-reachable impact** — see
Should know.

## Decisions

- `brand_name` set to the literal `'default'` sentinel (matches `admin.py`'s AA-471 pattern),
  not `parsed.brand_name` (the docx-parsed brand name) — confirmed with Nghiep before implementing
  (`AskUserQuestion`). Using the parsed name would reproduce the exact AA-471 root cause.
- Also fixed the UPDATE branch (not in original issue scope, but same root cause, same file):
  it never set `brand_name` either, so a tenant's seeded `'default'` row would silently stay
  `'default'` forever even though `admin.py`'s AA-471 comment claimed the upload flow keeps it in
  sync. Confirmed with Nghiep to bundle into this task rather than a separate ticket.
- No schema/model change — `brand_name` is hardcoded as the SQL literal `'default'` directly in
  `db.py`'s two queries, not added as a field on `BrandRulesRow`/`ParsedBrief`. There is no
  multi-brand concept live yet (AA-198's convention is single-primary-brand-per-tenant via the
  `'default'` sentinel), so adding a pass-through field would be speculative.

## Changed

- `services/acp_brand_brief_parser/db.py`: INSERT branch now includes `brand_name` column with
  literal `'default'`; UPDATE branch now includes `brand_name = 'default'` in its SET list.
- `api/routers/admin.py`: corrected an inaccurate comment (lines ~146-147) that claimed the
  upload flow "happened to fix brand_name too" / "still overwritten later" — that was never true
  before this fix (the UPDATE branch left `brand_name` untouched). Now accurate post-AA-383.
- `tests/unit/test_aa383_brand_brief_parser_db.py` (new): mocks `psycopg2.connect`, asserts the
  INSERT SQL contains `brand_name`/`'default'` and the UPDATE SQL contains
  `brand_name = 'default'`.

## Tradeoffs

- Placed the new test under `tests/unit/` (flat, `test_aaXXX_*.py` convention), not
  `tests/acp/` where the existing `test_brand_brief_parser.py` (parser-only, docx fixtures) lives
  — see Should know, `tests/acp/` isn't collected by CI at all.
- Did not add a live/integration-level test hitting the real Lambda handler end-to-end (S3
  download + docx parse + DB write) — out of proportion for a one-column SQL fix; the mocked
  unit test directly asserts the SQL text, which is the actual bug surface.

## Should know

- **Real, pre-existing, unrelated finding**: `tests/acp/test_brand_brief_parser.py` (the only
  existing test file for this Lambda) is **not collected by CI at all** — `.github/workflows/
  ci.yml` only runs `pytest tests/unit/` and `pytest tests/integration/`, never `tests/acp/`.
  Confirmed this test also fails to even *import* standalone on this machine
  (`ModuleNotFoundError: No module named 'models'` — `parser.py`'s bare `from models import ...`
  needs `services/acp_brand_brief_parser/` added to `sys.path` first, which nothing in `tests/acp/`
  does). Verified via `git stash` that this is not something this task's diff caused — reproduces
  identically on `main`. Not fixed here (out of AA-383's scope), flagging for a separate ticket.
- This task's own new test works around the same bare-import issue by inserting
  `services/acp_brand_brief_parser/` onto `sys.path` at the top of the test file before importing
  `db`/`models` — same pattern needed if `tests/acp/test_brand_brief_parser.py` is ever
  moved/fixed to actually run in CI.
- Given the real DB state (0/3 active tenants currently missing a row, and `create_tenant()`
  always seeding one), this Lambda's INSERT branch is not reachable via the normal onboarding
  path today — the existence check in `db.py` (`SELECT id FROM shared.tenant_brand_rules WHERE
  tenant_id = %s`, no `brand_name` filter) will always find the AA-471-seeded row and take the
  UPDATE branch instead. This fix closes a latent/defensive gap (a tenant reaching this Lambda
  without going through `create_tenant()` first), not an active production incident.
