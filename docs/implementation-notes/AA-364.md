## Decisions

### D1 — Schema: `acp_deliver`, not `acp_shared` or a new schema

`acp_deliver` schema already exists (migration 078, AA-302) and already holds exactly one
table: `acp_deliver.tenant_tour_pages` (per-tenant published URL tracking, read by
`services/acp_planning/runway.py` for CTA/route-to-sellable-adjacent checks). Schema-purpose
split confirmed by reading all 3 ACP schemas' real tables:

- `acp_contract` — source-of-truth **input** (tour_atoms, v_trip_registry)
- `acp_shared` — cross-stage **operational** state (acp_runs, acp_stage_checkpoints,
  acp_run_context, acp_lessons_*, acp_output_rules, quarter_plan)
- `acp_deliver` — the **output/delivery** layer

`Piece`/`Packet` are delivery-layer artifacts (a piece is what gets delivered; a packet is
the delivery unit) — `acp_deliver` is the correct namespace by the existing precedent, not
a guess. No new schema needed.

### D2 — Two tables, not one GROUP BY

`acp_deliver.packets` needs metadata that cannot be derived from grouping pieces: the
trust-ramp `publish_mode` (AA-365 will read/write this — task explicitly asked to add the
column now to avoid a second `ALTER TABLE`) and a packet-level `status` lifecycle
(`assembling` → `ready` → `delivered`) that is the mechanism for the STEP 5 boundary below.
`UNIQUE (tenant_id, year, week)` — one packet per tenant per ISO week, same pattern as
`acp_shared.quarter_plan`'s `UNIQUE (tenant_id, year, quarter)` (migration 092).

**Deliberately NOT ported from `aamc/models.py::Packet`**: `needed_from_you`,
`veto_deadline`. No Linear issue references either yet (`veto_loop`/G2 is not in the
AA-328/364/365 breakdown as read) — inventing them now would be the same "docstring/issue
promises a shape the code doesn't have" pattern AA-298 already flagged for P0-1/P0-2/B14.
Add them in whichever future issue actually consumes them.

### D3 — `piece_id`/`packet_id` types, `tenant_id` type

- `piece_id TEXT PRIMARY KEY` — matches `Piece.piece_id: str` in the real Pydantic model and
  `acp_contract.tour_atoms.atom_id TEXT PRIMARY KEY` (migration 079)'s precedent for an
  opaque string id that also appears verbatim inside body text (atoms are cited via
  `[R:atom_id]`; nothing cites `[piece_id]` today, but keeping the type consistent with the
  sibling id-inside-content convention costs nothing).
- `packet_id UUID PRIMARY KEY DEFAULT gen_random_uuid()` — no external string format for
  packets exists anywhere (unlike atoms/pieces), so the plain UUID convention used by
  `acp_shared.quarter_plan.plan_id` applies cleanly.
- `tenant_id TEXT NOT NULL`, **not UUID**: the one real, live Python call site that already
  touches a `Piece` and a `tenant_id` together — `rule_adapter.py::apply_output_rules_to_piece(piece, stage, tenant_id: str, db)`
  — types it `str`. `acp_deliver.tenant_tour_pages.tenant_id` (migration 078, same schema)
  is also `TEXT`, no FK. Migration 092's own comment warns explicitly: "Future acp_shared
  tables should not assume one convention from this alone — check the actual call site's
  type before copying either pattern." The actual call site here says `str`/TEXT.

### D4 — What's in `gate_ledger` vs its own column

`gate_ledger JSONB` stores the `list[GateResult]` shape as-is (`{gate, passed, violations}`)
— same shape `run_gates()` already builds, no transform needed. `gate_brand_seo_audit()`
(F9) uniquely returns `tuple[GateResult, dict | None]` — the `audit_dict` (`status`,
`brand_fit`, `human_read`, `seo_fit`, `trip_type_accuracy`, `publish_readiness`,
`failure_codes`, `notes`) carries structured fields no other gate has and that
`GateResult.violations` (a `list[str]`) cannot hold without flattening to text. Given
`failure_codes` (fixed vocabulary, gates.py:141-146) is exactly the kind of thing a future
N8 flywheel dashboard would want to query/aggregate directly, it gets its own
`brand_seo_audit JSONB` column rather than being lossy-encoded into `gate_ledger`.

**Not adding a separate `atom_ids` column** — the task's own suggestion to skip this is
correct and already the AA-361 design: `atom_usage.py::atom_ids_cited()` parses
`[R:atom_id]` from `body_tagged` on demand, no redundant column to keep in sync.

### D5 — `output_rules` gate (AA-363) integration note for the future orchestrator

Not this issue's problem to solve, but worth recording here since it was found while
designing the ledger: `run_gates()`'s `gate_fns: list[Callable[[str], GateResult]]` signature
doesn't actually match ANY of F1/F8/F9/output_rules as they exist today —
`gate_grounding(body_tagged, valid_ids, text_by_id)`, `gate_framework(piece_body, framework)`,
`gate_brand_seo_audit(piece_body, brand_rubric_text) -> tuple`, and
`apply_output_rules_to_piece(piece, stage, tenant_id, db)` (async) all need extra
brief/tenant-specific args bound before they fit the single-arg `Callable`. This is expected
(closures/partials bind the extra args per-brief before the loop) but the tuple-return of
F9 and the async-ness of the rule adapter mean **the future orchestrator needs its own
normalization layer**, not a naive `gate_fns.append(gate_brand_seo_audit)`.

## Tradeoffs

- RLS: `acp_silver_s3.ads_plan` (migration 031) has a `tenant_isolation` RLS policy;
  `acp_deliver.tenant_tour_pages` (migration 078, same schema `pieces`/`packets` are going
  into) does **not**. Precedent is genuinely split within `acp_deliver`'s own sibling tables
  — not deciding this silently. Recommendation: add RLS (piece bodies are tenant-specific
  generated content, closer to `ads_plan`'s risk profile than to a URL-tracking table), but
  this is called out as an open question for Nghiep to confirm, not assumed.
- `channel` is `TEXT NOT NULL`, no `CHECK` constraint — `aamc/models.py`'s `Channel` Literal
  (`blog|facebook|tiktok|email`) was never ported into `services/acp_produce/models.py`'s
  real `Piece` (it has no `channel` field at all yet — confirmed by re-reading the file).
  Adding a CHECK on values the real Python model doesn't even validate yet would be the same
  "ahead of the code that needs it" mistake migration 093's own comment warns against for
  `itinerary_day`. Revisit once `Piece.channel` exists in code.

## Should know

- **F1/F8/F9-only vs waiting for F2-F7 (task asked for a clear opinion, not a decision)**:
  recommend **starting persistence + orchestrator plumbing now with {F1, F8, F9,
  output_rules-adapter}**, but **not** letting a packet auto-publish (i.e., not advancing
  `publish_mode` past `propose_only` in the AA-365 trust ramp) until at minimum **F6
  (route-to-sellable)** exists. Reasoning: `apply_output_rules_to_piece` (AA-363, real,
  deterministic) already substantially covers the F3 banned-pattern/red-line gap once wired
  in (18/22 seed rules are pipeline-agnostic brand-voice checks per AA-363's own docstring)
  — the gap there is smaller than "F2-F7 entirely missing" makes it sound. F9's LLM rubric
  also covers some of F2/F5's intent probabilistically (`GENERIC_AI_WORDING`,
  `PRODUCT_TRUTH_RISK`, `DFS_INTENT_UNDERUSED` failure codes). The one gap with no coverage
  at all, deterministic or probabilistic, is **F6**: a piece can pass every existing/planned
  gate while pointing at a dead or missing CTA/`trip_url` — a concrete, cheaply-checkable
  (`acp_deliver.tenant_tour_pages.url_alive`, already exists) revenue defect. Build F6 before
  trusting any packet to leave `propose_only` mode; F2/F4/F5/F7 can follow in a later
  hardening pass while a human is still the one approving every packet.
- **STEP 5 — "gate-pass" vs "delivered" boundary** (the task flagged this as the easiest
  place to get `write_usage_log()` timing wrong):

  ```
  E1-E5 generates body_tagged
          │
          ▼
  run_gates() → status="passed" or "held"
          │
          ├─ INSERT/UPDATE acp_deliver.pieces (packet_id = NULL)
          │
          ▼
  ══════════════════ "GATE-PASS" MOMENT ══════════════════
  Fires:     emit_piece_metrics()  (AA-362, CloudWatch)
  Does NOT fire: write_usage_log() (AA-361)
  Why not:   a piece that passed gates may still be vetoed, held for next
             week's replacement, or sit in a packet that's never approved
             (propose_only mode) — it was never seen by a real audience.
             Logging usage here would falsely age/cooldown atoms that
             never actually shipped.
          │
          │   (packet assembly pulls in "passed" pieces, sets pieces.packet_id,
          │    packets.status: assembling → ready)
          │
          ▼
  packets.status → 'delivered', packets.delivered_at = now()
  (packet actually sent to tenant/channel)
          │
          ▼
  ══════════════════ "DELIVERED" MOMENT ══════════════════
  Fires:     write_usage_log(pieces_in_this_packet)  (AA-361)
  Does NOT fire again: emit_piece_metrics() (already emitted at gate-pass)
  ```

  `pieces.packet_id` is the only link — no `delivered_at` duplicated onto the piece row
  (avoids two timestamps that could drift; join to `packets.delivered_at` when needed).

## Migration draft (NOT applied — next free slot is 094, latest applied is 093)

```sql
-- Migration 094 (DRAFT — do not apply until Nghiep confirms D1-D5 above,
-- especially the RLS open question in Tradeoffs and the F1/F8/F9-only
-- question in Should-know)
--
-- AA-364 STEP 0 — acp_deliver.packets + acp_deliver.pieces: first DB
-- persistence for N7 Produce's Piece/gate_ledger (previously pure in-memory
-- Pydantic, confirmed zero existing table via grep across all migrations)
-- and the Weekly Packet grouping (AA-364/AA-365).
--
-- Schema: acp_deliver (existing, migration 078 — currently only
-- tenant_tour_pages) — delivery-layer namespace, matches acp_contract
-- (input) / acp_shared (operational) / acp_deliver (output) split already
-- established by the 3 real ACP schemas.
--
-- packets created before pieces (pieces.packet_id references packets) —
-- no circular FK, unlike quarter_plan/quarter_plan_version (migration 092)
-- which needed the ALTER-TABLE-after trick for a genuine two-way reference.

BEGIN;

CREATE TABLE acp_deliver.packets (
    packet_id     UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id     TEXT NOT NULL,
    year          INTEGER NOT NULL,
    week          SMALLINT NOT NULL CHECK (week BETWEEN 1 AND 53),
    publish_mode  TEXT NOT NULL DEFAULT 'propose_only'
                      CHECK (publish_mode IN ('propose_only', 'approve_to_publish', 'veto_window_auto')),
    status        TEXT NOT NULL DEFAULT 'assembling'
                      CHECK (status IN ('assembling', 'ready', 'delivered')),
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    delivered_at  TIMESTAMPTZ,
    UNIQUE (tenant_id, year, week)
);

CREATE INDEX idx_acp_deliver_packets_tenant ON acp_deliver.packets(tenant_id, year, week);

CREATE TABLE acp_deliver.pieces (
    piece_id         TEXT PRIMARY KEY,
    run_id           UUID NOT NULL REFERENCES acp_shared.acp_runs(run_id) ON DELETE CASCADE,
    tenant_id        TEXT NOT NULL,
    slot_id          TEXT,
    channel          TEXT NOT NULL,
    body_tagged      TEXT NOT NULL DEFAULT '',
    status           TEXT NOT NULL DEFAULT 'in_progress'
                          CHECK (status IN ('in_progress', 'passed', 'held')),
    gate_ledger      JSONB NOT NULL DEFAULT '[]',
    brand_seo_audit  JSONB,
    repair_count     SMALLINT NOT NULL DEFAULT 0,
    held_reason      TEXT,
    packet_id        UUID REFERENCES acp_deliver.packets(packet_id),
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_acp_deliver_pieces_run_id ON acp_deliver.pieces(run_id);
CREATE INDEX idx_acp_deliver_pieces_tenant_created ON acp_deliver.pieces(tenant_id, created_at DESC);
CREATE INDEX idx_acp_deliver_pieces_held ON acp_deliver.pieces(status) WHERE status = 'held';
CREATE INDEX idx_acp_deliver_pieces_packet_id ON acp_deliver.pieces(packet_id) WHERE packet_id IS NOT NULL;

VALUES ('094', now(), 'AA-364 STEP 0 DRAFT: acp_deliver.packets + acp_deliver.pieces -- N7 Piece/gate_ledger persistence, NOT YET REVIEWED')
ON CONFLICT (version) DO NOTHING;
```
