# AA-363 — Wiring apply_output_rules() into N7 (services/acp_produce/)

Architecture already chosen (Linear AA-363 comment, 05/08/2026, from the STEP-0-phụ survey): shared
`acp_output_rules` table, no new table, no migration. This issue is the actual wiring.

## STEP 0 finding (05/08/2026) — re-verified against real code, not the earlier survey's summary

- **Fail-open risk confirmed real.** `apply_output_rules()`'s `_TEXT_FIELDS = ("content", "content_md",
  "seo_title", "seo_meta", "title")`. `Piece.body_tagged` matches none of them. Calling the function
  with a raw `{"body_tagged": ...}` dict makes `_collect_text_fields()` return `[]`, so every rule
  silently no-ops — proven, not just asserted, by `test_no_adapter_fails_open` in
  `test_aa363_rule_adapter.py`: a "hidden gem" block rule against a piece whose text literally contains
  "hidden gem" produces `rules_applied == []`, no exception.
- **Call point is AFTER generation, not before — the issue's own draft assumption was wrong, confirmed
  by the real code, not argued around.** `acp_post_processor.py`'s own module docstring (line 5-6):
  `"Call order in S4 flow: LLM generation -> apply_output_rules() -> acp-s4-evaluate Lambda -> DB save"`.
  The function's signature and mechanism (`output: dict` in/out, raises `OutputRuleViolation` on a
  completed field's content) only make sense against already-generated text — there's nothing to check
  before a draft exists.
  `docs/implementation-notes/AA-298.md`'s one-line pipeline summary ("C1/C2 DFS → C3 brief compile →
  `apply_output_rules()` → E1-E5 generation → F1-F9 gates") is **wrong** about this ordering — not
  edited there (keeping that session's historical record intact), corrected here instead. Also: **no
  `ADR-009` exists anywhere in the repo** (`grep -rn "ADR-009"` — 0 hits) — the issue cited it for the
  before-generation claim; it isn't a real, checkable reference in this codebase. Trusted the code over
  both the issue text and the AA-298.md note, per the issue's own explicit instruction to do so.
- **Structurally cannot be plugged into `gates.py::run_gates()`'s `gate_fns` list.** Confirmed by reading
  the loop: `result = gate_fn(piece.body_tagged)` — synchronous, no `await`. `apply_output_rules()` is
  async and needs a live `db` connection plus `tenant_id`/`stage`. Also its "block" outcome is a raised
  exception and its "flag" outcome is a dict mutation — neither matches `Callable[[str], GateResult]`.
- **HITL reject in N7 — confirmed absent, not invented.** `Piece.gate_ledger`/`held_reason` only ever
  record automated gate failures (`_hold()` in `gates.py`, called from `run_gates()`'s repair-budget
  branch) — there is no field distinguishing "held by a gate" from "rejected by a human reviewer."
  `h3_rule_extractor.py::extract_and_save_rule()` requires a real `hitl_id` tied to an
  `acp_shared.acp_hitl_requests` row (itself FK'd through `acp_shared.acp_runs`) — N7 has no such
  reviewer UI or endpoint yet (Weekly Packet / Gate C = AA-364/AA-365, not built). Not implemented here,
  per the issue's explicit constraint — noted for N8-5 to wire once a real reviewer UI exists.

## Decisions

- New module `services/acp_produce/rule_adapter.py`:
  - `piece_to_rule_input(piece) -> dict` — pure, maps `body_tagged` → `{"content": ...}`. `"content"`
    chosen because it's the first name in `_TEXT_FIELDS` AND the generic fallback key
    `acp_post_processor.py`'s own `"replace"`/`"truncate"` logic already uses when `"content_md"` is
    absent — not an S4-specific choice.
  - `apply_output_rules_to_piece(piece, stage, tenant_id, db) -> GateResult` — async wrapper. Imports
    and calls the REAL `apply_output_rules()` unmodified. Catches `OutputRuleViolation` (block/
    score_gate) and folds `output["review_flags"]` (flag) into a single `GateResult(gate="output_rules",
    ...)`, matching how F1/F8/F9 already report into `piece.gate_ledger`. NOT appended to
    `piece.gate_ledger` by this function itself — returned for the (not-yet-built) orchestrator to
    append, same "ready building block" situation as AA-361's `write_usage_log()` and AA-362's
    `emit_piece_metrics()`.
  - `GateResult.passed = not violations` is this codebase's universal convention (F1/F8/F9 all follow
    it) — so a `"flag"`-type trigger is mapped to `passed=False` here too, even though S4's own flow
    treats `flag` as informational-only (content still ships). **This is a real, deliberate behavior
    difference for N7 (stricter than S4)** — flagged explicitly rather than silently inherited. If
    Nghiep wants N7 to match S4's softer flag semantics instead, that's a one-line change
    (`passed=True` with violations still populated) but changes what "passed" means for a gate for the
    first time in this codebase, so left as the stricter default pending a decision.
  - `stage=None` passed for N7 (not a new stage code) — all 22 seed rules are already `stage=NULL`
    (global); there is no second N7-only rule yet to justify inventing a stage number, and the schema
    has no CHECK constraint forcing one now. Left for whoever adds the first genuinely N7-only rule to
    choose deliberately.
- `api/services/acp_post_processor.py` — **0 lines changed** (`git diff --stat` confirms), per the
  issue's explicit constraint and matching the AA-356 precedent for `grounding.py`.

## Changed (vs. issue text)

- Confirmed call point is AFTER E1-E5 generation, not before, contradicting the issue's initial
  "inject before generate" framing — the issue itself anticipated and explicitly allowed this outcome
  ("code thật quyết định, không phải giả định"). No `ADR-009` exists in-repo to check against.

## Tradeoffs

- Did not wire this into a live call site — no N7 orchestrator exists yet to call it from (E1-E5
  generation itself isn't assembled, `docs/implementation-notes/AA-298.md`: "chưa lắp ráp thành 1 luồng
  end-to-end"). `apply_output_rules_to_piece()` is ready for that orchestrator to call once it exists,
  immediately after generation produces `piece.body_tagged`.
- HITL reject → `h3_rule_extractor` for N7 explicitly deferred to N8-5 (Gate C), not stubbed here.
